# Article Formatter - 文章优化排版大师

将任意格式的文本优化为标准中文排版，包括字符、标点符号的规范化，以及段落衔接的自然化处理。

## 触发条件

当用户说以下关键词时使用此技能：
- "优化排版"、"格式化文章"、"美化文章"
- "排版优化"、"文章排版"、"优化格式"
- "format article"、"beautify text"、"optimize layout"
- 提供文本并要求"整理一下"、"排版一下"、"美化一下"

## 核心能力

### 1. 字符与标点规范化
- 统一使用中文标点符号（，。！？：；""''）
- 规范英文与中文之间的空格
- 统一数字与单位的表示方式
- 处理全角/半角字符混用问题

### 2. 段落结构优化
- 删除过多重复影响阅读的文字
- 优化段落之间的衔接，使其自然流畅
- 合理划分段落，提升可读性
- 处理模棱两可的内容表达

### 3. 排版美学
- 保持信息的本质和准确性
- 根据文体风格调整排版方式
- 增强文字的视觉吸引力
- 提供专业、清晰的呈现形式

## 工作流程

### Step 1: 接收用户输入
- 等待用户提供需要优化的文本内容
- 识别文本的来源格式（如网页、PDF、聊天记录等）

### Step 2: 分析文本特征
- 识别当前文本的排版问题
- 分析文体风格（技术文档、新闻报道、个人随笔等）
- 检测需要优化的重点区域

### Step 3: 执行优化排版
按以下优先级进行优化：

1. **标点符号规范化**
   - 中文语境使用中文标点：，。！？：；""''
   - 英文语境使用英文标点：,.!?:;""''
   - 列表项使用统一的标点风格

2. **空格规范**
   - 中英文之间加空格
   - 中文与数字之间加空格
   - 数字与单位之间加空格
   - 标点符号后加空格（英文）

3. **段落优化**
   - 删除多余的空行（保留1个空行分段）
   - 合并碎片化的句子
   - 拆分过长的段落
   - 优化段落之间的过渡

4. **内容精简**
   - 删除重复表达
   - 简化啰嗦的句式
   - 保留核心信息
   - 消除歧义表达

### Step 4: 输出优化结果
- 返回完整的优化后文本
- 保持原文的核心信息和准确性
- 确保排版符合中文阅读习惯

## 约束条件

1. **信息准确性** - 排版优化不得改变原文的核心意思
2. **适度原则** - 删除重复内容但保留必要的强调
3. **主动优化** - 对模棱两可的内容必须进行优化
4. **风格一致** - 全文保持统一的排版风格

## 扩展能力

如需进一步增强功能，可在 `EXTEND.md` 中添加：
- 特定行业的术语规范（如技术、金融、医疗）
- 特殊格式处理规则（如代码块、表格、列表）
- 品牌名称的标准写法
- 自定义的排版风格偏好

## 注意事项

1. **代码块保护** - 遇到代码块（```标记）时，保持原样不做修改
2. **专有名词** - 保留专有名词的原始大小写和格式
3. **引用内容** - 引用的原文保持原样，只优化引用标记的格式
4. **数学公式** - 数学公式和特殊符号不做修改

## 网页抓取文章的"排版+UI 痕迹"双重清洗

针对从 Web 平台（如微信公众号 / web.cafe / 知乎 / 掘金等）抓取下来的 Markdown 文章，抓取脚本常常产生 **"网页 UI 痕迹 + 重复副本"** 噪声。标准化排版前先按本节清洗。

### 第一类：平台 UI 痕迹（必须清理）

识别特征 —— 出现在 frontmatter 之后到正文之前，或文件末尾的"导航/登录/分享/版权"模块里：

| 平台痕迹 | 典型样子 |
|------|------|
| **平台 Logo 占位图** | `![platform_name](images/.../img_NNN.svg)` 或 `[![...](images/.../img_NNN.svg)](https://.../)` |
| **空锚链接** | `[](https://.../home)` 或 `[](https://.../login)` |
| **"添加图片 / 添加隐藏回复"按钮文本** | 单独成行，紧贴留言区上下 |
| **作者元信息 + 分类标签 + "收藏"按钮** | "哥飞 2025-10-10 16:00\n[分类 A](...)[分类 B](...)... \n作者名\n哥飞小课堂\n收藏" 这种 |
| **二维码 / 公众号引导图** | `![二维码](images/.../img_NN.png)` + 紧跟的"关注公众号 / 输入登录 / 提交绑定" |

处理：整段删除，并保留图床上对应文件（目录级 .gitignore 不动）。

### 第二类：抓取重复副本（必须先去重）

抓取脚本在同一份文件里经常出现"两份几乎相同的完整内容"。识别特征：

- 文件长度异常偏大（200+ 行才一两段话）
- 中间出现第二个 `# 一级标题`（同 frontmatter `title`）
- 中间出现第二个作者元信息块（"哥飞 YYYY-MM-DD HH:MM"）
- 中间出现第二个 `[](https://.../home)` 空链接

处理原则：
1. **保留下文**（那是浏览器渲染后的版本，markdown 更规范，段落清晰）
2. **删除上文**（那是 web 模板头部 UI + 重复正文）
3. 如果两段都很精简、可对比找差异 → 把两段正文贴出来给用户判断；若用户说不确定，则**只保留下文**且向上文汇报"已删除上半段重复正文"
4. 这一步必须**早于**第二步标点/空格规范 —— 不然会改坏一半再发现前面要删、留下半规范一半

### 第三类：留言区头像占位（视场景而定）

抓取时，平台为每个发言用户和回复自动生成头像占位 `img_NNN.jpg`：

- **若用户希望"留言放末尾 + 头像去除"**（推荐）：删除所有 `![](images/.../img_NNN.jpg)` 头像行，统一 `- **用户名** + 时间戳 · 回复` 单行紧凑格式；嵌套回复用 `>` 引用块
- **若用户希望保留头像占位**：仅做规范化不动图

### 第四类：末尾装饰图

出现在留言块结束、文件最末，仅作装饰、无信息内容：
- `![](images/.../img_NNN.{jpg,png})` 单独成行的图
- 上方紧贴"评论区"或评论区最后一个 `- ` 项

处理：直接删除。

### 第五类：正文配图 vs 头像占位的区分

很多文件两种图共用 `images/article_slug/` 目录：

- **正文配图**：出现在文章段落里、被段落文字引用来解释某个具体观点。**保留**。
- **头像占位**：出现在留言区的"用户名前一行 + 紧贴留言 Markdown 列表项"。**删除**。

判断方法：
- 用 `grep -n "img_" file.md` 列出全部
- 区分每张图所在的上下文：第 X 段、第 X 个留言项之后
- 留言头像特征：紧邻 `**用户名**` 加粗行 + `时间戳` + `回复`，且文件名通常是 `img_NNN.jpg`（按编号连续）

### 工作流：UI 痕迹与排版规范的分步执行

**绝不**"边改标点边删 UI"，否则：
- 一旦发现前面要删整段，前面的标点/空格/反引号规范化就白做了
- 用户看到中间态会以为你已经改动很多，撤回成本变高

正确工作流：

```
[Read 全文]   ←  先读全文找 UI 痕迹清单
   ↓
[Step 1]  删除重复副本（如果存在）
   ↓
[Step 2]  清理 4 类 UI 痕迹：svg logo + 空 []() + 添加图片/隐藏回复按钮 + 末尾装饰图
   ↓
[Step 3]  清理留言头像占位 + 统一留言条目格式
   ↓
[Step 4]  标点/空格/反引号规范化（这一步才开始"动排版"）
   ↓
[Step 5]  章节化（按文章语义补 ## 二级标题，去掉混乱的* * * 分隔）
   ↓
[Read 中段/末段验证 + 提交给用户审阅 1 篇再批量化]
```

### 重做（彻底重做）vs 渐进清理

适用边界：

| 用户指示 | 处理 |
|------|------|
| "只清理 UI 痕迹，不动标点" | 仅做 Step 1~3，**不**做 Step 4 |
| "完整规范化" | 做 Step 1~5 |
| "排版优化 + AI 时代我想要的格式" | 中间穿插 Step 4 + Step 5 |
| "重写/重构段落结构" | 先 Step 5 重构，再 Step 4 |

**反例** —— 当用户说"重写"不要立即整篇重写：
- 用户通常要"清晰可读"，不是"用你的文风重写"
- 一定要保留 frontmatter + frontmatter 所必须的 title
- 重写后的标题必须与 frontmatter title 一致（或用 frontmatter title）
- 不要删除 frontmatter 时间戳、url、source 等字段

### 沟通模板

每次处理一篇，立即向用户报告：
- ✅ 已处理的文件名
- ❌ 已删除哪些 UI 类型（精确到行号或编号）
- 🟰 改了哪些标点/格式（不重写逻辑）
- 🔴 文中如有错别字（如"用上"应作"上"）单独征求用户确认是否要改

### 验证标准

完成一篇后做以下自检：
1. `grep` frontmatter 已有的 6 个字段完整
2. `grep` 4 类 UI 痕迹全为 0 命中
3. `wc -l` 行数显著减少（去重 + 删 UI + 紧凑格式共同贡献）
4. Read 第 15 行 / 中段 / 尾段 各一处，确认无错乱

## 历史教训：从 webcafe-xiaoketang 批量清洗中学到的

> 这是 2026-07-27 在清洗 18 篇哥飞小课堂文章时沉淀的经验。

1. **绝不擅自重写正文** —— 一旦发现"重复正文副本"应**先停下向用户报告**，由用户选择保留下文/保留下文/合并。绝不要"顺手"把上半段删了就开始规范化下半段。

2. **commit 的 stage / 工作区区分要早做** —— git status 的 `M`（已暂存）和无标识（仅工作区修改）不易一眼看出。如果 `git checkout -- file` 无效，就要用 `git restore --staged file` + `git restore file` 两步回退。

3. **批量前必须先验证 1 篇** —— 用户在意的可能不是"几十篇都做完"而是"每一篇都稳"。在做完 1 篇后**停下来让用户审**，再批量化剩下的。

4. **错别字要单独标注** —— 比如"用上"→"上"、"不要需要"→"不需要"这类，应在汇报时明确指出，用户可能会特意保留原文。

5. **留言头像特征 vs 正文配图** —— 二者经常共用同一目录。判断核心是"它是被哪个上下文引用的"：紧贴 `- **用户名**` 行 + 时间戳 + 回复 = 头像占位；段落里跟着具体描述 = 正文配图。

6. **留言块的视觉统一** —— 加粗用户名 + 时间戳 + "· 回复" 单行格式：`正文\n\n> **作者名** + 时间戳 · 回复\n>\n> 内容` 是更紧凑的嵌套回复格式。
