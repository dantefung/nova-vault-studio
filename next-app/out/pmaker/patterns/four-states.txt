<h1>四态齐全</h1>
<p>一块界面在真实环境里会出现四种样子，AI 通常只做出其中一种。剩下三种要么一片空白，要么直接把报错摊在用户面前。</p>
<p>你会遇到的现象</p>
<ul>
<li>
<p>自己演示一切正常，同事一登录就是白屏，因为他账号里没数据</p>
</li>
<li>
<p>网慢的时候页面先塌下去，数据回来又撑开，正要点的按钮跑掉了</p>
</li>
<li>
<p>接口一挂整页变成 Uncaught TypeError，用户只能刷新碰运气</p>
</li>
</ul>
<p>原因不在模型。你说做一个订单列表，它脑子里的画面就是一屏排列整齐的订单，因为你给它的描述里也只有这一种。空、加载、出错这三种情况在需求文档里从来不出现，只在真实用户手上出现：新注册的人第一次打开、地铁里信号断了、后端刚好在发版。</p>
<p>补齐的成本通常是几十行代码。真正的门槛是在写需求的时候就把它们当成需求的一部分，而不是等 bug 报上来再补。</p>
<h2>怎么判断</h2>
<p>任何一次取数据，结果只会落在四个格子里。照着这张图问一遍，就知道少写了哪个。</p>
<p>发起请求</p>
<p>还没回来
失败了
成功，但没数据
成功，有数据</p>
<p>加载态</p>
<p>错误态</p>
<p>空态</p>
<p>正常态</p>
<p>还要多久，页面会不会跳
怎么回事，我能做什么
为什么是空的，
下一步该干什么
最重要的那条看得到吗</p>
<p>空态还要再分一层：是这个人本来就没有数据，还是筛选条件把数据筛没了。前者引导他创建，后者提示放宽条件并给一键清除。</p>
<h2>设计考量</h2>
<ul>
<li></li>
</ul>
<p><strong>空态是介绍产品的机会，别只写暂无数据。</strong>
用户第一次进来看到的多半就是空态。这块地方应该说清楚这里将来会有什么、以及怎么让它有，一句解释加一个主按钮。四个字的暂无数据把最好的教学位置浪费掉了。</p>
<ul>
<li></li>
</ul>
<p><strong>加载用骨架屏，别用居中转圈。</strong>
骨架屏提前占住内容将来的位置，数据到达时页面不跳动；转圈会让整块区域先塌再撑开。超过一秒的等待才需要显示加载态，更短的反而闪一下更难受。</p>
<ul>
<li></li>
</ul>
<p><strong>错误文案按「说明当前状况 + 引导措施」写。</strong>
先讲发生了什么（没连上服务器），再讲他能做什么（重试或检查网络）。这个公式套在任何一条提示上都成立。重试按钮放在文案旁边，别让人去刷新整页。</p>
<p>提示用什么形式，取决于这件事严不严重。三档从强到弱，越级使用的代价是用户很快学会闭眼点确定。</p>
<p>弹窗 · 强
必须立刻处理的错误</p>
<p>全局横幅 · 中
状态变化，不必立刻行动</p>
<p>气泡 · 弱
可看可不看的信息</p>
<p>强度分档参考了提示语设计的常见做法。判断标准很简单：这件事如果用户不处理，会不会出问题。</p>
<ul>
<li></li>
</ul>
<p><strong>局部失败就局部提示，别让整页塌掉。</strong>
侧边栏的推荐模块挂了，不该导致整个页面变成错误页。状态的粒度要跟数据源的粒度对齐，每个独立请求各自管好自己那块区域。</p>
<ul>
<li></li>
</ul>
<p><strong>四种状态的容器高度尽量接近。</strong>
切换时高度剧烈变化会导致页面跳动，用户正要点的按钮会跑掉。给容器一个 min-height，是成本最低的体验改善。</p>
<ul>
<li></li>
</ul>
<p><strong>错误文案里不要用感叹号，句尾也不加标点。</strong>
感叹号会把一次网络波动渲染成事故。等待类文案统一用省略号收尾（加载中…），这是中文界面里比较通行的写法。</p>
<h2>给 AI 的话</h2>
<p>放进组件需求，或者直接沉淀到项目的 <code>CLAUDE.md</code>，之后每次生成数据组件都会默认带上四态。</p>
<p>复制
PROMPT · 组件需求
凡是涉及异步数据的组件，必须同时实现四种状态，缺一不可：</p>
<ol>
<li>正常态：有数据时的正常渲染。</li>
<li>空态：数据为空数组时。区分两种来源——</li>
</ol>
<ul>
<li>用户还没有任何数据：给一句说明 + 一个主行动按钮</li>
<li>筛选/搜索后无结果：提示放宽条件 + 一键清除筛选</li>
</ul>
<ol start="3">
<li>加载态：使用骨架屏，形状和数量贴近真实内容，不要用居中 spinner。</li>
<li>错误态：按「说明当前状况 + 引导措施」写文案，配一个「重试」按钮，
不要暴露状态码或堆栈。</li>
</ol>
<p>文案规范：</p>
<ul>
<li>不使用感叹号；句尾除疑问句外不加标点。</li>
<li>等待类文案统一以「…」结尾，例如「加载中…」。</li>
<li>提示强度分三档：必须立刻处理用弹窗，状态变化用全局横幅，
可看可不看用气泡。不要越级。</li>
</ul>
<p>其他约束：</p>
<ul>
<li>四种状态复用同一个外层容器，设置 min-height 避免切换时页面跳动。</li>
<li>错误只影响当前组件，不要向上冒泡导致整页变成错误页。</li>
<li>把状态做成组件的一个 prop（'ok' | 'empty' | 'loading' | 'error'），
这样我可以在不改后端的情况下逐个预览。</li>
</ul>
<p>先告诉我这四种状态分别打算怎么呈现，我确认后你再写代码。</p>
<p>最后一句很关键。让它先描述方案，你能在几秒内看出空态是不是又写成了四个字的暂无数据，比读完代码再返工快得多。</p>
<h2>相关模式</h2>
<p>首次体验
空态是首次体验的主要载体。新用户第一次打开时看到的几乎全是空态，这两个模式在同一块屏幕上碰头：一个管没有数据时显示什么，一个管没有数据时该引导他做什么。</p>
<p>操作反馈
加载态和错误态本质上都是反馈。区别是四态管的是页面进来时的数据，操作反馈管的是用户点击之后的结果，两者用同一套视觉语言才不会显得是两个产品。</p>
<p>先规格后代码
四态最容易在直接让 AI 写的时候漏掉。先要一份状态清单再动手，是把这个模式落地的具体手段。</p>
<p>真实数据压测
四态写完了不代表对。用零条数据和断网各跑一遍，是验证这个模式是否真的生效的唯一方式。</p>
