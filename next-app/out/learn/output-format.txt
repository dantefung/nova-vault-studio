<h1>控制输出格式</h1>
<p>只要模型的输出要被程序接住，格式就必须稳定。而「在提示词里说清楚」这一招，<strong>可靠性大概是九成——听起来不错，放到线上就是每天几百次失败。</strong></p>
<p>你会遇到的现象</p>
<ul>
<li>
<p>要求只返回 JSON，它偏要在前面加一句「好的，这是您要的结果：」</p>
</li>
<li>
<p>解析代码写了一堆兼容逻辑，还是时不时崩</p>
</li>
<li>
<p>开了流式输出之后，前端拿到半截 JSON 没法处理</p>
</li>
</ul>
<h2>三层手段</h2>
<p><strong>第一层：在提示词里请求。</strong></p>
<p>最基本的做法，写清楚要什么格式。有两个技巧能明显提高命中率：<strong>给一个格式样例</strong>（比描述格式有效得多，这是给例子那一招的应用），以及<strong>明确说「不要有任何解释文字，第一个字符必须是左花括号」</strong>。</p>
<p>但它终究是「请求」不是「保证」。模型本质上是在做概率延续，而「好的，这是您要的结果」这种开场白在语料里实在太常见了，总有概率冒出来。</p>
<p><strong>第二层：用接口参数强制。</strong></p>
<p>多数平台提供了 <code>response_format</code> 之类的参数，能在生成层面约束输出——生成的时候就只允许产出符合 JSON 语法的 token。这不是事后检查，是从根上不给它跑偏的机会。</p>
<p>更进一步的是提供 schema：不仅要求合法 JSON，还指定有哪些字段、什么类型。<strong>能用就一定要用</strong>，这是可靠性提升最大的一步。</p>
<p>但要清楚它保证的边界：**它保证语法合法，不保证内容正确。**字段是齐的，值可能是编的；类型是对的，数字可能是错的。格式约束管不了幻觉。</p>
<p><strong>第三层：你自己校验。</strong></p>
<p>这一层不能省，哪怕前两层都上了。解析失败怎么办、字段缺了怎么办、值明显不合理怎么办——这些分支必须写。</p>
<p>常见的兜底策略：<strong>重试一次</strong>（把错误信息带上，让它自己改）、<strong>降级</strong>（换个模型或退回简单模式）、<strong>拒绝</strong>（明确告诉用户这次没成功，而不是展示一堆乱码）。</p>
<p>还有个实践细节：**把「解析失败率」做成一个监控指标。**它悄悄上涨，通常意味着上游模型版本变了——尤其是你用了带 latest 的模型名的时候。</p>
<p>三层是叠加，不是三选一</p>
<p>① 在提示词里请求
给格式样例 ＋「第一个字符必须是左花括号，不要任何解释文字」</p>
<p>约九成
剩下那一成，放到线上就是每天几百次失败</p>
<p>② 用接口参数强制
response_format ＋ schema：生成时就只允许产出合法的 token</p>
<p>语法必对
但只保证语法，不保证内容——字段齐了，值可能是编的</p>
<p>③ 你自己校验
解析失败 → 带着错误重试一次 · 降级 · 明确拒绝，别展示乱码

<p>第二层是可靠性提升最大的一步，<strong>能用就一定要用</strong>。但它守的是语法边界，越过这条线的内容正确性，仍然要靠第三层和后面的核验来兜。</p>
<h2>格式本身要设计</h2>
<p>光有约束还不够，格式设计得好不好，直接影响模型填得对不对。四条经验。</p>
<p><strong>一、字段名要能自解释。</strong><code>category</code> 比 <code>c</code> 好，<code>confidence_0_to_1</code> 比 <code>score</code> 好。模型是顺着字段名的语义在填值的，名字含糊，它就得猜你要什么。</p>
<p>**二、别嵌套太深。**三层以上的嵌套结构，填错的概率明显上升。能拍平就拍平。</p>
<p>**三、给枚举值划定范围。**要分类就把可选项全列出来——「category 只能是这五个值之一：…」。否则它会自己发明新类别，而且发明得很合理，让你一时看不出问题。</p>
<p>**四、留一个「不确定」的出口。**这条常被忘。如果所有字段都必填，遇到材料里没有的信息，它只能编一个。给一个 <code>null</code> 或者 <code>&quot;未提及&quot;</code> 的合法选项，等于给了它一条说实话的路——这是防幻觉最实在的做法之一。</p>
<h2>和流式输出的冲突</h2>
<p>这是产品设计上必须做的一个取舍，很多团队踩了才发现。</p>
<p>流式输出能大幅改善感知速度：用户看着字一个个冒出来，比盯着转圈舒服得多。但它和结构化格式天然冲突——**半截 JSON 是没法解析的。**你只能等它全部生成完，那流式就白开了。</p>
<p>三种处理方式，按场景选。</p>
<p>**一、给人看的就别要 JSON。**如果输出是直接展示给用户的一段文字，那就开流式、要纯文本或 Markdown，别为了「整齐」硬套结构。</p>
<p>**二、给程序读的就关流式。**数据抽取、分类打标这类，输出本来就是给代码用的，用户看不见中间过程，流式没有意义。关掉，用严格格式约束。</p>
<p>**三、两者都要，就拆成两段。**这是最常见的真实场景——既要展示一段自然的回答，又要拿到结构化的元数据。做法是：<strong>让它先流式输出给人看的正文，最后再输出一小段结构化数据</strong>，前端渲染正文，程序解析末尾那段。或者干脆分成两次调用，各管各的。</p>
<p>最后提醒一句，这个取舍要在设计阶段就定，别等前端做完了才发现格式对不上。<strong>「这段输出是给人看的还是给程序读的」——这个问题该在写提示词之前就问清楚。</strong></p>
