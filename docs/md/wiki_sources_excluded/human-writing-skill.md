# 遇到好 Skill 别急着装：从拆解到融合的完整实践

导读：遇到一个有用的 Skill，直接装上用就完了？这篇文章记录了从发现 human-writing Skill 到深度拆解、对比自有 Skill、最终融合改进的完整过程。核心思路：先搞懂它为什么有效，再决定是装还是融。

GitHub 上有个叫 human-writing 的项目，4 天拿了近 2000 Star，专治"AI 写的中文没有人味"。作者有一个自己的微信公众号技术文章写作 Skill（wechat-tech-article），也带去 AI 味能力，但效果不如它。

碰到这种情况，常规操作是直接装来用。但他做了一件事：把它的源码全部拉下来逐行读，搞清楚它为什么有效，然后决定哪些能力直接搬、哪些要改造、哪些不用动。

这篇文章记录的就是这个拆解和融合的过程。

## human-writing 是什么

human-writing 是一个通用中文写作 Skill，目前约 2000 Star、174 Fork，MIT 协议，2026 年 8 月刚发布。它的定位很明确：让 AI 写的中文读起来像一个具体的人在说话。

它覆盖论坛长帖、公众号文章、小说、口播稿等通用场景，不专门处理技术文章。整个 Skill 由 6 个文件组成：SKILL.md（主流程）、forum-prose.md（写法指南）、revision.md（七遍改稿流程）、check_prose.py（量化检测脚本）、reality.md（事实核验）、dist/human-writing-lite.md（2000 字蒸馏版，可直接粘到 ChatGPT 用）。

## 它为什么有效：6 个设计

读完源码后，总结了 6 个核心设计。下图分三层：写前门槛（从源头防注水）、写中规范（改变模型生成行为）、写后检测（量化机器校验）。前两层是关键，在"怎么写"之前就把大部分 AI 味挡住了。

![human-writing 三层设计](images/human-writing-skill/001.png)

如果没耐心看长文，这里是快速版：

- **材料门槛前置**：动笔前必须列出至少 5 件具体材料，材料不够就不写长稿，宁可交短稿也不灌字数
- **说话位置锚定**：动笔前先回答"谁在说、他凭什么知道、最在意什么判断"，给文章一个明确的人格
- **修辞动作级禁令**：不禁具体字符串（「不是…而是…」），禁的是整个修辞动作（「先立误解再推翻」），覆盖所有变形
- **正向写法示范**：不只说"别这样写"，还给"可以这样写"的对照示例和完整段落
- **七遍结构化改稿**：每遍只管一件事（人格、材料、句式、韵律、禁令、事实、结尾），避免一遍全查的顾此失彼
- **量化检测脚本**：check_prose.py 用统计方法检测 AI 味，核心指标包括句长变异系数、连词密度、翻案腔正则匹配

这 6 个设计里，前 3 个是关键。

### 材料→人格→禁令：一个递进的防注水链

human-writing 最独特的地方是它在写作流程的最前面设了两道关卡：材料门槛和说话位置。这两道关卡在"怎么写"之前就把大部分 AI 味挡住了。

传统去 AI 味方案是"写完再检查"。模型生成完毕，然后用关键词匹配找出 AI 味的句子修改。这种方式有个问题：文章的整体结构已经是 AI 式的了（3 条观点灌成十几段，每段换种说法重复），你改句式也没用。

human-writing 的做法是在源头卡住。材料门槛要求你拿出 5 件具体的东西（代码片段、真实数据、踩坑记录、原话引用），然后才能写长稿。每写完一段，要标注这段靠哪件材料站住。如果一段话只能标注出"进一步解释"或"可能的影响"，说明这段没有新材料，删掉。

说话位置锚定解决的是另一个问题：AI 写的文章"没有人"，根源不在缺第一人称代词。一个没有明确说话者立场的文本，加再多"我觉得"也救不了。human-writing 要求先确定"谁在说、他凭什么知道、最在意什么判断、读者会追问什么"。有了这个锚点，文章自然有了取舍，有了人格。

### 修辞动作禁令：v1.0 到 v1.1 的关键迭代

这个 Skill 的作者在 v1.0 用的是字符串禁令（禁「不是…而是…」），然后发现模型会换一套字面继续做同样的事。「你以为…其实…」「回头才发现」「表面A，实际B」，这些都是同一个修辞动作的不同马甲：先立一个读者并没有的误解，再推翻它给下文抬价。

v1.1 升级为禁整个修辞动作，列出了 7 种变形外衣。命中任何一种，都拆回正面陈述。这个思路比"全文最多出现 1-2 处"的数量限制有效得多。数量限制只是减少了出现次数，模型换个说法就绕过了。禁修辞动作才真正改变了生成行为。

### check_prose.py 里最有技术含量的两个检测

量化检测脚本不只做关键词匹配，最硬的两个是：

**句长变异系数。** 把每句话的汉字数提取出来，算标准差除以均值。人写的文章长短句差距大，十个字的句子会挨着四十个字的句子。模型写的太齐，每句长度差不多。CV 低于 0.42 就报警。这个统计信号很难通过"写短一点"或"写长一点"来绕过，因为它检测的是整篇文章的节奏分布。

**翻案腔语义变形匹配。** 17 种正则模式覆盖所有"先立误解再推翻"的变形，从"不是A而是B"到"总以为…后来才发现"到"A不重要，重要的是B"。模型每换一种说法，只要做的还是同一个动作，都能被匹配到。

## 和 wechat-tech-article 的对比

作者有自己的微信公众号技术文章写作 Skill，叫 wechat-tech-article。同样带去 AI 味能力，但定位完全不同：它是技术文章专用，不管通用写作。

两套 Skill 的能力分布几乎不重叠。下图左边是 human-writing 的 6 项（蓝色），右边是 wechat-tech-article 的 4 项（绿色），两者互补：

![两个 Skill 的能力对比](images/human-writing-skill/002.png)

human-writing 强在：让中文像人写的（材料门槛、说话位置、修辞动作禁令、量化检测、正向示范、七遍改稿）

wechat-tech-article 强在：让技术文章有深度、能发布、事实准确（内容价值审计、事实查证、10 维度打分、发布流程）

具体来说，wechat-tech-article 有 human-writing 完全不具备的 4 块能力：

- **内容价值审计（防水文）**。技术文章最常见的质量问题是停在"是什么"层面。提了语义缓存，但只说"它很重要"，不给工具名和配置，踩坑细节也没有。wechat-tech-article 要求每个技术建议必须有三层：是什么、为什么需要、怎么做。只停在第一层就是水文。
- **GitHub 项目事实查证**。涉及 GitHub 项目时，必须直接调 API 取最新的 Stars、Forks、pushed_at 和 archived 字段。搜索结果可能是几个月前的旧数据。比如 Semantic Kernel 被微软合并进 Agent Framework、GPTCache 更新停滞，这些只有查了 API 才知道。archived 为 true 的项目禁止推荐。
- **10 维度终审打分**。受众定位、技术准确性、时效前沿性、实操落地性、原创洞察等 10 个维度，每维度 1-10 分，总分 100。低于 80 分不发，低于 70 分重写。human-writing 没有"打分"这个概念。
- **完整发布流程**。封面图生成、摘要准备、wenyan-cli 一键推送草稿箱。human-writing 完全不管发布。

反过来，human-writing 有 wechat-tech-article 完全缺失的能力：

- 材料门槛（写之前卡住注水）
- 说话位置锚定（给文章人格）
- 修辞动作级禁令（覆盖所有变形）
- 量化文风检测脚本（句长 CV、连词密度等）
- 正向写法示范（不只给检查清单）

两者是互补关系。

## 具体改了什么：5 项优化

读完 human-writing 源码后，给自己的 wechat-tech-article 做了 5 项优化。按优先级排列。

### 优化 1：材料门槛（最大改动）

在写作流程的最前面插入了一个新阶段"材料清点"。技术文章 2000 字以上，必须先在内部列出至少 5 件具体材料：代码片段、配置示例、踩坑记录、真实性能数据、架构图、可运行项目链接。

不合格的"假材料"明确列出：抽象观点换四种说法、模型编造的"比如某团队"案例、常识推演、把一条材料拆成"用途意义风险未来"四段。

材料不够时，能查到的先研究，研究后仍不够就缩小题目或缩短篇幅。宁可交一篇更短更实的文章，也不用假例子填满。每段写完后内部标注：它靠哪件材料站住。

这一个改动从源头消灭了"3 条观点灌成十几段"的注水式 AI 味。

### 优化 2：翻案腔禁令升级

从"全文最多 1-2 处不是…而是…"升级为禁整个修辞动作。覆盖 7 种变形外衣：

- 不是A，而是B / 并非A，而是B
- 你以为A，其实B / 回头才发现
- 表面上A，实际上B / 看似A，实则B
- A不重要，重要的是B
- 与其说A，不如说B
- 省字变形：不是A，是B / 不是A。而是B
- 命中任何一种，只有一种修法：找到原本想下的判断，从正面说出来，把依据放旁边。

同时新增了三项以上同构排比禁令、名词化句式禁令（「进行了优化」改「改了」、「完成了对流程的调整」改「把流程改了」）、模型路标词禁令（「更微妙的是」「值得注意的是」「需要指出的是」）。

### 优化 3：文风量化检测脚本

移植了 check_prose.py 的核心统计检测，写了 check_style.py，适配技术文章场景。脚本分两层：

**硬禁令层（FAIL）**：翻案腔正则匹配、技术黑话（「赋能」「抓手」「商业闭环」「降本增效」「全链路」等）、硬停词（「说白了」「说穿了」「先说结论」）、模型路标词、破折号。

**统计信号层（WARN）**：句长变异系数（CV < 0.42 报警）、连词密度（每千字 > 7 个报警）、同构排比检测、名词化句式检测、重定语句检测（一句话 4 个以上"的"）、段落开场重复检测。

用 AI 味文字做了测试，脚本能正确检出 3 个 FAIL 和 8 个 WARN。脚本接入写作流程的质检阶段，和乱码扫描并列作为交稿前的必做检查。硬禁令清零才能交稿。

### 优化 4：说话位置锚定

在写初稿前增加了 4 个内部问题：

1. 这篇文章的作者是谁（做过这件事的工程师 / 调研了方案的架构师）
2. 他最在意的判断是什么，依据是什么
3. 读者读完上一段最自然追问什么
4. 哪里是作者真正在意的，哪里只是陈述事实

### 优化 5：正向写法示范

在去 AI 味检查清单旁边，补充了 3 组技术文章的对照示例。

## 改完之后的架构

优化后的 wechat-tech-article 变成了 8 阶段流程。紫色阶段借鉴自 human-writing，绿色阶段是原有优势，两者前后衔接：

![改完之后的 8 阶段架构](images/human-writing-skill/003.png)

1. **阶段零**：材料清点（动笔前的硬门槛）
2. **阶段一**：素材整理与结构规划（含说话位置锚定）
3. **阶段二**：去 AI 味（修辞动作级禁令 + 正向示范）
4. **阶段三**：去重与逻辑审查
5. **阶段四**：内容价值审计（防水文）
6. **阶段五**：事实查证（GitHub API + WebSearch）
7. **阶段六**：编码质检与终审打分（乱码扫描 + check_style.py + 10 维度打分）
8. **阶段七**：封面图与发布

前半段（阶段零到二）管"让中文像人写的"，借鉴自 human-writing。后半段（阶段四到六）管"让技术文章有深度、能发布、事实准确"，是原有优势。两者不冲突。

## 遇到好 Skill 的处理框架

这次实践让他总结了一个处理框架。遇到一个好的 Skill，不要直接装来用，先走三步：

**第一步：拆解它为什么有效。** 拉源码逐行读。不要只看 README 的功能介绍，要看具体实现。README 告诉你"能做什么"，源码告诉你"怎么做到的"。比如 human-writing 的 README 说"材料门槛"，但只有读了 SKILL.md 才知道它具体怎么卡材料、材料不够时怎么处理。

**第二步：判断是直接装还是融合。** 如果新 Skill 的能力和你已有 Skill 完全不重叠，直接装。如果有重叠或互补关系，融合更好。融合的好处是保持一套工作流，避免在两个 Skill 之间来回切换。融合的前提是你对新 Skill 有足够理解，知道哪些设计可以直接搬、哪些要适配。

**第三步：融合时保留各自的核心壁垒。** 这次融合中，wechat-tech-article 的技术深度审计、事实查证流程、10 维度打分全部原封不动。这些是 human-writing 没有的能力，也是技术文章场景特有的需求。两个 Skill 各管各的强项，叠加起来用。

wechat-tech-article 已开源，地址在 https://github.com/songjiayang/wechat-tech-article ，包含完整的 SKILL.md 和 check_style.py 检测脚本，可以直接安装使用或参考改造。
