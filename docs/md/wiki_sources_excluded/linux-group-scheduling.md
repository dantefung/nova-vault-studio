# 从进程到进程组：Linux 组调度背后的公平性重构

## 0. 引言

操作系统的 CPU 调度，本质上是对稀缺计算资源的「公平分配」。从早期时间片轮转、O(1) 调度器到完全公平调度器（CFS），Linux 内核始终在优化「单个进程之间的公平」——让每个进程按自身权重获得匹配的 CPU 时间。这套逻辑在单用户桌面场景下非常合适，但在多用户共享主机的场景中，却存在着一个逻辑漏洞：公平的粒度，并不适合多用户场景。

Linux 中的组调度（Group Scheduling），正是为了解决公平粒度的问题。它没有推翻 CFS 的核心算法，而是通过对「调度实体」的抽象升级，把公平的单位从单个进程向上延伸到进程集合，以极小的侵入性完成了整个调度体系的粒度重构（以 Linux 2.6.26 版本来进行分析）。

## 1. 问题描述：进程公平不等于用户公平

在传统调度模型中，调度器的最小操作单元是单个进程。CFS 为每个可运行进程维护虚拟运行时间，通过红黑树始终选择虚拟时间最少的进程运行，保证所有进程按权重比例分配 CPU 时间。在单用户环境下，所有进程归属同一使用者，「进程粒度的公平」与「用户维度的公平」完全等价，这套逻辑自洽且高效。

![进程级公平的调度模型](images/linux-group-scheduling/001.png)

但 Linux 从诞生起就是多用户操作系统，当一台主机同时承载多个独立用户时，问题开始出现：如果用户 A 启动 10 个进程，用户 B 仅启动 2 个进程，在进程级公平规则下，A 能占用的 CPU 时间天然是 B 的 5 倍。在早期多用户服务器中，这或许只是体验差异；但随着虚拟主机（VPS）商业模式普及，这个问题直接触及到了商业公平的底线 —— 两个付费标准相同的用户，仅因启动进程数不同，获得的计算资源相差数倍。

更极端的场景下，恶意用户可以通过持续 fork 子进程的方式，近乎掠夺式地占用整机 CPU 资源。传统调度对此毫无办法：每个子进程都是合法调度实体，都有权获得时间片。这个问题不是调度算法本身不公平，而是「公平的作用对象」，从一开始偏离了实际需求导致的问题。

## 2. 组调度的核心：把调度单位上移一层

组调度的解决思路非常简单：既然要保证用户间的公平，就把「用户的所有进程」打包成一个整体作为一级调度实体；先在组之间分配 CPU 时间，再在组内部给单个进程做二次分配。这是一种典型的「分层公平」设计，用两级调度实现了维度的升级。

### 两层分配的时间逻辑

在组调度模型下，CPU 时间的分配被拆分为两个独立的层级，每一层都遵循 CFS 的权重分配规则：

1. **组间分配**：系统将所有进程组视为一级调度实体，按照各组的 shares 权重值比例分配整机 CPU 时间。两个权重相同的进程组，将各自获得 50% 的 CPU 总时间，与组内进程数量完全无关。
2. **组内分配**：每个进程组获得的时间配额，再在组内部的进程（或子组）之间，按各自权重进行二次分配。

![两层分配的组调度模型](images/linux-group-scheduling/002.png)

回到多用户的例子：A 用户的 10 个进程归属组 A，B 用户的 2 个进程归属组 B，两组权重相等。那么组 A 与组 B 先各分得一半 CPU 时间；组 A 的 10 个进程平分这一半配额，单个进程仅获得总 CPU 的 5%；组 B 的 2 个进程平分另一半配额，单个进程可获得总 CPU 的 25%。最终两个用户占用的 CPU 总量完全相等，实现了用户维度的公平。

权重机制的存在，让组调度不止能实现「平等分配」，更能实现「差异化分配」——权重为 2048 的组，获得的时间天然是权重 1024 组的两倍，可以灵活适配不同优先级的业务场景。

### 树形分组：超越扁平隔离的层级管控

组调度没有停留在扁平分组的形态，而是借助 cgroup 体系实现了树形层级分组。系统启动时创建根进程组 `init_task_group`，所有进程默认归属根组；用户通过 cgroup 的 CPU 子系统，可以在任意组下创建子组，形成与文件目录完全对应的进程组树。

![树形进程组分层结构](images/linux-group-scheduling/003.png)

这种树形结构的价值，在于它能匹配现实中多层级的资源管理需求。比如一台企业服务器，可先按部门划分一级组，部门下按项目划分二级组，项目内再运行具体业务进程。调度时从根节点开始逐层分配：先给各部门按权重分配总 CPU，部门内部再给各项目分配，项目内最终分给进程。每一层都遵循统一的公平规则，每一层都可独立设置权重，实现了精细化的层级资源管控。

## 3. 内核实现：一套抽象兼容两种实体

组调度几乎没有对 CFS 的核心调度逻辑做侵入式修改，而是通过对调度实体的抽象扩展，无缝融入了原有调度体系。

### 嵌套的调度实体

CFS 的核心调度单元是 `sched_entity`（调度实体），运行队列是 `cfs_rq`，所有调度算法都围绕这两个结构展开。组调度要解决的核心问题，就是让「进程组」也能成为一个合法的调度实体，放进 CFS 的运行队列中。

首先是调度实体本身的扩展，核心是新增了 `my_q` 指针实现「一体两用」：

```c
struct sched_entity {
    struct load_weight load;      /* 调度实体权重，决定时间片分配比例 */
    struct rb_node run_node;      /* 红黑树节点，挂载到cfs_rq的红黑树上 */
    unsigned int on_rq;           /* 标记是否处于运行队列中 */
    u64 exec_start;               /* 本次运行起始时间 */
    u64 sum_exec_runtime;         /* 累计物理运行时间 */
    u64 vruntime;                 /* 虚拟运行时间，CFS调度核心依据 */
    /* 组调度核心字段：
     * 普通进程：my_rq == NULL
     * 进程组：my_rq 指向该组私有的cfs_rq运行队列
     * 仅凭该指针即可区分实体类型，实现C层面的轻量多态 */
    struct cfs_rq *my_rq;
};
```

内核用 `task_group` 结构完整描述一个进程组，最具代表性的是 per-CPU 设计 —— 每个 CPU 有独立调度队列，因此进程组需要为每个 CPU 都准备对应的调度实体和运行队列：

```c
struct task_group {
    struct cgroup_subsys_state css;       /* 关联cgroup文件系统 */
    /* per-CPU 调度实体：每个CPU上，该组都作为一个实体参与父组调度 */
    struct sched_entity **se;
    /* per-CPU 运行队列：每个CPU上，该组都有独立的队列管理内部进程 */
    struct cfs_rq **cfs_rq;
    unsigned long shares;                 /* 进程组全局权重，对应cpu.shares配置 */
    /* 树形结构三件套，构建进程组的层级关系 */
    struct task_group *parent;            /* 父进程组指针 */
    struct list_head siblings;            /* 兄弟进程组链表 */
    struct list_head children;            /* 子进程组链表 */
    struct rcu_head rcu;
};
```

三者的关联关系如下图：

![sched_entity / cfs_rq / task_group 关联关系](images/linux-group-scheduling/004.png)

简单来说，一个进程组对外是一个 `sched_entity`，可以挂到父组的运行队列中参与调度；对内它又拥有自己的 `cfs_rq`，管理组内的所有调度实体。就像一个嵌套的盒子：外部看是一个可被调度的单元，打开后又是一个完整的调度队列。

### 递归调度的核心：一个 do-while 循环

调度器的核心入口 `schedule()` 函数，几乎不需要为组调度做任何修改。真正的适配逻辑，藏在 CFS 的 `pick_next_task_fair` 函数中，仅用一个 do-while 循环就实现了层级递归调度。核心实现代码如下（精简版）：

```c
static inline struct cfs_rq *group_cfs_rq(struct sched_entity *grp) {
    return grp->my_q;
}

/* 从指定cfs_rq中选出最优实体：虚拟运行时间最小的红黑树最左节点 */
static struct sched_entity *pick_next_entity(struct cfs_rq *cfs_rq) {
    struct rb_node *left = cfs_rq->tasks_timeline.rb_node;
    struct sched_entity *se;
    if (!left) return NULL;
    while (left->rb_left)
        left = left->rb_left;
    se = rb_entry(left, struct sched_entity, run_node);
    return se;
}

/* CFS调度类的核心选程函数，组调度递归逻辑的核心 */
static struct task_struct *pick_next_task_fair(struct rq *rq) {
    struct task_struct *p;
    struct cfs_rq *cfs_rq = &rq->cfs;     /* 从根运行队列开始 */
    struct sched_entity *se;

    do {
        se = pick_next_entity(cfs_rq);    /* 当前层选出最优实体 */
        if (!se) return NULL;
        /* 核心：若实体是进程组，替换为组内队列，进入下一层 */
        cfs_rq = group_cfs_rq(se);
    } while (cfs_rq);

    p = task_of(se);                      /* 从调度实体转换为进程结构体 */
    set_next_entity(cfs_rq, se);
    return p;
}
```

![pick_next_task_fair 递归调度流程](images/linux-group-scheduling/005.png)

整个过程如同在树形结构中做深度优先查找：从根节点出发，每一层都按 CFS 规则选择最应该运行的实体，一路走到叶子节点，最终得到要运行的进程。而每一层的选择逻辑，都复用了同一套虚拟时间比较算法 —— 红黑树最左节点的规则完全没变，只是树上挂的节点，既可以是进程，也可以是另一个调度队列。

这种设计的优雅之处在于，**CFS 核心算法零改动**，仅通过实体的嵌套抽象，就实现了组调度的全部能力。调度器甚至不需要感知当前处于第几层分组，只需要按统一规则选择下一个实体即可，逻辑高度内聚。

## 4. 权衡与延续

和所有内核机制一样，组调度并不是完美方案，它本质上是在调度开销与隔离粒度之间做出的权衡。

层级越深的分组树，调度时需要遍历的层数越多，调度延迟也会相应上升。此外，组调度保证的是 CPU 时间总量的公平，无法保证组内进程的响应延迟 —— 如果一个组内有大量计算密集型进程，组内的交互进程响应速度会明显低于组外交互进程。

但这些局限，都掩盖不了组调度设计的长远价值。它真正的内核是「机制与策略分离」：内核只提供「按组分配 CPU 资源」的底层机制，至于分组维度、权重设置、层级划分，全部交给用户态定义。可以按用户分组，也可以按业务、项目、容器分组，适配无限多的场景。

从进程调度到组调度，Linux 的调度体系完成了一次从「个体公平」到「群体公平」的升级。它没有发明颠覆性的调度算法，却通过调整公平的粒度，解决了多租户场景下的核心矛盾。
