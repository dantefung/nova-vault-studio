# 互斥锁是如何一步步被发明出来的？

> 整个演化过程：关中断 → Peterson 算法 → 原子指令(TAS/CAS) → 自旋锁 → 互斥锁 → 读写锁。每一步都是被前一步的缺陷逼出来的。

大家好，我是小康。先问你一个问题——两个线程同时对一个变量做 `count++`，结果会是多少？很多人会说两个线程各加一次，结果是 2。错了。结果可能是 1。这不是玄学，是真实会发生的 bug。

<!-- more -->

## 第一步：count++ 为什么会出错？

`count++` 看起来是一行代码，但 CPU 执行它其实是三步：① 从内存读出 count 的值；② 把值加 1；③ 把新值写回内存。

两个线程并发执行，会交叉成这样：

![count++ 竞态条件](images/mutex-evolution/001.png)

B 读 count 的时候，A 还没写回去，所以 B 读到的也是 0。两个线程各自加了 1，但最终 count 只变成了 1。

这就是**竞态条件**（Race Condition）——结果取决于线程执行的时机，不确定，不可重现，最难排查的一类 bug。根本问题是："读-改-写"这三步必须一起完成，中间不能被打断。这种"不能被打断的一段代码"叫**临界区**（Critical Section）。

## 第二步：最原始的方案——关中断

第一个想到的办法很粗暴：进入临界区之前把 CPU 的中断关掉。没有中断，操作系统就没法切换线程，自然也就没人能打扰。

单核 CPU 上可以，但问题一堆：
- **只对单核有效**：多核 CPU 上，关掉一个核的中断，另一个核照样可以并发访问
- **太危险**：中断关掉期间，键盘、网卡、磁盘的信号全部无响应，系统卡死
- **用户程序不能乱关中断**：这是特权操作

关中断是内核里偶尔用的救急手段，在用户程序里根本没法用。

## 第三步：用一个标志位——Peterson 算法

1981 年，Gary Peterson 提出了一个优雅的软件方案，只用两个变量，不借助任何硬件支持：

```c
int flag[2] = {0, 0};  // 各自是否想进临界区
int turn = 0;           // 谦让：让谁先进

// 线程 i 想进临界区：
flag[i] = 1;            // 举手：我想进
turn = j;               // 谦让：你先
while (flag[j] && turn == j);  // 等对方出来
// --- 临界区 ---
count++;
// --- 临界区结束 ---
flag[i] = 0;            // 放手：我出来了
```

逻辑上完全正确，也不需要特殊硬件。但在现代 CPU 上，它跑不起来。原因：现代 CPU 和编译器为了性能会**乱序执行**，`flag[i] = 1` 和 `turn = j` 的顺序可能被颠倒，导致两个线程同时进入临界区。软件方案被硬件的优化给破坏了。

## 第四步：硬件出手——原子指令

必须让硬件提供一个"不可分割的操作"。CPU 厂商为此设计了专门的原子指令，最经典的是 **Test-And-Set（TAS）**——读取一个变量的值，同时把它设为 1，这两步合为一个不可分割的原子操作。

```c
// 这个函数是原子的，不可被打断
int test_and_set(int* lock) {
    int old = *lock;  // 读旧值
    *lock = 1;        // 设为1（加锁）
    return old;       // 返回旧值
}
```

有了这个，可以实现一把简单的锁——**自旋锁**（Spinlock）：

```c
int lock = 0;  // 0=空闲，1=有人占用
// 加锁：一直尝试，直到抢到
while (test_and_set(&lock) == 1);
// --- 临界区 ---
count++;
// --- 临界区结束 ---
lock = 0;  // 解锁
```

抢不到锁的线程，会一直在 while 循环里"转圈"等待——像一只不停旋转的陀螺。

## 第五步：自旋锁的问题——转得太累了

自旋锁有效，但等锁的线程一直在空转，白白消耗 CPU：

![自旋锁空转](images/mutex-evolution/002.png)

想象线程 A 拿到锁要做耗时 100ms 的操作（比如读磁盘），线程 B 在 while 循环里疯狂空转 100ms，把一个 CPU 核跑满，什么有用的事都没干。

自旋锁适合等待时间极短的场景（内核里保护数据结构，临界区执行几十纳秒），但对于用户程序——等几毫秒、几十毫秒——自旋锁简直是在烧 CPU。

## 第六步：互斥锁诞生——等不到就去睡觉

解决方案：抢不到锁，就让线程睡眠，把 CPU 让给别人用。锁释放时，再由操作系统把它唤醒。这就是**互斥锁**（Mutex，Mutual Exclusion）。

![Mutex 内部逻辑](images/mutex-evolution/003.png)

Mutex 的实现本身底层还是用了原子指令（比如 CAS），但在抢不到锁时，通过系统调用让线程挂起，而不是空转。

## 第七步：自旋锁 vs 互斥锁——怎么选？

| 场景 | 推荐 | 理由 |
|------|------|------|
| 临界区极短（纳秒级），多核 | 自旋锁 | 睡眠唤醒的开销比等待时间更大 |
| 临界区较长（微秒/毫秒级） | 互斥锁 | 睡眠让出 CPU，不浪费 |
| 单核 CPU | 只能互斥锁 | 自旋会把唯一的 CPU 占死，锁永远释放不了 |
| 内核中保护数据结构 | 自旋锁 | 内核不能随便睡眠 |
| 用户程序 | 互斥锁 | 几乎永远是更好的选择 |

## 第八步：锁的更多演化——读写锁

互斥锁有个浪费：它把"读"和"写"都同等保护了。但其实多个线程同时读是安全的，只有"写"和"读/写"之间才需要互斥。

于是有了**读写锁**（RWLock）：
- 多个线程可以同时拿到"读锁"，并发读没问题
- 写锁是排他的，写的时候读和写都得等

读多写少的场景（比如配置表、路由表），读写锁的性能远好于互斥锁。

## 第九步：死锁——锁用错了的后果

最经典的场景：A 等 B 释放锁 2，B 等 A 释放锁 1，谁都不会动，永远等下去——死锁。

![死锁](images/mutex-evolution/004.png)

死锁的四个必要条件，缺一不可：
1. **互斥**：锁本来就是排他的
2. **持有并等待**：拿着一把锁，等另一把
3. **不可剥夺**：别人拿的锁，你抢不走
4. **循环等待**：A 等 B，B 等 A

破坏任意一个条件，死锁就不会发生。最常用的实践方法是：给锁规定一个固定的获取顺序，所有线程都按同一顺序加锁，就不会出现循环等待。

## 总结：互斥锁的演化全貌

> 关中断（粗暴，不适合用户程序）→ 软件算法 Peterson（被 CPU 乱序破坏）→ 硬件原子指令（TAS/CAS）→ 自旋锁（空转，适合临界区极短的场景）→ 互斥锁（睡眠等待，用户程序的标准选择）→ 读写锁（读多写少场景的进一步优化）

每一步都是被前一步的缺陷逼出来的，这就是**工程演化的本质**。
