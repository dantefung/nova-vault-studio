# Agent 开发到底解决哪些问题？

> **摘要**：从一份真实大厂 JD 切入的 Agent 开发全景——八个每天真在打交道的问题。**场景选错是最贵的错误**（七成工单用传统接口更优）；**模型决定下限，数据链路决定上限**（PDF 表格被解析成碎片，模型再强也答不对）；**让 AI 稳定做对一万次**靠固定步骤节点 + 校验回滚 + 二次确认，不靠调 Prompt；上线后的四类值班问题（响应变慢/答案漂移/账单翻倍/越权访问）没有一个能靠调 Prompt 解决；成本复盘发现八成调用用不上最强模型，靠意图分类前置 + 缓存 + 上下文裁剪降六成；**没有评测体系的代价是两周说不清每版是变好还是变坏**。后端转 Agent 只需补 RAG 链路、Agent 工作流、评测、部署运维四块。

> 做了两年 Agent 开发，从 RAG 知识库做到 Agent。翻 BOSS 直聘看到一份大厂 JD 的 AI 智能体研发工程师（北京，18-28K），几乎没有提"写 Prompt"，也没有堆一堆花哨的框架名词，列的全是项目里真正每天打交道的东西——RAG 检索链路、工具调用、模型评测、私有化部署、异常回滚、人工接管、可观测性。

## 一、场景：先想清楚 AI 该放在哪

**Agent 开发中最贵的错误不是模型选错，而是场景选错。**

业务方提了个需求，说要做个 Agent 自动处理全部客服工单。听起来很美，但把三个月的工单日志拉出来分析，发现**七成的工单是查订单状态、改地址这类确定性操作**——用传统接口十行代码就搞定，上 Agent 反而又慢又贵还可能出错。真正需要 AI 的，是剩下那三成描述模糊、要跨系统查信息的工单。

所以 JD 里那句"参与需求澄清、场景拆解、技术可行性评估"特别有共鸣：**入行之后你会发现，一半的时间不是在写代码，是在判断这个环节到底该不该让用 AI。**

## 二、回答不准，问题多半在数据链路

每个 Agent 项目的第一个危机几乎都一样：上线没几天，客户找过来——"AI 答得不准"。

第一反应也是换模型、改 Prompt，折腾了半个月没起色。后来把链路一层层扒开看，发现问题出在**文档解析**上——客户给的 PDF 里全是表格，解析器把表格拆成了一句句破碎的文字，检索召回的都是残片，模型再强也答不对。

改了切分策略、上了 Rerank 重排，准确率一下子上来了。

> **模型决定下限，数据链路决定上限。**

这也是为什么 JD 里会单独列出 Embedding、Rerank、上下文构建和评测集构建——这些才是吃功底的地方。

## 三、执行：让 Agent 稳定跑完任务

Demo 里 AI 表现再好，到了生产环境都会遇到同一个问题：**它不听话。**

测试 Agent 在演示的时候行云流水，上了真实数据就开始翻车：工具调用传错参数、分析到一半忘了用户要什么、生成的报告数字对不上。改 Prompt 有用，但只是把出错概率从十分之一降到二十分之一，对企业来说仍然不可接受。

最后真正解决问题的是**工程手段**：

- 把大任务拆成固定的步骤节点
- 每步做完做校验，校验不过就回滚或转人工
- 涉及资金数据的关键动作，一律要求二次确认

这套东西写进 JD，就是"Agent 工作流、异常回滚、人工接管"那几行。

> **让 AI 偶尔做对不难，难的是稳定做对一万次。**

## 四、工程：上线之后，问题才刚开始

Demo 阶段大家只关心效果，上线之后才是真正的战场。值班手机上收到过的问题：

- 为什么今天响应慢了三倍？
- 为什么昨天答对的问题今天错了？
- 为什么模型账单这个月翻了一倍？
- 为什么测试账号能查到别的部门的数据？

**没有一个问题靠调 Prompt 能解决。** 解决它们靠的是日志监控、权限控制、Prompt 注入防护、审计日志，以及 Docker 和 K8s 那一套。

**私有化部署经验，现场联调。** 政企客户不会把数据放到你的云上，意味着你要去客户的机房里部署、对着他们的内网环境排查问题。这些活不性感，但占了这个岗位日常工作的大头。

> 后端转 Agent 是最顺的路——这部分工作本来就是后端的老本行，只是服务的对象从业务系统换成了 AI 系统。

## 五、成本问题

模型账单翻倍那次，做了一次成本复盘，结论很打脸：**八成的调用根本用不上当时那个最强的模型。**

后来的改造是老三样：

1. **意图分类前置**——简单问题走规则和小模型，复杂的才路由到大模型
2. **高频问题结果缓存**
3. **每轮对话裁掉无效的上下文再发给模型**

成本降了六成，响应还快了不少。

JD 里"持续优化响应速度、模型效果和交付效率"，说白了就是这件事。**成熟的 Agent 系统从来不追求模型越强越好，追求的是每一分钱花在刀刃上。**

## 六、Agent 评测体系

两年里吃过最大的亏，是早期没有评测体系。

那时候每次改完 Prompt，就拿几个问题手动试一遍，感觉变好了就发版。结果上线三天，客服找到我们：某个高频问题的回答被改坏了，而我们的测试用例里恰好没有它。**整整两周，我们说不清每一版到底是变好了还是变坏了。**

后来专门建了几百条的评测集，覆盖检索命中、回答准确性和格式合规，每次改动先跑一遍再说话。

JD 里把"模型评测"和"效果分析"写进职责，说明这个团队是真做过的。**没用过评测体系的人，写不出这一条。**

## 七、沉淀：把项目经验变成团队能力

JD 里还有一条很多人会略过：沉淀可复用组件、部署文档、评测集、排查手册。

**Agent 这行，框架半年换一代**，例如 LangChain 的版本更新，这些都不是长期资产。真正跟着你走的，是对业务场景的判断力、工程化的底座能力，以及每做完一个项目都把经验整理成文档和组件的习惯。

这也是这份 JD 最舒服的地方——它写着"不是纯算法研究岗，也不是普通后端执行开发"。要的是能独当一面做落地的人。

## 八、写在最后

> **LLM 负责会说话，Agent 开发负责让它把活干完、干对、干得起、干得安全。**

| 环节 | 决定什么 |
|------|---------|
| 场景设计 | 决定 AI 做什么 |
| RAG | 决定它说得准不准 |
| 工作流和护栏 | 决定它做得稳不稳 |
| 工程与部署 | 决定它上不上得了生产 |
| 成本优化 | 决定企业用不用得起 |
| 评测体系 | 决定你能否证明它变好了 |
| 经验沉淀 | 决定团队能不能持续交付 |

如果你是后端工程师想转这个方向，建议很直接：**不用焦虑算法，把 RAG 链路、Agent 工作流、评测和部署运维这四块补上**，剩下的靠已有工程经验就能接住。

这个岗位需要的，从来不是让 AI 变聪明的人，而是让 AI 可靠干活的人。
