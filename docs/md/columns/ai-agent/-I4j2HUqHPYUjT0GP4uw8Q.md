## 01Agent 的「金鱼记忆」问题



大模型是无状态的：每次推理，它拿到的只有当前塞进上下文窗口的那点 token；请求一结束，说过什么、对方是谁、聊到哪，统统清零。这就是 Agent 的    「金鱼记忆」——问题不在记性短，而在每次会话都从一张白纸重新开始。



单轮问答时代，这无关痛痒；但 Agent 的目标远不止于做一个随问随答的「工具」。一旦它要长期驻场、持续陪伴、独立推进任务，就必须成为真正意义上的长期协作者——懂你的偏好、记得共同的上下文、能接着上次的进度继续干。



⚠️ 记忆缺失的四种典型症状答非所问：不记得用户上一句刚说的背景，反复追问；重复劳动：不记得昨天已经得出的结论，重新推导一遍；缺乏个性化：不记得用户偏好，每次都给出「千人一面」的答案；知识断层：模型自身训练数据过时或缺失，回答不了私有知识。

### 2.1　短期 / 工作记忆



短期记忆是 Agent 维护「当前对话与任务」的即时上下文，一般就是上下文窗口里装的那些东西：本轮历史消息、中间推理、工具调用结果。它的特点决定了它的局限：



业界（Letta、AWS 等）的主流口径里，短期记忆 = 工作记忆 = 上下文窗口内的消息缓冲，两者不作区分。少数资料会再把「当前上下文（RAM）」与「单会话历史」切开，但工程上合并处理更实用，本文采用合并口径。



### 2.2　长期记忆的三种形态



长期记忆是跨会话、跨任务持久保存的那部分。按「内容性质」可再细分为三种，这种细分在工程上极具指导意义——因为它直接对应三种不同的存储与检索手段：



把这三者分开，是为了避免一个常见的混乱：很多人把「知识库」当成「记忆」的全部，其实知识库只覆盖了语义记忆这一小块，用户的个性化情景记忆、可执行的程序记忆同样不可或缺。

如果说「记忆层次」回答的是存多久（纵轴），那么「范式」回答的则是怎么构建与存取（横轴）。按「记忆如何被构建、如何与模型交互」这条主线，业界方案可以收敛为三大范式。

## 04记忆的消费——上下文工程



记忆「存」下来只是第一步，真正决定 Agent 表现的是「怎么用」。Letta 有一句精辟的论断：记忆的本质，是决定在每一个时刻往上下文窗口里放哪些 token。



这就引出了「上下文工程（Context Engineering）」——它是记忆系统的「调度员」，负责在生成前，把记忆检索、组织、注入到上下文里：



1检索触发：什么时候去取记忆？取多少？（如知识库的 Top-K、相似度阈值）2注入组织：取回的记忆以什么形式拼进上下文？（追加到系统指令？还是作为参考资料？）3冲突消解：记忆与用户当前表述冲突时以谁为准？4压缩与遗忘：上下文超限时如何摘要、卸载、淘汰？
