# AI Agent 核心架构详解

架构师（JiaGouX）我们都是架构师！架构未来，你来不来？昨天写 Claude Code 团队的 code review 时，有个细节很难略过。一夜之间，一条 Claude Code CLI 的 PR 在评审与修复之间跑了五十多轮：评审 Agent 找到问题，修复 Agent 改代码、提交新版本，评审再读一遍新的 diff。直到作者手动叫停，这个循环仍没有自己收住。团队后来用 git blame 回看这些反复出现的意见，发现大约 59% 指向的代码，在第一次评审时就已经存在。评审器并不是每轮都发现了新的关键问题，它更多是在旧代码里继续翻，修复 Agent 则继续照单修改。单看每个 Agent，它们都在认真工作。放到整项任务里，系统却没有收敛。这个场景比一张组件图更容易说明 AI Agent 的核心架构。问题不只是“模型会不会找 Bug”，而是：这一轮该看什么，谁决定下一步，改动怎样留下证据，新提交出现后哪些结论要失效，以及什么情况下必须停下来。顺着这条 PR 往下看，一个完整的 Agent 系统其实可以先抓住三件事：一条控制循环，推动任务向前，也负责让它停下来；两条数据流，把事实送进 Agent，再把行动和证据带回来；三层系统，分别负责判断、控制和真实执行。图 01：Agent 三层系统图中每一层都只承担一种责任：模型做判断，控制层做约束，外部系统留下可回读的事实。                 ┌──────── 上下文流 ────────┐                 │                          ▼PR 目标 ──&gt; [ 决策层：理解改动，提出下一步 ]                 │                          ▲                 ▼                          │ 新观察          [ 控制层：轮次、状态、风险、审批 ]                 │                          ▲                 ▼                          │ diff、CI、回执          [ 执行与事实层：Git、CI、PR、合并队列 ]                 │                 └──── 行动与证据流 ────&gt; 完成 / 转人工这三部分不一定要拆成三套服务。小系统完全可以放在一个进程里。真正重要的是，边界不要混：模型提出判断，控制层管理任务，外部系统保存事实。一条 PR，五十多轮先不急着谈 Loop，看看一条改动实际上怎样走。在 Claude Code 团队公开的流程里，代码提交 PR 之前，Agent 先运行测试、构建，或者拿截图和设计稿做对照。接着，一个拿到新上下文的子 Agent 再看一次 diff。团队还会运行几类内部 Skill：找 Bug、简化改动、检查端到端行为。PR 创建后，评审 Agent 会同时读取三类东西：这次改动想解决什么、当前 diff 改了什么、整个仓库里相关代码怎样工作。CLAUDE.md 提供项目约定，代码所有者维护的 REVIEW.md 则告诉评审器：这个目录最怕什么、哪些路径可以跳过、评论必须给出哪一行证据，以及不要把多少精力花在无关紧要的 nit 上。随后，多个 Agent 并行找问题，另一组 Agent 对候选问题做验证。只有得到足够支持的意见才会发到 PR 上，并标为 Important、Nit 或 Pre-existing。作者或修复 Agent 处理意见，推送新的 commit；CI、评审和安全检查再看新的版本。正常情况下，它应该越走越接近合并：真正的问题越来越少，未解决评论逐步清零，测试和构建转绿，最后进入审批与合并队列。那条五十多轮的 PR，卡在了“还能继续”与“值得继续”之间。评审器总能再找到一点东西，修复 Agent 也总能再改一点，但系统没有及时判断这些新发现是否仍属于本次改动，也没有尽早把反复出现的问题归成同一类。后来团队收紧了重评规则：前几轮之后只看新的 diff；同一类问题只报一次，让作者一次修完；已经发过的意见不再重复；超过三轮，就请作者停下来重新看整体方案。这些变化看起来不大，却把“评审器还能不能继续找”改成了“这条 PR 还有没有继续自动转下去的价值”。调整后，一轮评审加修复就通过的 PR 从 65% 升到 78%，需要五轮以上的从 8.9% 降到 1.5%。这组数字对应的是整套收敛措施，不能简单归功于其中某一条。到这里，控制循环才真正露出来。一条循环，先要会停Agent 不是模型外面套几个工具。它更像一段不断读现场、做选择、执行动作、再看结果的程序。观察 ──&gt; 判断 ──&gt; 执行 ──&gt; 验证 ▲                         │ └────── 继续 / 停止 ──────┘放在 code review 里：观察，是读取 PR 目标、当前 diff、相关代码、历史评论和 CI 结果；判断，是识别一处可能的缺陷，或者决定某个意见已经解决；执行，是发布评论、修改代码、运行测试或推送 commit；验证，是确认问题是否消失、新改动有没有引入别的问题、当前版本是否满足合并条件。ReAct 论文讲“推理与行动交替”，工程里真正麻烦的是最后那根回线。每次行动都会改变现场。Agent 下一轮看到的，不该只是原始任务再加一句“工具调用成功”，而应该是新的 diff、新的 commit SHA、新的测试结果和仍未解决的意见。循环还必须知道什么时候退出。能继续调用工具，不等于值得继续；任务是否结束，必须由当前版本上的外部证据决定。模型不再调用工具，只代表这轮推理停了；执行进程正常结束，只代表这次运行收住了；PR 是否可以合并，要看评论、CI、风险审批和当前 commit 是否一致。Claude Code 团队有一个很关键的规则：人的批准只绑定到一个具体 commit。后来又推了无法被系统信任的新 commit，原来的批准就要重新来。这就是任务级停止条件。它不问“Agent 还有没有话说”，而问“用户要的结果，有没有在当前版本上得到证明”。前面写《Agent、Harness、Loop 到底怎么分？一条运行链看清楚》时，我们把 Loop 分成运行、任务和演进三种节奏。code review 的一轮观察、修改和验证，是最里面的运行循环；一条 PR 能否结束，由外面的任务状态决定；事故和回滚后来变成评测集，又进入更慢的演进循环。三个循环可以互相喂数据，但不能混成一个永远不停的“大循环”。两条数据流控制循环每转一轮，系统里都有两条方向相反的数据流。一条向里走，把本轮真正需要的事实送到 Agent 面前；另一条向外走，把 Agent 的判断变成受控动作，再把执行结果和证据带回来。很多 Agent 演示看起来聪明，接进真实系统后却不稳，往往不是模型差，而是这两条流中间断了。Agent 看到了什么评审 Agent 不可能把一个大型仓库、全部聊天记录和几十轮工具输出原样塞进上下文。它需要的是一个经过选择的现场。在这条 PR 里，至少有几类信息：信息解决什么问题不能拿来替代什么PR 目标这次为什么改不能证明实现已经正确当前 diff 与相关代码具体改了什么、会影响哪里不能代表整个仓库的最新状态，除非重新读取CLAUDE.md、REVIEW.md项目约定、目录风险、评审边界不能替代权限与合并规则历史评论与轮次哪些问题已报、哪些已处理不能证明当前 commit 已通过CI、构建与测试结果哪些确定性检查已经跑过不能覆盖测试没有表达的风险这就是 Context Engineering 落到真实任务后的样子：不是把上下文做得更长，而是让每一轮都拿到足以做当前判断的事实，同时知道这些事实来自哪里、对应哪个版本。这里也能看出“上下文”“任务状态”和“业务事实”的区别。模型上下文只是这一轮临时看到的材料；任务状态记录 PR 已经走到第几轮、还有哪些未解决项；Git、CI 和合并队列保存的是可重新读取的外部事实。上下文被压缩甚至丢失，任务仍应能从这些事实恢复，而不是靠模型回忆“我上次好像已经处理过了”。长期记忆也不该直接混进来。某类 Bug 反复出现，可以沉淀进 REVIEW.md、Skill 或 lint 规则；这叫把经验写回系统。至于当前 PR 是否仍有这个问题，还是要回到当前 diff 上确认。上下文还有安全边界。仓库代码、Issue 文本和外部文档都可能是不可信输入。Simon Willison 提到的“致命三要素”——私有数据、不可信内容和对外通信——一旦在同一个 Agent 里碰到，提示注入就可能从错误回答变成真实操作。只靠提示词提醒“不要被攻击”不够，读取范围、工具权限和高风险动作仍要在程序侧隔开。意见怎样变成证据另一条流从 Agent 往外走。评审器说“这里可能有竞态”时，这还只是候选判断。它要先经过其他 Agent 的验证，再落到具体文件和行号；作者修复后，要有新的 commit；CI 和重评在这个 commit 上通过；需要人工批准的风险等级，还要拿到对应的人类批准；最后合并队列把它与最新主干放在一起重新跑检查。候选问题   │   ▼交叉验证 ──&gt; 文件与行号 ──&gt; PR 评论                              │                              ▼修复 commit ──&gt; CI / 重评 ──&gt; 风险审批                              │                              ▼                         合并队列 / 发布这条链路里，模型可以参与语义判断：改动是否偏离目标、修复有没有治到根因、评论是不是重复。确定性检查则交给程序：文件是否存在、测试是否通过、评论是否解决、批准是否绑定当前 SHA、必需检查是否全部转绿。图 02：评审中的行动与证据闭环候选问题并不是证据。它要经过验证、版本变更和回读，才能支撑“任务完成”的结论。如果要给一次评审留下最小运行记录，大致需要关联下面这些内容：任务、运行轮次、输入 commit、候选问题、验证结果、输出 commit，以及最后在哪个 commit 上通过。这里说的是通用架构记录，并不是 Anthropic 公开的内部数据格式。task_id        一条 PR 的评审任务run_id         某次具体运行input_sha      本轮读取的版本finding_id     一项可追踪的问题output_sha     修复后产生的版本verified_sha   最终完成验证的版本有了这些关联，系统才说得清一条意见为何出现、改动是否真的处理了它，以及后来哪次提交让之前的结论失效。《输出结果不等于完成任务：Agent 最容易忽略的一环》里区分过模型停止、工具返回、动作生效和目标达成。code review 正好把这四件事摊开了：Agent 写完一段评论，不等于评论正确；修复 Agent 推送 commit，不等于 Bug 消失；CI 通过，也不等于风险审批已经完成。三层系统两条数据流要跑稳，系统里至少要把三类责任分开。决策层：提出下一步决策层主要由模型、指令和本轮上下文组成。它擅长理解 PR 想做什么，阅读代码关系，发现名字对了但语义不对的地方，也能根据新结果调整下一步。在评审任务里，它可以提出这样的判断：某个错误分支没有释放资源；这个修复只挡住了表象，没有处理根因；这条意见属于旧代码，不该算到本次 PR 头上。但这些仍然是判断，不是外部事实。模型输出的是下一步提议。评论有没有发出、代码有没有改变、测试有没有通过，要由外部系统确认。让模型停在这条边界内，并不是削弱它。模糊目标、语义理解和现场选择，本来就是模型最有价值的部分；版本、权限和确定性约束，交给程序会更稳。控制层：盯住现场控制层通常藏在 Harness 或 Agent Runtime 里。它负责装配上下文、调用模型、解析提议、调度工具，也保存轮次、预算、超时、审批、取消和恢复所需的状态。放在那条五十多轮的 PR 上，控制层真正该记住的是：这一轮从哪个 commit 开始；哪些意见已经发过，哪些已经解决；当前是在看全仓相关代码，还是只重看新增 diff；已经跑了多少轮，是否触发人工接管；当前风险等级需要几个批准；哪些批准仍然覆盖现在的 commit。这些信息如果只藏在对话里，进程一重启就容易丢。更麻烦的是，模型可能把上一轮的结论当成当前事实继续使用。状态机在这里不是为了把图画得复杂，而是让几种不同的现场有地方可放：运行中、等待检查、等待人工、已通过、需要重做、已取消。系统不知道是否完成时，也应该允许停在“不确定”，而不是为了流程好看，硬猜一个成功或失败。此前《Codex Harness 源码拆解：Agent 控制面如何嵌进业务系统》里写到 Thread、Turn、Item、审批、取消和恢复。换成今天这条 PR，它们做的是同一类工作：留住运行现场，并限制下一步怎样发生。执行层：留下事实执行与事实层包括代码仓库、CI、PR 平台、合并队列，也包括 Agent 真正使用的文件系统、终端和浏览器。这一层的特点是，结果可以重新读取。模型说“我已经修复”不算，Git 里要有对应 commit；模型说“测试通过”不算，CI 要留下实际执行结果；评审器说“可以合并”也不算，分支保护、风险策略和当前批准共同决定能不能进合并队列。Anthropic 披露的流程里，合并队列还会把改动放到最新主干上重新跑检查。两个 PR 分开都通过，不代表合在一起仍然正确。新功能先走内部 flag，再到 latest，最后才到 stable；真的出问题，flag 和回滚负责把影响尽快收住。这也是为什么执行层不能只返回一句 success: true。一次调用至少应让控制层知道：它针对哪个输入版本，生成了哪个外部对象，当前状态是什么，后续应该到哪里查询。代码评审里的写操作大多还能通过新 commit 或 revert 修正。换成退款、发券、删数据这类有业务副作用的动作，边界会更严格：接口超时不等于没有执行，系统需要稳定的操作标识和回查入口；查不清时就停在 UNKNOWN，不能换个请求再做一遍。架构没有变，只是“行动与证据流”的要求更高了。名词落到链路里Agent 领域名词很多。把它们放回这条 PR，反而容易分清。Tool 是可以调用的能力：读取文件、搜索代码、运行测试、发布评论。它要把输入、输出和失败方式说清楚，但工具能被调用，不等于当前任务有权调用。Skill 是完成某类工作的办法。找 Bug、简化 diff、检查端到端行为，都可以做成 Skill。反复出现的评审经验也适合沉淀进去。Skill 能提高判断质量，却不会替系统保存 PR 状态。Workflow 固定已经明确的步骤。每个 PR 必须跑哪些 CI，安全评论未解决不能合并，高风险路径需要几个人批准，这些无需每次交给模型重新决定。Graph 适合表达依赖、并行和恢复节点。多个 Agent 可以并行找问题，验证 Agent 再汇总；但节点不幂等、状态不持久、停止条件不清楚，换成 Graph 也只是把失控的循环画得更整齐。Memory、State 和 Evidence 也各有位置。Memory 保存下次还值得复用的经验，State 说明当前 PR 走到哪里，Evidence 证明这个 commit 为什么可以通过。它们可以存在同一套基础设施里，但不能共用一段越来越长的聊天记录。前面《从 Prompt 到 Graph：五层 Agent 工程，真正解决的是什么》讲的是能力怎样逐层长出来。放到真实任务里，我更愿意先问：眼前缺的是信息、控制、固定流程，还是可恢复的依赖关系？问题没出现之前，不必急着把所有名词都装进系统。多 Agent 为什么有用Claude Code 的 code review 适合多个 Agent，并不是因为“Agent 越多越强”，而是它恰好满足两个条件。第一，查找任务可以真正并行。不同 Agent 能从正确性、安全、简化和端到端行为几个方向独立阅读，不必轮流修改同一份状态。第二，结果容易交叉验证。一项发现可以落到文件、行号和具体 diff，再由另一组 Agent 判断它是不是真问题。意见错了，可以丢掉；意见重复，可以合并；它不像付款操作那样一执行就产生难撤回的业务副作用。一旦任务变成强顺序、共享状态和高副作用，随意拆 Agent 往往只会多出交接成本。比如查订单、判断重复支付、退款、通知客户，本来就有明确先后关系。把每一步都变成一个角色，不会自动更可靠。单 Agent 配一组边界清楚的工具，常常更好调试。只有子任务能真正并行、上下文或权限必须隔离，或者一个 Agent 的工具和指令已经多到影响判断时，拆分才开始划算。图 03：单 Agent 与多 Agent 的适用边界多 Agent 的收益来自可并行、可验证的子任务，不来自角色数量本身。即便拆了，委派也不能只留一句自然语言。目标、范围、输入版本、可用工具、预算、输出格式和验收条件，都要一起交过去。主任务接回来时，核对的也应该是产物和回执，而不是子 Agent 的一句“已经完成”。Peter Steinberger 把注意力从“怎样提示 Agent”推向“怎样设计会提示 Agent 的循环”；Gergely Orosz 随后提醒，这种循环有真实成本，不是每项工作都值得一直跑。放到五十多轮的 PR 上，两句话刚好接在一起：循环能继续，不代表继续仍然划算。真正难的是生产一个 code review 演示，只要模型能读代码、给意见，看起来就已经像个 Agent。进入生产后，难点很快转到模型外面。系统要知道每轮用了哪一版输入，保存任务和运行状态，约束工具权限，给高风险动作安排审批，处理超时和取消，最后用外部事实验收结果。它还要把事故、回滚和误报留下来，变成下一轮评测。Anthropic 的做法里，历史事故和对应修复会进入专家确认过的评测集。评审器的提示、工具或模型变了，都要重新跑这些案例。团队还观察人们怎样处理评论：是修复、认为误报、说明行为本来如此，还是决定无关紧要。否则系统只会学会“报得更多”，不一定学会“报得更准”。这与《设计 Self-Harness 架构：会自我改进的 Harness，先要学会留证据》里的主线一致。没有输入版本、配置版本、运行轨迹和结果证据，所谓自我改进很容易只剩下主观感受：这次好像更聪明了。生产 Agent 最后都绕不开五个问题：问题系统要留下什么每轮看到了什么上下文来源、选择方式、输入版本任务走到了哪里task/run 状态、轮次、检查点动作为什么被放行身份、权限、策略、审批结果为什么可信外部回执、权威回读、验收证据下一版怎样变好失败分类、评测集、回归结果这些东西不够“智能”，却决定了一个 Agent 能不能从好看的演示，变成团队敢长期使用的系统。顺着任务看架构回到开头那条 PR。问题不是评审 Agent 不工作，也不是修复 Agent 不配合。恰恰相反，它们一直在工作。真正缺的是任务层的边界：新一轮必须带来什么新信息，旧意见怎样去重，哪些发现属于本次改动，跑到第几轮应该换人或换方案，以及哪一份外部证据能宣布结束。把这些补上以后，一条控制循环才不会变成无限重来；上下文流和行动证据流才接得起来；决策、控制、执行三层也各自有了清楚的责任。所以现在看一张 Agent 架构图，我通常不会先数里面有几个模型、几个 Agent、几个向量库。我会先顺着一项真实任务走一遍：它第一轮拿到了什么？做完动作后，现场怎样变化？这个变化由谁确认？进程中断后从哪里恢复？如果一直有新动作，系统靠什么判断该停？这些问题都有具体答案，模型、Tool、Skill、Workflow、Graph 和 我们都是架构师！架构未来，你来不来？



昨天写 Claude Code 团队的 code review 时，有个细节很难略过。



一夜之间，一条 Claude Code CLI 的 PR 在评审与修复之间跑了五十多轮：评审 Agent 找到问题，修复 Agent 改代码、提交新版本，评审再读一遍新的 diff。直到作者手动叫停，这个循环仍没有自己收住。



团队后来用 git blame 回看这些反复出现的意见，发现大约 59% 指向的代码，在第一次评审时就已经存在。评审器并不是每轮都发现了新的关键问题，它更多是在旧代码里继续翻，修复 Agent 则继续照单修改。



单看每个 Agent，它们都在认真工作。放到整项任务里，系统却没有收敛。



这个场景比一张组件图更容易说明 AI Agent 的核心架构。问题不只是“模型会不会找 Bug”，而是：这一轮该看什么，谁决定下一步，改动怎样留下证据，新提交出现后哪些结论要失效，以及什么情况下必须停下来。



顺着这条 PR 往下看，一个完整的 Agent 系统其实可以先抓住三件事：



一条控制循环，推动任务向前，也负责让它停下来；



两条数据流，把事实送进 Agent，再把行动和证据带回来；



三层系统，分别负责判断、控制和真实执行。



图中每一层都只承担一种责任：模型做判断，控制层做约束，外部系统留下可回读的事实。



┌──────── 上下文流 ────────┐                 │                          ▼PR 目标 ──&gt; [ 决策层：理解改动，提出下一步 ]                 │                          ▲                 ▼                          │ 新观察          [ 控制层：轮次、状态、风险、审批 ]                 │                          ▲                 ▼                          │ diff、CI、回执          [ 执行与事实层：Git、CI、PR、合并队列 ]                 │                 └──── 行动与证据流 ────&gt; 完成 / 转人工



这三部分不一定要拆成三套服务。小系统完全可以放在一个进程里。真正重要的是，边界不要混：模型提出判断，控制层管理任务，外部系统保存事实。



## 一条 PR，五十多轮



先不急着谈 Loop，看看一条改动实际上怎样走。



在 Claude Code 团队公开的流程里，代码提交 PR 之前，Agent 先运行测试、构建，或者拿截图和设计稿做对照。接着，一个拿到新上下文的子 Agent 再看一次 diff。团队还会运行几类内部 Skill：找 Bug、简化改动、检查端到端行为。



PR 创建后，评审 Agent 会同时读取三类东西：这次改动想解决什么、当前 diff 改了什么、整个仓库里相关代码怎样工作。CLAUDE.md 提供项目约定，代码所有者维护的 REVIEW.md 则告诉评审器：这个目录最怕什么、哪些路径可以跳过、评论必须给出哪一行证据，以及不要把多少精力花在无关紧要的 nit 上。



随后，多个 Agent 并行找问题，另一组 Agent 对候选问题做验证。只有得到足够支持的意见才会发到 PR 上，并标为 Important、Nit 或 Pre-existing。作者或修复 Agent 处理意见，推送新的 commit；CI、评审和安全检查再看新的版本。



正常情况下，它应该越走越接近合并：真正的问题越来越少，未解决评论逐步清零，测试和构建转绿，最后进入审批与合并队列。



那条五十多轮的 PR，卡在了“还能继续”与“值得继续”之间。评审器总能再找到一点东西，修复 Agent 也总能再改一点，但系统没有及时判断这些新发现是否仍属于本次改动，也没有尽早把反复出现的问题归成同一类。



后来团队收紧了重评规则：前几轮之后只看新的 diff；同一类问题只报一次，让作者一次修完；已经发过的意见不再重复；超过三轮，就请作者停下来重新看整体方案。



这些变化看起来不大，却把“评审器还能不能继续找”改成了“这条 PR 还有没有继续自动转下去的价值”。调整后，一轮评审加修复就通过的 PR 从 65% 升到 78%，需要五轮以上的从 8.9% 降到 1.5%。这组数字对应的是整套收敛措施，不能简单归功于其中某一条。



到这里，控制循环才真正露出来。



## 一条循环，先要会停



Agent 不是模型外面套几个工具。它更像一段不断读现场、做选择、执行动作、再看结果的程序。



观察 ──&gt; 判断 ──&gt; 执行 ──&gt; 验证 ▲                         │ └────── 继续 / 停止 ──────┘



放在 code review 里：



观察，是读取 PR 目标、当前 diff、相关代码、历史评论和 CI 结果；



判断，是识别一处可能的缺陷，或者决定某个意见已经解决；



执行，是发布评论、修改代码、运行测试或推送 commit；



验证，是确认问题是否消失、新改动有没有引入别的问题、当前版本是否满足合并条件。



ReAct 论文讲“推理与行动交替”，工程里真正麻烦的是最后那根回线。每次行动都会改变现场。Agent 下一轮看到的，不该只是原始任务再加一句“工具调用成功”，而应该是新的 diff、新的 commit SHA、新的测试结果和仍未解决的意见。



循环还必须知道什么时候退出。



能继续调用工具，不等于值得继续；任务是否结束，必须由当前版本上的外部证据决定。



模型不再调用工具，只代表这轮推理停了；执行进程正常结束，只代表这次运行收住了；PR 是否可以合并，要看评论、CI、风险审批和当前 commit 是否一致。



Claude Code 团队有一个很关键的规则：人的批准只绑定到一个具体 commit。后来又推了无法被系统信任的新 commit，原来的批准就要重新来。



这就是任务级停止条件。它不问“Agent 还有没有话说”，而问“用户要的结果，有没有在当前版本上得到证明”。



前面写《Agent、Harness、Loop 到底怎么分？一条运行链看清楚》时，我们把 Loop 分成运行、任务和演进三种节奏。code review 的一轮观察、修改和验证，是最里面的运行循环；一条 PR 能否结束，由外面的任务状态决定；事故和回滚后来变成评测集，又进入更慢的演进循环。



三个循环可以互相喂数据，但不能混成一个永远不停的“大循环”。



## 两条数据流



控制循环每转一轮，系统里都有两条方向相反的数据流。



一条向里走，把本轮真正需要的事实送到 Agent 面前；另一条向外走，把 Agent 的判断变成受控动作，再把执行结果和证据带回来。



很多 Agent 演示看起来聪明，接进真实系统后却不稳，往往不是模型差，而是这两条流中间断了。



### Agent 看到了什么



评审 Agent 不可能把一个大型仓库、全部聊天记录和几十轮工具输出原样塞进上下文。它需要的是一个经过选择的现场。



在这条 PR 里，至少有几类信息：



信息



解决什么问题



不能拿来替代什么



PR 目标



这次为什么改



不能证明实现已经正确



当前 diff 与相关代码



具体改了什么、会影响哪里



不能代表整个仓库的最新状态，除非重新读取



、REVIEW.md



项目约定、目录风险、评审边界



不能替代权限与合并规则



历史评论与轮次



哪些问题已报、哪些已处理



不能证明当前 commit 已通过



CI、构建与测试结果



哪些确定性检查已经跑过



不能覆盖测试没有表达的风险



这就是 Context Engineering 落到真实任务后的样子：不是把上下文做得更长，而是让每一轮都拿到足以做当前判断的事实，同时知道这些事实来自哪里、对应哪个版本。



这里也能看出“上下文”“任务状态”和“业务事实”的区别。



模型上下文只是这一轮临时看到的材料；任务状态记录 PR 已经走到第几轮、还有哪些未解决项；Git、CI 和合并队列保存的是可重新读取的外部事实。上下文被压缩甚至丢失，任务仍应能从这些事实恢复，而不是靠模型回忆“我上次好像已经处理过了”。



长期记忆也不该直接混进来。某类 Bug 反复出现，可以沉淀进 REVIEW.md、Skill 或 lint 规则；这叫把经验写回系统。至于当前 PR 是否仍有这个问题，还是要回到当前 diff 上确认。



上下文还有安全边界。仓库代码、Issue 文本和外部文档都可能是不可信输入。Simon Willison 提到的“致命三要素”——私有数据、不可信内容和对外通信——一旦在同一个 Agent 里碰到，提示注入就可能从错误回答变成真实操作。只靠提示词提醒“不要被攻击”不够，读取范围、工具权限和高风险动作仍要在程序侧隔开。



### 意见怎样变成证据



另一条流从 Agent 往外走。



评审器说“这里可能有竞态”时，这还只是候选判断。它要先经过其他 Agent 的验证，再落到具体文件和行号；作者修复后，要有新的 commit；CI 和重评在这个 commit 上通过；需要人工批准的风险等级，还要拿到对应的人类批准；最后合并队列把它与最新主干放在一起重新跑检查。



候选问题   │   ▼交叉验证 ──&gt; 文件与行号 ──&gt; PR 评论                              │                              ▼修复 commit ──&gt; CI / 重评 ──&gt; 风险审批                              │                              ▼                         合并队列 / 发布



这条链路里，模型可以参与语义判断：改动是否偏离目标、修复有没有治到根因、评论是不是重复。确定性检查则交给程序：文件是否存在、测试是否通过、评论是否解决、批准是否绑定当前 SHA、必需检查是否全部转绿。



候选问题并不是证据。它要经过验证、版本变更和回读，才能支撑“任务完成”的结论。



如果要给一次评审留下最小运行记录，大致需要关联下面这些内容：任务、运行轮次、输入 commit、候选问题、验证结果、输出 commit，以及最后在哪个 commit 上通过。这里说的是通用架构记录，并不是 Anthropic 公开的内部数据格式。



task_id        一条 PR 的评审任务run_id         某次具体运行input_sha      本轮读取的版本finding_id     一项可追踪的问题output_sha     修复后产生的版本verified_sha   最终完成验证的版本



有了这些关联，系统才说得清一条意见为何出现、改动是否真的处理了它，以及后来哪次提交让之前的结论失效。



《输出结果不等于完成任务：Agent 最容易忽略的一环》里区分过模型停止、工具返回、动作生效和目标达成。code review 正好把这四件事摊开了：Agent 写完一段评论，不等于评论正确；修复 Agent 推送 commit，不等于 Bug 消失；CI 通过，也不等于风险审批已经完成。



## 三层系统



两条数据流要跑稳，系统里至少要把三类责任分开。



### 决策层：提出下一步



决策层主要由模型、指令和本轮上下文组成。它擅长理解 PR 想做什么，阅读代码关系，发现名字对了但语义不对的地方，也能根据新结果调整下一步。



在评审任务里，它可以提出这样的判断：某个错误分支没有释放资源；这个修复只挡住了表象，没有处理根因；这条意见属于旧代码，不该算到本次 PR 头上。



但这些仍然是判断，不是外部事实。



模型输出的是下一步提议。评论有没有发出、代码有没有改变、测试有没有通过，要由外部系统确认。



让模型停在这条边界内，并不是削弱它。模糊目标、语义理解和现场选择，本来就是模型最有价值的部分；版本、权限和确定性约束，交给程序会更稳。



### 控制层：盯住现场



控制层通常藏在 Harness 或 Agent Runtime 里。它负责装配上下文、调用模型、解析提议、调度工具，也保存轮次、预算、超时、审批、取消和恢复所需的状态。



放在那条五十多轮的 PR 上，控制层真正该记住的是：



这一轮从哪个 commit 开始；



哪些意见已经发过，哪些已经解决；



当前是在看全仓相关代码，还是只重看新增 diff；



已经跑了多少轮，是否触发人工接管；



当前风险等级需要几个批准；



哪些批准仍然覆盖现在的 commit。



这些信息如果只藏在对话里，进程一重启就容易丢。更麻烦的是，模型可能把上一轮的结论当成当前事实继续使用。



状态机在这里不是为了把图画得复杂，而是让几种不同的现场有地方可放：运行中、等待检查、等待人工、已通过、需要重做、已取消。系统不知道是否完成时，也应该允许停在“不确定”，而不是为了流程好看，硬猜一个成功或失败。



此前《Codex Harness 源码拆解：Agent 控制面如何嵌进业务系统》里写到 Thread、Turn、Item、审批、取消和恢复。换成今天这条 PR，它们做的是同一类工作：留住运行现场，并限制下一步怎样发生。



### 执行层：留下事实



执行与事实层包括代码仓库、CI、PR 平台、合并队列，也包括 Agent 真正使用的文件系统、终端和浏览器。



这一层的特点是，结果可以重新读取。



模型说“我已经修复”不算，Git 里要有对应 commit；模型说“测试通过”不算，CI 要留下实际执行结果；评审器说“可以合并”也不算，分支保护、风险策略和当前批准共同决定能不能进合并队列。



Anthropic 披露的流程里，合并队列还会把改动放到最新主干上重新跑检查。两个 PR 分开都通过，不代表合在一起仍然正确。新功能先走内部 flag，再到 latest，最后才到 stable；真的出问题，flag 和回滚负责把影响尽快收住。



这也是为什么执行层不能只返回一句 success: true。一次调用至少应让控制层知道：它针对哪个输入版本，生成了哪个外部对象，当前状态是什么，后续应该到哪里查询。



代码评审里的写操作大多还能通过新 commit 或 revert 修正。换成退款、发券、删数据这类有业务副作用的动作，边界会更严格：接口超时不等于没有执行，系统需要稳定的操作标识和回查入口；查不清时就停在 UNKNOWN，不能换个请求再做一遍。架构没有变，只是“行动与证据流”的要求更高了。



## 名词落到链路里



Agent 领域名词很多。把它们放回这条 PR，反而容易分清。



Tool 是可以调用的能力：读取文件、搜索代码、运行测试、发布评论。它要把输入、输出和失败方式说清楚，但工具能被调用，不等于当前任务有权调用。



Skill 是完成某类工作的办法。找 Bug、简化 diff、检查端到端行为，都可以做成 Skill。反复出现的评审经验也适合沉淀进去。Skill 能提高判断质量，却不会替系统保存 PR 状态。



Workflow 固定已经明确的步骤。每个 PR 必须跑哪些 CI，安全评论未解决不能合并，高风险路径需要几个人批准，这些无需每次交给模型重新决定。



Graph 适合表达依赖、并行和恢复节点。多个 Agent 可以并行找问题，验证 Agent 再汇总；但节点不幂等、状态不持久、停止条件不清楚，换成 Graph 也只是把失控的循环画得更整齐。



Memory、State 和 Evidence 也各有位置。Memory 保存下次还值得复用的经验，State 说明当前 PR 走到哪里，Evidence 证明这个 commit 为什么可以通过。它们可以存在同一套基础设施里，但不能共用一段越来越长的聊天记录。



前面《从 Prompt 到 Graph：五层 Agent 工程，真正解决的是什么》讲的是能力怎样逐层长出来。放到真实任务里，我更愿意先问：眼前缺的是信息、控制、固定流程，还是可恢复的依赖关系？问题没出现之前，不必急着把所有名词都装进系统。



## 多 Agent 为什么有用



Claude Code 的 code review 适合多个 Agent，并不是因为“Agent 越多越强”，而是它恰好满足两个条件。



第一，查找任务可以真正并行。不同 Agent 能从正确性、安全、简化和端到端行为几个方向独立阅读，不必轮流修改同一份状态。



第二，结果容易交叉验证。一项发现可以落到文件、行号和具体 diff，再由另一组 Agent 判断它是不是真问题。意见错了，可以丢掉；意见重复，可以合并；它不像付款操作那样一执行就产生难撤回的业务副作用。



一旦任务变成强顺序、共享状态和高副作用，随意拆 Agent 往往只会多出交接成本。比如查订单、判断重复支付、退款、通知客户，本来就有明确先后关系。把每一步都变成一个角色，不会自动更可靠。



单 Agent 配一组边界清楚的工具，常常更好调试。只有子任务能真正并行、上下文或权限必须隔离，或者一个 Agent 的工具和指令已经多到影响判断时，拆分才开始划算。



多 Agent 的收益来自可并行、可验证的子任务，不来自角色数量本身。



即便拆了，委派也不能只留一句自然语言。目标、范围、输入版本、可用工具、预算、输出格式和验收条件，都要一起交过去。主任务接回来时，核对的也应该是产物和回执，而不是子 Agent 的一句“已经完成”。



Peter Steinberger 把注意力从“怎样提示 Agent”推向“怎样设计会提示 Agent 的循环”；Gergely Orosz 随后提醒，这种循环有真实成本，不是每项工作都值得一直跑。放到五十多轮的 PR 上，两句话刚好接在一起：循环能继续，不代表继续仍然划算。



## 真正难的是生产



一个 code review 演示，只要模型能读代码、给意见，看起来就已经像个 Agent。进入生产后，难点很快转到模型外面。



系统要知道每轮用了哪一版输入，保存任务和运行状态，约束工具权限，给高风险动作安排审批，处理超时和取消，最后用外部事实验收结果。它还要把事故、回滚和误报留下来，变成下一轮评测。



Anthropic 的做法里，历史事故和对应修复会进入专家确认过的评测集。评审器的提示、工具或模型变了，都要重新跑这些案例。团队还观察人们怎样处理评论：是修复、认为误报、说明行为本来如此，还是决定无关紧要。否则系统只会学会“报得更多”，不一定学会“报得更准”。



这与《设计 Self-Harness 架构：会自我改进的 Harness，先要学会留证据》里的主线一致。没有输入版本、配置版本、运行轨迹和结果证据，所谓自我改进很容易只剩下主观感受：这次好像更聪明了。



生产 Agent 最后都绕不开五个问题：



问题



系统要留下什么



每轮看到了什么



上下文来源、选择方式、输入版本



任务走到了哪里



task/run 状态、轮次、检查点



动作为什么被放行



身份、权限、策略、审批



结果为什么可信



外部回执、权威回读、验收证据



下一版怎样变好



失败分类、评测集、回归结果



这些东西不够“智能”，却决定了一个 Agent 能不能从好看的演示，变成团队敢长期使用的系统。



## 顺着任务看架构



回到开头那条 PR。



问题不是评审 Agent 不工作，也不是修复 Agent 不配合。恰恰相反，它们一直在工作。真正缺的是任务层的边界：新一轮必须带来什么新信息，旧意见怎样去重，哪些发现属于本次改动，跑到第几轮应该换人或换方案，以及哪一份外部证据能宣布结束。



把这些补上以后，一条控制循环才不会变成无限重来；上下文流和行动证据流才接得起来；决策、控制、执行三层也各自有了清楚的责任。



所以现在看一张 Agent 架构图，我通常不会先数里面有几个模型、几个 Agent、几个向量库。我会先顺着一项真实任务走一遍：



它第一轮拿到了什么？做完动作后，现场怎样变化？这个变化由谁确认？进程中断后从哪里恢复？如果一直有新动作，系统靠什么判断该停？



这些问题都有具体答案，模型、Tool、Skill、Workflow、Graph 和 Memory 才能各归其位。若每一处都只能回答“模型会判断”，那些没有画出来的责任，迟早会在第五十多轮、一次超时，或者一个已经失效的批准里重新出现。
