# 先找现有替代方案

## 先找现有替代方案

如果一个问题真的存在，用户一定已经在用某种笨办法解决它了。找到那个笨办法，比做十次访谈都有用。

你会遇到的现象

*   做出来的功能比用户实际需要的复杂五倍
*   用户说要，但你说不清他现在没有这个东西是怎么活的
*   上线后用户还是回去用他原来那套

没有替代方案有两种可能：这个问题不痛，或者这个问题痛到没人能凑合。前者别做，后者是大机会。区分方法是看他有没有为此付出过别的代价——比如干脆不做这件事了，或者花钱请了人。

**反过来，如果替代方案已经足够好用，你也别做。**用户从一个能用的方案换到你这儿，需要的收益差距通常要有好几倍，不是好一点点。

## 去哪儿找

| 找什么 | 它意味着什么 |
| --- | --- |
| 自己搭的表格 | 需求最清楚的一种。列名就是字段，颜色就是状态 |
| 一堆截图和微信收藏 | 他在做的是「攒起来以后找得到」，核心诉求是检索 |
| 写了个小脚本 | 能写脚本说明痛到愿意学。这类用户是最好的早期用户 |
| 雇了个人在做 | 已经在付钱了，且能算出具体金额。定价的锚点 |
| 几个工具串着用 | 你的机会在那几个工具的接缝处，不在其中任何一个里面 |
| 干脆放弃了这件事 | 需求存在但成本太高。做出来可能是全新的市场 |

最后一种最难发现，因为用户不会主动提起自己已经放弃的事。要靠问「有什么事你以前想做，后来觉得太麻烦就算了」。

## 怎么读

拿到替代方案之后，按这四条拆一遍，能直接拆出产品的雏形。

第一条最容易被忽略。用户表格里没有的列，多半是他真的不需要——AI 生成的界面往往会自作主张补上一堆字段，那些字段全是负担。
