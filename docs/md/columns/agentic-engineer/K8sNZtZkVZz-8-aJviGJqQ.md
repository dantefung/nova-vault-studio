## 6.1 Memory 写入时机与规范



### 背景：AI 的"分层记忆"与"分层现实"



在讲 Harness 的 Memory 之前，我先带你了解一个背景概念，它是整个 Memory 系统设计的理论源头。



Claude Code 的源码揭示了一个六层记忆体系——同一个 Agent 在不同公司、不同项目里看到的"现实"是不同的，因为它的记忆被分成了从宏观到微观的六层：



这个体系的关键设计是：上层覆盖下层，越上层越稳定，越下层越动态。 第 1 章里我说过 OpenAI 的"仓库即现实"哲学（Agent 在运行时无法访问的东西就是不存在的）——六层记忆体系在此基础上更进了一步：分层仓库，即分层现实。 一个 Agent 在 A 公司和 B 公司里，读到的"现实"完全不同，因为喂给它的记忆层不同。



Harness 的 Memory 系统，正是这个分层模型在工程层面的落地——它的 scope 五分类（backend / frontend / tooling / infra / shared）直接对应"哪些记忆属于哪一层现实"：backend 的坑与前端无关，工具链的坑人人相关。Scope 不是为了分类而分类，是为了让每个 Agent 只加载与它当前任务同层的记忆。



### 写入时机：踩坑 ≥2 次才写，一次通过不写



Memory 系统最大的敌人不是"记不住"，而是"记太多"。如果每个任务都往里塞条目，Memory 会迅速膨胀成一本没人看的流水账——检索成本上升，信噪比下降，最终整个系统被废弃。



所以 Harness 给写入时机立了硬规矩：不是"有经验就写"，而是"有价值的经验才写"。 判断标准是这样的：



写（这些是"真坑"）



不写（这些不是经验）



CR REJECT / TE FAIL（实现层 bug）



一次通过、0 REJECT/FAIL 的任务



开发中踩坑 ≥2 次尝试才解决



需求/方案本身错（应反馈到 proposal，不是 Memory）



OS/依赖/配置类坑（有强复现性）



同一任务内反复调试的小细节（如 CSS 间距）



编排层出现漂移（PM/Agent 契约不一致）



没踩坑就没有经验要沉淀



为什么是"≥2 次"？ 因为第一次踩坑可能是运气不好，第二次还踩同一个坑，才证明这里存在一个结构性的、会复发的问题——这种问题才值得占用团队的记忆空间。一次通过的任务不产生 Memory，这看似"浪费"了经验，实则是保护了信噪比：Memory 的每一条都应该是"下次能直接救命"的，而不是"今天干了什么"的流水账。

注意 slug 的约束里藏着一条深刻的规则：slug 描述根因，不描述现象。 比如某次事故的表象是"列表坏了"，但根因是"分页参数传了 NaN"——条目应该叫 pagination-limit-nan 而不是 list-broken。为什么？因为检索是按根因检索的：下一个任务的分页逻辑又出问题时，AI 搜的是"分页/NaN"，而不是"列表坏"。

### 条目模板：五段式结构



每条 Memory 条目按固定模板书写，五段缺一不可（模板位于 memory/templates/entry.md）：



---id: M-YYYYMMDD-scope-slug               # 稳定 id，不随文件名改date: YYYY-MM-DDscope: backend|frontend|tooling|infra|sharedtags: [keyword1, keyword2]              # 3-5 个关键词，检索辅助---# &lt;标题：一句话描述根因机制&gt;## 症状（怎么爆的）- 关键报错/日志片段- 触发条件（操作序列/环境特征）## 根因（为什么会发生）- 底层机制/不变量被破坏点- 为什么以前没暴露/这次才暴露## 修复（怎么修）- 关键改动点- 取舍与约束## 防复发措施（怎么防复发）至少落到以下之一：- 静态约束（lint/脚本扫描规则）/ 测试约束（新增测试）- 契约约束（Agent 定义/命令模板更新）/ 验证约束（纳入 verify.py）## 复发检测（机器怎么抓）- 命令- 预期输出/判定



注意最后两段的深意："防复发措施"和"复发检测"是 Memory 与普通笔记的本质区别。 一条 Memory 不仅要记录"发生了什么"，还要回答"怎么保证它不再发生"（防复发措施必须落到具体的文件/测试/契约上，不是"以后注意"）和"机器怎么发现它复发了"（复发检测必须给出可执行的命令和判定标准）。没有这两段，Memory 就只是故事；有这两段，Memory 才是免疫系统。



## 6.2 Agent 检索策略与 autoDream 展望



### 检索策略：按 scope 过滤，节省上下文预算



Memory 写进去了，下一个问题是：Agent 什么时候读、怎么读？ 答案是两步检索：



第一步：扫 index.md —— 按 scope 匹配本任务涉及的域，不涉及的域直接跳过第二步：读条目全文 —— 命中 scope 的条目读完整文件，重点看「防复发措施」+「复发检测」



这条策略背后是上下文预算（context budget）的账：Agent 的上下文窗口是有限的，Memory 条目读得越多，留给代码和文档的空间就越少。所以 Harness 定了两条量级规则：



场景



策略



原因



条目数 ≤10



信噪比高，全读的成本低于漏读的风险



条目数 &gt;10



只加载与本任务同域的条目，省下 token 预算



一个后端任务不该去读 frontend 的 Memory，一个工具链修复不该去读 infra 的连接池坑——scope 过滤让"该读的读到、不该读的读不到"。



### PM 调度时如何利用 Memory



那么 Memory 在流水线里实际是怎么用的？以 PM 为例：PM 在分派每个 Worker 时，Worker 提示词模板里包含了 memory/index.md 的检索义务——Worker 进场后先扫索引，命中自己 scope 的条目再读全文。同时，PM 在归档时执行 Memory Merge（第 10 章展开）：回顾本任务的 dev-log、code-review、test-report，把踩坑经验提炼成新条目，写进 entries/，更新 index.md。



由此形成一条完整的"记忆闭环"：



这条闭环，就是第 1 章"知识流失"痛点的解药：经验不再散落在个人聊天记录里，而是被归档机制强制收敛进团队的错题本，被检索机制强制送入下一个任务的上下文。



### autoDream 展望：



讲完现状，最后展望一下未来。Claude Code 的源码里有一个叫 autoDream 的后台程序，它的设计理念非常有意思——如果 Agent 记不住，就给它配一个自动整理记忆的程序。



autoDream 会在用户不用的时候，自动跑一轮"记忆大扫除"：



- 收集新信息；



- 合并重复条目；



- 删除矛盾记录；



- 把模糊表述转成具体表述；



- 把相对日期（"上周"）转成绝对日期（"2026-08-27"）；



- 把记忆文件精简到 200 行以内。



这对 Harness 的 Memory 系统是一个直接的方向性启发：今天的 Memory Merge 靠 PM 在归档时人工执行——它有效，但依赖 PM 的自觉；而 autoDream 展示了另一种可能：一个独立的后台程序，自动维护 Memory 的卫生。 你可以现在就问自己一个问题：你们的团队 Memory，如果两个月没人整理，会不会变成一本没人再看的流水账？如果答案是"会"，那么"记忆整理员"就值得被提上日程——这和第 3 章 3.5 节"组件该拆就拆"的演化观一脉相承：Memory 系统本身也在演化，它今天的形态不是终点。



## 6.3 三层知识路由模型（L1/L2/L3）



Memory 解决了"经验在哪"，但还有一个更大的问题没解决：代码知识在哪？ 一个 74 模块的后端 + 32 个应用的前端，AI 怎么知道"改订单功能该看哪个模块、读哪份规范、查哪段代码"？



Harness 的答案是三层知识路由模型，采用知识外置策略：代码知识不放在 Harness 框架内，而是由各子工程自行维护，Harness 只维护路由表。三层结构如下：



逐层解释：



层



位置



性质



用途



人工编写



技术栈、框架模式、模块发现索引——"这个工程用什么技术、有哪些模块"



人工编写，团队持续打磨



编码规范——"在这个工程里代码该怎么写"



CodeGraph 自动生成



类/方法/调用链——"这个符号在哪、谁调用了它"



访问方式也有分工：L1 是 Agent 直接读文件，L2 是 Agent 按需读规范，L3 是 AI 通过 codegraph explore 查询（一次调用返回符号源码 + 调用链 + 影响面，替代 grep + 多轮读文件）。



### codebase-guide：路由表，不是知识仓库



三层模型里最容易误读的一点是 codebase-guide 的定位。我再强调一次：codebase-guide 不是代码知识的仓库，而是路由表。 它只回答一个问题——"想知道什么时，去哪个文件看"：



- index.md：知识分布三层模型 + 按角色路由规则 + 子工程文件清单；



- overview.md：项目架构总览（技术栈、目录结构、子工程关系）——所有 Agent 的必读文件；



- harness/agent-roles.md：七个角色职责速查。



知识存在各子工程的 CLAUDE.md 里，Harness 只告诉你"去哪里找"。 这个设计正是"知识外置"的落地：代码知识天然与代码一起演进（放在子工程里，改代码的人顺手改文档），而路由表保持轻量稳定（Harness 维护）。如果反过来——Harness 把代码知识全抄进自己肚子里——那么每次代码演进，路由表都会过时，而没有任何机制保证它被同步更新。



### 按角色路由：每个角色该读什么



三层模型落到每个角色，是一张明确的路由规则表：



角色

注意这张表的分工逻辑：



- PM 读最少的代码知识（它只调度，不碰代码——读 overview 是为了"知道任务在哪个世界"）；



- SA/Dev 读最多（他们要落地，必须掌握 L1 框架模式 + L2 规范 + L3 调用链）；



- CR 的重点是 L2 规范（它审的是"合不合规"，检查项从 CLAUDE.md 和 CODE_STANDARDS 派生）；



- TE 的重点是 deliverables（它验的是"符合不符合需求文档"）。



路由规则的意义在于：每个角色只加载自己需要的知识层，谁也不多读、谁也不少读——这就是"知识按需到达"。



## 小结



这一章，我讲完了 Harness 知识体系的另外两块拼图：



- Memory——组织的错题本：踩坑 ≥2 次才写、一次通过不写；scope 五分类对应"分层现实"；五段式模板让每条记忆都是"免疫系统"而不是"故事"；两步检索策略按 scope 过滤，守护上下文预算；autoDream 展示了"记忆整理员"的未来方向；



- codebase-guide——知识的路由表：三层知识路由（L1 入口 / L2 规范 / L3 索引）采用知识外置策略，Harness 只维护路由、不囤积知识；按角色路由规则让每个 Agent 只读自己需要的那一层。



到这里，第三部分（基础设施）就完整了：目录与配置（第 4 章）是地基的布局，Spec（第 5 章）是能力的真相，Memory 与 codebase-guide（第 6 章）是经验与知识的导航。
