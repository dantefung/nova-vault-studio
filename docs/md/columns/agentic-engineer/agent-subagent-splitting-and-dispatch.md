# Agent 怎么做 sub-agent 拆分与派活：本地 spawn 与分布式 ACP-Worker 全解

> 面试官问：Agent 怎么做 sub-agent 拆分、派活的？我说了拆分本地 sub-agent，面试官说 sub-agent 分布式怎么拆？

这道题具备很强的代表性，也是很多只停留在大模型应用层开发的同学容易卡壳的地方。

## 核心结论

QwenClaw 要区分**进程内本地子 Agent** 和**分布式 Worker（ACP-Worker）**两套独立的执行体系。

这两套体系之间，不存在谁替代谁的关系，而是**分层配合、按需选型**的组合方案，整套设计思路源自 QwenPaw + AgentTeams 蜂群架构。

## 一、进程内本地 sub-agent（单机 spawn）

### 适用场景

进程内本地 sub-agent 的拆分，是在同一个主 Agent 进程内部完成任务拆解。这种场景适合**上下文关联性很强、任务体量偏轻或中等、对执行时延有较高要求**的场景。

常见例子：

- 一份体量较大的文档做分片解析
- 针对同一份素材做多维度信息抽取
- 主任务内部拆成多个连续的子步骤依次推进

### 底层 API

```
orchestrator.spawn_subagent(subtask)   # 创建子 Agent
reap(sub_agent)                        # 执行完成后回收销毁
```

### 关键约束

1. **独立会话上下文**——子 Agent 会生成一份独立会话上下文，作用是在一定程度上控制主流程里 token 持续膨胀的问题。但所有子 Agent 依旧共享主进程的 CPU 和内存资源
2. **工具集交集裁剪**——父 Agent 预先配置好可用工具全集，子 Agent 能调用的工具集合只能是父 Agent 授权后的交集范围，依靠这个机制实现最小权限管控
3. **禁止再次 spawn**（`disallow_spawn=True`）——避免任务派生链路无限向下延伸，防止出现失控的 Agent 树
4. **只回传最终产物 artifact**——不回传完整中间对话。子 Agent 执行过程中的对话记录、中间思考过程都不会向上透传给主 Agent，避免主 Agent 上下文再次膨胀

### 单机 spawn 短板（面试官追问点）

一旦子 Agent 内部出现死循环、内存泄漏、持续占用 CPU 把核心打满这类异常，整个主进程当中正在运行的**全部任务**都会受到连带影响。

同时，本地子 Agent 没有独立的资源配额配置能力，也无法跨机器调度。所以**风险等级高、资源消耗大的重型任务**，从工程层面不适合放到这套模式里执行。

> 面试官追问：那如果我任务很重、风险很高，不想牵连主进程怎么办？—— 引出分布式 sub-agent，也就是 ACP-Worker。

## 二、分布式 sub-agent：ACP-Worker

分布式场景下一般不称为子 Agent，工程上统一叫 **Worker**，依靠 ACP 协议完成跨网络调用。每个 Worker 都是独立进程或独立容器部署运行。

**调用链路差异：**

- 进程内 spawn 本质上是**内存调用**，调用开销很低
- 分布式 Worker 走的是**网络 ACP 协议调用**，中间会多出序列化、网络传输、报文解析一系列开销

### 1、什么时候选分布式 Worker？

当任务特征满足下面多数条件时，就可以考虑下沉到集群 Worker 执行：

1. **任务重**——需要占用大量内存、GPU 算力，或属于长时间运行的 CPU 密集型计算
2. **高风险不可信**——需要执行用户自定义代码、输入来源不可控，需依托容器沙箱完成故障隔离，防止恶意输入或异常逻辑扩散
3. **需要复用**——这个能力不只服务当前主 Agent，集群里多个主 Agent 都可能调用
4. **要横向扩缩容**——单台机器算力已无法支撑流量增长，需要多台机器弹性调度
5. **上下文弱耦合**——父 Agent 和 Worker 之间只需传递输入报文和输出结果，不需要同步大量会话上下文

代价也很明确：这套方案会引入分布式体系自带的复杂度，包含**对象序列化、进程启动耗时、网络超时重试、任务状态持久化与恢复**等一系列问题，都是架构设计阶段需要纳入考量的。

### 2、完整架构角色

| 角色 | 职责 |
|------|------|
| **ACPClient** | 部署在主 Agent 内部，向注册中心发起查询请求，并组装报文发起 ACP 网络调用 |
| **WorkerRegistry**（AgentTeams 自研注册中心） | 不是 Nacos。检索逻辑按能力位图 capabilities 匹配合适的 Worker，而非按服务名称查找；存储 worker_id、acp_endpoint、能力位图、资源标签、鉴权 token、心跳负载 |
| **ACP-Worker** | 独立部署的 QwenPaw 实例，实例内部开启 ACP 服务端。启动后主动向注册中心注册，并持续上报心跳 |
| **AgentTeams 治理平面** | 调度策略执行、实例健康检查、熔断逻辑、异常实例剔除等治理工作 |

> **重点：ACP 只是通信协议，本身不含注册发现逻辑，注册发现由 AgentTeams WorkerRegistry 完成。**

### 3、完整派活流程

1. 主 Agent 持续运行 ReAct 循环，在循环中识别出可拆分出去的子任务。**这里有一条优先级规则：硬编码规则的优先级高于 LLM 推理输出结果**，高危类型的任务会被强制路由到外部 Worker 执行，防止大模型推理出错把高危任务分配到本地 spawn 链路
2. ACPClient 向 WorkerRegistry 传入需要的能力位图，检索当前状态健康、负载水平合适的 Worker 实例列表
3. 获取目标 worker 的 acp_endpoint 与鉴权 token，把 subtask 序列化封装成 ACP 请求报文，发起 HTTP 网络调用
4. **Worker 容器内部**：收到 ACP 请求后，内部依旧可以 spawn 本地子 Agent 做内部拆解，即嵌套架构
5. Worker 完成全部执行逻辑后，**只把产物 artifact 序列化返回**给主 Agent
6. 主 Agent 接收返回产物，合并到自己的任务上下文。Worker 本身的生命周期交给集群治理模块统一管控

### 4、Worker 注册、心跳、失效剔除

1. Worker 启动后，主动向注册中心上报 worker_id、acp_endpoint、capabilities 能力位图、resource_tags 资源标签等基础信息
2. Worker 开启循环心跳任务，持续上报自身负载状态，包含 GPU 占用、内存使用率、排队任务数量等指标
3. 注册中心侧：某个实例心跳超时，就标记为 unhealthy 状态，后续查询候选 Worker 时自动过滤掉不健康实例
4. ACPClient 调用时连续多次报错，会向治理平面上报故障事件，触发针对该 Worker 实例的临时熔断策略

**为什么不用 Nacos？**

Nacos 这类通用注册中心，只能够依托服务名称完成实例检索。而 AI Agent 场景的诉求往往是"找一个具备代码执行能力的 worker"，依靠能力位图完成过滤匹配，而不是绑定固定服务名。这是自研 WorkerRegistry 相对通用注册中心的核心价值。

## 三、关键：混合架构

真实生产中绝大多数是两套一起用——不会把所有子任务全部放到本地 spawn，也不会不加区分全部下发到分布式 Worker，而是**按任务属性做分流**。

以一条完整业务链路为例：

1. 主 Agent 接收复杂业务需求，进入任务规划环节
2. 需求包含大量文档分片解析工作——**上下文耦合程度高、单分片处理逻辑轻量**，优先在进程内 spawn 一批本地子 Agent，拿到每个分片抽取后的产物
3. 规划阶段识别出分片结果里包含高危重型数据计算任务——不再走本地派生链路，把前面本地子 Agent 产出的分片产物序列化，交给 AgentTeams 调度层下发到对应的分布式 ACP-Worker
4. Worker 容器内部收到任务后，本身也可以继续 spawn 本地子 Agent，完成内部子任务拆解
5. Worker 执行完毕，依靠 ACP 协议把结果回传给主 Agent
6. 主 Agent 把本地子 Agent 产出的产物和分布式 Worker 返回的产物**合并汇总**，生成最终交付结果

## 四、面试高频追问总结

### Q1：进程内 spawn 子 Agent 和分布式 ACP-Worker 核心区别？

| 维度 | 进程内 spawn | 分布式 ACP-Worker |
|------|-------------|-----------------|
| 通信方式 | 进程内内存调用，低时延 | ACP 网络协议，有网络开销 |
| 故障爆炸半径 | 子 Agent 异常会牵连整个主进程 | 故障隔离，只影响当前 Worker 容器 |
| 资源边界 | 共享单机 CPU/GPU 内存 | 独立容器资源配额，支持跨机器扩缩容 |
| 上下文依赖 | 和主任务强上下文耦合 | 上下文弱耦合，需要序列化传输 |
| 生命周期 | 临时分身，reap 就销毁 | 可常驻，集群多业务复用 |
| 安全隔离 | 依靠工具白名单裁剪权限 | 容器沙箱 + 网络策略强隔离 |
| 适合任务 | 轻-中等、高频交互，同任务内部拆解 | 重型计算、高风险、多业务复用，需分布式扩缩容 |

### Q2：怎么决策用本地 spawn 还是分布式 Worker？

1. 任务和主流程上下文耦合程度高、体量偏轻、业务对时延敏感、故障扩散范围可控 → 优先进程内 spawn
2. 资源消耗大、高风险代码执行类任务、需要独立资源配额、能力要多个业务复用、有跨机器弹性扩缩容诉求 → 走分布式 ACP-Worker
3. 生产环境中混合部署比较常见：单机负责轻量任务拆解，重型高风险任务交给集群处理

### Q3：WorkerRegistry 和 Nacos 的区别？

WorkerRegistry 是面向 AI Worker 场景自研的注册中心，核心检索逻辑按能力位图 capabilities 检索 worker，而非传统微服务的服务名匹配；存储内容包含能力位图、资源标签、负载指标、鉴权 token，Worker 实例主动维持心跳上报。

通用注册中心 Nacos 解决的是"按服务名找到对应 IP 端口"的问题，它本身很难表达"具备代码执行能力"这类 AI 业务语义。

### Q4：主 Agent 怎么防止 LLM 把高危任务错误放到本地 spawn？

整套机制分为**两层决策逻辑**：硬编码业务规则优先级高于 LLM 推理输出。高危任务类型会被规则强制路由到分布式 Worker，大模型输出的动作更多是起动态补充作用，不承担最终路由决策职责。依靠这个分层控制，规避大模型幻觉带来的路由错误。

### Q5：分布式 Worker 内部还能 spawn 子 Agent 吗？

可以。整套架构支持嵌套设计：分布式 Worker 是划定的**故障隔离边界**，Worker 进程内部依旧可以运行单机 spawn 本地子 Agent 的逻辑，完成自己内部的任务拆解。

### Q6：不管哪种模式，产物契约的共同点？

**只回传最终 artifact 产物，不回传完整中间对话过程。** 依靠统一的产物契约，从机制层面避免主 Agent 上下文持续爆炸。

## 架构思想总结

- 单机内 spawn 这套方案，在一定程度上解决主 Agent 上下文持续膨胀的问题
- ACP 协议 + AgentTeams 集群体系，用来解决故障隔离、资源隔离、分布式扩缩容的诉求
- 两套方案可以嵌套部署，也可以按任务特征混合搭配使用
