# 企业架构思考：从 Harness 到 AgentOS

你好，我是看山。先叠个甲： 以下仅为个人理解，水平有限，难免有疏漏，欢迎讨论和指正。现在可用的 Harness 工具已经很多了。Codex、Claude Code、DeepSeek Harness 等，都在把模型能力组织成能够实际完成任务的执行系统。个人办公、研发辅助，甚至一部分团队协作，已经可以围绕这些工具展开。但我觉得，企业内部的 Agent 平台还有一层问题需要解决。员工以什么身份访问资料，任务交给谁审核，执行中断后怎样继续，工具操作出了问题由谁接手——这些要求会随着智能体接入业务系统逐渐出现。现有工具可能已经覆盖其中一些能力，企业仍需要把它们接入自己的身份、数据和业务流程。Harness 提供了很好的起点。我想讨论的是，在这个起点之上，企业还需要补上哪些运行和管理能力，以及哪些事情应该继续留在应用里。这也是本文看待 AgentOS 的角度：平台建立自己的运行契约，通过协议适配接入不同的 Harness。执行、任务与组织三个尺度图 1：Harness 的执行循环位于平台内部；任务与组织尺度引入持久状态、权限、版本、成本及责任。一、任务、会话与执行实例，为什么需要分开假设一位员工要求：“读取本部门最近一个季度的项目资料，分析延期原因，生成报告，交给负责人审核。”平台需要完成的链路是：识别发起人，确定资料范围，创建任务，执行检索与分析，保存产物，等待审核，再交付结果。中途换一台执行机器，或者用户关闭页面，任务都应该有明确的去向。如果用一个会话 ID 关联所有状态，最初实现起来很方便。但同一个任务可能重试多次，也可能跨过几次会话才完成，报告还需要独立保存和授权。会话不足以表达这些关系。AgentOS 对象关系图 2：对象之间的关系。Run 固定引用发布版本，Task 与 Session 多对多关联；步骤、尝试、产物与记忆承担不同职责。下表补充各对象的含义、生命周期与边界。对象含义生命周期与边界Agent Definition智能体的代码、工作流、提示词、技能及资源声明开发阶段可修改；发布后形成不可变版本Task一次业务目标及其负责人、截止时间和验收条件可以包含多个执行轮次，独立于聊天窗口Run为完成 Task 发起的一次执行固定资产版本，记录预算、状态、执行历史与结果Step／Attempt一个执行步骤及它的尝试记录区分逻辑步骤与重试，关联实际外部操作Session用户交互和上下文关联一段会话可关联多个任务，一个长任务可跨多次交互Artifact文件、报告、代码和其他产物有版本、所有者、来源和独立访问权限Memory经筛选、允许被后续执行复用的信息有作用域、来源、有效期和删除规则Agent 实例是执行资源，Task 是业务对象，Run 是执行记录，Session 是交互对象。将它们分开，平台才可以在执行资源被释放之后继续保存任务，在长时间等待期间恢复运行，也能避免把“聊天记录仍在”误认为“任务可以续跑”。二、架构图里的方框，得有人负责可以先从能力分层观察这个问题：上层放应用，侧面放开发与能力分发，中间放执行框架，下层放分布式运行时与系统服务。这样的分层覆盖了开发、运行、部署与管理的不同职责。企业 AgentOS 能力分层示意图 3：企业 AgentOS 的能力分层——应用、能力分发、开发工作台、执行框架、分布式运行时与系统服务。看这张图时，我更关心各组件负责什么。定义有误、请求未获准入、执行中断、结果没有提交，需要由不同的模块处理。如果这些职责没有划清，排错时很容易把问题都归到“Agent 出错了”，却找不到该修改的地方。下面沿着发布和执行两条链路，看这些职责怎样衔接。企业 AgentOS 整体架构图 4：企业 AgentOS 的职责关系示意。实线表示运行关系，虚线表示资产交付；组件可以合并，图示不限定部署拓扑。发布链路把可变的开发内容转成可部署的版本；执行链路把业务请求转成可追踪的 Run，再将结果交付给用户。两条链路在 Agent Release 处连接：每个 Run 都引用一个明确的发布版本。权限策略和凭证生命周期需要单独处理。Run 固定智能体资产版本，便于追溯行为；访问权限则在实际访问资源时按当前策略复核，凭证可以过期和轮换。不能为了复现旧任务，继续使用已经撤销的权限。三、应用能力，为什么不该全部沉进平台底座复杂研究任务很适合观察应用与平台的分界。它通常经历查询规划、信息收集、理解分析和结果生成，规划阶段还可能接受用户反馈。这条链路可以建立在通用执行框架之上，但具有自己的业务判断：研究什么、什么资料值得采信、缺少哪些证据、报告应该怎样组织。复杂研究任务与共享平台的关系图 5：研究应用组织规划、收集、分析、报告与验收；共享平台提供执行、访问、状态与质量反馈机制。两条回路分别补充证据和修订方向。例如，“项目延期原因分析”与“行业趋势研究”可以共用检索、模型、产物存储和执行恢复，但对信息充分性的判断不同。前者更依赖内部记录、人员反馈与责任归属，后者更依赖多源比较、时间范围和不确定性说明。平台适合统一资源访问与执行机制，应用则保留分析方法和验收标准。我不赞成把业务判断都塞进通用底座。“通用”很容易成为收纳特例的理由，最后平台团队既要维护运行机制，又要替每个业务解释什么叫好结果。带权限的检索、引用关系、报告存取值得复用；“延期证据是否充分”“行业趋势是否可信”，应留给应用和业务负责人。平台可以帮助检查证据，不能替他们承担结论的责任。执行平台做得再好，也不会自动长出一套好的研究方法。四、统一入口之后，任务的语义由谁接管入口可以是 Web、企业 IM、CLI、API，也可以是定时任务、业务事件和订阅触发。各渠道有自己的消息格式。值得统一的部分，是请求背后的身份、业务目标与执行约束；渠道呈现方式可以继续保持差异。网关适合承接身份校验、渠道适配、限流和请求路由；Task 与 Run 的创建、状态管理和审核恢复，则属于任务控制职责。两者可以部署在一起，但职责混合后，新增渠道或调整执行语义时更容易互相影响。渠道管理与成员注册发现是两种职责，注册服务只提供发现信息，业务消息不必经过注册中心转发。信息类别背后的架构问题身份与组织范围服务端从可信身份凭证解析；客户端提交的 tenant_id 不能直接成为授权依据task_id／run_id／session_id分别关联业务目标、执行记录和交互，避免一个 ID 承担所有含义agent_release_id引用不可变发布版本，运行中不自动切到最新定义idempotency_key在租户、接口和约定有效期范围内去重，并检查请求内容是否一致deadline／budget约束总时长、模型费用、工具费用与并发额度input_refs引用带权限的资料与产物，避免重复复制大文件到每条消息trace_context关联跨服务调用；属于追踪信息，不替代身份凭证如果任务可能长时间运行，创建请求可以先返回 Run 标识。短任务可以同时返回结果，长任务通过事件流展示进度；用户关闭连接后，执行继续由平台管理。重新连接时从已授权的游标续读事件，查询接口提供权威状态，实时推送只是一个交互通道。任务提交与执行数据流图 6：任务创建、分发、执行和结果回传。Run 与待发送事件在同一事务中提交，事件发送器负责可靠投递；接收方仍须处理重复事件。队列中的消息不是 Run 的唯一事实来源。若创建与分发跨越数据库和队列，事务 outbox 是一种选择：控制服务提交 Run 与待发记录，发送器再投递队列；Worker 收到消息后领取执行权并读取权威状态。如此可以处理“数据库提交成功，队列发送失败”的间隙。重复投递通过状态检查与去重消化，不依赖队列永不重复的假设。一次允许失败后重新发起的短查询，未必需要持久工作流。我会在两个条件出现时认真考虑这条链路：任务必须在用户断开后继续，或者它会产生不能随意重做的业务动作。队列、去重和积压监控的维护成本，得有这类需求来支撑。五、确定的流程与开放的推理，怎样放在同一系统里执行内核包含模型与工具接口、上下文、工作流，以及组织任务循环的 Harness。这里需要划清两层状态管理：执行引擎管理当前步骤、上下文和局部控制流，平台运行时管理任务的执行权、计算资源与调度回收。两层通过执行标识和状态协议衔接，任务的权威记录不能只留在引擎进程里。这套 AgentOS 不应强制绑定某一个 Harness。 开源、闭源或自研，都可以作为执行引擎接入；选择依据是任务需要什么能力，以及企业能接受怎样的运行和数据边界。我更愿意让平台稳定管理任务、权限、版本和成本，把执行引擎的选择留给应用。同一个平台也可以同时接入多种 Harness。连接两者的是运行协议和适配器。平台把 Run 标识、输入引用、执行版本及权限和预算约束交给适配器，适配器再转换成具体 Harness 的调用方式；执行进度、结果、错误、产物和使用量则映射回平台记录。协议还要明确启动、查询、取消，以及引擎支持时的暂停和恢复语义。权限约束不能只作为一段提示词传进去，必须由工具调用路径或执行环境落实。协议适配也有边界。一个只能提交请求、查询最终结果的闭源服务，可以作为整体执行单元接入，但平台不能据此承诺步骤级恢复或完整的工具审计。任务要求这些能力时，就需要引擎开放相应接口，或者由平台控制工具调用与持久步骤。适配器可以统一接口，不能补出引擎没有提供的控制能力；接入时应声明这些差异，调度时按任务要求选择。可替换主要体现在新任务可以选择其他引擎。在途 Run 仍应绑定原来的引擎、适配器和能力版本，恢复记录也未必能跨引擎使用。因此，解除产品绑定不等于让运行中的任务随时切换 Harness，而是让企业不必为了更换执行工具，重建整套任务管理和业务接入。显式工作流适合步骤明确、条件和审核要求固定的任务。动态决策适合需要探索、检索与调整计划的任务。两者可以组合：报告生成流程中，资料分析由 Agent 自主探索，资料范围校验和最终审核由显式节点控制。我愿意让 Agent 自己决定下一轮检索什么资料，却不愿让它临场决定自己有没有权读这些资料，或者报告是否可以跳过审核。探索的空间可以很大，授权与验收的边界必须明确。整个智能体没有必要在“自主”和“工作流”之间二选一。执行内核与工具授权图 7：工作流可执行确定性节点，也可按需进入推理；资源操作经过工具授权，工具和子任务结果回到同一上下文。两处授权框表示两条路径上的同一授权职责。执行图还涉及批处理与流式输出的组合：有些节点等待完整输入，有些节点不断产生片段。统一图结构可以组织二者，但输出片段未必代表一个步骤已经提交完成。首个片段、最终结果、检查点与可交付产物，是不同的事件；背压、取消和错误传播也会影响上下游如何继续。模型可以提出动作，但执行内核需要把动作转换成可检查的调用：校验参数，识别目标资源，提交工具网关授权，再执行并记录结果。授权拒绝也属于执行结果，应返回可解释的错误，不应靠模型反复改变参数绕过策略。上下文管理同样需要预算。输入资料、记忆和工具返回值都可能很大，执行内核应采用按需检索、产物引用和明确的裁剪策略；保留原始内容的受控引用和摘要来源。模型输出进入恢复记录时，保存的是已发生的决策及结果，恢复流程不要求模型再次生成相同内容。能复用记录保证的是控制流连续性；如果检索资料或外部业务状态已经变化，继续使用旧结果是否合理，仍然需要业务层判断。六、运行时真正管理的，是计算与等待的关系当执行从本地进程走向共享平台，运行时开始承担部署、资源准入、调度和回收。选择进程、容器还是更强隔离环境，本质上是在依赖自由度、隔离强度、启动成本与运维复杂度之间取舍。承载方式适用情况需要管理的边界进程或共享 Worker可信代码、依赖统一、隔离需求较低的执行运行时身份、内存、并发和异常隔离；同进程通常不作为强租户隔离边界容器或 Pod独立依赖、较强资源隔离、弹性工作负载网络、卷挂载、凭证、CPU／内存与回收更强隔离的执行环境不可信代码、高敏感数据或更严格隔离需求VM 或等效隔离机制、宿主风险与资源成本计算、持久等待与恢复图 8：同一个 Run 可经历不同 Worker。等待期间保留持久状态并释放计算资源；事件到达后重新准入、授权并检查取消意图，再分配资源恢复。等待人工审核可能持续数小时，期间不需要一直占用 Worker。平台可以保存等待状态，释放计算资源，等事件到达后再恢复。前提是状态能够序列化，事件能关联到原任务，恢复时所需的版本和依赖仍然可用。短任务未必需要这套机制，但长时间等待会让它变得很有价值。运行时调度不能只看集群空闲 CPU。还需要考虑租户配额、模型供应方限流、工具并发、数据位置、任务优先级与截止时间。模型调用通常消耗远端或独立推理资源，Agent Worker 的扩容不能自动突破模型吞吐瓶颈。算力亲和也应落到具体瓶颈上：数据搬运慢，就在授权允许的区域靠近数据执行；重复加载依赖昂贵，就考虑复用环境。不能为了提高缓存命中率，把原本需要隔离的任务放到一起。Worker 心跳用于判断执行资源是否存活。业务层的定时触发、任务超时检查和周期主动任务需要自己的持久调度记录，不能与 Worker 心跳混为一个机制。七、多智能体协作，为什么会变成分布式系统问题对企业平台，多智能体协作首先是一种任务分解和资源管理方式。协调者把一个目标拆成可验收的子任务，为成员规定输入、输出、权限、预算和截止时间。成员可以在同一个进程内运行，也可以由分布式运行时承载。协作控制与成员执行图 9：协调者分配子任务、权限与预算，成员结果经检查后汇总。注册提供发现信息，成员状态写入检查执行代次。成员分布在不同 Worker 上以后，消息要能关联到父 Run 和子任务，任务领取要有有效期，状态写入要校验租约和执行代次。协调者还需要明确完成、重开和取消的条件。预算也得实际分配：每个成员都拿到父任务的完整额度，就可能同时把这笔额度花掉。提示词中的角色分工解决不了这些问题。注册信息只说明成员的可发现能力，真正的调度准入仍由运行时确认。成员不响应时，协调者应先判断子任务是否已产生副作用，再决定重派；已知完成结果通过结果记录复用。团队消息可采用至少一次投递，加上接收去重和有序状态转换，而不要求整个网络“恰好传送一次”。我对“给几个 Run 应能关联模型调用、工具操作、子任务、审批、状态转换和产物版本。跨服务 trace 用于定位性能和错误，权威操作记录用于回答业务动作发生过没有；两者通过标识关联，不能将可能丢失的采样追踪当作完整审计。模型调用记录需要统一字段与版本，至少能关联 Run、模型、耗时、用量和错误。敏感提示词与返回内容不默认记录，避免观测系统变成另一份缺少访问约束的业务资料库。我会先看任务有没有被业务验收，再看完成它花了多少钱。调用次数多、成员数量多、吞吐量高，都不能单独说明平台在进步。运行侧还要追踪排队、恢复和未决操作；成本把重试、协作成员和候选评测都算进去，并能追到任务、部门和版本。任务结果与改进闭环图 崩溃，审核等待期间版本更新，执行到一半用户权限被撤销。任务怎样继续，哪些操作被阻止，哪些结果需要人工核对，应当有明确答案。只验证服务重启成功，还不够。十五、AgentOS 的边界，最终由企业怎样使用它决定并非每个组织都需要相同的 现在可用的 Harness 工具已经很多了。Codex、Claude Code、DeepSeek Harness 等，都在把模型能力组织成能够实际完成任务的执行系统。个人办公、研发辅助，甚至一部分团队协作，已经可以围绕这些工具展开。



但我觉得，企业内部的 Agent 平台还有一层问题需要解决。员工以什么身份访问资料，任务交给谁审核，执行中断后怎样继续，工具操作出了问题由谁接手——这些要求会随着智能体接入业务系统逐渐出现。现有工具可能已经覆盖其中一些能力，企业仍需要把它们接入自己的身份、数据和业务流程。



Harness 提供了很好的起点。我想讨论的是，在这个起点之上，企业还需要补上哪些运行和管理能力，以及哪些事情应该继续留在应用里。这也是本文看待 AgentOS 的角度：平台建立自己的运行契约，通过协议适配接入不同的 Harness。

## 一、任务、会话与执行实例，为什么需要分开



假设一位员工要求：“读取本部门最近一个季度的项目资料，分析延期原因，生成报告，交给负责人审核。”平台需要完成的链路是：识别发起人，确定资料范围，创建任务，执行检索与分析，保存产物，等待审核，再交付结果。中途换一台执行机器，或者用户关闭页面，任务都应该有明确的去向。

可以先从能力分层观察这个问题：上层放应用，侧面放开发与能力分发，中间放执行框架，下层放分布式运行时与系统服务。这样的分层覆盖了开发、运行、部署与管理的不同职责。

看这张图时，我更关心各组件负责什么。定义有误、请求未获准入、执行中断、结果没有提交，需要由不同的模块处理。如果这些职责没有划清，排错时很容易把问题都归到“Agent 出错了”，却找不到该修改的地方。

## 三、应用能力，为什么不该全部沉进平台底座



复杂研究任务很适合观察应用与平台的分界。它通常经历查询规划、信息收集、理解分析和结果生成，规划阶段还可能接受用户反馈。这条链路可以建立在通用执行框架之上，但具有自己的业务判断：研究什么、什么资料值得采信、缺少哪些证据、报告应该怎样组织。



图 5：研究应用组织规划、收集、分析、报告与验收；共享平台提供执行、访问、状态与质量反馈机制。两条回路分别补充证据和修订方向。



例如，“项目延期原因分析”与“行业趋势研究”可以共用检索、模型、产物存储和执行恢复，但对信息充分性的判断不同。前者更依赖内部记录、人员反馈与责任归属，后者更依赖多源比较、时间范围和不确定性说明。平台适合统一资源访问与执行机制，应用则保留分析方法和验收标准。



我不赞成把业务判断都塞进通用底座。“通用”很容易成为收纳特例的理由，最后平台团队既要维护运行机制，又要替每个业务解释什么叫好结果。



带权限的检索、引用关系、报告存取值得复用；“延期证据是否充分”“行业趋势是否可信”，应留给应用和业务负责人。平台可以帮助检查证据，不能替他们承担结论的责任。执行平台做得再好，也不会自动长出一套好的研究方法。



## 四、统一入口之后，任务的语义由谁接管



入口可以是 Web、企业 IM、CLI、API，也可以是定时任务、业务事件和订阅触发。各渠道有自己的消息格式。值得统一的部分，是请求背后的身份、业务目标与执行约束；渠道呈现方式可以继续保持差异。



网关适合承接身份校验、渠道适配、限流和请求路由；Task 与 Run 的创建、状态管理和审核恢复，则属于任务控制职责。两者可以部署在一起，但职责混合后，新增渠道或调整执行语义时更容易互相影响。渠道管理与成员注册发现是两种职责，注册服务只提供发现信息，业务消息不必经过注册中心转发。

## 五、确定的流程与开放的推理，怎样放在同一系统里



执行内核包含模型与工具接口、上下文、工作流，以及组织任务循环的 Harness。这里需要划清两层状态管理：执行引擎管理当前步骤、上下文和局部控制流，平台运行时管理任务的执行权、计算资源与调度回收。两层通过执行标识和状态协议衔接，任务的权威记录不能只留在引擎进程里。



这套 AgentOS 不应强制绑定某一个 Harness。 开源、闭源或自研，都可以作为执行引擎接入；选择依据是任务需要什么能力，以及企业能接受怎样的运行和数据边界。我更愿意让平台稳定管理任务、权限、版本和成本，把执行引擎的选择留给应用。同一个平台也可以同时接入多种 Harness。



连接两者的是运行协议和适配器。平台把 Run 标识、输入引用、执行版本及权限和预算约束交给适配器，适配器再转换成具体 Harness 的调用方式；执行进度、结果、错误、产物和使用量则映射回平台记录。协议还要明确启动、查询、取消，以及引擎支持时的暂停和恢复语义。权限约束不能只作为一段提示词传进去，必须由工具调用路径或执行环境落实。



协议适配也有边界。一个只能提交请求、查询最终结果的闭源服务，可以作为整体执行单元接入，但平台不能据此承诺步骤级恢复或完整的工具审计。任务要求这些能力时，就需要引擎开放相应接口，或者由平台控制工具调用与持久步骤。适配器可以统一接口，不能补出引擎没有提供的控制能力；接入时应声明这些差异，调度时按任务要求选择。



可替换主要体现在新任务可以选择其他引擎。在途 Run 仍应绑定原来的引擎、适配器和能力版本，恢复记录也未必能跨引擎使用。因此，解除产品绑定不等于让运行中的任务随时切换 Harness，而是让企业不必为了更换执行工具，重建整套任务管理和业务接入。



显式工作流适合步骤明确、条件和审核要求固定的任务。动态决策适合需要探索、检索与调整计划的任务。两者可以组合：报告生成流程中，资料分析由 Agent 自主探索，资料范围校验和最终审核由显式节点控制。



我愿意让 Agent 自己决定下一轮检索什么资料，却不愿让它临场决定自己有没有权读这些资料，或者报告是否可以跳过审核。探索的空间可以很大，授权与验收的边界必须明确。整个智能体没有必要在“自主”和“工作流”之间二选一。



图 7：工作流可执行确定性节点，也可按需进入推理；资源操作经过工具授权，工具和子任务结果回到同一上下文。两处授权框表示两条路径上的同一授权职责。



执行图还涉及批处理与流式输出的组合：有些节点等待完整输入，有些节点不断产生片段。统一图结构可以组织二者，但输出片段未必代表一个步骤已经提交完成。首个片段、最终结果、检查点与可交付产物，是不同的事件；背压、取消和错误传播也会影响上下游如何继续。



模型可以提出动作，但执行内核需要把动作转换成可检查的调用：校验参数，识别目标资源，提交工具网关授权，再执行并记录结果。授权拒绝也属于执行结果，应返回可解释的错误，不应靠模型反复改变参数绕过策略。



上下文管理同样需要预算。输入资料、记忆和工具返回值都可能很大，执行内核应采用按需检索、产物引用和明确的裁剪策略；保留原始内容的受控引用和摘要来源。模型输出进入恢复记录时，保存的是已发生的决策及结果，恢复流程不要求模型再次生成相同内容。能复用记录保证的是控制流连续性；如果检索资料或外部业务状态已经变化，继续使用旧结果是否合理，仍然需要业务层判断。



## 六、运行时真正管理的，是计算与等待的关系



当执行从本地进程走向共享平台，运行时开始承担部署、资源准入、调度和回收。选择进程、容器还是更强隔离环境，本质上是在依赖自由度、隔离强度、启动成本与运维复杂度之间取舍。

等待人工审核可能持续数小时，期间不需要一直占用 Worker。平台可以保存等待状态，释放计算资源，等事件到达后再恢复。前提是状态能够序列化，事件能关联到原任务，恢复时所需的版本和依赖仍然可用。短任务未必需要这套机制，但长时间等待会让它变得很有价值。



运行时调度不能只看集群空闲 CPU。还需要考虑租户配额、模型供应方限流、工具并发、数据位置、任务优先级与截止时间。模型调用通常消耗远端或独立推理资源，Agent Worker 的扩容不能自动突破模型吞吐瓶颈。



算力亲和也应落到具体瓶颈上：数据搬运慢，就在授权允许的区域靠近数据执行；重复加载依赖昂贵，就考虑复用环境。不能为了提高缓存命中率，把原本需要隔离的任务放到一起。



Worker 心跳用于判断执行资源是否存活。业务层的定时触发、任务超时检查和周期主动任务需要自己的持久调度记录，不能与 Worker 心跳混为一个机制。



## 七、多智能体协作，为什么会变成分布式系统问题



对企业平台，多智能体协作首先是一种任务分解和资源管理方式。协调者把一个目标拆成可验收的子任务，为成员规定输入、输出、权限、预算和截止时间。成员可以在同一个进程内运行，也可以由分布式运行时承载。



图 9：协调者分配子任务、权限与预算，成员结果经检查后汇总。注册提供发现信息，成员状态写入检查执行代次。



成员分布在不同 Worker 上以后，消息要能关联到父 Run 和子任务，任务领取要有有效期，状态写入要校验租约和执行代次。协调者还需要明确完成、重开和取消的条件。预算也得实际分配：每个成员都拿到父任务的完整额度，就可能同时把这笔额度花掉。提示词中的角色分工解决不了这些问题。



注册信息只说明成员的可发现能力，真正的调度准入仍由运行时确认。成员不响应时，协调者应先判断子任务是否已产生副作用，再决定重派；已知完成结果通过结果记录复用。团队消息可采用至少一次投递，加上接收去重和有序状态转换，而不要求整个网络“恰好传送一次”。



我对“给几个 Agent 分配角色，它们就会协作得更好”持保留态度。如果成员读同一份输入、反复讨论同一个问题，增加的可能只是模型调用和协调成本。拆分至少应该带来独立信息、并行空间或专门能力。只是并行查几个系统，用工作流的并行节点就能解决。



协作还需要知道什么时候停。没有新信息、成员反复争论、预算接近上限，就应该结束探索，说明不确定性，必要时交还给人。这些退出条件需要由协调逻辑执行，不能只期待成员自己判断。



## 八、记忆之外，还有哪些状态需要被认真对待



把轨迹、知识、文件和执行记录都叫“记忆”，听起来统一，真要恢复任务或删除资料时却找不到边界。哪些记录决定任务下一步，哪些只供检索，必须先说清楚。

企业知识库与长期记忆也值得分开讨论。知识库保存可查验的资料及其索引，记忆沉淀经历、偏好和可复用经验；两者可以共享存储技术，来源与更新语义却不同。企业研究中的融合检索可以结合关键词、向量、图结构与网页信息，检索后再评估和精炼，不能把“找到了相似内容”直接等同于“获得了可靠证据”。



报告里的引用可以关联到具体资料片段，而不只是文末的一组网页。这样更容易检查某个结论是由什么支持的，也更容易处理来源纠正和访问权限变化。保存来源版本、片段位置与生成关系，会增加维护成本，却使结果审查不必完全依赖模型自述。引用正确仍不代表推论正确，来源检查和观点验收需要分开。



读记忆时检查用户、团队和组织作用域，写记忆时检查来源、敏感性和复用价值。给查询加一个租户字段并不等于完成授权，服务端还得校验访问范围，并落实存储隔离。



为了避免记忆提取拖慢业务结果提交，可以异步消费已提交的轨迹与结果；代价是后续任务未必立刻看到新经验。哪些轨迹值得进入共享知识，还需要单独判断。来源资料删除、权限撤回或内容纠正后，需要让受影响记忆和索引按规则失效；历史审计的保留与业务内容删除各自遵守保留策略。



跨存储一致性需要明确协议。例如，报告先上传为暂存对象，再由事务记录确认产物引用，成功后对用户可见；未被引用的对象定期回收。记忆和搜索索引消费已提交事件更新，允许有界的可见性延迟。没有跨库事务时，就不能声称任务、文件和向量索引在同一时刻提交成功。



## 九、“能够恢复”究竟恢复到哪一步



恢复问题会把平台带向持久执行：记录步骤输入、决策、工具操作和已提交结果，在可恢复边界保存检查点。这样，恢复可以围绕已经发生的事实继续推进。已记录完成的模型调用可以复用结果，尚未执行的调用才重新发出。但记录到什么粒度，决定了恢复精度，也决定了存储、隐私与版本兼容成本。



图 11：Run 恢复与取消的逻辑关系。恢复围绕已发生的事实继续，取消意图独立保留；确认停止并核对未决操作后才报告已取消。



恢复要分清三种情况：步骤尚未发出，可以重新调度；步骤结果已持久化，可以继续后续步骤；外部操作可能已发生，但结果没有确认，需要核对。



我最在意第三种。业务系统已经创建了工单，Worker 却在保存结果前崩溃，此时“再跑一次”可能就是再建一张工单。只检查 Worker 是否重新启动，就会漏掉这次重复操作。



图 12：工单可能已创建，平台却只知道结果未知。按目标系统能力选择核对、幂等重试或人工处理，继续前仍需检查取消意图。



工具适配器应为同一个逻辑操作使用稳定的幂等标识，将发送记录与 Run 步骤关联。目标系统支持幂等创建时，重试复用原标识；支持查询时，通过业务键确认结果；既不支持去重也无法核对时，操作应进入人工处理或补偿流程。对外部副作用的保证，要由完整调用协议来定义。取消意图需要独立持久化；结果核对完成后，仍要检查是否已经要求停止，避免核对流程意外把任务重新排入队列。



租约代次可以阻止旧 Worker 向平台提交过期状态，但不能自动阻止它向外部系统发送操作。工具网关在派发时检查执行权，外部操作仍依赖幂等、目标系统的 fencing 支持或结果核对。已经在途的请求不能因为本地取消就假定没有发生。



取消也是持久命令。Run 进入取消处理中后停止调度新步骤，向运行中的工具和成员发送取消请求，回收资源，核对未决操作，再提交终态。若无法确认业务副作用，应保留待处理记录而非提前报告“已取消”。



持久执行可以保存事件历史，把模型调用与外部操作封装成可记录的活动，重放控制逻辑时复用已提交结果。结果未知的活动仍需要按目标系统能力决定如何重试或核对。



## 十、授权不能交给模型判断



平台至少维护三类身份：发起用户、执行服务和工具凭证。发起用户决定业务访问范围，执行服务决定哪个组件可以代表平台行动，工具凭证决定实际系统接受哪些操作。授权应按照明确的委托策略约束调用，避免共享服务账号把普通用户提升为管理员。



图 13：模型提出调用后，工具网关复核身份、资源与操作策略。高影响操作进入审批，审批后重新检查并取得短期凭证。



工具网关负责参数校验、资源授权、操作账本和调用审计。对高影响操作，审批绑定 Run、目标、规范化参数摘要、批准者权限、有效期与使用次数；参数改变或授权过期后重新审批。审批记录可以冻结意图，实际操作仍需按执行时的策略复核。



只读分析可以按资料范围授权，高影响写入则需要确认具体参数。把所有动作都弹窗审批，会把人拖进执行循环；只批一次笼统的“同意执行”，又无法约束后续动态生成的动作。审批界面至少得让人看懂：要改什么，影响谁，批准的范围到哪里。



Secrets 由凭证服务按范围发给工具执行侧，不进入模型上下文，也不暴露在轨迹和普通日志中。工具结果经过敏感字段处理，外部文档与工具返回内容按不可信数据处理，不能自行获得系统指令或授权的地位。



沙箱限制进程、文件、网络、资源和凭证暴露范围。不同可信等级使用不同执行池，默认不挂载宿主敏感目录或开放全部内网。容器、网络策略、存储权限与资源配额需要配合；只建立一个 namespace 不能被视为完整租户隔离。



## 十一、智能体为什么需要自己的发布语义



不管开发入口是代码还是画布，我都会要求运行时消费明确的发布版本。运行中的任务悄悄读到了新提示词，事后很难解释为什么同一个任务前后行为不同。发布边界在这里直接关系到能否排错、能否恢复。



图 14：发布及回滚改变新 Run 的默认版本，在途 Run 保留已经绑定的版本；实际访问仍按当前权限策略复核。



为了追溯一次执行，Release 可以关联智能体代码或 DSL、提示词和技能版本、工具与连接器契约、模型配置、依赖环境、资源与策略声明、评测结果及来源摘要。用户数据和运行凭证不打入发布包；模型服务的实际版本和调用参数在 Run 中记录，可追溯并不等于可以精确复现供应方所有输出。



技能、连接器、专家智能体和工作流可以进入内部资产目录。目录需要搜索与分发，更需要所有权、兼容性、授权、退役和使用范围。接口协议变更必须有版本和迁移路径；已有任务能否继续使用旧版本，需要根据风险与兼容性决定。



回滚首先改变新 Run 的默认版本。已经运行的任务仍使用原 Release，除非安全策略要求停止，或者有明确的迁移方案。为此保留旧依赖、支持多个版本会麻烦一些，但我更愿意承担这份麻烦，也不愿让持续数天的任务在升级时无声地改变行为。



## 十二、自演进越快，能力变更的边界越重要



任务失败、工具错误、用户纠正和效果评测都可以成为改进信号。平台从轨迹中抽取经验，形成候选记忆、候选技能或候选配置；不同产物走不同治理流程。



图 15：经验生成与正式发布之间设置评测和批准。生成器只能产出候选，不拥有直接修改生产权限的能力。



个人格式偏好可以在用户确认后进入个人记忆；通用工具使用方法可以通过团队评测进入技能版本；业务决策规则和权限策略的修改，需要对应责任人的批准。候选生成允许探索，正式发布要求证据与可回滚版本。



评测同时检查成功率、业务结果、越权行为、成本、时延和对旧任务的影响。仅在同一批训练轨迹上变好，不足以说明可以推广。模型路由、上下文压缩和 Harness 参数调整也进入同一候选评测流程，并设置试验预算与停止条件。



自演进最吸引我的地方，是能更快找到值得试验的改动。我不会因此把生产变更权交给生成器。提出一个技能，和允许这个技能在企业里执行，是两件需要分别负责的事。



## 十三、怎样知道平台是在进步，而不是只在消耗资源



调试、观测、评测与调优需要串起来：定位一次执行的错误，检查线上是否反复出现，比较改动前后的结果，再决定是否发布。共同的轨迹和版本标识让这条链路有据可查。



每个 Run 应能关联模型调用、工具操作、子任务、审批、状态转换和产物版本。跨服务 trace 用于定位性能和错误，权威操作记录用于回答业务动作发生过没有；两者通过标识关联，不能将可能丢失的采样追踪当作完整审计。



模型调用记录需要统一字段与版本，至少能关联 Run、模型、耗时、用量和错误。敏感提示词与返回内容不默认记录，避免观测系统变成另一份缺少访问约束的业务资料库。



我会先看任务有没有被业务验收，再看完成它花了多少钱。调用次数多、成员数量多、吞吐量高，都不能单独说明平台在进步。运行侧还要追踪排队、恢复和未决操作；成本把重试、协作成员和候选评测都算进去，并能追到任务、部门和版本。



图 16：验收、运行记录和成本共同进入评测，候选改动经验证与批准后发布。追踪用于定位性能与错误，操作审计记录业务动作，两者分别保留。



需要控制并发执行的费用风险时，可以采用原子预留和结算：派发前预留额度，完成后按实际使用量结算，未知用量保守保留至核对。只做费用归属的平台，也可以接受事后计量；额度预留则需要维护估算、余额和未决记录，会降低部分资源利用率。父任务分配给多个成员的额度不能超过可用总额。对于供应方价格或结算延迟，平台应区分预估与已结算费用，不能承诺对无法即时计量的外部费用实现零超支。



服务目标要按业务定义。交互任务关心首个有效响应，批处理任务关心截止前完成率，审批任务关心提醒与恢复是否可靠。平台指标需要扣除或单独记录人工等待时间，避免把人的审核速度当成模型或运行时性能。



## 十四、别急着把每个方框都做成服务



逻辑分层有助于讨论职责，物理拆分还要承担网络故障、分布式事务和跨服务运维成本。任务控制、资产管理与审批管理可以作为同一服务内的模块，共享明确划分的事务表；需要隔离或独立扩容的 Worker、工具执行和模型调用出口，则更有理由分开。状态所有权先在代码与接口中成立，服务数量随后随规模增长。



图 17：职责与状态边界可以在同一服务内成立，也可以支撑按需独立部署。隔离、扩容和故障影响决定拆分理由，两种形态不代表成熟度高低。



随着任务量增加，优先分离有明确瓶颈或隔离需求的部分：持久调度、模型限流、工具执行池、记忆检索和高容量产物处理。队列、数据库、对象存储和密钥系统尽量复用企业现有基础设施，避免为 AgentOS 再建立一套无人维护的运维体系。



部署管理需要检查依赖、数据库迁移、配置与密钥、组件版本和镜像摘要。启停计算服务与销毁数据分开；升级前确定在途任务处理规则，恢复数据库备份时明确恢复点之后已发生的外部操作如何对账。数据库恢复不会自动撤销已经写入业务系统的动作。



拆分服务之前，我会先验证几个故障场景：工单创建后 Worker 崩溃，审核等待期间版本更新，执行到一半用户权限被撤销。任务怎样继续，哪些操作被阻止，哪些结果需要人工核对，应当有明确答案。只验证服务重启成功，还不够。



## 十五、AgentOS 的边界，最终由企业怎样使用它决定



并非每个组织都需要相同的 AgentOS。一个只做内部知识问答的平台，对副作用恢复的要求可能较轻，却更关心资料权限和来源；一个可以修改业务数据的平台，需要更明确的操作账本、幂等与审批；一个面向不可信代码的研发平台，执行隔离和环境管理会占据更大比重。



图 18：三类业务共享任务身份、状态所有权、授权链路和发布版本，并按各自需求强化不同能力；这些是需求侧重点，不是互斥的能力清单或建设阶段。



对我来说，企业 AgentOS 最该提前稳定的是任务身份、状态所有权、授权链路和发布版本。这些边界含糊，后续每加一个工具、一个成员、一个后台任务，都会把同一批问题再放大一次。至于蜂群、自动演进、复杂算力调度，可以等业务证明需要时再加。



我感觉当前最优先的是让已有任务可靠地运行，而不是尽快补齐架构图。平台要让使用者看见任务进度、撤销后续执行，也要让负责的人在故障后接手处理。等这些事情能做好，再增加协作和自动演进能力，才有把握知道新增能力究竟改善了什么。
