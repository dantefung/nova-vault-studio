# Workflow、Agent、Multi-Agent，架构到底怎么选？

> **摘要**：Anthropic《Building effective agents》里有个小标题值得停下来看——**Workflow: Orchestrator-workers**。它描述的系统已经能让模型动态拆任务、派给多个 worker 再汇总，连子任务都不是提前列好的，Anthropic 却仍把它放在 Workflow 下面。**这个细节直接影响架构选型**。核心是拆开两个问题：**下一步怎么走**（预先安排的流程 vs 模型根据新信息决定）关乎行动如何推进，**一项任务交给一个 Agent 还是拆给多个**关乎怎样分工。分开才看得清为什么 Workflow 能组织多个 Agent。全文用「订单延期分析」一个业务贯穿：材料够就用固定查询+一次模型；核对事项随订单变化就用模型生成清单、程序派发；下一步依赖新线索才上单 Agent 自主调查；供应与产能都需独立调查才拆多 Agent；**多检查一遍未必能补上事实**——措辞可改，缺失的证据只能补查或保留未知。

## 一个值得停下来看的小标题

读 Anthropic 的《Building effective agents》，有个小标题值得停下来看看：**Workflow: Orchestrator-workers**。

它描述的系统已经能让模型动态拆任务、派给多个 worker，再汇总结果。**连要做哪些子任务都不是提前列好的，Anthropic 却仍把它放在 Workflow 下面。**

这个细节会影响架构选型。一个系统即使能动态拆任务，也可能保留预先安排的整体流程；即使用了多个 Agent，也不代表每一步都由模型自由决定。

这里其实有两个问题：

1. **下一步怎么走**——由预先安排的流程决定，还是由模型根据新信息决定？
2. **一项任务交给一个 Agent，还是拆给多个 Agent？**

前一个关乎行动如何推进，后一个关乎怎样分工。**把它们分开，才容易看清为什么 Workflow 能组织多个 Agent**，也容易判断一次模型调用是否已经够用。

下面用一个假设的订单延期分析任务，把 Workflow、单 Agent 和多 Agent 放进同一套业务里比较。重点是看每增加一种结构，它具体解决了什么问题。

## 太长不看版

- **先分清怎样推进，再考虑怎样分工。** Workflow 可以包含模型路由和动态任务，也可以组织多个 Agent；"拆分—处理—汇总"由程序安排，不妨碍任务清单在运行时生成
- **引入 Agent 的一个理由，是调查路径需要随证据改变。** 查库存后发现物料未放行，才转去查质检、追审批。若这些路径已有成熟规则，工作流分支也能处理
- **Multi-Agent 的价值要落到分工上。** 供应商调查与产能调查各有材料、工具和后续查询，可以分开推进；同时要考虑约束是否一致、结果有没有丢失关键条件
- **多检查一遍，未必能补上事实。** 把预计日期写成承诺日期，可以依据原记录纠正；没有质检记录，却把延期归因于质检，就需要补查或保留未知
- **第一版可以从固定流程与单 Agent 调查的组合开始。** 后续是否拆成多个 Agent，用同一批订单比较原因是否查清、方案能否执行、还需多少人工补查，以及耗时和成本

## 一、步骤已经清楚，先用 Workflow 组织工作

假设业务需要查清几笔订单为什么延期，会影响哪些交付，再给出处理建议。

如果订单系统已记录延期原因、生产进度和预计出库日期，就可以读取记录、整理事实，再生成说明。**程序按订单编号关联生产与物流记录，计算日期差、核对库存数量；模型负责读懂备注、组织解释。**

材料不多时，取齐之后调用一次模型，可能就够了。如果模型在解释时混淆了原始记录与推测，也可以分成两步：先按订单列出日期、状态、备注和记录出处，再据此生成说明。**排查错误时，便能分清是读错了记录，还是写解释时加了材料里没有的结论。** 两步的提示词也可以分别调整——这是提示链（Prompt chaining）的一种用法。

这些步骤按已知顺序执行，可以用 Workflow 组织。**一次调用能做好，就不必拆开；需要分步检查、分别调整时，拆成提示链也方便定位问题。**

### 入口可以加一个路由

有的请求只问预计交期，有的要分析原因，有的要求比较处理方案。模型把自然语言请求归入不同类别，程序再启动相应流程。

只查交期的请求，可以跳过原因调查和方案比较，这时路由能省下后续工作。但如果几类请求都读取同一批数据、执行同一段逻辑，**增加分类就多了一次调用，也多了一处需要排查的判断。**

路由中的模型在已知类别里选择，后续有哪些处理路径，由开发者安排。Anthropic 在《Building effective agents》中把路由（Routing）归为工作流，分类可以由模型完成。

> **"流程固定"，固定的是组织方式，不是每次执行的内容。** 工作流可以包含分支、循环和模型判断，每次运行可以走不同分支。

已知订单编号后，互不依赖的订单记录、物流记录查询还可以并行；生成处理建议则要等待调查结果。**这里调整的是先后依赖和等待时间，无须为了并行查询就增加几个 Agent。**

业务判断难不难，与处理步骤能不能预先安排，是两回事。此前介绍过的 Uber 合同审阅助手，第一代系统把意图识别、风险评估和规则查询组织进 LangGraph workflow——法律判断涉及条款含义与业务风险，其中一些工作依然可以按已知结构展开。

## 二、任务清单未知，也可以使用工作流

订单备注未必能把原因说全：一笔疑似缺料、涉及物料替换，一笔涉及客户修改规格，另一笔可能与承运商有关。

这时可以让模型读一遍材料，为每笔订单列出核对事项：查物料到货与替换审批，查规格变更时间，或查物流轨迹。**不同订单生成不同的清单，数量也不固定。** 程序随后逐项处理，再汇总。

这就接近 Anthropic 所说的编排者与工作者（Orchestrator-workers）：编排者根据当前输入拆任务，再交给 worker 完成。**任务清单虽然临时生成，"拆分—处理—汇总"的组织方式仍然可以提前安排。**

LangGraph 官方教程用生成报告演示了这一点：先由模型列出章节，再为每节启动一个 worker。

```python
sections = orchestrator(topic).result()
section_futures = [llm_call(section) for section in sections]
final_report = synthesizer(
    [section_fut.result() for section_fut in section_futures]
).result()
```

`sections` 的数量在运行时才知道，程序据此派发任务，再等待结果。这里的 `llm_call` 只调用一次模型来写一节，`synthesizer` 则直接拼接各节文本。**worker 承担了子任务，却没有自行搜索、反复调用工具的调查过程。**

同一教程的图式实现使用 `Send` 按章节列表动态派发。**框架预先定义节点怎样工作，运行时再决定执行多少个任务，这两件事可以同时成立。**

回到订单分析：查规格变更记录的 worker，可以接收订单编号，调用指定接口，再从结果里提取变更内容与时间。**若各项核对都能按这样的步骤完成，就无须为每个 worker 再安排一套自主调查循环。**

不过，模型列出的清单可能漏项。还有一种麻烦：**查询没有报错，清单也执行完了，延期原因却没查清。** 值得追查的线索藏在第一轮返回的记录里，原来的清单没有安排下一步。

## 三、查到什么，决定下一步查什么

继续看那笔疑似缺料的订单。

假设系统核对后发现，这笔订单需要的物料**已足量入库，但其中一批尚未放行**。接下来可以按批次编号查质检记录；若记录写着"等待替代料审批"，再沿审批单号查工程变更，确认卡在哪个环节。

> **下一项有价值的查询，要看上一项查询得到了什么。** 最初的"缺料"备注只是一条待核实的线索，后续行动会随调查结果改变。

如果这些情形有限、处理规则成熟，可以写成工作流分支。**线索组合多到难以逐条列出路径时，可以考虑让 Agent 利用工具返回的信息，决定接下来查哪里。**

这段调查可以拆开看：模型读到"已入库、未放行"，提出查询质检记录，并给出批次编号；运行程序检查参数和权限，执行查询，再把结果交回模型。模型读到"等待替代料审批"，才选择下一次查询。

> **这里反复运行的是"判断—调用工具—读取结果"。** 模型选择查什么，运行程序负责把查询执行出来。工具结果进入下一轮判断，原先的计划才有机会被修正。

工具返回什么，会影响这段调查：

- "查不到记录"可能需要核对查询条件或换一个来源
- "接口请求失败"需要根据错误决定是否重试
- "记录显示没有异常"才提供了继续排查其他原因的依据

**如果三种情况都返回空文本，模型连刚才是否查成功都无从判断。**

对这套订单助手，工具结果可以保留查询状态、订单或批次编号、记录出处与时间，以及关键字段。这样才能区分：该换一个查询条件，还是先处理接口故障。

最初的计划也要随结果调整。**物料已经足量入库，却还沿着"没有到货"查供应商，调用记录会越积越多，眼前那批物料为什么不能用却仍没答案。**

Agent 也可能选错方向，或反复查询同一份记录，因此调查需要有结束的条件：

- 查到足够的证据，可以形成解释
- 拿不到关键材料，就留下已查过的记录、缺少的审批或检验结果，供后续补查
- 超过时间或调用预算，则返回已有发现与未完成的部分

Anthropic 的原文也提到了最大迭代次数等程序停止条件。

> **对这个例子来说，Agent 的价值在于顺着证据找到下一步。** 如果它重复查询旧记录，或者把一次能取齐的材料拆成多轮，就只增加了等待和调用费用。

## 四、什么时候值得拆成多个 Agent

这段订单调查，**可以先交给一个 Agent 负责**。它按需要查询采购、仓储、质检和工程记录，直到能解释延期原因，或确认缺少关键材料。

采购、仓储、质检都参与这笔订单，**也不必一开始就按部门各设一个 Agent**。查质检时加载检验规范，查工程变更时再读取审批说明，单 Agent 可以按任务取用知识；工具多时，也可以随处理阶段调整可用工具。

LangChain 的多 Agent 文档也提到，**工具和提示词配置合适的单 Agent，可以完成复杂任务**。缺检验规范时补充材料，选错工具时检查工具说明，这些问题未必需要通过拆分 Agent 解决。

### 拆分的真正依据：两项相对独立的调查

接下来若要给出处理方案，就可能出现两项相对独立的调查：一项研究替代供应商，另一项研究内部产能调整。

- 供应商调查：从资质文件 → 可供规格 → 交期和最低采购量
- 产能调查：工单 → 设备 → 可用时段

**两边各有一段随结果变化的调查过程，交给两个 Agent 就有了具体的分工依据。** 供应商资料和排产细节可以留在各自的调查上下文中，两边也有机会并行推进。这两个 Agent 可以使用同一个底层模型，**分开的是任务上下文、可用工具和调查过程。**

### 约束必须一致

分工时，两边需要拿到同一个交付截止时间、同一版产品规格。否则，**一边认为替代料可以买到，另一边按原物料计算产能，两份结果各自合理，放在一起却用不上。**

调查都做完了，才发现双方算的不是同一版规格，还得重新来过，确实可惜。**截止时间和规格适合由外层传入，双方再调查各自的问题。**

### 汇总契约决定结论质量

汇总时，子 Agent 返回的内容也影响结论。**一句"方案可行"若省略最低采购量、设备限制或尚未确认的审批，主 Agent 就可能给出无法执行的建议。**

这个例子中，供应商调查要带回候选方案、交期依据、适用规格和待确认项，主 Agent 才能把它与产能方案放在一起比较。若两边每查一步都要等对方回答，**分开执行省下的时间也可能花在往返询问上。**

外层可以规定先确认问题，再启动两项调查、比较结果——这是一种工作流组织多个 Agent 的方式。若需要随着调查进展决定找哪位协作者，则可以让主 Agent 动态调用它们。

### 两种交接方式

分工之后，还有交接的问题：子 Agent 做完，是返回结果，还是接着处理后面的事？

| 方式 | 含义 | 适用 |
|------|------|------|
| **Supervisor / Subagents** | 做完交回结论，由主 Agent 统一比较 | LangChain 的做法是把子 Agent 包成工具，主 Agent 传入任务，子 Agent 执行后返回结果 |
| **Handoff** | 改变当前由谁处理任务，不只是送回结果 | 用户选定替代采购方案后，让采购 Agent 接手后续交互，连续确认规格、数量和交期 |

LangChain 当前的 Handoffs 文档既支持多个 Agent 之间交接，也支持同一个 Agent 按状态更换提示词和工具。**如果只是进入下一个处理阶段，未必需要增加一个独立 Agent。**

## 五、多检查一遍，能补上缺失的事实吗

调查结束，报告仍可能有错。有些错误藏在措辞里，有些则是证据缺了一块：

- 记录写的是"预计周五出库"，报告却写成"周五可以交付"。**已有材料足以发现这种承诺过度，可以退回修改；出库日期也不能当作到货日期**
- 报告声称"质检导致延期"，却没有相应记录。这时需要补充调查，或者保留为待核实原因

> **修改措辞与补充证据，需要不同的后续动作。** 若检查器只能要求重写，生成器既不能补查，也不允许承认信息不足，几轮之后，措辞可能更肯定，依据却一条没增加。**这样的报告反而让人不放心。**

Anthropic 把生成与评价交替进行的结构称为 **Evaluator-optimizer**，也归在工作流中。它适合评判标准明确、反馈能推动下一轮改进的任务。

反馈也可以来自模型之外。Andrew Ng 介绍反思（Reflection）时，就谈到借助测试、搜索等工具检查结果。模型检查自己的输出，或由两个 Agent 分工，都可以实现反思；**效果取决于检查能发现什么错误，以及后续能否修复。**

有些修改也用不到反复迭代。Uber 在合同审阅助手中单独增加了一次模型调用，调整回复的语气。团队报告，针对已经识别出的表达问题，一次定向修改就能取得较可靠的效果，**因此没有采用更复杂的反思循环。**

Uber 这个选择针对的是已识别的语气问题。订单分析若缺少质检记录，就要把反馈变成补查任务；如果记录拿不到，报告中也应保留这个缺口。**评价之后能执行哪种修复，决定了多一轮检查有没有用。**

## 六、第一版怎么搭，下一步怎么改

这套订单助手可以保留一条外层流程：取齐已有事实，调查未明的原因，形成建议，再交给业务人员确认。调查和比较方案这两段，可以按任务安排：

| 当前任务的难点 | 可以采用的结构 | 需要关注的代价 |
|--------------|--------------|--------------|
| 材料已足够，需要整理解释 | 固定查询与计算，加一次模型分析 | 原始记录与推测容易混淆 |
| 核对事项随订单变化 | 模型生成清单，程序派发、汇总 | 清单漏项，后续照单执行 |
| 下一步依赖新线索 | 单 Agent 根据工具结果继续调查 | 查错方向、重复调用、等待变长 |
| 供应与产能都需独立调查 | 多 Agent 分工，外层统一约束与比较 | 条件不一致，交接丢失依据 |

**这些选择可以出现在同一套系统里。选型落到某一段任务上，才知道增加的结构解决了什么。**

第一版可以先覆盖常规订单和单 Agent 调查：已有记录能解释延期的，就沿工作流完成；原因不明的，交给 Agent 继续查。**等到供应与产能都需要各自追查材料时，再考虑拆分**，并约定它们要共享哪些条件、返回什么结果。

改动有没有帮助，可以拿同一批订单比较：每个延期原因能否找到对应记录，有没有漏掉订单，建议是否满足交期和规格，业务人员还要打开多少张单据补查。**这些结果与耗时、调用成本放在一起，才看得出增加的结构是否值得。**

同样是没能给出可用方案，问题也可能出在不同地方：

- 一个 Agent 已经拿到关键线索，却持续选错下一项查询 → 检查工具说明和它当时看到的材料
- 两项独立调查各自有效，合并后却冲突 → 核对双方采用的交期、规格与比较方式

> **如果分析失败的订单总是缺同一种记录，下一步可能只需要补一个固定查询。如果记录本身不存在，再加一个 Agent 也不会让事实凭空出现。** 能把查到的依据、没查到的材料和卡住的审批交代清楚，接手的人就不必从头翻一遍。
