# 我是如何用 Orca 做 Graph Engineering

> 做移动端开发，这一个月手上有几个大需求，拆成一百多个任务交给一批 agent 去跑，用 Orca 的编排调度它们。

## 核心发现：地图不是疆域

Anthropic @trq212 的说法：**地图不是疆域**。

- 你给 agent 的 prompt、skill、spec、case 代码，都是**地图**
- 真实的代码库、线上约束、没人写下来的规矩，是**疆域**
- 两者的差叫 **unknowns**
- 最麻烦的是 **unknown unknowns**：你连自己漏了什么都不知道

## 长活怎么立住：三样同时成立

graph 先解决一件事：长活怎么拆开、怎么往下接。但它只解决这一件。

跑得对不对要靠 **eval**，跑偏了能不能拐回来要靠**改图权**。

三样同时成立，长任务才立得住：
1. **图把活拆开跑起来**
2. **agent-device 把假前提拦下来**
3. **orchestrator 拿着证据补节点、重连依赖**

少了第二件，你会拿到**假成功**：每步都绿，整张图却建在空气上。

少了第三件，就算发现了也只能整单推倒重来。

## 一 · graph 是长出来的，不是画出来的

### 真实运行的样子

- 绿色是已完成，橙色是正在跑，蓝色是就绪待派，灰色是写好了还没轮到
- 四种状态同时存在，这是常态

### 我的使用方法

开工只写两个任务：

1. **探路**（wayfinder skill）：不写代码，只去摸这活的边界——相关代码在哪、有哪些没写进文档的约束、哪几处一碰就会牵动别的地方
2. **第一块实现**：两个都 dispatch出去，各派一个 worker，然后等回执

worker 干完把结果交回 orchestrator，它据此补任务、改依赖，或者回答 worker 的 ask。多数时候是 task-create 加两三个新任务，deps 指向刚做完的那个。只有裁不了的才升到我这儿。

### 结论

task graph **持续增长**——开工时 graph 上只有 2 个任务，41 个任务分布在 33 个创建时间点上。

## 二 · 跑得对：怎么防假成功

### 假成功的来源

「后端和 Runner 已就绪」在计划里读起来跟别的条件没什么两样。它不会自己报错，只是被默认为真，然后底下挂了一串任务。这就是假成功。

### 三类证据

- **单元测试**：管数据和方法层
- **agent-device**：管端上的真实行为（真机验收）
- **系统日志**：补时序和权限（注意：没有那一行可能是真没发生，也可能是埋点挂了）

### 我的接法

**顺序是吃过亏才排对的。**

第一道先把**前提验成事实**：这个功能依赖的后端、Runner、配置，得有一条真跑过的证据说它在，而不是「计划里写了它在」。对不上就直接停，后面一项都不用跑。

接起来只有一句话：**这一步没过，依赖它的任务就不派发**。

### 另一种失败：漏做了，自己却不知道

一个节点列了八项检查，它做了六项，漏了两项，然后交回一份「完成」。

最难发现的漏项，是**执行者和验收者都没检查到的那一项**。

所以后来我把能单独验收的步骤**拆成独立节点**，漏一项就有一项亮红。

## 三 · 拐得回来：权在谁手里

有了 eval，你知道哪儿不对了。但光知道不够。下游要不要停、要不要加节点、谁拍板，才是第三件事。

### 失败的分类

- 大多数失败会自己撞出来：报错、超时、断言不过
- 但漏做一项而自己不知道，不会主动报错

### 关键机制

失败催生了原计划外的修正任务。卡住下游的不是哪个 reviewer 说「看起来不太行」，是设备上**真的没过**。

## 共识部分

### 判断要不要 graph

四条的判断标准：
- 先判断这活要不要 graph（@ericosiu 的 rails/motor 最好用）
- 砍掉不传数据的边
- 把执行和复核分开
- 按节点难度选模型

@humzaakhalid 讲成本那句话印象最深：**people discover this on the invoice**。你不会在设计的时候意识到一次宽的并行按顶配计费，你会在账单上意识到。
