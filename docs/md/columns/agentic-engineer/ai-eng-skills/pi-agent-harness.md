# 从 Pi 看 Agent Harness：少做功能，怎样换来更可控的运行时

架构师（JiaGouX）我们都是架构师！架构未来，你来不来？最近正在做 Agent，免不了看看 DSH、Pi、Codex 的代码。这几个项目放在一起看，挺有意思。它们都要处理同一件事：模型开始调用工具、修改文件、跑很长时间以后，模型外面的那层程序应该接管多少工作？有的产品把常见工作流都准备好了，用户打开就能用；有的项目只保留一条很短的主链路，剩下的交给扩展、命令行和项目文件。表面上看，这是功能多少的区别。顺着源码往下看，实际差别在于：哪些状态由系统保存，哪些动作由系统决定，哪些事情仍然交给使用者自己组合。之前我们梳理过 Pi 的 Loop、会话树和上下文压缩。这次重新对着仓库看了一遍，又把它和 Codex、DSH 的实现放在一起比较，Pi 最值得看的地方，不是“默认只有四个工具”，而是它有意把产品工作流和 Agent 的基础运行部分拆开了。这条路，和 Claude Code 的方向几乎相反。Claude Code 更像一张已经铺好的工作台：循环、工具、权限、上下文和常用工作流，都尽量组织在产品里面，用户拿到的是一套完整体验。Pi 则把核心压到更底层，只负责把模型请求发出去、把工具调用接回来、把会话保存下来，再给扩展和外部环境留下足够大的空间。两种做法没有谁天然更正确。一个适合直接交付给更多用户，另一个适合希望自己掌控工作流的人。对正在做 Agent 的团队来说，Pi 提供的是一个反向检查：新增的功能，究竟是在解决运行时必须解决的问题，还是把某一种使用方式写死进了核心？先把几条路线放在一起Claude Code 的重点是完整。更多能力进入默认产品，用户少做装配，换来的就是运行时替用户做更多决定。它更接近成品化工作台，而不是一组等待组合的零件。Codex 关注的是稳定的运行过程。模型、Thread、Turn、工具执行、审批和事件有相对明确的归属。最近的上下文管理实验又把notes、history、主动切窗和预算控制放到一起，尝试让长任务在换窗口后继续，而不是只依赖一次压缩摘要。这条路径目前仍有明确的实验范围，不能简单说成已经替代了 Compaction。DSH 把可替换性再往下推了一层。模型、文件、进程、Session，甚至 Agent Loop，都有正式的能力位置，由插件和运行时组装。这样做对远程沙箱切换、生命周期管理和运行时组合很有吸引力，但组件越多，启动、停止、状态交接和回滚也越需要明确规定。Pi 的选择最克制。默认工具就是read、write、edit和bash。MCP、子 Agent、计划模式、后台 Bash、权限弹窗，没有被放进默认主路径。想要这些能力，可以用 Extension、Skills、CLI、项目文件，或者外部沙箱补上。Pi 和 Claude Code 的“相反”，不在于一个有功能、一个没功能，而在于产品替使用者做决定的程度不同。Claude Code 把一整套工作方式放在产品里；Pi 尽量只保留模型调用、工具执行、事件和会话这些基础部分，把工作流留在核心之外。Pi 少做的是内置工作流，不是放弃运行时工程。它的Session、Operation、Lane和AgentHarness，都在处理长任务、恢复和状态记录。默认入口很薄，底下的实现并不简单。核心代码只管几件事Pi 的 monorepo 分得很清楚。pi-ai处理不同模型提供方的接口，pi-agent-core处理 Agent 消息、工具调用和事件，pi-coding-agent组合编码场景，pi-tui负责终端界面，其他能力再由应用层和扩展接上。![image](./images/001.png)Pi 的包结构与运行时分层图 1：模型接口、Agent Loop、编码场景和终端界面分别落在不同的包里。这几个包可以单独拿出来使用。只想统一模型接口，可以停在pi-ai；需要一个 Agent Loop，可以使用pi-agent-core；要完整的终端编码体验，再进入coding-agent。上层的工作流没有反过来污染底层契约，这比“所有功能都可配置”更能说明它为什么容易嵌入别的产品。默认工具少，也不表示工具执行很随意。模型返回工具调用后，Pi 会先做参数预处理和校验，执行前还可以拦截，执行后可以修改结果。流式输出如果撞到 token 上限，工具参数可能只生成了一半，这时整批调用都会被拒绝，不会拿残缺 JSON 去执行。这些处理不会出现在产品宣传页上，但出了问题，至少可以分别追查：模型收到了什么，系统准备执行什么，工具实际上执行了什么，结果怎样回到了下一轮上下文。Loop 不是一条直线最简单的 Agent Loop 可以写成：调用模型，执行工具，把结果放回去，再调用模型。真正跑起来以后，用户可能在中途插话，工具可能并行执行，也可能有任务排在本轮之后，循环还要处理取消、失败和提前结束。Pi 的agent-loop.ts把这些时序分成内外两层。内层围绕当前 Turn 工作：发起模型请求，接收流式响应，执行工具，再把结果放回上下文。如果收到steering消息，当前运行可以调整方向；外层则在本轮结束后查看followUp队列，有追加任务就继续，没有才发出agent_end。另外还有nextRun，它消费的是下一次运行才处理的输入。steer、followUp和nextRun分开以后，“现在改方向”“做完当前任务再继续”和“下次启动时再处理”不会挤在同一个队列里。模型内部使用的是AgentMessage。真正调用 Provider 前，Pi 会经过convertToLlm，把带有运行时信息的内部消息转换成模型接口能理解的消息格式；Provider 的差异留在适配层，Loop 和工具不需要知道每家 API 的细节。工具批次可以并行执行，但结果落盘仍按模型给出的顺序处理。事件通过事件流发出去，终端界面只负责订阅和渲染。这样的安排让pi-tui不必把业务状态再实现一遍。![image](./images/002.png)Pi 的 Trace 与 Turn 嵌套图 2：一次运行包含多个 Turn，只有模型继续返回工具调用时才进入下一轮。Loop 里最值得看的，不是“用了两层循环”，而是停止条件写得很清楚：没有工具调用时自然结束，模型报错或被中止时收尾，工具或 Hook 可以请求终止，当前批次的工具结果也可能触发结束，内层结束后还要检查followUp是否为空。![image](./images/003.png)Pi 根据 stopReason 决定继续或停止图 3：`toolUse` 继续进入工具执行，`stop` 正常结束，`error` 和 `aborted` 进入失败收尾。用户按下 Ctrl+C 时，已经完成的工具结果仍会先写入历史，后面的模型请求再沿统一的中止路径结束。这个细节能避免会话停在一个只有半截结果的状态。Session 保存发生过什么Agent 跑久以后，不能只把当前上下文当作数据库。当前上下文会压缩、切换分支，也会随着模型和工具变化；如果历史只剩一段摘要，很多事情就无法核对。Pi 的 Session 使用 JSONL，但每条记录不是简单的聊天消息。Entry 有id、seq、parentId和时间戳，除了message，还可以记录模型切换、思考等级、活动工具、压缩摘要、分支摘要以及扩展自己的数据。同时，Operation 记录运行过程：一次运行何时开始和结束，某个步骤尝试过几次，工具何时启动，队列何时入列或取消，延迟写入是否完成，以及本次用量。这两类记录放在一起，才能同时回答“发生过什么”和“这次是怎么走到这里的”。模型下一轮真正看到的内容，是从当前分支投影出来的工作集。buildSessionContext沿着当前路径读取 Entry，恢复模型、思考等级和活动工具状态，再把消息、压缩摘要、分支摘要和扩展内容拼成上下文。完整历史留下来，当前工作集按需生成。这是 Pi 会话树的关键。用/tree回到旧节点，或者从某个节点/fork，并不是把一段文本复制成新对话，而是在同一份历史上换一条路径继续走。![image](./images/004.png)Pi Agent 的 Memory 分层图 4：Session 保存原始记录，上下文只装入当前任务需要的部分。![image](./images/005.png)Pi 的上下文组装流程图 5：分支、资源、压缩摘要和扩展内容经过整理、转换后再发给模型。这和 Codex 的notes、history、新窗口是两种不同的实现。Pi 把分支、Entry 和摘要放在同一棵会话树里；Codex 的实验路径把交接信息和历史回查拆得更开。它们面对的是同一个现实：模型眼前的上下文可以重建，任务已经产生的事实不能只靠模型记住。压缩不是把旧消息删掉上下文接近窗口上限时，Pi 会根据 Provider 返回的用量，或者字符数估算，判断是否需要压缩。当前代码里的默认配置会为摘要请求和输出预留16384个 token，并尽量保留最近约20000个 token。选切点时不能随便从中间截断。toolResult不能作为切点，否则工具调用和工具结果会被拆开；如果要压缩的部分正好落在一轮任务中间，代码会识别这一轮的起点，对前缀单独生成摘要，再和历史摘要合并。压缩完成后，原始 Entry 仍然在 Session 里。系统新增一条compactionEntry，里面记录摘要、压缩前的 token 数、保留的尾部以及读写过的文件。下一次构建上下文时，模型拿到的是摘要加上最近内容，不会再次装入全部旧消息。分支摘要也遵循同样的思路。切换分支时，Pi 找到旧叶子和目标节点的最近公共祖先，只整理离开的那条路，并记录目标、约束、进展、关键决定、下一步，以及这条分支读过和改过的文件。摘要会丢信息，所以不能代替原始历史。它只负责把模型带回一个可以继续工作的检查点；需要核对时，仍然要回到 Session 的原始记录。少做功能，复杂度去了哪里Pi 不把 MCP、子 Agent、计划模式和后台任务放在默认核心，一个直接原因是这些东西会增加工具说明、状态和控制路径，而且不是每个任务都需要。Mario Zechner 在关于 MCP 的文章里举过两个例子：Playwright MCP 的 21 个工具描述约占13.7Ktoken，Chrome DevTools MCP 的 26 个工具描述约占18Ktoken。Pi 更倾向于让 Agent 在需要时读取 README，再通过 CLI 和 Bash 使用能力。这样做不代表 CLI 在所有场景都优于 MCP。需要稳定的结构化协议、细粒度授权和服务治理时，MCP 仍然有价值。Pi 只是没有把这套成本默认摊给每一次请求。计划文件也是同一个思路。计划写在PLAN.md，任务写在TODO.md，人和模型都能读，Git 也能看到变化。代价是项目需要自己维护约定，系统不会自动替所有任务协调状态。功能没有进入核心，复杂度并不会消失。它会落到扩展、CLI、项目文件和外部运行环境。对于需要自己搭工作流的人，这种安排比较自由；对于希望打开就用的人，确实会多几步准备。安全问题不能靠“以后加个 Hook”一笔带过。Pi 默认使用启动进程拥有的文件、进程、网络和凭据权限，也没有内置进程沙箱。Extension 和内置工具一样，运行在 Pi 进程的权限范围内。beforeToolCall可以做确认、白名单和审计，但它不是进程隔离。面对不可信仓库、敏感凭据或受限网络，文件挂载、网络出口、凭据注入和回滚，应该交给 Gondolin、Docker、OpenShell 或其他真正能限制进程的环境。把源码放回研发日常以这次读到的 Pi 仓库最新提交f4d802c303cd4ab8cb1fd10d76c6207e217547f0为准，AgentHarness已经把模型、思考等级、活动工具、Skills、Prompt Templates、队列、重试、压缩、运行模式和会话投影放进了一个比较完整的契约里。但这个契约还没有全部实现。当前版本的prompt、compact、navigateTree、resume、队列操作，以及部分hooks、events接口，仍会返回HarnessNotImplemented。它是正在成形的运行时接口，不是所有控制能力都已经可用的产品功能。先把模型、工具、会话、队列和恢复之间的关系写清楚，后面再逐步填实现，至少不会每加一个功能就重新定义一遍状态。架构先定下“谁保存、谁执行、谁能中断、失败后从哪里恢复”，比一开始把菜单做满更稳妥。把 Pi、Codex、DSH 和 Claude Code 放在一起看，判断一个 Harness 是否稳，还是得回到几件具体的事：Provider 差异有没有被隔离在适配层；模型上下文、工具执行和运行事件是否各自有清楚的记录；完整历史和当前工作集是否分开；项目规则能不能被人直接读懂和修改；安全策略是不是落在真正控制进程和网络的地方。这些问题没有统一答案。把权限、后台任务、计划和子 Agent 全部放进核心，用户会省事，运行时也会更重；把它们都交给外部，核心会更干净，但装配和治理的工作会落到项目自己身上。Pi 的取舍并不适合所有产品，但它把一个常被忽略的问题摆到了台面上：真正需要每次运行都经过的部分，才有必要进入核心；只服务某类任务的工作流，留在扩展、项目文件或外部环境里，后面通常更容易调整，也更容易撤回。参考资料Pi 这几个包可以单独拿出来使用。只想统一模型接口，可以停在pi-ai；需要一个 Agent Loop，可以使用pi-agent-core；要完整的终端编码体验，再进入coding-agent。上层的工作流没有反过来污染底层契约，这比“所有功能都可配置”更能说明它为什么容易嵌入别的产品。

默认工具少，也不表示工具执行很随意。模型返回工具调用后，Pi 会先做参数预处理和校验，执行前还可以拦截，执行后可以修改结果。流式输出如果撞到 token 上限，工具参数可能只生成了一半，这时整批调用都会被拒绝，不会拿残缺 JSON 去执行。

这些处理不会出现在产品宣传页上，但出了问题，至少可以分别追查：模型收到了什么，系统准备执行什么，工具实际上执行了什么，结果怎样回到了下一轮上下文。

Loop 不是一条直线

最简单的 Agent Loop 可以写成：调用模型，执行工具，把结果放回去，再调用模型。真正跑起来以后，用户可能在中途插话，工具可能并行执行，也可能有任务排在本轮之后，循环还要处理取消、失败和提前结束。

Pi 的agent-loop.ts把这些时序分成内外两层。内层围绕当前 Turn 工作：发起模型请求，接收流式响应，执行工具，再把结果放回上下文。如果收到steering消息，当前运行可以调整方向；外层则在本轮结束后查看followUp队列，有追加任务就继续，没有才发出agent_end。

另外还有nextRun，它消费的是下一次运行才处理的输入。steer、followUp和nextRun分开以后，“现在改方向”“做完当前任务再继续”和“下次启动时再处理”不会挤在同一个队列里。

模型内部使用的是AgentMessage。真正调用 Provider 前，Pi 会经过convertToLlm，把带有运行时信息的内部消息转换成模型接口能理解的消息格式；Provider 的差异留在适配层，Loop 和工具不需要知道每家 API 的细节。

工具批次可以并行执行，但结果落盘仍按模型给出的顺序处理。事件通过事件流发出去，终端界面只负责订阅和渲染。这样的安排让pi-tui不必把业务状态再实现一遍。

图 2：一次运行包含多个 Turn，只有模型继续返回工具调用时才进入下一轮。

Loop 里最值得看的，不是“用了两层循环”，而是停止条件写得很清楚：没有工具调用时自然结束，模型报错或被中止时收尾，工具或 Hook 可以请求终止，当前批次的工具结果也可能触发结束，内层结束后还要检查followUp是否为空。

图 3：`toolUse` 继续进入工具执行，`stop` 正常结束，`error` 和 `aborted` 进入失败收尾。

用户按下 Ctrl+C 时，已经完成的工具结果仍会先写入历史，后面的模型请求再沿统一的中止路径结束。这个细节能避免会话停在一个只有半截结果的状态。

Session 保存发生过什么

Agent 跑久以后，不能只把当前上下文当作数据库。当前上下文会压缩、切换分支，也会随着模型和工具变化；如果历史只剩一段摘要，很多事情就无法核对。

Pi 的 Session 使用 JSONL，但每条记录不是简单的聊天消息。Entry 有id、seq、parentId和时间戳，除了message，还可以记录模型切换、思考等级、活动工具、压缩摘要、分支摘要以及扩展自己的数据。

同时，Operation 记录运行过程：一次运行何时开始和结束，某个步骤尝试过几次，工具何时启动，队列何时入列或取消，延迟写入是否完成，以及本次用量。这两类记录放在一起，才能同时回答“发生过什么”和“这次是怎么走到这里的”。

模型下一轮真正看到的内容，是从当前分支投影出来的工作集。buildSessionContext沿着当前路径读取 Entry，恢复模型、思考等级和活动工具状态，再把消息、压缩摘要、分支摘要和扩展内容拼成上下文。

完整历史留下来，当前工作集按需生成。这是 Pi 会话树的关键。用/tree回到旧节点，或者从某个节点/fork，并不是把一段文本复制成新对话，而是在同一份历史上换一条路径继续走。

图 4：Session 保存原始记录，上下文只装入当前任务需要的部分。

图 5：分支、资源、压缩摘要和扩展内容经过整理、转换后再发给模型。

这和 Codex 的notes、history、新窗口是两种不同的实现。Pi 把分支、Entry 和摘要放在同一棵会话树里；Codex 的实验路径把交接信息和历史回查拆得更开。它们面对的是同一个现实：模型眼前的上下文可以重建，任务已经产生的事实不能只靠模型记住。

压缩不是把旧消息删掉

上下文接近窗口上限时，Pi 会根据 Provider 返回的用量，或者字符数估算，判断是否需要压缩。当前代码里的默认配置会为摘要请求和输出预留16384个 token，并尽量保留最近约20000个 token。

选切点时不能随便从中间截断。toolResult不能作为切点，否则工具调用和工具结果会被拆开；如果要压缩的部分正好落在一轮任务中间，代码会识别这一轮的起点，对前缀单独生成摘要，再和历史摘要合并。

压缩完成后，原始 Entry 仍然在 Session 里。系统新增一条compactionEntry，里面记录摘要、压缩前的 token 数、保留的尾部以及读写过的文件。下一次构建上下文时，模型拿到的是摘要加上最近内容，不会再次装入全部旧消息。

分支摘要也遵循同样的思路。切换分支时，Pi 找到旧叶子和目标节点的最近公共祖先，只整理离开的那条路，并记录目标、约束、进展、关键决定、下一步，以及这条分支读过和改过的文件。

摘要会丢信息，所以不能代替原始历史。它只负责把模型带回一个可以继续工作的检查点；需要核对时，仍然要回到 Session 的原始记录。

少做功能，复杂度去了哪里

Pi 不把 MCP、子 Agent、计划模式和后台任务放在默认核心，一个直接原因是这些东西会增加工具说明、状态和控制路径，而且不是每个任务都需要。

Mario Zechner 在关于 MCP 的文章里举过两个例子：Playwright MCP 的 21 个工具描述约占13.7Ktoken，Chrome DevTools MCP 的 26 个工具描述约占18Ktoken。Pi 更倾向于让 Agent 在需要时读取 README，再通过 CLI 和 Bash 使用能力。这样做不代表 CLI 在所有场景都优于 MCP。需要稳定的结构化协议、细粒度授权和服务治理时，MCP 仍然有价值。Pi 只是没有把这套成本默认摊给每一次请求。

计划文件也是同一个思路。计划写在PLAN.md，任务写在TODO.md，人和模型都能读，Git 也能看到变化。代价是项目需要自己维护约定，系统不会自动替所有任务协调状态。

功能没有进入核心，复杂度并不会消失。它会落到扩展、CLI、项目文件和外部运行环境。对于需要自己搭工作流的人，这种安排比较自由；对于希望打开就用的人，确实会多几步准备。

安全问题不能靠“以后加个 Hook”一笔带过。Pi 默认使用启动进程拥有的文件、进程、网络和凭据权限，也没有内置进程沙箱。Extension 和内置工具一样，运行在 Pi 进程的权限范围内。

beforeToolCall可以做确认、白名单和审计，但它不是进程隔离。面对不可信仓库、敏感凭据或受限网络，文件挂载、网络出口、凭据注入和回滚，应该交给 Gondolin、Docker、OpenShell 或其他真正能限制进程的环境。

把源码放回研发日常

以这次读到的 Pi 仓库最新提交f4d802c303cd4ab8cb1fd10d76c6207e217547f0为准，AgentHarness已经把模型、思考等级、活动工具、Skills、Prompt Templates、队列、重试、压缩、运行模式和会话投影放进了一个比较完整的契约里。

但这个契约还没有全部实现。当前版本的prompt、compact、navigateTree、resume、队列操作，以及部分hooks、events接口，仍会返回HarnessNotImplemented。它是正在成形的运行时接口，不是所有控制能力都已经可用的产品功能。

先把模型、工具、会话、队列和恢复之间的关系写清楚，后面再逐步填实现，至少不会每加一个功能就重新定义一遍状态。架构先定下“谁保存、谁执行、谁能中断、失败后从哪里恢复”，比一开始把菜单做满更稳妥。

把 Pi、Codex、DSH 和 Claude Code 放在一起看，判断一个 Harness 是否稳，还是得回到几件具体的事：Provider 差异有没有被隔离在适配层；模型上下文、工具执行和运行事件是否各自有清楚的记录；完整历史和当前工作集是否分开；项目规则能不能被人直接读懂和修改；安全策略是不是落在真正控制进程和网络的地方。

这些问题没有统一答案。把权限、后台任务、计划和子 Agent 全部放进核心，用户会省事，运行时也会更重；把它们都交给外部，核心会更干净，但装配和治理的工作会落到项目自己身上。

Pi 的取舍并不适合所有产品，但它把一个常被忽略的问题摆到了台面上：真正需要每次运行都经过的部分，才有必要进入核心；只服务某类任务的工作流，留在扩展、项目文件或外部环境里，后面通常更容易调整，也更容易撤回。
