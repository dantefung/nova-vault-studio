# 可逆不是逆向运行：DeepSeek Harness 架构的数学本质

> 作者：可逆计算 | 原文 54k 字长文，从可逆计算理论（GRC）角度分析 DSH 底层插件运行时 Cordis 的设计原理

---

## 一句话结论

DSH 的"可逆"不是逆向运行，而是**逆转对运行时结构空间的变更**。每个插件在安装时就把自己的撤销函数写好交出去——"Δ 出生即带逆"。可逆的对象始终是结构（谁注册了什么、谁监听了什么），不是状态（业务数据）。

---

## 一、一切皆插件 => 一切皆差量

**App = Base + Plugin1 + Plugin2 + ...**

在传统软件工程中，这只是启发式描述。Cordis 论文要把它落实为一个真正的数学公式——精确回答：

- Plugin 的具体结构形态是什么？
- "加号"在数学上如何精确定义？
- Base + Plugin1 + Plugin2 和 Base + Plugin2 + Plugin1 等价吗？

从可逆计算的角度，**A = 0 + A**——一切全量都可以看作是与 0 结合的差量。当一切插件都不存在时，系统没有任何业务侧可见的功能，对应于数学空间中的零。但这个零不是"一无所有"，就像物理学中的真空——它内部存在隐秘的结构。

---

## 二、插件皆可逆 => Delta 可正可负

### 可逆的对象是结构，不是状态

软件存在两个性质不同的空间：

| 空间 | 内容 | 可逆路径 |
|------|------|----------|
| 编译期结构空间 | 代码、模型、DSL、配置 | Nop 平台（差量合并 x-extends） |
| 运行时结构空间 | 进程状态、内存、依赖图 | DSH/Cordis（effect 撤销函数） |

DSH 走的是互补路径：在运行时空间实现可逆。

### tool-stats 插件示例

```ts
// 插件激活时做三件事，全部以 effect 形式登记
export function apply(ctx: Context) {
  // 1. 注册工具
  ctx.tools.register(defineTool({ name: 'stat_summary', ... }))
  
  // 2. 监听事件
  ctx.on('agent/request-error', async (payload, next) => {
    countFailure(payload)
    return next()
  })
  
  // 3. 启动定时器
  ctx.effect(() => {
    const timer = setInterval(heartbeat, 60_000)
    return () => clearInterval(timer)  // 配对的撤销函数
  })
}
```

关键机制：插件无需手动登记任何东西，每次注册完成的同时，撤销函数就交到了运行时手里。运行时把撤销函数按顺序累积在 fiber 的 `disposables` 列表中。插件卸载时，`fiber.dispose()` 清空列表并反序执行撤销函数——LIFO 逆序，像退栈一样。

### 动态更新的自然推论

安装与卸载都是对运行时结构空间的加减法，"动态更新插件"就成了自然推论：

```
旧插件 → 施加 Δ⁻¹（卸载） → 新插件 → 施加 Δ（安装）
```

不需要重启，因为结构空间的变化本来就是可逆的。

### 逆由插件作者提供，运行时不验证

运行时不验证撤销函数是否正确（那是组件作者的义务），它保证的只是：你的撤销函数会被保存、会被执行、不会被执行两次。

## 三、Pi Agent 与 DSH 的区别

**核心问题：扩展坐标由核心预定义，还是可以由插件通过 service/inject 关系持续生成？**

### DSH 的运行时结构空间

由三部分构成：

1. **服务表**（ReflectService）：唯一共享，由"服务名+隔离标签"定位
2. **fiber 树**：每次 `ctx.plugin()` 产生独立 fiber，承载生命周期
3. **ctx 链**：原型链决定可见性，fiber 决定归属账本

### 与 Nop delta 文件系统的对比

| 维度 | Nop delta 文件系统 | DSH ctx 链 |
|------|-------------------|------------|
| 物理布局 | 层携带内容，查找跨层 | 层携带路由，值在共享表 |
| 合并粒度 | 节点级合并（x-extends） | 整值遮蔽（provide） |
| 时间性 | 装配期确定，基本静态 | 运行时创建/重启/卸载 |
| 逆的承载 | 结构差量（x-diff 声明式） | 闭包函数（不透明） |

### Pi vs DSH 的本质区别

| 维度 | Pi Agent | DSH |
|------|----------|-----|
| 扩展空间 | Ext(AgentLoop)：核心预定义槽位 | Compose(Plugin...)：插件生成新坐标 |
| 拓扑 | 放射状（围绕 Agent Loop） | 依赖图（ServiceA → Plugin2 → ServiceB） |
| 生命周期 | session_start/session_shutdown 分离 | fiber 统一治理，LIFO 逆序卸载 |
| 依赖管理 | 无建模，全靠约定和代码审查 | reconciliation 自动协调 |

Pi 的插件化是"往预先定义好的槽里填"，DSH 的插件化是"插件可以 provide 任意服务，其他插件 inject 它"——新的扩展点不是被核心"设计"出来的，而是被插件生态"涌现"出来的。

### 结构空间的两种变化路径

1. **轻路径（注册表替换）**：无状态能力（如 Web Search），调用时才按当前配置选择实现——撤销旧注册即可，使用者无需重启
2. **重路径（依赖收敛）**：被长期持有的 Service 消失时，依赖它的消费者退出、旧 fiber 清理，新服务出现后再激活——这就是 reconciliation

## 四、可逆计算角度的进一步分析

### 4.1 可逆需要定义在结构空间中

DSH 论文引入了对结构空间的形式化定义：

- **coeffect 上下文 Σ**：一张从 key 到值的部分函数表 `σ: K ⇀ V_k`——整张表就是运行时结构空间本身
- **读写只有两个原语**：`get(k)`（读坐标）和 `set(k,v)`（写坐标，单写者）
- **isolation realm 表**：坐标翻译层，同一 key 经不同 realm 解析到不同绑定
- **单写者**：每个坐标只能被写一次，`set` 本身是带逆的效应函数

坐标系必须是稳定的——Git 的行号是不稳定坐标（新增一行后续全漂移），Docker 的文件路径是稳定坐标。只有稳定坐标才能在其上定义数学上精确的差量运算。

### 4.2 单坐标上的差量代数：交换律与逆

**不同坐标处的运算天然独立**——各自只读、只写自己坐标上的值，坐标不同则两两独立。

单坐标上是否满足交换律取决于该坐标的运算能否区分两种先后顺序：

| 坐标类型 | 判据 | DSH 对应 |
|----------|------|----------|
| 值是一张表的 key | 可交换（注册类操作） | `ctx.emit`：同步广播，监听器彼此独立 |
| 值是一条有序链的 key | 不可交换 | `ctx.waterfall`：洋葱链，顺序真实影响结果 |

不满足交换律时的处理：顺序由 coeffect 承载。单个 fiber 内部 LIFO 撤销，跨 fiber 通过声明的 coeffect 排序，元理论层以依赖关系无环为前提。

**"一事件一结合律"由"声明+校验"共同保证**：目录生成器强制每个事件必填 `@mode`，doc-sync 门禁对"代码 ↔ 声明"做再生成 diff。

### 4.3 动态资源的统一管控

dsh 的解法不是追踪资源本身，而是要求一切受管动态资源在创建时转化为句柄、以差量条目的形式登记到坐标系统上：

```ts
ctx.effect(() => {
  const timer = setInterval(heartbeat, 60_000)
  return () => clearInterval(timer)  // 销毁动作
})
```

坐标（槽位）+ 名称（label）+ 可枚举性（getEffects）——否则进程里不可枚举的动态资源根本无从管控。

**可逆性的前提是坐标化**——一切受管动态资源必须转化为坐标上的句柄差量；完全隐式的副作用连转化都没发生，框架无从观测、无从逆转。

### 4.4 单写者 + 累加 + 无删除

dsh 的运行时叠加遵循三条约定：

1. **单写者**：每个坐标由一个 fiber 提供一次，同层同名直接报错
2. **累加**：注册操作只做插入，运行时结构单调增长
3. **无删除**：运行时不提供"删掉别人的贡献"的原语，只能执行自己的逆

**关键结论**：插件是结构（可定制）还是代码（只能替换），决定了定制能力的上限。Nop 的 Delta 包本身就是结构，可定制到字段级；DSH 的插件是代码，只能停留在"代码的入口"。

要让插件内部支持 delta 定制，只有两条路：
- 插件内部声明式化（DSL 结构，用 x-extends 做任意深度的增删改）
- 在运行时结构空间上定义差量代数（与 DSH 的"单写者+累加"设计冲突）

### 4.5 apply 的双重身份：Generator + Delta Applier

可逆计算核心公式：**App = F(X) ⊕ Δ**

DSH 的 `apply(ctx)` 函数兼具 Generator 与 Delta Applier 的双重作用——插件代码就地执行注册，而不是先返回声明式 Delta 描述再由框架统一应用。

对比 Nop 的路线：ΔP = setup(config); C' = apply(C, ΔP)——差量的生成与应用分离为两个步骤，外部引擎完全接管差量运算。此时撤销的结构正确性由合并代数保证。

`apply` 把生成与应用混合为一步，要求应用窗口内"时间静止"——dsh 的异步 effect 展开在每一步都检查 `runner.epoch` 是否变化（依赖一变立即中止展开）。

### 4.6 哪些 Delta 必须定义在运行时结构空间

分界线不是由"能不能前提前"的偏好决定，而是由**"注册内容何时可知"的认识论边界决定**：

- 凡是在结构空间中可确定的内容 → 提到结构空间
- 凡是在运行期才可确定的内容 → 留在运行时并用可逆机制管理

最典型的例子是 DSH 的 agent 级 scope：同一插件代码在不同 agent 的 scope 中执行时，注册的具体内容可能完全不同——注册什么，取决于这个 agent 是谁，而这些信息在编译期并不存在。

### 4.7 可逆性（能力）与响应式（治理）正交

| 维度 | 可逆性 | 响应式 |
|------|--------|--------|
| 性质 | 能力 | 治理 |
| 保证 | 撤得回来 | 不会跑到无效状态 |
| 实现 | 逆函数存在且会被执行 | reconciliation 主动触发 |
| Nop | 编译期天然 | 被动缓存检查 |
| DSH | effect 撤销函数 | 主动依赖计算 |

即便完全没有响应式机制，可逆性依然成立：手工调用 `fiber.dispose()` 同样会反序执行全部逆。

论文 Theorem 63 保证提供者严格晚于依赖者卸载（ordering），Theorem 66 保证级联卸载的守卫最终一定释放——依赖协调的终止性由定理保证。

### 4.8 观测等价性

逆操作后"回到原始状态"是**观测等价**，不是物理状态完全恢复：两个状态等价，当且仅当没有观察者能够区分它们。

等价性在可逆计算理论中有专门讨论：
- **表象转换等价性**：同一信息可以有不同的表示，按信息内容比、不按表示细节比
- **往返变换等价性**：经过观测等价这一"自然同构"修正的准逆，不是强等式

## 五、可逆的哲学思考：控制熵增

热力学第二定律：系统自发演化时熵永不减少。软件演化服从同样的规律——大型软件普遍经历从有序到混乱，增加功能越来越难，最终推倒重建。

可逆计算的核心命题：**熵保持不变就意味着可逆**——如果系统的每一次演化都是可逆的，则合起来看，系统始终处于确定、可回退的状态，演化并不积累混乱。

但现实世界中熵增无法逃避。可逆计算的态度是：**控制不了熵增，但可以选择熵增发生的地方**——把不可逆性集中到显式边界，让它发生在差量层而不是核心架构里。

**可逆 = 信息可追溯 + 信息可分离**

- 可追溯：每个差量都带着自己的逆，随时可以枚举并反序执行
- 可分离：差量以 fiber/scope 为边界登记，任何一部分都可以被完整拿走而不波及其他

分离得好不好，看它能不能被完整拿走。

可逆性的另一个工程价值在于它可以复合：如果每个局部都可逆、且局部之间的结合关系也可逆，那么整体就可逆。逐步构建大型可逆系统因此成为可能。

## 六、结语

Cordis 的设计正好补足 Nop 平台一直未详细设计的运行期 plugin 机制。Nop 的可逆计算机制主要集中在编译期模型构建，在运行期规划了 plugin 机制但未深入设计。后续 Nop 平台中会引入类似 Cordis 的机制，进一步完善在运行时的动态合成能力。

理想形态是两者的结合：
- **结构空间**负责"注册什么"的差量代数（Nop 已证明）
- **运行时结构空间**负责"结构如何激活/卸载"的可逆管理（DSH 已形式化）

## DSH vs Nop 全景对比

| 维度 | DSH | Nop |
|------|-----|-----|
| 可逆空间 | 运行时结构空间 | 编译期结构空间 |
| 逆的形式 | 闭包函数（不透明） | 结构差量 x-diff（声明式） |
| 坐标 | 服务名+隔离标签（平铺映射） | 路径坐标（tree 结构） |
| 负元素 | 无（单写者+累加） | 有（Delta 可正可负） |
| 响应式 | 有（reconciliation 主动触发） | 无（被动式缓存检查） |
| 时间静止 | epoch 检查 + inertia | 编译期天然时间静止 |
| 合并代数 | twisted composition | 声明式合并 |
| 定制粒度 | 插件整体替换 | 字段级 x-extends |
