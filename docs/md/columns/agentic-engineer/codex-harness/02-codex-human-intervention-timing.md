# Codex 核心团队复盘：从 30 秒一次反馈，到放手跑几小时

> **摘要**：基于 Every 对 Codex 团队的万字复盘，回答一个核心问题——**当 Agent 从 30 秒一次反馈变成可以独立跑几小时，人该在什么时候回来？** 答案是：**长任务没有取消反馈，只是改变了反馈的单位**。早期反馈动作（读了哪个文件、执行了什么命令），长任务该反馈**事件**（为什么停下、缺什么信息、哪个动作越过权限、方向是否要调整、最后拿什么证据验收）。文章用「数据库驱动升级」做工程示意，串起三块：Agent 负责执行、Runtime 保存状态并接住人的介入、测试/日志/制品负责证明结果。以及一条稳定交接链——**任务处于什么状态，为什么停下，人要决定什么，决定后从哪里继续，最后拿什么验收**。

## 变化的起点：30 秒一次反馈

2025 年 11 月，Codex 桌面 App 距离发布只剩几周，开发它的人白天仍然主要待在 VS Code 里。Alexander Embiricos 每天都会问一圈：今天有人把 App 当主力工具了吗？答案一直是"没有"。

这款 App 没有代码编辑器。想顺手改一行，工程师也得重新告诉 Agent。负责设计与工程的 Andrew Ambrosino 因此把"不允许直接改文件"看作发布前最大的疑点。

到了 12 月，团队的动作变了。原本希望加入编辑器的人，开始在 Diff 上留下行内评论，让 Codex 接着修改。Ambrosino 仍会指出方向，却很少再亲手补模型写出的代码。

**工程师没有停止看代码。变化在于，人的工作从亲手修改，转向处理偏差、权限和验收。**

## 不是少看几眼，而是换一种反馈

2024 年末，Embiricos 刚看到推理模型接入终端时，给产品定过一条标准：**用户每隔 30 秒、最多 1 分钟，就要知道模型做到哪里了。**

当时的模型走不了太远。读几个文件、跑一条命令、遇到一个报错，都可能把任务带偏。**人频繁查看，是在替系统保存方向。**

后来模型能处理跨文件修改，也能自己运行测试。把每条命令都推给人，反而会打断任务。可如果几个小时后只回来一句"完成了"，人也不敢直接合并。

> **长任务没有取消反馈，只是改变了反馈的单位。**

早期反馈的是**动作**：读了哪个文件，执行了什么命令。长任务更该反馈**事件**：为什么停下，缺什么信息，哪个动作越过权限，方向是否需要调整，最后有什么证据证明结果可用。

| | 短任务 | 长任务 |
|---|--------|--------|
| 反馈什么 | 动作 | 事件 |
| 人回来的时机 | 每 30 秒~1 分钟 | 信息不足、权限越界、方向变化、执行异常、等待验收 |

Codex 几次转向，表面上从 Cloud 走到 CLI、IDE 和桌面 App；底下反复修的，是**人离开以后，怎样重新接回同一条任务**。

## 第一版 Cloud 把执行搬走，也把人挡在了外面

2025 年春天，Codex 团队用了大约 7 周做出第一版 Cloud。开发者交出任务，Agent 在远端机器里读代码、改文件、跑测试。电脑可以合上，结果稍后再看。

这个设想在 OpenAI 内部跑得不错，放到外部却卡住了。

外部开发者先要把笔记本上的软件、权限、设置、凭证和依赖搬进云端。复盘里提到，这个准备过程可能耗掉几个小时。任务启动以后，如果 Agent 理解错了，用户也不能在原任务里补一句要求——**追加提示会拉起另一台云端机器。**

> 代码过去了，开发现场没有完整过去。任务一旦跑起来，人的手也伸不回原来的执行链。

```
提交任务 → 远端执行 →（方向偏了）→ 新开一台机器 → 返回结果
```

"云端配置麻烦"只是表面问题。异步执行要成立，**人离开前留下的目标、Agent 已经做过的尝试，以及人回来后的补充指令，得落在同一个任务状态里。** 少了其中一段，所谓"放手"只是把中途纠偏换成事后返工。

## 一次数据库驱动升级，会在哪儿把人叫回来

下面是**一条工程示意**（非 OpenAI 内部案例）。

开发者把一个任务交给 Agent：升级数据库驱动，并修复受影响的测试。Agent 先改驱动版本和锁文件，再调整连接池的兼容代码。单元测试通过后，它准备执行：

```bash
./scripts/test-migrations.sh
```

脚本需要读取沙箱外的 `/srv/shared/test-db.env`，任务停在了权限边界。

这时，如果界面只弹一句"需要审批"，开发者几乎没法判断。**审批请求至少要把这几件事摆出来：**

1. 准备执行 `./scripts/test-migrations.sh`
2. 将读取 `/srv/shared/test-db.env`
3. 驱动版本、锁文件和兼容层已经修改
4. 当前还没有执行迁移，也没有触碰共享数据库
5. 拒绝后保留现有改动，等待新的测试路径

开发者看完没有放开共享配置，而是补充一句："不要碰共享环境，改用仓库里的 `docker-compose.test.yml` 启动本地 PostgreSQL。"

Agent 保留前面已经完成的依赖和兼容代码修改，只调整测试夹具，从迁移测试继续。

验收时，开发者看到的是驱动版本、Diff 影响范围、迁移命令退出状态、单元测试与迁移测试结果，以及一份可检查的迁移日志，**不是一句"已完成"**。

> 这个过程中，开发者只被叫回来两次。第一次决定权限和测试路径，第二次验收结果。中间的文件读取、修改和重试，都由 Agent 完成。
>
> **少看了很多过程，不等于少了控制。控制被压缩到两个真正影响结果的时刻。**

## Runtime 要记住的，不只是聊天记录

Codex Cloud 受挫后，Tibo 接手工程团队，把重心转回本地 CLI。他没有先给终端堆功能，而是推动团队**用 Rust 重写底层 Agent**，把任务循环、工具调用、上下文和运行状态从界面里拆出来。

这个选择后来支撑了 CLI、IDE、桌面和手机。入口不同，下面接的是同一条任务链。

公开的 Codex App Server 接口已经能看出这条链怎样工作：

| 接口 | 作用 |
|------|------|
| `thread` | 保存任务及其历史 |
| `turn/steer` | 把补充要求送进正在运行的 Turn |
| `turn/interrupt` | 中断当前执行 |
| `thread/status/changed` | 执行状态变化时通知外层产品 |
| `thread/resume` | 人回来后恢复原来的 Thread |

回到数据库驱动的例子，系统至少要保住这几样东西：

- **原目标**：升级数据库驱动并修复受影响的测试
- **已完成**：驱动版本、锁文件、连接池兼容代码
- **当前停因**：迁移脚本申请读取 `/srv/shared/test-db.env`
- **人的决定**：拒绝共享配置，改用仓库内的本地 PostgreSQL
- **恢复位置**：保留已有改动，从迁移测试继续
- **验收要求**：Diff、退出状态、单元测试、迁移测试、迁移日志

> 如果这些状态只躺在某个界面的内存里，换到手机、重启客户端或中断一次，任务就要重新解释。**Runtime 把它们从界面中拿出来，人的补充才不是"再发一个 Prompt"，而是对当前执行的转向。**

Agent 控制面不是一块更复杂的任务看板。它先要回答四件事：**任务走到哪里，为什么停下来，人要决定什么，决定后从哪里继续。**

## 手机只接住那个决定

状态从界面里拆出来以后，手机入口才有用。

OpenAI 的 Remote Connections 文档写得很清楚：项目、文件、凭证、Shell、工具和执行环境仍在连接的电脑或远程主机上。手机可以继续任务、回答问题、补充要求、处理审批，也能查看 Diff、测试结果、终端输出和截图。

**它没有把 IDE 缩进一块小屏幕，而是把一个具体决定送到人手里。**

比如刚才那次迁移测试。开发者在排队或吃饭时，很难重新理解整个代码库，但看得懂这条命令要读哪份配置，也能决定改用本地测试容器。回到电脑后，再看完整 Diff 和测试记录。

通知如果只写"任务需要关注"，人还得重新翻上下文。**一个可处理的通知，至少要带上停因、已完成的动作、影响范围和可选路径。**

> 手机不是新的开发现场，它只是离人最近的控制入口。

## Goal 保存目标，证据决定结束

任务能持续几小时，也不等于一次 Turn 要无限延长。

Codex 的 Goal 是 Thread 范围的持久目标。一次 Turn 结束、Thread 空闲、没有待处理工作和排队输入时，系统才判断是否继续。中断会暂停目标；一次续跑没有调用工具，下一次自动续跑也会被抑制，避免原地空转。

放到数据库驱动升级里，Goal 可以一直保留"升级驱动并让相关测试通过"。中途换测试路径、重跑迁移或修兼容代码，都不用重新声明目标。

**但 Goal 不能替 Agent 宣布完成。**

- 预算用完，只能说明这次不能再跑
- Turn 结束，只能说明一轮执行结束
- 模型回复"已经修复"，也只是一句话

最终还得回到可检查的东西：驱动版本是否更新，Diff 有没有越界，迁移命令的退出状态是什么，单元测试和迁移测试是否通过，日志里有没有跳过或被忽略的失败。

> 长任务里有三件事不能混在一起：**Agent 负责执行，Runtime 保存状态并接住人的介入，测试、日志与制品负责证明结果。** 模型能力变强，扩张最快的是执行；人能不能放心离开，取决于后两块有没有跟上。

## 从 30 秒到几小时，变化的是人回来的理由

再看 Embiricos 最早那条"30 秒到 1 分钟"的要求，它并没有过时。

模型只能走几步时，人回来是为了看动作，防止它早早走偏。模型能独立跑几小时后，人不用看每次文件读取和命令执行，却仍要在几个节点回来：**信息不够、权限越界、方向改变、执行异常，以及结果等待验收。**

这段产品史不必归结为"本地战胜云端"，也不意味着桌面 App 会取代 IDE。入口还会变，模型能独立处理的任务也会继续变。

相对稳定的是一条交接链：

> **任务处于什么状态，为什么停下来，人要决定什么，决定后从哪里继续，最后拿什么验收。**

> **Agent 越能自己干活，人越不该被困在过程里。但每次被叫回来，都要有一个具体、可判断的理由。**
