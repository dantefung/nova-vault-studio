# 本体驱动的AI原生应用开发-个人ontology-driven-dev开源项目解读和说明

大家好，我是人月聊IT。今天再次介绍下个人的一个本体驱动的AI原生应用开发项目。这个项目已经开源，具体地址大家可以访问并下载，也欢迎大家fork和star。https://github.com/sharptoolbox/ontology-driven-dev一、它想解决的问题这两年用大模型写业务系统，几乎每个人都撞过同一堵墙。你给模型一段需求，它几分钟就能吐出一整套前后端代码，页面能跑、接口能通，看起来很唬人。但往前推两周，问题就来了：需求改了一句话，代码要改哪几处？没人知道。数据库字段叫 contract_type，前端下拉框的选项却散在一个常量文件里，模型里根本没有这层语义。等到项目跑到第二期，需求文档、数据模型和代码已经分成三张皮，谁也说不清哪一份是"对的"。根子不在模型不够强，而在于"业务语义"从头到尾没被当成一份可以被机器消费的正式资产。需求是人写的散文，代码是人写的程序，中间那层"业务由哪些对象、行为、规则、角色构成"的共识从没被沉淀下来，模型只能凭上下文去猜，于是每一轮生成都是一次重新猜。ontology-driven-dev 这个项目，就是冲着这堵墙去的。它给出的答案很朴素，也很硬：在需求和代码之间，钉死一层叫"本体模型"的东西，让需求变成模型、让模型生成代码，并且让运行时的 AI 也读同一份模型。它把这件事拆成三段——需求探索 → 本体建模 → 应用构建，做成了一套可以交给 AI 助手执行的技能包（Skill），能在 WorkBuddy、Claude Code、Codex、Cursor 等工具里跑起来。README 里有一句很能代表它气质的话：一套基于七模型本体 YAML 与内置技术底座、强制每个需求探索阶段人工确认、最终产出严格对齐需求文档、本体模型与代码的可运行浏览器前后端系统的开发技能。注意"强制人工确认"这五个字——它不是装饰，而是贯穿整个项目的纪律：AI 可以很快，但每一步的"业务真相"必须由人拍板，AI 不许替用户假设。二、整体骨架：三步法与五份规范整个项目是围绕一条强顺序的三阶段管线组织的。第一个阶段是需求探索，把一句话或一段描述煲成一份符合《软件需求编写规范 V9.0》的需求规格说明书；第二阶段是本体建模，把文档里已确定的业务语义翻译成七份 YAML 模型；第三阶段是应用构建，把七份模型落成一套能登录、能录入、能审批、能查询、右侧还挂着 AI 助理的可运行系统。三个阶段不能跳步，第一阶段内部八个子阶段每一个结束都必须停下来等人确认。支撑这条管线的是五份方法论文档，放在 references/ 下，它们是这个项目真正的"大脑"：AI需求探索与确认提示词V9.0.md 是第一阶段唯一的依据，内部完整收录了《软件需求编写规范 V9.0》全文；ontology_modeling_framework_v9.md 定义七个模型的元规范、字段语义和 YAML 模板；本体模型业务功能开发指导书.md 给出"模型元素落到代码哪个位置"的完整映射表和十步流水线；AI 原生应用技术架构设计文档.md 规定技术栈、分层、语义注册表与 AI 编排；UI-UE界面设计规范.md 把界面长什么样写死成可复用的 token 与 CSS 库。除了这五份规范，项目还带了三块"实物"：techbase/（code-paas 干净底座，复制一份就能扩展）、reference-example/（黄金范例：一份完整需求规格说明书加七份 YAML 加 HTML 原型）、code-app-example/（照着方法论真正跑起来的销售合同执行管理系统）。规范管"应该怎么做"，范例管"做出来长什么样"，底座管"从哪开始做"。三、第一步：需求探索，把散文变成契约需求探索这一阶段，是整个项目里最体现"克制"的部分。传统做法是把需求丢给 AI、让它直接写代码，项目认为这是错的：业务信息里有两类东西，性质完全不同。一类是行业通识（"合同通常有编号、名称、金额、签订时间"），AI 完全可以自己补全；另一类高度依赖企业的组织架构、管理制度和合规要求（"合同金额是否含税""某张单据要不要审批、谁来审批"），AI 一旦自行假设，就会生成一个逻辑上就错了的系统——字段命名风格不对无所谓，业务逻辑错了是灾难。于是有了贯穿全篇的 A 类 / B 类划分。A 类内容 AI 直接给出建议并标注"基于行业通用做法自动补全，请确认"，让用户快速扫一眼；B 类内容 AI 必须提问，而且不许只提问不给答案。项目规定了统一的提问格式，任何问题都要同时给出明确建议、建议理由、其他选项和快捷回复方式，用户可以只回一句"按 AI 建议"就过——这看似小事，实际很关键：它把用户回答问题的成本压到最低，同时又不让 AI 替用户做决定。这套提问长这样：问题N：[需要用户确认的问题]AI建议：[明确的建议答案]建议理由：[为什么推荐该答案，以及它对业务模型的影响]其他选项：A. [备选答案及影响]B. [备选答案及影响]请回复"按AI建议"、选项字母，或直接说明修改意见。八个子阶段依次是：阶段零总体理解确认，阶段一业务对象，阶段二业务功能与规则，阶段三跨对象联动识别，阶段四端到端协同流与审批流，阶段五查询统计与固定报表，阶段六岗位角色与功能权限，阶段七可选的 UI 原型探索（必须用户先明确说"需要"，否则不得擅自产出界面内容）。这里面有两个设计我认为特别值得说。第一个是规则归属的唯一性。项目明确规定不是所有规则都进规则模型：只依赖单个属性值的约束写进属性自带的 refRules（"合同总金额必须大于 0"就写成 value &gt; 0），绝不允许为它单独建一条 M3 规则；依赖同一对象多个属性或聚合内部子实体的约束进对象级 invariants（如"付款阶段比例合计等于 100"）；只有真正跨对象、跨行为、或者需要被多个行为复用的判断，才进 M3。这条规定把一个常见的坏习惯按死了——为了让模型"看起来很完整"而到处堆规则，结果是同一条业务判断在三个地方各写一遍，改一个漏两个。第二个是跨对象联动被单独拎出来当一个阶段。项目规定阶段三是强制且独立的，不许并进业务功能梳理里顺手处理。一句"合同收款完成后如全部收齐则关闭合同"，表面上是一件事，实际上藏着两个独立对象和一条跨对象因果链；如果不专门拆解，很容易被简化成"收款行为里顺手把合同也改了"——而项目的纪律是：行为只操作一个对象，跨对象联动必须通过 syncTriggers 显式声明，条件判断必须引用 M3 规则，规则只判断、不改状态。 这条边界是后面所有代码能保持干净的前提。需求探索的终态是一份 &lt;业务域&gt;-需求规格说明书-V9.md，必须对照规范里 47 项自检全部通过、附录 B 里不残留任何 [待确认] 项，才能标记为"完整（可进入本体建模阶段）"。文档里还有一个附录 C：七模型建模输入基线，把对象、行为、规则、角色、流程、查询报表、界面都按模型的语言整理成确定性输入——也就是说，第二阶段不是重新理解业务，而是拿着这份基线做"翻译"。四、第二步：本体建模规范，七个正交的模型本体建模是这个项目的心脏，规范叫《本体驱动的软件建模方案》，当前版本 9.0。v9.0 是从更早的 v6.0 裁剪来的，裁剪的方向很明确——面向"单体同步部署的中小型业务系统"。它移除了四个模型（事件模型 ME、场景模型 M4、对象-数据表映射模型 MM、接口模型 MI），把原来的事件驱动架构换成了同步编排：M2 行为里新增 syncTriggers 字段来表达"行为成功后同步调用下游行为"，M3 规则里去掉了事件驱动那一类，M6 流程里去掉了事件触发和事件等待。所以现在剩下七个模型，编号是 M1、M2、M3、M5、M6、M7、MU，编号不连续是有意保留的，方便跟历史版本和工具链对齐。七个模型各自的职责是这样的。M1 对象模型 是地基，描述业务世界里"存在什么"，用领域驱动设计（DDD）的语言组织：聚合根是业务完整性的边界和对外唯一入口，子实体不能脱离聚合根独立存在，值对象无标识、靠值判断相等。合同和它的付款条款明细属于同一聚合（同生共死），合同和开票属于两个独立聚合（通过 ID 引用关联）。属性类型体系里，AggregateRootRef 表示"存储另一个聚合根 ID 的标量属性"，DictionaryRef 表示"值来自数据字典、保存 code 显示 label"——数据字典也在 M1 里定义，字典项保存稳定的 code、界面显示 label，已使用项应停用而非删除。M2 行为模型 定义"能做什么"，最核心的约束是原子性：每个行为只做一件事、只操作一个对象、产生确定性的状态变更。行为分 COMMAND（改状态）和 QUERY（只读），触发方式分 USER_ACTION（用户点按钮）和 SYSTEM（系统自动）。这里有一个重要的语义分工：行为只回答"做什么、改变什么状态"，规则只回答"条件是否满足"，联动关系由 syncTriggers 显式声明——规范禁止把"全部收齐时关闭合同"这类条件结论写进源行为本身，必须拆成"一条 M3 关闭校验规则 + 一个目标关闭行为"。看看合同案例里收款行为的声明方式，就能明白这套语义边界是怎么落到纸面的：- id:Receipt_Recordname:录入收款ownerEntity:AGG-RECEIPT-001behaviorType:COMMANDtriggerType:USER_ACTIONpostconditions:    -field:receipt.status      setValue:"已收款"appliedRules:    -RULE-RECEIPT-AMOUNT-CHECKsyncTriggers:    -ruleRef:RULE-CONTRACT-CLOSE-CHECK      behaviorRef:Contract_Close      description:收款录入后检查合同是否全部收齐，满足则同步关闭合同M3 规则模型 只处理超出单个对象边界的判断，分验证、计算、推导、转换、风控五类；规则是无副作用的被动组件，一律被行为同步调用，不主动订阅任何东西，也不直接改状态，且支持独立版本管理。M5 主体模型 解决"谁能做什么"，以 RBAC 为基础、支持 ABAC 扩展：角色是权限的集合单元且支持继承，权限粒度到行为级，并带数据范围（ALL / OWN / DEPT / CUSTOM）和 ABAC 条件表达式（如 actor.dept == resource.dept）。v9.0 把它裁剪到只保留内部角色与权限。M6 流程模型 承载 COLLABORATION 端到端协同流和 APPROVAL 审批流两类流程，有一条硬约束——所有人工活动和审批活动的参与人只能通过 roleRef 引用 M5 的角色，不许引用具体人、也不许填"财务经理"这种自由文本。审批节点的不同结果通过边上的 approval_outcome（APPROVE / REJECT / RETURN）区分，网关至少两个分支、最多一个默认分支，子流程调用图不许成环。M7 查询统计与报表模型 承载跨对象的查询和固定报表，分详情查询、列表查询、统计分析、固定报表四类。它的依赖约束很干净：只与 M1 和 M2 直接发生关系，每个 M7 对象必须绑定且只绑定一条 M2 QUERY 行为，两者严格一对一；M7 不引用规则、角色或流程，查询条件和聚合公式属于查询对象自身的定义。还有个容易忽略的细节：两个以上一对多明细来源同时参与聚合时，必须先用 preAggregation 按关联键分别汇总再关联，禁止用 SUM(DISTINCT amount) 去凑结果。MU UI 模型 是入口层和追溯层，层级是"总体界面 → 一级菜单 → 二级菜单 → UI 界面 → 操作功能点"。菜单固定两级，一级菜单只做分组、必须至少带一个二级菜单，只有二级菜单关联具体屏幕；屏幕分单表维护、列表维护、主从表维护、查询列表四类，用等宽 ASCII 图表达布局。控件类型由 M1 属性类型固定映射：日期用日期控件、枚举和数据字典用下拉框、对象引用（AggregateRootRef）用"跳选框"（文本框显示目标对象名称 + 按钮弹出选择对话框）、布尔用复选框、长文本用多行文本域。还有一条硬规定：带审批流的功能界面创建时必须提供"保存草稿"和"提交"两个独立按钮，分别对应两个 M2 行为，不许合并成一个"保存"。MU 里有一个我认为是整个项目最精巧的设计：它是纯引用层，不重新定义任何语义。 MU 只通过稳定 ID 引用 M1～M7，也不承载配色、字体、像素级布局这些视觉内容——那些属于 UI-UE 规范。这样一来，"用户点哪个按钮 → 调用哪个行为 → 操作哪个对象 → 应用哪条规则 → 需要哪个权限"这条链路全程由稳定 ID 串起，既能被机器追踪、也能被人核对。七个模型之间还有明确的依赖和引用关系，规范把它们整理成一张矩阵，并在建模后设了强制的一致性门禁：USER_ACTION 行为必须被至少一个 MU 操作功能点引用（防止"孤儿行为"）；M7 的 behaviorRef 与 M2 的 queryReportRef 必须双向一致、严格一对一；M6 的各路引用必须都存在且子流程调用图无环。建模顺序也有推荐路径：M1 对象 → M5 角色 → M3 规则 → M2 行为 → M7 查询 → M5 权限 → M6 流程 → MU 界面。五、第三步之一：开发指导书，模型到代码的落地点如果说本体建模规范定义了"业务语义长什么样"，那么开发指导书解决的是一句更实操的话：拿到七份 YAML，代码到底写在哪。指导书开篇就立了一条规矩——底座不动。技术底座 code-paas 是只读基线，新功能一律先整体复制成 code-app 再开发，后续所有扩展都只在 code-app 里做。这样底座永远干净，出问题可以随时回退对照。接下来是全篇最重要的那张表：模型 → 实现映射总表。M1 的聚合根落成主表、子实体落成从表（外键 {master_alias}_id），属性类型映射到 SQL 类型和表单控件；M2 的 COMMAND 行为落成 services/*_service.py 里一个事务内的方法，USER_ACTION 行为落成前端一个按钮，syncTriggers 落成方法成功后的同步调用；M3 规则落成规则引擎求值；M5 落成 sys_role / sys_permission / sys_user_role 这套系统管理表；M6 的活动和分支落成 flow_definition.node_graph（JSON 的 nodes + edges）；M7 落成查询 service；MU 落成 sys_resource 菜单加前端路由和页面。围绕这张表，指导书还把几条容易踩坑的强制约定写死了。第一条是编号自动生成：业务编号由系统生成，界面不显示不可编辑，规则是"对象别名大写取前三位 + 四位流水号"（合同 CON0001、开票 INV0001），且必须在同一事务内生成以免并发重号。第二条是五默认字段：任何业务表必须追加 created_by、created_at、updated_by、updated_at、flag 五个字段，界面不显示、写入时自动赋值，删除一律走逻辑删除（flag=0），查询默认只返回 flag=1。第三条是主从表单的单事务与从表外键自动赋值：先插入主表拿到主键，再为每个从表行自动写入 {master}_id（不让用户填），整套操作在同一事务里完成，任一失败整体回滚。第四条是规则必须完整实现，不许只建模不落地：属性级 refRules 与聚合级 invariants 在 service 保存时校验，跨对象规则走 simpleeval 规则引擎在行为执行中或联动条件里求值，失败必须给用户明确的中文提示。除此之外，指导书还规定了权限码命名（{域}:{对象}:{动作}）、统一响应格式（{ success, message, data, errorCode, traceId }）、前端页面约定，并给出十步标准流水线：写七模型 YAML → 登记 manifest → 生成 DDL → 注册数据字典 → 实现行为与规则 → 配置角色权限种子 → 配置流程引擎 → 配置菜单页面 → 实现右侧 AI 对话 → 全链路联调验收。注意第九步是"强制实现 AI 对话"——在这个项目里，AI 助理不是可选装饰，而是每个由此产出的系统的标配。六、第三步之二：技术架构，一套 AI 原生的底座技术架构文档定义的是这套系统的"骨架"，选型克制到有点固执：后端 Python + Flask，单体分层、不拆微服务；数据访问直接 sqlite3、不引入 ORM；前端 React 18 + TypeScript + Vanilla CSS + Vite；图表固定 ECharts；大模型走 OpenAI 兼容协议，Base URL、API Key、模型 ID 全部通过界面配置，可接 DeepSeek 也可接通义或智谱。分层从下往上依次是：本体模型层（七份 YAML，只表达语义）→ 语义注册层（Ontology Registry）→ 后端服务层（Flask API、行为、查询、规则、SSE）→ AI 编排层（意图识别、能力路由、工具调用、渲染）→ 前端 Hybrid UI 层 → 数据存储层（SQLite）。这里面有两个概念是这个项目最核心的原创设计。第一个是本体模型的三重角色。本体模型不只是文档载体，它在系统里同时是业务建模载体、程序生成基础、以及 AI ## 一、它想解决的问题



这两年用大模型写业务系统，几乎每个人都撞过同一堵墙。



你给模型一段需求，它几分钟就能吐出一整套前后端代码，页面能跑、接口能通，看起来很唬人。但往前推两周，问题就来了：需求改了一句话，代码要改哪几处？没人知道。数据库字段叫 contract_type，前端下拉框的选项却散在一个常量文件里，模型里根本没有这层语义。等到项目跑到第二期，需求文档、数据模型和代码已经分成三张皮，谁也说不清哪一份是"对的"。



根子不在模型不够强，而在于"业务语义"从头到尾没被当成一份可以被机器消费的正式资产。需求是人写的散文，代码是人写的程序，中间那层"业务由哪些对象、行为、规则、角色构成"的共识从没被沉淀下来，模型只能凭上下文去猜，于是每一轮生成都是一次重新猜。



ontology-driven-dev 这个项目，就是冲着这堵墙去的。它给出的答案很朴素，也很硬：在需求和代码之间，钉死一层叫"本体模型"的东西，让需求变成模型、让模型生成代码，并且让运行时的 AI 也读同一份模型。



它把这件事拆成三段——需求探索 → 本体建模 → 应用构建，做成了一套可以交给 AI 助手执行的技能包（Skill），能在 WorkBuddy、Claude Code、Codex、Cursor 等工具里跑起来。README 里有一句很能代表它气质的话：一套基于七模型本体 YAML 与内置技术底座、强制每个需求探索阶段人工确认、最终产出严格对齐需求文档、本体模型与代码的可运行浏览器前后端系统的开发技能。



注意"强制人工确认"这五个字——它不是装饰，而是贯穿整个项目的纪律：AI 可以很快，但每一步的"业务真相"必须由人拍板，AI 不许替用户假设。



## 二、整体骨架：三步法与五份规范



整个项目是围绕一条强顺序的三阶段管线组织的。



第一个阶段是需求探索，把一句话或一段描述煲成一份符合《软件需求编写规范 V9.0》的需求规格说明书；第二阶段是本体建模，把文档里已确定的业务语义翻译成七份 YAML 模型；第三阶段是应用构建，把七份模型落成一套能登录、能录入、能审批、能查询、右侧还挂着 AI 助理的可运行系统。三个阶段不能跳步，第一阶段内部八个子阶段每一个结束都必须停下来等人确认。



支撑这条管线的是五份方法论文档，放在 references/ 下，它们是这个项目真正的"大脑"：AI需求探索与确认提示词V9.0.md 是第一阶段唯一的依据，内部完整收录了《软件需求编写规范 V9.0》全文；ontology_modeling_framework_v9.md 定义七个模型的元规范、字段语义和 YAML 模板；本体模型业务功能开发指导书.md 给出"模型元素落到代码哪个位置"的完整映射表和十步流水线；AI 原生应用技术架构设计文档.md 规定技术栈、分层、语义注册表与 AI 编排；UI-UE界面设计规范.md 把界面长什么样写死成可复用的 token 与 CSS 库。



除了这五份规范，项目还带了三块"实物"：techbase/（code-paas 干净底座，复制一份就能扩展）、reference-example/（黄金范例：一份完整需求规格说明书加七份 YAML 加 HTML 原型）、code-app-example/（照着方法论真正跑起来的销售合同执行管理系统）。规范管"应该怎么做"，范例管"做出来长什么样"，底座管"从哪开始做"。



## 三、第一步：需求探索，把散文变成契约



需求探索这一阶段，是整个项目里最体现"克制"的部分。



传统做法是把需求丢给 AI、让它直接写代码，项目认为这是错的：业务信息里有两类东西，性质完全不同。一类是行业通识（"合同通常有编号、名称、金额、签订时间"），AI 完全可以自己补全；另一类高度依赖企业的组织架构、管理制度和合规要求（"合同金额是否含税""某张单据要不要审批、谁来审批"），AI 一旦自行假设，就会生成一个逻辑上就错了的系统——字段命名风格不对无所谓，业务逻辑错了是灾难。



于是有了贯穿全篇的 A 类 / B 类划分。A 类内容 AI 直接给出建议并标注"基于行业通用做法自动补全，请确认"，让用户快速扫一眼；B 类内容 AI 必须提问，而且不许只提问不给答案。项目规定了统一的提问格式，任何问题都要同时给出明确建议、建议理由、其他选项和快捷回复方式，用户可以只回一句"按 AI 建议"就过——这看似小事，实际很关键：它把用户回答问题的成本压到最低，同时又不让 AI 替用户做决定。

八个子阶段依次是：阶段零总体理解确认，阶段一业务对象，阶段二业务功能与规则，阶段三跨对象联动识别，阶段四端到端协同流与审批流，阶段五查询统计与固定报表，阶段六岗位角色与功能权限，阶段七可选的 UI 原型探索（必须用户先明确说"需要"，否则不得擅自产出界面内容）。



这里面有两个设计我认为特别值得说。



第一个是规则归属的唯一性。项目明确规定不是所有规则都进规则模型：只依赖单个属性值的约束写进属性自带的 refRules（"合同总金额必须大于 0"就写成 value &gt; 0），绝不允许为它单独建一条 M3 规则；依赖同一对象多个属性或聚合内部子实体的约束进对象级 invariants（如"付款阶段比例合计等于 100"）；只有真正跨对象、跨行为、或者需要被多个行为复用的判断，才进 M3。这条规定把一个常见的坏习惯按死了——为了让模型"看起来很完整"而到处堆规则，结果是同一条业务判断在三个地方各写一遍，改一个漏两个。



第二个是跨对象联动被单独拎出来当一个阶段。项目规定阶段三是强制且独立的，不许并进业务功能梳理里顺手处理。一句"合同收款完成后如全部收齐则关闭合同"，表面上是一件事，实际上藏着两个独立对象和一条跨对象因果链；如果不专门拆解，很容易被简化成"收款行为里顺手把合同也改了"——而项目的纪律是：行为只操作一个对象，跨对象联动必须通过 syncTriggers 显式声明，条件判断必须引用 M3 规则，规则只判断、不改状态。 这条边界是后面所有代码能保持干净的前提。



需求探索的终态是一份 &lt;业务域&gt;-需求规格说明书-V9.md，必须对照规范里 47 项自检全部通过、附录 B 里不残留任何 [待确认] 项，才能标记为"完整（可进入本体建模阶段）"。文档里还有一个附录 C：七模型建模输入基线，把对象、行为、规则、角色、流程、查询报表、界面都按模型的语言整理成确定性输入——也就是说，第二阶段不是重新理解业务，而是拿着这份基线做"翻译"。



## 四、第二步：本体建模规范，七个正交的模型



本体建模是这个项目的心脏，规范叫《本体驱动的软件建模方案》，当前版本 9.0。



v9.0 是从更早的 v6.0 裁剪来的，裁剪的方向很明确——面向"单体同步部署的中小型业务系统"。它移除了四个模型（事件模型 ME、场景模型 M4、对象-数据表映射模型 MM、接口模型 MI），把原来的事件驱动架构换成了同步编排：M2 行为里新增 syncTriggers 字段来表达"行为成功后同步调用下游行为"，M3 规则里去掉了事件驱动那一类，M6 流程里去掉了事件触发和事件等待。所以现在剩下七个模型，编号是 M1、M2、M3、M5、M6、M7、MU，编号不连续是有意保留的，方便跟历史版本和工具链对齐。



七个模型各自的职责是这样的。



M1 对象模型 是地基，描述业务世界里"存在什么"，用领域驱动设计（DDD）的语言组织：聚合根是业务完整性的边界和对外唯一入口，子实体不能脱离聚合根独立存在，值对象无标识、靠值判断相等。合同和它的付款条款明细属于同一聚合（同生共死），合同和开票属于两个独立聚合（通过 ID 引用关联）。属性类型体系里，AggregateRootRef 表示"存储另一个聚合根 ID 的标量属性"，DictionaryRef 表示"值来自数据字典、保存 code 显示 label"——数据字典也在 M1 里定义，字典项保存稳定的 code、界面显示 label，已使用项应停用而非删除。



M2 行为模型 定义"能做什么"，最核心的约束是原子性：每个行为只做一件事、只操作一个对象、产生确定性的状态变更。行为分 COMMAND（改状态）和 QUERY（只读），触发方式分 USER_ACTION（用户点按钮）和 SYSTEM（系统自动）。这里有一个重要的语义分工：行为只回答"做什么、改变什么状态"，规则只回答"条件是否满足"，联动关系由 syncTriggers 显式声明——规范禁止把"全部收齐时关闭合同"这类条件结论写进源行为本身，必须拆成"一条 M3 关闭校验规则 + 一个目标关闭行为"。



看看合同案例里收款行为的声明方式，就能明白这套语义边界是怎么落到纸面的：



M3 规则模型 只处理超出单个对象边界的判断，分验证、计算、推导、转换、风控五类；规则是无副作用的被动组件，一律被行为同步调用，不主动订阅任何东西，也不直接改状态，且支持独立版本管理。



M5 主体模型 解决"谁能做什么"，以 RBAC 为基础、支持 ABAC 扩展：角色是权限的集合单元且支持继承，权限粒度到行为级，并带数据范围（ALL / OWN / DEPT / CUSTOM）和 ABAC 条件表达式（如 actor.dept == resource.dept）。v9.0 把它裁剪到只保留内部角色与权限。



M6 流程模型 承载 COLLABORATION 端到端协同流和 APPROVAL 审批流两类流程，有一条硬约束——所有人工活动和审批活动的参与人只能通过 roleRef 引用 M5 的角色，不许引用具体人、也不许填"财务经理"这种自由文本。审批节点的不同结果通过边上的 approval_outcome（APPROVE / REJECT / RETURN）区分，网关至少两个分支、最多一个默认分支，子流程调用图不许成环。



M7 查询统计与报表模型 承载跨对象的查询和固定报表，分详情查询、列表查询、统计分析、固定报表四类。它的依赖约束很干净：只与 M1 和 M2 直接发生关系，每个 M7 对象必须绑定且只绑定一条 M2 QUERY 行为，两者严格一对一；M7 不引用规则、角色或流程，查询条件和聚合公式属于查询对象自身的定义。还有个容易忽略的细节：两个以上一对多明细来源同时参与聚合时，必须先用 preAggregation 按关联键分别汇总再关联，禁止用 SUM(DISTINCT amount) 去凑结果。



MU UI 模型 是入口层和追溯层，层级是"总体界面 → 一级菜单 → 二级菜单 → UI 界面 → 操作功能点"。菜单固定两级，一级菜单只做分组、必须至少带一个二级菜单，只有二级菜单关联具体屏幕；屏幕分单表维护、列表维护、主从表维护、查询列表四类，用等宽 ASCII 图表达布局。控件类型由 M1 属性类型固定映射：日期用日期控件、枚举和数据字典用下拉框、对象引用（AggregateRootRef）用"跳选框"（文本框显示目标对象名称 + 按钮弹出选择对话框）、布尔用复选框、长文本用多行文本域。还有一条硬规定：带审批流的功能界面创建时必须提供"保存草稿"和"提交"两个独立按钮，分别对应两个 M2 行为，不许合并成一个"保存"。



MU 里有一个我认为是整个项目最精巧的设计：它是纯引用层，不重新定义任何语义。 MU 只通过稳定 ID 引用 M1～M7，也不承载配色、字体、像素级布局这些视觉内容——那些属于 UI-UE 规范。这样一来，"用户点哪个按钮 → 调用哪个行为 → 操作哪个对象 → 应用哪条规则 → 需要哪个权限"这条链路全程由稳定 ID 串起，既能被机器追踪、也能被人核对。



七个模型之间还有明确的依赖和引用关系，规范把它们整理成一张矩阵，并在建模后设了强制的一致性门禁：USER_ACTION 行为必须被至少一个 MU 操作功能点引用（防止"孤儿行为"）；M7 的 behaviorRef 与 M2 的 queryReportRef 必须双向一致、严格一对一；M6 的各路引用必须都存在且子流程调用图无环。建模顺序也有推荐路径：M1 对象 → M5 角色 → M3 规则 → M2 行为 → M7 查询 → M5 权限 → M6 流程 → MU 界面。



## 五、第三步之一：开发指导书，模型到代码的落地点



如果说本体建模规范定义了"业务语义长什么样"，那么开发指导书解决的是一句更实操的话：拿到七份 YAML，代码到底写在哪。



指导书开篇就立了一条规矩——底座不动。技术底座 code-paas 是只读基线，新功能一律先整体复制成 code-app 再开发，后续所有扩展都只在 code-app 里做。这样底座永远干净，出问题可以随时回退对照。



接下来是全篇最重要的那张表：模型 → 实现映射总表。M1 的聚合根落成主表、子实体落成从表（外键 {master_alias}_id），属性类型映射到 SQL 类型和表单控件；M2 的 COMMAND 行为落成 services/*_service.py 里一个事务内的方法，USER_ACTION 行为落成前端一个按钮，syncTriggers 落成方法成功后的同步调用；M3 规则落成规则引擎求值；M5 落成 sys_role / sys_permission / sys_user_role 这套系统管理表；M6 的活动和分支落成 flow_definition.node_graph（JSON 的 nodes + edges）；M7 落成查询 service；MU 落成 sys_resource 菜单加前端路由和页面。



围绕这张表，指导书还把几条容易踩坑的强制约定写死了。



第一条是编号自动生成：业务编号由系统生成，界面不显示不可编辑，规则是"对象别名大写取前三位 + 四位流水号"（合同 CON0001、开票 INV0001），且必须在同一事务内生成以免并发重号。



第二条是五默认字段：任何业务表必须追加 created_by、created_at、updated_by、updated_at、flag 五个字段，界面不显示、写入时自动赋值，删除一律走逻辑删除（flag=0），查询默认只返回 flag=1。



第三条是主从表单的单事务与从表外键自动赋值：先插入主表拿到主键，再为每个从表行自动写入 {master}_id（不让用户填），整套操作在同一事务里完成，任一失败整体回滚。



第四条是规则必须完整实现，不许只建模不落地：属性级 refRules 与聚合级 invariants 在 service 保存时校验，跨对象规则走 simpleeval 规则引擎在行为执行中或联动条件里求值，失败必须给用户明确的中文提示。



除此之外，指导书还规定了权限码命名（{域}:{对象}:{动作}）、统一响应格式（{ success, message, data, errorCode, traceId }）、前端页面约定，并给出十步标准流水线：写七模型 YAML → 登记 manifest → 生成 DDL → 注册数据字典 → 实现行为与规则 → 配置角色权限种子 → 配置流程引擎 → 配置菜单页面 → 实现右侧 AI 对话 → 全链路联调验收。



注意第九步是"强制实现 AI 对话"——在这个项目里，AI 助理不是可选装饰，而是每个由此产出的系统的标配。



## 六、第三步之二：技术架构，一套 AI 原生的底座



技术架构文档定义的是这套系统的"骨架"，选型克制到有点固执：后端 Python + Flask，单体分层、不拆微服务；数据访问直接 sqlite3、不引入 ORM；前端 React 18 + TypeScript + Vanilla CSS + Vite；图表固定 ECharts；大模型走 OpenAI 兼容协议，Base URL、API Key、模型 ID 全部通过界面配置，可接 DeepSeek 也可接通义或智谱。



分层从下往上依次是：本体模型层（七份 YAML，只表达语义）→ 语义注册层（Ontology Registry）→ 后端服务层（Flask API、行为、查询、规则、SSE）→ AI 编排层（意图识别、能力路由、工具调用、渲染）→ 前端 Hybrid UI 层 → 数据存储层（SQLite）。



这里面有两个概念是这个项目最核心的原创设计。



第一个是本体模型的三重角色。本体模型不只是文档载体，它在系统里同时是业务建模载体、程序生成基础、以及 AI 推理的知识底座（运行时 prompt 的结构化语义来源）。第三重角色最有意思——同一份 YAML 既用来生成代码，又被喂给大模型当作业务知识的权威来源，从根上解决了"AI 不懂你的业务"：它不需要猜，因为业务语义被显式注入了上下文。



第二个是运行时语义注册表 Ontology Registry。系统启动时先解析全部 YAML，构建一张内存语义索引（对象、子实体、数据字典、行为、规则、角色、权限、流程、查询报表、界面、菜单、数据库白名单），供 API 层、AI 编排层、前端元数据接口和只读 SQL 控制器共用。它是"一份模型，多处消费"的物理实现点：加载时按 model_type 分派，把各模型分别注册进对应索引，顺手生成数据库白名单。



AI 编排层的系统提示词每次对话都动态拼装：业务域概述、本体模型语义（对象字段、行为、规则、流程）、只读 API 能力清单、完整的数据库表结构（连字段中文标签和表关联关系都写进去），最后一层是行为准则。摘一段本体语义部分的拼装：



行为准则里有一条特别值得讲：统计、聚合、按条件汇总、自定义列查询必须由 AI 自己构造只读 SQL（NL2SQL）通过 readonly_sql_query 动态查询，禁止用返回固定列的报表工具，以免返回无关列。 这条规定承认了一件事：固定查询工具覆盖不全即席提问，与其硬凑一堆报表，不如把"能安全地跑自由 SQL"做好，再放手让 AI 用。能力路由优先级因此被定成：行为 API → 标准查询 → 只读 SQL → 语义解释。



而"能安全地跑自由 SQL"这件事由 sql_readonly/ 用一整套边界守住：只允许 SELECT、只允许白名单表、强制追加 LIMIT（默认 200）、禁止多语句、正则拦截 insert / update / delete / drop / alter / truncate 等关键字、执行超时、记录审计日志。核心校验就是十几行代码，但该堵的口都堵上了：



AI 对话的流式输出走 SSE，协议切成六个分片（message_start → delta → tool_call → tool_result → render_payload → message_end），前端按分片增量拼接文本、展示"正在查询…"这类状态、最后切换成结构化渲染。渲染协议只有四种：text、table、chart（固定 ECharts）、action（引导打开页面或执行行为）。工具也由注册表自动生成 schema。



还有一个设计很能代表这个项目的气质：Hybrid UI——既不是纯固定菜单，也不是纯聊天机器人。高频、确定性、结构化的操作给固定页面，低频、探索式、临时性的需求交给 AI 对话区；两者共用同一后端能力层和同一套设计系统，AI 对话框里渲染的表格和主工作区里查出来的表格被视为同一设计系统下的两个容器。



## 七、UI/UE 规范，把"长什么样"也变成可复用的资产



UI-UE 规范这份文档的定位很清楚，它和 MU 模型是分工关系：MU 决定"有哪些界面、每个界面有哪些字段和按钮"，规范决定"这些界面长什么样、如何排布、用什么样式"。 前者是语义，后者是视觉。



规范整体走的是"紧凑专业"的路线：全局 9pt 字体，信息密度高，接近传统企业级桌面系统的观感；表单是标签右对齐、控件左对齐的表格化布局；卡片扁平化，圆角归零、无阴影，靠边框和底色分层；配色是深色导航栏加品牌蓝 #2266e3 贯穿。



三栏结构是最先定下来的框架：顶栏深色、左菜单 250px 两级、中间多标签工作区、右侧 400px 可拖拽调宽的 AI 对话区，两侧都可显隐。规范特别强调"即使某一级菜单下只有一个二级菜单，也必须保留两级结构"——这份固执和 MU 模型里"一级菜单必须至少包含一个二级菜单"是同一条纪律。



表单布局是最见功力的一条：标签列固定宽度 96px、右对齐，控件左对齐，形成规整的"标签列 + 控件列"网格。三类界面布局同样是硬规则——单表一行 2 个控件、备注占满整行；主从表主表一行 3 个控件、从表在下方表格内完成新增维护删除；查询列表条件在上、结果表格在下并支持分页。控件类型映射与 MU 完全一致，带审批的界面必须"保存草稿"和"提交"两个独立按钮。



规范最后还给了一整套可直接复用的东西：完整 CSS 变量表、完整样式库，以及五段 TSX 骨架。说白了，它把"界面长什么样"也从提示词里抽出来，变成一份可以反复调用的资产。



## 八、参考案例：把方法论跑成一套能点的系统



规范再好看，不能跑起来也没用。这个项目很实在的地方，是它带了一套完整的、能跑的实物——销售合同执行管理系统。



这套案例的交付物是咬合在一起的三份东西。一份是 reference-example/合同管理需求规格说明书-V9.md，真正走完八阶段探索、状态标记为"完整"的需求文档，六个部分加三个附录齐全（功能清单、用例图、业务规则按 REF / INV / R 分层列、状态机图、跨对象联动矩阵、两条协同流的 Mermaid 图、五张固定报表、角色权限矩阵），最后是附录 C 的七模型建模输入基线。第二份是同一目录下的七份 YAML 加 manifest.json，把文档"翻译"成模型。第三份是 code-app-example/，照着模型真正实现出来、能登录能审批能查报表的前后端系统。



业务本身不复杂但足够有代表性：管的是"已经线下签字盖章完成"的销售合同，从登记开始，覆盖付款阶段、开票、收款、内部审批和查询统计，涉及十个对象、十四个业务功能（FUNC-01～FUNC-14）、五张查询报表（REP-01～REP-05）、六个角色，外加两条协同流和两条审批流。



其中最能体现"本体驱动"价值的，是那条跨对象联动链。业务上它只是一句话：财务人员录入一笔收款，系统自动重算开票收款状态，再判断合同是否全部收齐，收齐就自动结清。 在本体模型里它被拆成完整一条链：FUNC-07 录入收款 → B-02 更新开票收款状态 → R-10 合同结清校验规则 → B-03 更新合同结清状态——收款和合同关闭是两个独立聚合上的两个行为，靠 syncTriggers 声明联动、靠 M3 规则判断条件。需求文档里连"联动失败怎么办"都确认清楚了：源业务事实仍然成立，下游状态进入"待处理"并自动重试，不因联动失败回滚源事实。



审批也一样完整：合同登记按金额分级（财务经理先审，满 100 万元再走总经理），开票审批是财务经理单节点，两条都确认了驳回与撤回路径，并都加了职责分离规则 R-09（提交人不得审批自己提交的单据）——这些判断不是写死在代码里，而是从需求文档确认、到 M3 规则定义、到流程引擎网关求值一路贯下来的。



跑起来是这样：销售填合同、暂存、提交；财务经理在待办里通过或驳回，金额够大自动流转总经理；财务录开票、录收款，收款一提交，开票和合同状态跟着变；报表中心看三张固定报表。右侧的 AI 助理，问"按部门统计合同总金额"会自己写 SQL 画成柱状图，问"合同维护在哪个菜单"会给出可点的跳转按钮。



案例还带了两份很别致的产物。一份是单文件自包含的高保真可交互原型 HTML，把需求文档里的界面意图直接变成能点的页面。另一份在 界面调用链/ 下，是一个"UI 调用链追踪工作台"：读七份 YAML 后生成一个可沿引用逐级穿透的可视化工具——从一个界面出发，看它有哪些元素和操作，点某个操作会调用哪个行为，这个行为属于哪个对象、应用哪些规则、需要什么权限、关联哪张报表、由哪个角色承担。它最狠的一点是数据完全驱动，所有 ID、名称、关系全部从 YAML 读出来——这其实就是在用可视化验证：模型里的引用链是不是真的自洽、完整。



## 九、这套方式的核心价值和优势



把上面这些串起来看，这个项目的价值不在某个单点技术，而在于它把"AI 写业务系统"从一次性生成变成了可追溯、可验证、可演进的工程过程。我觉得至少有这么几层优势是实打实的。



语义有了唯一来源，模型和代码不再两张皮。 数据库表、接口、菜单、权限、流程、规则全部可以回溯到某个本体模型元素，不存在"模型一套、代码一套"；改需求就是改 YAML，代码和模型始终同步——项目把它写成了一条不可违反的纪律。



需求是"确认"出来的，不是"假设"出来的。 八阶段加人工门禁把 B 类业务信息拉回到用户面前，每个问题都带 AI 建议，既不让人被问题淹没，也不让 AI 越权拍板；附录 B 里没有残留的 [待确认] 项，文档才算完整。



七模型正交分解，让复杂系统的每一面都能被单独讨论和演进。 对象归对象、行为归行为、规则归规则，跨对象联动有 syncTriggers、跨对象读取有 M7、界面入口有 MU，同一件事不会被写三遍。更大的好处是可测试——每条一致性门禁都是一次机器能跑的检查。



AI 是真的"原生"进来了，而且是安全的。 AI 不是事后补的聊天框，从提示词构建、工具注册、能力路由、流式渲染到只读 SQL 白名单，整套都围绕"让 AI 复用同一套业务能力"设计：写操作一律不碰、引导用户去固定页面，读操作优先走标准 API、必要时走严格受限的只读 SQL，所有工具调用记录审计日志。



交付完整、技术栈不绑死。 走完三步法，手里有一份需求规格说明书、一套七模型 YAML、一套能跑的系统、可选一份 UI 原型和一张调用链工作台；技能不依赖 WorkBuddy 专有机制，主流 AI 编程工具都能跑；底座选的是最没脾气的组合——Flask + SQLite + React，单体、无 ORM。



## 十、边界与实话



一个负责任的解读，不能只讲好话。这个项目的边界，规范文档自己写得很清楚，值得照实转述。



它面向的是单体同步部署的中小型业务系统，比如合同管理、资产管理、CRM 这类。v9.0 明确移除了事件驱动架构，跨对象协作走同步调用和流程编排，追求"链路顺序、可预测、可调试"，而不是分布式解耦。如果你的业务是大型分布式、强事件驱动、需要独立 BI 数仓和指标平台，这套模型不是为它准备的——M7 明确声明自己不是 BI 指标模型。



它也有明确的"框架外"清单：对象到数据库表的映射由实现阶段的 DDL 落地，性能容量可用性这类非功能需求不在七模型里，视觉样式、动画、多端适配属于设计系统。换句话说，七模型不是一份完整 SRS 的唯一物理载体——它覆盖"系统做什么、核心业务为何如此运转、用户如何驱动系统"，至于"达到什么质量目标、如何部署运行"，仍需配套规格文档。



还有一层门槛：这套方法的价值建立在"使用者愿意先花时间把业务想清楚"这个前提上，八阶段探索、每步人工确认、逐条核对门禁都不是零成本。需求本身就模糊的话，再好的建模框架也救不了；但如果是一个边界清晰、要长期演进、还要能被 AI 持续接手维护的业务系统，这套三步法省下的时间和踩掉的坑会相当可观。



## 结语



ontology-driven-dev 最打动我的地方，是它没有把希望寄托在"模型再强一点就好了"上面，而是回到软件工程的根上——先把业务语义固化成一份可被机器消费的正式资产，再让需求、模型、代码和运行时的 AI 都围着这份资产转。



它给出的三步法——需求探索、本体建模、应用构建——本质上是在给"AI 时代的业务系统开发"补上一条缺失的中间层：不是让人更快地写散文，也不是让模型更快地吐代码，而是让整个团队（包括 AI）对"这个业务到底长什么样"拥有一份共同的、可追溯的、能被验证的认知。



这份认知，才是 AI 原生应用真正的地基。
