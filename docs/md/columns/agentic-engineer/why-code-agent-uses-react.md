# 拼多多三面实录：为什么 Code Agent 用 ReAct，不用 Plan-Execute、Multi-Agent、CoT、ReWOO、LLMCompiler

> **摘要**：一道真实的大厂面试题——「Code Agent 主流范式是什么？为什么工业级普遍用 ReAct，而不是 Plan-and-Execute、Multi-Agent、CoT、ReWOO、LLMCompiler？」核心判断：**Code Agent 要在庞大代码仓库里完成调试、重构、bug 修复，场景本身的特性筛选出了适配度最高的主循环范式**，其余范式只能作为局部补充组件。**ReAct**（ICLR 2023）把推理、工具执行、环境观测绑成闭环，五大工程组件配套（结构化工具调用/按需上下文/轻量动态规划/可验证反馈闭环/人在回路）。**纯 CoT 两个死穴**：幻觉突出（类名签名依赖版本都不在权重里）、缺少校正反馈。**规划类范式的边界**：代码信息逐步涌现，提前写的计划容易失效——「Plan-and-Execute 适合信息充足的建造任务，ReAct 适合信息未知的诊断调试任务」。**纯 Multi-Agent 三项成本吃掉收益**：上下文传递损耗、故障排查复杂度、收益持续递减。最终形态是**混合架构**：ReAct 内核 + 可选前置规划层。

## 一、这是一道高频面试题

蚂蚁、字节、阿里这类大厂，很多面试官喜欢问 Code Agent 相关问题：

- 当前工业界 Code Agent，主流基础设计模式是什么？
- Plan-and-Execute、多智能体、CoT 都是成熟 Agent 范式，为什么它们没有成为 Code Agent 的核心底座？

> **Code Agent 和通用问答、文案创作不一样。** Code Agent 要在庞大的代码仓库里，完成调试、新增功能、重构、bug 修复。
>
> **场景本身的特性，筛选出适配度最高的主循环范式**；其余范式只能作为局部补充组件，很难成为整套体系的核心骨架。

## 二、ReAct 循环：思考-行动-观测

ReAct 出自 ICLR 2023 论文《ReAct: Synergizing Reasoning and Acting in Language Models》。它打破了早期大模型仅靠内部链式推理的局限，把**推理、工具执行、环境观测绑定成闭环**。

**ReAct 标准三步循环：**

1. 模型基于已有观测做推理决策，输出下一步动作
2. 调用标准化工具在沙箱执行动作
3. 采集报错、文件内容、命令输出作为观测，更新全局状态，进入下一轮推理，直到任务完成或判定无法继续

**以修复登录接口 500 报错为例：**

| 轮次 | 推理 | 行动 | 观测 |
|------|------|------|------|
| 1 | 报错大概率在鉴权链路，检索 login 相关文件 | grep 检索 | 定位 auth.py |
| 2 | 读取 auth.py 查看校验逻辑 | view 读文件 | 发现缺少字段空判断 |
| 3 | 查找函数上游调用链 | 检索调用关系 | 上游无入参校验，存在空值传入风险 |
| 4 | 补充空值判断，修改代码并跑单元测试 | str_replace 改源码、执行 pytest | 拿到测试结果，持续迭代直到用例全部通过 |

**整套流程没有提前写死的固定步骤，每一步决策完全依赖上一步真实观测，不存在一份不可修改的全局执行清单。**

### 成熟 Code Agent 配套的五大工程组件

**第一，结构化工具调用层。** 文件读写、检索、shell、git 操作全部封装为强结构 Function Call，不允许模型自由输出危险脚本。以 Claude Code 的 `str_replace` 为例，传入路径、原文片段、替换文本，由沙箱安全执行，配套权限拦截、日志审计。

**第二，按需上下文管理。** 业务仓库动辄几十万、上百万行代码，超出大模型上下文上限。ReAct 天然适配增量拉取，Agent 不会一次性加载全仓库，而是按需检索、读文件、看函数片段，控制 token 开销，缓解长上下文遗忘——**和工程师排查问题思路一致**。

**第三，轻量动态规划组件。** 复杂任务可以生成 TODO 清单辅助推理，**但清单不是固化总计划**。比如新增邮箱注册功能，初始 TODO 包含加字段、发邮件逻辑、接口、前端、测试；**如果观测到数据库已有对应字段，直接删除这条任务**，动态调整，不会僵化执行过时计划。TODO 只是辅助记忆，不是流程核心。

**第四，可验证反馈闭环。** 这是代码场景独有的机器可读客观反馈：编译报错、静态扫描、单元测试、集成测试结果，信息精确到代码行。TypeError、AttributeError 这类报错可以直接送入下一轮推理，形成修改-验证-修正的自校正链路。**这也是 ReAct 在代码场景收益远高于通用场景的关键。**

**第五，人在回路安全机制。** rm、强制推送等高风险操作不会自动执行，强制人工确认。

> **ReAct 不排斥规划，它排斥一次性全局固化规划。** 轻量动态规划属于 ReAct 内部增强插件，不等于 Plan-and-Execute 范式。

## 三、为什么纯 CoT 无法支撑工业级 Code Agent

链式思维 CoT 依靠模型内部分步推理直接输出结果，全程不调用外部工具、不和环境交互，信息来源只有模型权重和用户输入上下文。早期直接让模型写代码，就是典型纯 CoT。

**纯 CoT 有两个难以根治的短板，在代码场景会被放大：**

**（1）幻觉突出。** 代码正确性强依赖仓库私有事实——类名、函数签名、依赖版本、历史逻辑都不在模型权重里。模型只能靠先验推测，经常虚构函数、错误入参、过时 SDK，一旦仓库和训练数据不一致，输出直接失效。

**（2）缺少校正反馈。** 推理闭环完全封闭，代码输出后模型感知不到编译、测试报错。很多 bug 根因藏在多层调用链，仅靠用户一句报错描述，内部推理很难穷举所有可能性。

CoT 并非一无是处：**独立小脚本、算法题、短 Demo，信息全部在 prompt 内，纯 CoT 效率高、token 更少。** 但只要需要读存量代码、调试报错、理解工程结构，可靠性就快速下滑，只能作为局部推理增强，不能做主循环。

> **ReAct 对比纯 CoT 的核心升级：把推理从模型封闭空间，迁移到和真实代码环境联动的开放闭环，依靠外部观测抑制幻觉，依靠测试反馈完成自校正。**

## 四、Plan-and-Execute、ReWOO、LLMCompiler 的能力边界

Plan-and-Execute 是经典两阶段范式：先一次性拆解任务生成完整有序执行清单，再按顺序执行，**规划阶段不再介入**。

BabyAGI 是早期代表，后续衍生 ReWOO、LLMCompiler，同属规划路线迭代版本。

- **ReWOO** 优化原版 Plan-and-Execute，拆分规划、工具调用、结果汇总，减少 LLM 调用次数，降低 token 消耗
- **LLMCompiler** 更进一步，不再输出串行步骤，生成 DAG 有向无环图，识别可并行子任务，缩短整体耗时

### 核心痛点：代码任务的不确定性

**代码信息是逐步涌现的。** 规划阶段 Agent 还没有读代码、跑测试，信息缺口很大，提前写好的计划很容易偏离真实情况。执行后遇到意料之外的代码结构、依赖、报错，原有计划直接失效。此时只有两条路：

- **频繁全量重规划**——开销和延迟超过原生 ReAct
- **无视新观测强行执行旧计划**——产出无效操作，甚至破坏代码

> 举个例子：计划修改 UserService 增加校验逻辑，读取文件后发现模块已经重构，逻辑迁移到 AccountService。原版计划失效，反复重规划之后，**本质上就退化成 ReAct 的逐步决策模式**，全局计划失去意义。

### 边界总结

规划系范式有适合的场景：**信息完备、路径确定、分支少、子任务可并行**，比如脚手架初始化、标准化 CRUD、模板批量迁移。LLMCompiler 的 DAG 并行在这类场景吞吐量更高、更省 token。

SWE-bench 评测也印证：**简单确定任务，LLMCompiler 表现不输甚至优于 ReAct；复杂调试、跨模块根因排查，ReAct 优势明显。**

> **一句话总结边界：Plan-and-Execute 家族适合信息充足的"建造任务"；ReAct 适合信息未知、需要探索的"诊断调试任务"。**
>
> 而 Code Agent 日常高频需求，恰恰是 bug 修复、存量代码理解、增量改造这类探索型任务——这也是 ReAct 成为主流的核心原因。

## 五、为什么纯 Multi-Agent 收益有限

纯多智能体思路依靠角色拆分分工：架构师 Agent 做方案拆分、编码 Agent 落地、测试 Agent 收集报错、评审 Agent 审核，角色之间消息协同。MetaGPT 是典型项目。

理论上分工解耦、各司其职，但在强耦合的代码仓库里，**三项成本会快速抵消收益**：

**（1）上下文传递损耗。** 理解代码依赖大量细节，隐式依赖、兼容逻辑、历史坑很难压缩。Agent 之间只能传递摘要，关键约束丢失，很容易出现转述失真，写出错误代码；**耦合越高，摘要失真越严重**。

**（2）故障排查复杂度高。** 单 Agent 只需要追踪一条 ReAct 轨迹；多 Agent 故障可能来自分工、消息丢失、时序冲突、状态不同步，**定位协同问题的成本，经常高于修复业务代码**。

**（3）收益持续递减。** 当前主流强模型本身同时具备读码、推理、改代码、解析报错能力，很多任务单 Agent 就能闭环。强行拆分角色，只会增加多轮调用、拉高延迟和 token，准确率提升幅度很小。

### 工业界的折中方案

不是抛弃多 Agent，而是**放弃长期常驻多角色团队，采用「主 ReAct Agent + 临时 Sub-Agent」轻量化模式**，Claude Code 的 Sub-Agent 就是典型。

主 Agent 持续跑 ReAct 主循环；遇到独立、可隔离、结果可摘要的任务（比如全仓库检索废弃 API、批量统计埋点），才派短期子 Agent 执行，拿到摘要后子 Agent 直接销毁。

> **Sub-Agent 本质是 ReAct 循环里的特殊工具，不是对等长期协作的智能体。**

## 六、ReAct 原生短板，以及行业改良思路

ReAct 并非完美，核心痛点集中三点：

1. **长任务目标漂移**
2. **容易陷入局部最优**
3. **步数爆炸**

原因：循环次数变多，历史观测不断灌入上下文，Agent 容易卡在细节调试、遗忘顶层需求；token 和延迟持续上涨。同时 **ReAct 是贪心决策，只看当前观测选下一步，缺少全局视角**，容易走进无效探索分支。

**ReCode 就是针对这些痛点的改良方向：**

- 把规划和动作统一用 Plan-and-Execute 表达
- 用结构化 Multi-Agent 任务图替代松散自然语言 TODO
- 给长任务增加全局约束

> **它不是替换 ReAct，而是在 ReAct 外层增加结构化规划层，属于混合范式路线。**

## 七、主流 IDE / Code Agent 实际采用了哪些范式

对照商业化产品落地，可以验证前面的结论：

- **ReAct 是主流 Agent IDE 的底层底座**
- **Plan-and-Execute 大多封装成可选前置 Plan 模式**，作为增强能力，不做主循环
- **ReWOO、LLMCompiler 大多停留在学术框架、内部编排引擎**，没有主流 IDE 把它们作为产品主范式

**GitHub Copilot Agent、Cursor Agent Mode、Claude Code、Cline、Aider，内核都是 ReAct 思考-行动-观测循环。**

微软官方文档把 Copilot Agent 定义为 think→act→observe，依托 Function Call 操作文件、终端；arXiv 基于 GitHub 千万级流量的论文也验证，工具调用和 LLM 推理耦合，是标准 observe-reason-act 链路。

**Cline 虽然标注 Plan-and-Act，只是增加前置规划，修改调试的主循环依旧是 ReAct。**

Plan-and-Execute 没有消失，而是变成**可选预览模式**：Cursor Plan、Claude Code Plan，Agent 先只读探索仓库、输出改动方案，等待用户确认后才执行。但**执行阶段不会死板遵守计划**，遇到新信息依然动态调整，底层还是 ReAct。

**Devin 采用 planner + executor 双模型，支持中途重规划，并非固定一次性计划。**

ReWOO、LLMCompiler 很少直接落地 IDE，它们的思路被拆解吸收：ReWOO 节约 token 的思路用于内部优化；LLMCompiler 的 DAG 并行适合脚手架、批量迁移、CI 配套工具。**IDE 场景需求不确定性强、探索分支多，很难提前构建 DAG，所以很难成为主流程。**

> **整体产品版图很清晰：没有单一范式的商业化 Code Agent。行业统一方案是 ReAct 内核 + 可选前置规划层的混合架构。**
>
> Plan 模式是面向用户的方案预览，降低大规模改动风险；**ReAct 循环才是处理未知问题、调试报错、动态探索的执行引擎**。

## 八、大总结

**Code Agent 范式之争不存在绝对最优解，选型核心是匹配场景约束：**

| 范式 | 适合场景 |
|------|---------|
| 纯 CoT | 简单独立代码生成 |
| LLMCompiler、Plan-and-Execute | 信息完备、路径固定的模板开发 |
| 长期多角色 Agent | 边界清晰的大型方案推演 |
| **ReAct** | **存量代码理解、bug 排查、增量改造这类占比最高的场景，天然是 ReAct 的舒适区** |

**回到开篇面试题，一套完整有深度的回答框架：**

1. 先点明主流底座是 ReAct，解释思考-行动-观测闭环
2. 抛出代码任务三大核心约束
3. 依次分析 CoT、Plan-and-Execute、多智能体在约束下的局限性
4. 同时说明各自适用场景，结合主流 IDE 落地案例佐证
5. 最后点明工业界是混合架构，ReAct 作为内核，其余范式作为局部增强组件
