# Trust Doesn't Live in Code Review：当 Agent 写代码时如何做审查

> 来源：raft.build

## 1. 为什么传统 Review 开始吃力？

Review 的价值来自对代码深入、鲜活的理解。亲自编写、调试、修改代码，是建立这种理解的过程。

一个已经不再亲自编写代码的人，也很难保持足够深入的理解，从而有效地 Review 它。

## 2. 那人还怎么对项目负责？

大型项目的负责人，原本就不会逐行阅读自己负责的所有代码。我们也不会因此认为他们不负责任。

他们的信任来自：**团队、架构、测试、线上表现，以及对整个系统的持续理解**。

Agent 时代，让更多开发者进入了这个位置。说白了就是**像 CTO/Tech Lead 一样去把控项目**。

## 3. 审查的重心该放在哪里？

### 1. 系统是否仍然可预测

单个改动正确、测试全部通过，也可能同时积累重复状态、模糊边界和复杂依赖。直到你无法预测，改了这里，那里会发生什么。

### 2. 看 Bug 的分布

哪些模块反复出错？哪些接口不断冒出新的边界情况？这些记录能帮助定位系统的问题。

### 3. 看结构和协作

哪里分支过多？同一份事实是否存了两遍？多个 Agent 是否反复在同一个边界上发生冲突？

### 4. 验证检查本身

故意改错一个条件，测试能否发现？真正的回归能否让测试变红？

没有报警，也要先确认报警机制确实有效。

## 4. 发现问题以后怎么办？

追溯产生失败的条件：
- 需求是否漏了情况？
- 接口是否容易误解？
- 环境是否缺少验证手段？

修复 Bug，同时补上防止它再次出现的测试。条件允许时，调整类型和设计，让这类错误无法发生。

**把代码阅读更多交给掌握实现细节的 Agent。人继续负责方向、取舍和控制，通过系统持续发出的信号建立信任，再把每次失败转化为更清晰的约束。**
