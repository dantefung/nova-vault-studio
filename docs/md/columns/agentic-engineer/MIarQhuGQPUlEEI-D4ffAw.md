# 「大家用 AI 胆子还不够大！」Anthropic 工程经理亲授 4 种顶级用法

> **摘要**：Felix Rieseberg（Anthropic 工程经理）把「更有野心」的 AI 用法拆成四个方向——**Speed**（把原来的事做快）、**Altitude**（别派活，先说结果）、**Depth**（别学专家说话，要学专家干活）、**Range**（把别的行业方法借进来）。四种用法不是并列技巧，都在扩大同一件事：**AI 对结果承担到哪一步**。任务边界扩大，系统就要补上数据、工具、状态、环境、验证、回滚和人工接管。仍有三件事必须由人决定：什么结果值得追求、什么代价不能接受、什么时候已经够好。

```markmap height=420
# AI 更大胆的用法
## Speed 做快
- 改邮件/补接口/整理报表
- 人已选好路，AI 只执行
- 省时间，不接路径选择
## Altitude 说结果
- 修崩溃 → 让应用保持稳定
- 季度复盘层层上提
- 验收要看数据库不只看对话
### 配套系统
- 会话=只追加事件日志
- Harness=调用+转发+恢复
- Sandbox=跑代码，坏了可换
## Depth 学专家干活
- 用原始材料不摘要
- 接数据库和统计模型
- 目标设 200ms 逼出真问题
- 提问：谁来证明结果对
## Range 借别行方法
- 把名词改成动作
- 分析师/记者/编辑/做空者
- 借方法不借腔调
- 多 Agent 要不同材料+不同责任
## 为什么不敢放手
- 自我效能感影响尝试
- 熟练用户：自动批准 20%→40%
- 熟练用户：打断率 5%→9%
- 自治范围=可验证可撤回的程度
```

> Felix Rieseberg 参与 Claude 的开发，却几乎每天还会遇到自己没想过的用法。他是 Anthropic 工程经理，曾负责 Claude.ai、Cowork 和 Claude Code Desktop 的工程工作。

有些结果，他原本觉得做不到；有些路径，则来自他从未考虑过的方向。

这些意外让 Felix 注意到，**AI 没有发挥出来，有时不是模型已经到了头，而是人一开始只交给它一件小活。**

我们让 AI 改一封邮件、补一个函数、做几页 PPT。任务被切成小块，步骤由人提前定好，AI 只是把执行环节做快。至于为什么做、还有没有别的办法、结果能不能直接拿去用，仍然留给人处理。

Felix 把这个问题说得很直白：**大家用 AI 的胆子还不够大。**

他说的不是把权限开满，让 Agent 一口气跑到天亮。所谓"胆子大一点"，是别急着替 AI 写完所有步骤，先把真正想要的结果交代清楚。任务往上提一层，AI 才有机会换方法、用工具、查原始数据，并承担更多路径选择。

Felix 把这种"更有野心"的用法拆成四个方向：**Speed、Altitude、Depth 和 Range。**

## 第一种：Speed，把原来的事做快

写邮件、补接口、整理材料、更新报表，AI 只是把同一件事做快。这是 Speed，也是大家最熟悉的一层。

这类任务里，人已经选好了路。要改哪段代码、表格填哪几列、PPT 放哪几页，AI 负责执行。它省下的是时间，没有接手多少路径选择。

很多工作做到这里就够了。有些任务还能再往上交一层：不只交动作，也交结果。

## 第二种：Altitude，别派活，先说结果

从"修这个崩溃"到"让应用保持稳定"，改变的是任务高度。

2025 年初，Felix 还在让 Claude 修一个个应用崩溃。哪里出错，就把那条报错交给它。后来，他把任务改成了一句话：**让应用保持稳定。**

前者有明确入口，修完、测试通过，任务结束。后者没有现成清单。Claude 要持续查看新报告，判断优先级，选择修复路径，并决定何时继续、何时暂停并请人判断。

这不是把提示词缩短就能做到。Felix 先改了工作流，让 Claude 能读取崩溃报告，查出故障版本对应的 Git 提交，再到 Windows、macOS 和 Linux 上复现。改完以后，它还得验证崩溃是否消失，有没有带来新的问题。**缺一项，"保持稳定"都只是一句愿望。**

### 季度业务复盘的层层上提

常见做法是把数据和模板交给 AI，让它更新数字、补图表。

- 往上一层：让它先查清本季度发生了什么、为什么发生、下一步该做什么
- 再往上一层：让它找出管理层需要决定的三个问题，准备每个选择的依据、反对意见和未知风险
- 还可以继续问：季度复盘本来是为了尽早发现问题，把钱和人放到合适的位置。既然如此，能不能根据历史数据设计一套预警办法，先和现有复盘并行跑一个季度？

**PPT 还在，但它不再是任务本身，只是过程中的一个产物。**

Felix 有个判断办法：**做完之后，是不是还要开会讨论，再安排下一步？** 如果是，可以把"会后要解决什么"一起交给 AI。

目标也不能空到只剩一句"把产品做好"。目标抬高以后，完成条件、禁区、回滚办法和人工接管点也要一起写清楚。否则，Agent 拿到的只是一句更大的口号。

### 指令越短，系统要补的东西越多

"保持应用稳定"会跨过多份报告、多次修复和多套环境。任务跑久以后，状态不能只放在模型的上下文里，执行环境也不能坏一次就丢掉全部进度。

Anthropic 公开 Managed Agents 架构时，讲过他们早期踩到的一个问题：**会话记录、Harness 和 Sandbox 全塞在同一个容器里。** 容器一旦失效，会话也跟着丢；工程师只能进机器排查，到底是 Harness、网络连接还是执行环境出了问题。

后来，他们把三者拆开：

| 组件 | 职责 | 故障处理 |
|------|------|---------|
| 会话 | 保存成只追加的事件日志 | 进度有地方保存 |
| Harness | 调用 Claude 和转发工具请求 | 崩溃后可从日志恢复 |
| Sandbox | 只负责运行代码和修改文件 | 坏了就换一个 |

初始化 Sandbox 时，系统用仓库令牌拉取代码，并把认证接到本地 Git remote；MCP 的 OAuth 令牌则保存在外部保险库。Claude 可以执行 pull、push 和调用 MCP，却拿不到令牌本身。

三者拆开以后，进度有地方保存，权限有明确边界，坏掉的执行环境也能单独替换。**人不再逐条发命令，系统就要负责保存进度、隔离权限和恢复环境。**

### 结果验收不能只看对话

Anthropic 在 Agent 评测指南里举过订票的例子：Agent 说"票已订好"，只能证明它生成了这句话。验收程序还要查询数据库，确认预订记录存在。

代码任务也一样。"问题已修复"不是证据。**测试结果、界面截图、性能基准和上线指标，才是修复是否生效的证据。**

把 Altitude 放到工程里，会多出这样一条运行链：

> 目标上移之后，难点不在提示词。原来由人盯住的状态、环境和验收，要由系统补上。

## 第三种：Depth，别学专家说话，要学专家干活

很多人想把结果做得更专业，会先给 AI 加一个身份："请扮演一位有 20 年经验的专家。"

这通常只能改变说法，不能改变做法。输入还是一份整理过的摘要，输出还是一篇看起来完整的分析。

**Felix 所说的 Depth，不是换一套专家措辞，而是换成专家使用的原始材料、工具和方法。**

假设团队认为用户流失来自新手引导：

- 浅一层的做法，是把汇总表交给 AI，让它解释原因
- 深一层的做法，是给它原始日志、交易记录和用户行为，让它**先尝试推翻**"新手引导导致流失"这个判断

如果它只能用 Markdown 表格，就接上数据库和统计模型。验证了已有判断之后，再让它寻找团队还不知道的早期信号，并在没有见过的数据上检验这个信号。

性能优化也是同一回事。把加载时间从 10 秒降到 5 秒，可能只会得到几项常规修改；**把目标设为 200 毫秒**，Agent 就得重新检查数据路径、缓存、网络往返和架构假设。200 毫秒未必能实现，但它会逼出原任务没有触及的问题。

### Felix 的提示词

> 我要的是更深的任务，不是更大的任务。先说说，这个领域的顶尖专业人士还会做哪些我没有要求的工作；他们会从哪些原始材料开始；会用什么方法和工具；除了你和我，还有什么能证明结果是对的。然后按这些答案重写任务。

这段提示词最后问：**谁来证明结果是对的？**

执行任务的 Agent 可以提出方案，不适合独自给方案盖章。数据库终态、编译器、测试程序、性能基准和证明检查器，都比模型的自我评价可靠。

在 Anthropic 一项形式化验证项目中，Claude 生成了约 10 亿行 Rocq 候选证明，其中约 1.8 亿行通过独立检查器，覆盖 123 个开源库的 239 个入口。

**10 亿行是生成量，1.8 亿行才是通过量。** 候选证明不能靠文字解释过关，Rocq 检查器会按规格逐项验证。

这也不等于"代码没有 Bug"。证明只能覆盖给定规格、运行环境和假设；规格漏掉的情况，检查器也不会替人补上。**独立检查器提高了证据强度，没有消除规格边界。**

日常开发不需要动用形式化验证。单元测试、集成测试、真实命令输出、截图和流量回放，足以把不少"我做完了"变成可检查的结果。

## 第四种：Range，把别的行业方法借进来

Felix 建议**先把名词改成动作**。季度复盘如果被定义成"一份 PPT"，常会变成写稿、制图和排版。

换一种说法，它是在 30 分钟内，让一群忙碌的人理解业务变化和因果关系，并在信息不完整时作出决定。

任务改成动作后，方法也跟着变了：

| 角色 | 方法 |
|------|------|
| 分析师 | 查数据 |
| 记者 | 核来源和因果 |
| 编辑 | 删掉没有证据的结论 |
| 做空者 | 寻找公司不愿面对的问题 |
| 法证会计师 | 追数字之间的矛盾 |

需要现场呈现，再加入动效和声音设计。

给五个 Agent 分配五种角色，再让它们读同一份摘要，**只会得到五种口吻。** "记者 Agent"要回到原始来源，区分亲历与转述，核对谁在什么时间说了什么。

做空者的价值也不在语气尖锐。它要主动查反证、利益关系和被忽略的风险。**借方法，不借腔调。**

Felix 看到同事 Alex Albert 用 Blender 渲染室内设计，才想到让 Claude 为自己的主页制作 3D 场景。Felix 做过游戏，却也没有把 Blender 和个人主页连在一起。

**多开几个 Agent 还不算 Range。** 不同 Agent 得拿不同材料、使用不同方法，并承担不同责任。有人实现，有人找反例；有人读取原始数据，有人只检查最终证据。协调者可以分配工作，不能顺手替验收者宣布通过。

## 为什么我们还是习惯给 AI 派小活

Felix 用心理学里的"自我效能感"解释这件事：人对自己能力的判断，会影响他是否愿意尝试。

- **1939 年**，George Dantzig 上统计课迟到，把黑板上的两道题当成作业抄走并解了出来。交上答案后，他才知道那是尚未解决的统计学问题
- **1954 年 5 月**，Roger Bannister 首次跑进四分钟一英里。46 天后，第二个人也做到了

这些故事不能证明只要相信就会成功。它们说明，**人一旦认定某条路走不通，尝试本身就不会发生。**

模型和工具在变，我们给它的任务还停在"润色一封邮件""补一个函数"。它已经能读代码、运行程序、操作软件和查询数据，我们却仍按聊天框的方式使用它。

Felix 所说的"胆子大一点"，是重新检查这条能力边界。**这条边界要和验证、纠错一起调整。**

## 熟练用户为什么放手更多，也打断更多

Anthropic 分析 Claude Code 的真实使用情况时，发现了一组看似矛盾的数据。

使用不足 50 个会话的新用户，约 20% 的会话开启完全自动批准；用户累计到约 750 个会话时，这个比例超过 40%。

熟练用户也更常打断 Claude。使用约 10 个会话的用户，会在约 5% 的交互轮次中主动打断；经验较多的用户约为 9%。任务复杂度上升后，Claude 主动停下来请求澄清的次数也会上升。

**熟练用户不再逐条批准，而是在方向偏离、证据不足或影响范围扩大时介入。**

这组数据来自软件工程场景，不能直接套到所有行业。软件改动便于比较，通常也能用测试和 Git 回滚。错误发现得快、操作能撤回、过程有记录，Agent 就可以多走几步。

如果错误要到月底才暴露，操作无法撤销，最后只能相信模型的总结，**自治范围就该收小**。

从架构上看，Agent 能走多远，不只取决于模型。**模型找路，工具执行，Harness 保存状态和控制节奏，验证器检查结果，人保留目标、偏好和不可逆决定。**

> 系统能验证多少、撤回多少，Agent 才适合自行决定多少。

## 顶级用法不是一条神奇提示词

四种用法不是四个并列技巧，它们都在扩大同一件事：**AI 对结果承担到哪一步。**

- **Speed** 让原任务更快
- **Altitude** 把任务抬到结果
- **Depth** 把工作压到原始材料和专业方法
- **Range** 把其他行业的工具和观察方式引进来

任务边界扩大，系统就要补上数据、工具、状态、环境、验证、回滚和人工接管，不能只靠模型自己想办法。

**有三件事仍要由人决定：什么结果值得追求，什么代价不能接受，什么时候已经够好。**

把结果说清，把工具和证据接上，再让 AI 多走一段。走偏时，能叫停，也能回到上一个可靠状态。
