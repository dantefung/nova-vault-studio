# 透析 Skill 与 Tool 底层：Agent 两大核心底座的关系

> **摘要**：以 QwenPaw 为样本，从0到1拆透 Agent 的两层底座。**工具底座（Runtime 执行层）**回答"函数能不能安全跑起来"——四段链路：**注册**（裸函数不注册，注册的是套了 `PolicyGuardedTool` 治理壳的 `FunctionTool`）/ **查找**（按名寻址，**fail-closed**，未注册直接拒）/ **注入**（`BootstrapFactory` 统一装配，MinIO+ETag 支持热刷新）/ **执行**（**四道独立校验门**：技能体检→渠道准入→策略裁决→参数安检）。**技能底座（资产管理层）**回答"能力能不能被模型识别、按需分发"——只托管不执行，管技能包全生命周期。两者关系是**技能在上、工具在下，单向向下交付**；技能底座管"能力入口"，工具底座守"执行出口"，**装配期允许 ≠ 运行时放行**。

## 第一部分：从0到1吃透 Agent 工具底座

### 1. 引子：工具底座的核心工作

Agent 要真正动手干活，离不开工具调用：跑 shell、读写文件、发消息、调 MCP 服务。

工具底座就是承载这些能力的运行基座，负责回答四类问题：

1. 工具怎么进来（**注册**）
2. Agent 怎么找到它（**查找**）
3. 工具怎么进入 Agent 的运行环境（**注入**）
4. 工具怎么被安全执行（**执行**）

**这四件事就是工具底座的完整闭环。** QwenPaw 把它拆成四段链路：注册中心做资产登记、Workspace 装配做能力注入、LLM 决策做工具选择、三重门治理做执行安全。

### 2. 工具注册：把业务函数变成可调用的 Agent 资产

**注册的本质**，是把一段普通业务函数包装成 Agent 可以识别、可以调用、可以治理的标准工具对象。注册要回答三个问题：

| 要素 | 作用 |
|------|------|
| `name` | Agent 查找的唯一标识 |
| `schema` | 给 LLM 看的接口契约，说明入参出参 |
| `func` | 真实执行逻辑 |

#### 2.2 注册的同时，挂载治理壳

QwenPaw 的一个关键设计：**注册工具时不注册裸函数，而是注册一个被"治理壳"包装过的工具。**

`PolicyGuardedTool` 用动态 `type()` 构造 `FunctionTool` 子类，把 `check_permissions`、`__call__` 这些治理方法真实挂在类上。业务工具在注册时自动获得「策略拦截 + 审批闭环」能力，**工具内部不需要手写任何权限逻辑**。

#### 2.3 注册的两种形态

- **函数工具注册**——代码内置的工具，启动时统一登记
- **技能包注册**——技能就是 SKILL.md + scripts 目录，存放在对象存储（如 MinIO），按需加载进运行环境

前者是静态注册，后者是动态加载，二者共同构成 Agent 的能力资产池。

### 3. 工具查找：Agent 如何定位可用工具

查找的起点是 **LLM 的决策**——模型在推理过程中根据任务上下文决定调用哪个工具，输出工具名 + 入参。底座的查找逻辑就是拿着这个工具名去注册表定位对象。

一个核心细节是 **fail-closed（闭包安全 / 失败即关闭）**：未注册的工具，查找阶段直接拒绝，而不是猜测执行。治理层面这属于"类型检查"第一关——Phase0 遇到未知工具直接 DENY，理由写清楚"未注册工具"。

查找还要解决"**谁有资格调用**"。`ChannelACL` 就是干这个的：白名单直通、黑名单拒绝、陌生人进入 pending 审批队列。

> 一个被拉进 Telegram 群的 Bot，不该等于把整台机器交出去——命令无害但发起者无权，仍会酿祸。

### 4. 工具注入：把工具能力装配进 Agent 运行环境

分两个时机：启动时一次性注入、运行过程中动态新增。

#### 4.1 启动装配：BootstrapFactory 统一注入

Agent 进程启动时，`WorkspaceBootstrapFactory` 负责把三类东西塞进 Workspace 对象：

- **内置工具列表**：文件读写、shell 执行、HTTP 调用等
- **生命周期钩子**：工具执行前/后的回调，用于审计、日志、超时控制
- **运行模式**：是否允许联网、是否启用沙箱等行为配置

这三类通过 `build_kwargs()` 统一构造，返回给 Workspace 初始化函数。**Web 入口（FastAPI）和 ACP 入口（命令行）都调用同一个 `build_kwargs()`**，保证两边注入的工具集合完全一致，不会出现"Web 能调但 CLI 调不了"。

代码层面就是构造一个 dict，key 是 `tools`、`hooks`、`modes`。Workspace 拿到后在后续 LLM 推理时，把 tools 的工具描述塞进 system prompt。

#### 4.2 运行期注入：技能热刷新

启动后如果需要新增工具（比如新装一个 git 技能），**不需要重启进程**：

1. **Manager 侧**：把技能目录（SKILL.md + scripts/）通过 `mc mirror` 推送到 MinIO 的 `agents/member01/skills/` 路径
2. **Worker 侧**：`update.py` 定期检查 MinIO 上技能目录的 ETag 指纹，发现变化后调用 `refresh_and_enable_skills()`
3. **激活**：新技能被加载进当前进程的 Workspace，**正在执行的任务不受影响**，新任务可以立即使用新技能

> **关键约束：MinIO 是唯一的传递媒介，Manager 和 Worker 之间没有直接的 RPC 连接。** Manager 只负责往 MinIO 写文件，Worker 只负责从 MinIO 读文件，两边通过文件路径和 ETag 指纹达成一致。

MCP 工具清单走同一条管道：`mcporter.go` 生成 `mcporter.json` 写到 MinIO，Worker 拉取后解析出可用的 MCP 服务地址和工具列表，注入到工具注册表。

整条链路是"**渲染 → 下发（投影）→ 收敛**"三段：治理平面把技能渲染成配置资产下发到 MinIO，执行平面自主拉取收敛。**控制面与执行面靠 MinIO 文件契约解耦，中间没有任何直连通道。**

### 5. 工具执行：四道纵深防御的校验门

工具执行链路是：**LLM 输出 tool_call → 底座拦截 → 逐层校验 → 真实执行**。

QwenPaw 在 Agent 调用工具与工具真实执行之间设置了四道相互独立的校验关：

| # | 校验门 | 时机 | 职责 |
|---|--------|------|------|
| 1 | **技能体检**（SkillScanner） | 加载时 | 静态扫描技能目录 |
| 2 | **渠道准入**（ChannelACL） | 消息入口 | 校验发送者身份 |
| 3 | **策略裁决**（PolicyGuardedTool） | 执行前 | 四态权限裁决 |
| 4 | **参数安检**（ToolGuard） | 参数层面 | 查参数是否像攻击 |

**四道门的代码路径完全独立，任何一道的崩溃不会导致其他门失效。**

#### 5.1 技能体检（加载时）

在技能被加载进 Workspace 之前，`SkillScanner` 对技能目录做静态扫描：

- 扫描文件数量（**上限 500 个**）和单文件大小（**上限 10MB**），防止资源耗尽
- 检查是否包含恶意模式（硬编码密钥、危险系统调用）
- 产出 `ScanResult{is_safe: bool}`，**不安全的技能直接拒绝加载**

这一步发生在工具注入阶段，不是在每次调用时。SkillScanner 在技能安装、市场拉取阶段就做静态扫描，**把防线从"调用时"前移到"加载时"**。扫描本身也有护栏——恶意技能还没进入系统就被拒收。

#### 5.2 渠道准入（ChannelACL）

用户消息进入系统时先校验发送者身份：

- **白名单用户**：直接放行，进入 LLM 推理
- **黑名单用户**：直接拒绝
- **未登记用户**：进入 pending 队列，等待管理员审批

**这层只校验"谁在发消息"，不校验消息内容、不校验工具参数**，与后续的策略层、参数层完全解耦。

#### 5.3 策略裁决（PolicyGuardedTool）

LLM 决定调用某个工具后，在执行前触发 `check_permissions()`：

| 裁决 | 行为 |
|------|------|
| `ALLOW` | 直接执行 |
| `DENY` | 拒绝执行，返回错误给 LLM |
| `ASK` | 暂停执行，等待人工审批 |
| `SANDBOX_FALLBACK` | 在沙箱环境中执行，沙箱内违规则升级为 ASK |

两个关键边界条件：

1. **governor 为 None 时一律 DENY**——治理层组件没初始化成功，宁可全部拒绝，不裸奔
2. **OFF 模式不等于不隔离**——OFF 模式只跳过"问用户"这一步，但**仍然挂沙箱**。不问人 ≠ 不隔离

无论放行还是拒绝，每次裁决结果都通过 `governor.audit()` 落审计日志。

#### 5.4 参数安检（ToolGuard）

最后一道门是参数安全引擎，检查"这次调用的参数像不像攻击"。四类守卫串行执行：

| 守卫 | 检查内容 | 热更新 |
|------|---------|--------|
| **SharedSafety** | 灾难命令分类（`rm -rf /`、`mkfs` 等） | 否（always_run） |
| **FilePath** | 敏感路径访问（`/etc/passwd`、`~/.ssh` 等） | 否（always_run） |
| **RuleBased** | YAML 规则匹配自定义危险模式 | **是** |
| **ShellEvasion** | 引号状态机检测命令混淆 | **是** |

### 6. 端到端：一次工具调用的完整旅程

1. **技能体检**——技能包入场前 SkillScanner 静态扫描，恶意技能直接拒收
2. **渠道准入**——用户消息过 ChannelACL，白名单直通、陌生人 pending
3. **LLM 决策**——模型根据任务上下文，从注册表解析出目标工具名 + 入参
4. **策略裁决**——PolicyGuardedTool 四态裁决，决定放行、拒绝、审批还是沙箱试探
5. **沙箱执行**——SANDBOX_FALLBACK 进沙箱试探，违规升级人工审批
6. **参数安检**——ToolGuard 四守卫做参数形态检查，混淆命令被引号状态机还原拦截
7. **真实执行**——通过全部校验，在沙箱内执行并返回结果，全程审计落盘

## 第二部分：工具底座与技能底座的关系

### 7. 核心定位：两层底座各司其职

#### 7.1 工具底座（Runtime 执行层）

**定位**：原子能力运行基座，负责函数的注册、查找、权限校验、沙箱执行，解决"函数能不能安全跑起来"的问题。

面向代码函数，是 Agent 的手脚运行时。它只关心执行动作：把裸业务函数封装成带治理壳的工具对象，提供注册表寻址、身份 ACL、参数安检、沙箱隔离、调用审计整套运行保障。

**核心对象**：`FunctionTool`、`PolicyGuardedTool`、全局工具注册表、`ToolGuard` 参数安全引擎、`ChannelACL` 渠道准入、`Sandbox` 沙箱。

**解决的四大命题**：工具怎么注册进来、怎么按名称查找定位、怎么注入 Agent 运行环境、怎么被多层校验之后安全执行。

> **本质**：执行运行时，只管控调用行为，不管理业务语义与文档描述。

一个需要补充的关键认知：**工具底座本身不产生任何给大模型阅读的提示词素材。** FunctionTool 内部可以携带 schema，但 schema 仅作为注册阶段入参；工具底座不会主动解析、提炼、整理 schema 投喂给 LLM。**schema 的收集、多语言适配、按工作区过滤、prompt 裁剪，全部属于上层技能底座的职责。**

#### 7.2 技能底座（资产管理层）

**定位**：能力资产管控基座，负责技能包的入库、版本管理、多租户筛选、提示词注入，解决"能力能不能被模型识别、按需分发"的问题。

技能底座只做三件事：

1. 从磁盘或 MinIO 读取技能目录
2. 解析 `skill.md` 得到文本，解析 manifest 得到函数入口引用
3. 把这些信息登记到全局技能池（一个内存 dict）

**核心组件**：market 市场源、registry 注册中心、pool_service 技能池、store 原子存储、Workspace 装配器、生效技能集合筛选器。

**核心链路**：技能包拉取 → 文件签名校验 → 暂存中转 → 原子写入 manifest → 池内登记 → Agent 装配筛选 → SKILL.md 文本注入 Prompt。

> **本质**：资产管理层，只管控能力分发与模型决策素材，不参与代码执行。技能底座是面向"资产"的完整生命周期系统——从市场下载、版本升级、本地定制修改、冲突重命名、跨工作区复用、子 Agent 权限裁剪，直到被禁用、被删除，整套生命周期全部由技能底座接管。

**技能底座并不会调用 scripts 内部函数**，它只读取目录元信息、SKILL.md 文档、提取 scripts 入口函数引用；真正的函数执行，会向下委托给下层工具底座完成。

### 7.3 两层底座的上下级关系（最关键底层逻辑）

#### 1. 技能底座在上，工具底座在下

技能底座完成能力筛选后，把选中的技能包解析成内存对象；再把技能包里的 scripts 业务函数，交给下层工具底座完成注册、封装与执行。

**要区分清楚引用关系**：技能底座保存的不是已经实例化完成的 `FunctionTool` 对象，而是**函数引用路径 + 元信息 schema + SKILL.md 文档**；只有进入 Agent 装配阶段，才会向下实例化、交付给工具底座做注册。

> **全局技能池不会持有工具运行时对象，避免多 Agent 实例之间对象互相污染。**

#### 2. 技能底座管理"能力入口"，工具底座守住"执行出口"

- **技能底座管控**：哪些技能可以进入当前 Agent（多租户过滤、父子 Agent 求交、黑名单裁剪）
- **工具底座管控**：选中的工具能不能调用、调用参数是否存在攻击、调用主体是否具备权限

> **工程现实：就算技能底座已经允许某一个技能进入 Agent 的生效集合，工具底座依旧可以在运行时拒绝本次调用。装配期的允许不等于运行时 100% 放行，这正是双层纵深防护的设计初衷。**

#### 3. 技能底座负责 LLM 决策侧，工具底座负责 Runtime 执行侧

技能底座把 SKILL.md 文档送入 Prompt，让大模型知道"该调用哪个能力"；工具底座接收模型输出的调用指令，完成寻址、校验、运行、异常回写。

> **技能底座是能力的"资产管理平台"，工具底座是能力的"安全运行引擎"。**

### 8. 底层原理：两条链路的衔接流程

#### 阶段 1：技能底座完成技能资产入库（静态资产阶段）

> 本阶段发生在 Agent 实例创建之前，属于全局系统初始化 / 用户导入技能的动作，不属于某个 Agent 会话内部行为。

1. 从内置仓库 + 四源市场拉取技能包（SKILL.md + scripts 脚本）
2. 进入 registry 注册中心：做语言变体解析、文件签名变更检测，避免重复加载
3. 进入 store 存储层：先存入 staged 临时目录做静态体检（SkillScanner 恶意扫描），校验通过后用**原子 rename** 写入 manifest，防止进程崩溃损坏账本；同时检测同名冲突，自动生成带版本后缀的名称，避免覆盖用户配置
4. 进入 pool_service 技能池：以 upsert 唯一入口完成登记，打上 `builtin`/`customized`/`external` 来源标记；通过 `preserve_from` 保留用户自定义配置，版本升级不丢失配置；同时加全局锁防止多线程并发改写造成数据错乱

至此，技能包安全存入全局技能池，成为静态资产。

#### 阶段 2：技能底座完成 Agent 装配筛选（能力裁剪阶段）

> 本阶段发生于 `AgentBuilder.build()`，也就是 Agent 实例初始化阶段；此时还没有发起大模型推理，全部是内存静态集合运算，不会执行任何业务脚本。

`resolve_effective_skills` 做多层过滤：

- **渠道过滤**：按 ChannelACL 黑白名单剔除渠道禁用技能
- **双目录合并**：全局共享池 + 工作区私有副本，工作区副本优先级更高，支持局部定制覆盖全局能力
- **父子 Agent 求交**：子 Agent 声明的技能集合必须和父 Agent 生效技能做交集，**从源头阻断权限越界**
- **来源保护**：`protected` 受保护技能禁止子 Agent 继承，`external` 外部挂载技能自动校验目录有效性

这里输出的"生效技能元集合"**不是实例化好的工具对象列表**，仅仅是一组元数据记录：技能名称、来源标记、SKILL.md 路径、scripts 函数入口引用、schema 信息。真正的工具对象实例化推迟到向下交付给工具底座时再完成。

> 好处：同一个技能池，可以批量生成多份不同 Agent 的生效元集合，而不会提前大量消耗内存实例对象。

#### 阶段 3：技能底座向工具底座交付可执行函数（衔接点）

> **两层底座的关键边界就在本阶段**，元数据从技能底座跨层传递到工具底座，开始 Runtime 侧的实例化工作。这是静态资产转向运行时对象的分界点。

1. 技能底座加载选中的技能包：读取 SKILL.md 文档文本、解析入参 Schema、读取 scripts 目录下的业务函数
2. 把业务函数向下交付给下层工具底座
3. 工具底座执行工具注册流程：把裸函数封装为 `FunctionTool`，再套上 `PolicyGuardedTool` 治理壳，自动挂载权限校验、审计、沙箱能力
4. 封装完成的工具实例，注册进入工具底座的内存注册表 `toolkit._qp_skills`，完成两层底座的数据打通

**交付过程是单向向下。** 工具底座不会反向回写任何数据到技能池 manifest。运行时产生的调用日志、会话状态，全部保存在 Agent 实例内存与会话数据库，不会污染磁盘上全局技能池资产。

如果多个 Agent 使用同一个技能，每个 Agent 都会生成**属于自己的一套独立 `PolicyGuardedTool` 实例**，实例之间相互隔离。

#### 阶段 4：模型决策 + 工具底座执行（调用闭环）

1. 技能底座把 SKILL.md 描述文本注入模型 Prompt，大模型输出斜杠调用指令（工具名 + JSON 入参）
2. 指令下发到工具底座：
   - 第一步：按工具名做注册表查找，**未注册工具直接 fail-closed 拒绝**
   - 第二步：执行 ChannelACL 渠道准入，校验调用用户身份
   - 第三步：执行 PolicyGuardedTool 四阶段策略裁决（身份权限 → 入参校验 → 风险检测 → 结果审计）
   - 第四步：ToolGuard 四守卫做参数安检，用引号状态机拦截 Shell 混淆攻击
   - 第五步：校验全部通过，在沙箱中执行业务函数；异常自动捕获，格式化报错信息回写给模型
3. 调用结果回写入 Agent 上下文，开启新一轮模型推理循环

即便技能底座已经把技能加入生效集合，在本运行时阶段依旧有多道关卡——用户身份不在白名单、参数构造出 Shell 混淆攻击、治理服务 governor 挂掉，都会直接拒绝调用。

> 同时要注意：**模型只能看到 SKILL.md，看不到 scripts 内部代码。** 模型输出调用指令，但完全不知道底层函数实现逻辑。

### 8.2 两层底座的边界隔离设计（底层核心工程约束）

#### 1. 语义边界隔离

技能底座只读写 SKILL.md 文档，**绝不读取 scripts 脚本源码**；模型只能读取 SKILL.md，完全看不到业务代码。工具底座只执行 scripts 函数，不读取技能文档，所有决策依据完全由上层模型传入。

> 好处：实现"**决策与执行解耦**"——修改业务脚本不需要改动 Prompt 文档，修改技能描述不需要重新发布代码。

这里会带来一个工程约束：**SKILL.md 必须是模型理解技能语义的唯一结构化入口。** scripts 内部注释、代码 docstring 不会被喂给模型。如果 SKILL.md 和脚本实际行为不一致，就会出现"模型认知和真实执行行为错位"bug。**版本迭代时必须保证 SKILL.md 与 scripts 脚本一同变更**，由技能底座的版本同步机制做约束。

#### 2. 数据存储隔离

| | 技能底座数据 | 工具底座数据 |
|---|-------------|-------------|
| 存储位置 | 磁盘持久化的技能池、manifest 账本、工作区配置 | 仅存在于单 Agent 实例内存中的注册表、工具实例、调用日志 |
| 生命周期 | 全局静态资产，支持跨会话持久化、版本迭代、市场分发 | Agent 销毁即释放，不持久化函数运行时对象 |

**不能把运行时工具实例序列化存入 manifest 账本。** manifest 只记录元信息：技能名称、来源标记、文件路径、用户配置 config/tags/automation。Agent 重启后，工具实例全部重新由元信息向下实例化生成。

#### 3. 权限防护分层隔离（双层纵深防御）

- **上层技能底座**：装配期做静态权限裁剪（父子技能求交、渠道黑名单），在模型决策之前就把越权能力剔除出候选集合
- **下层工具底座**：运行时做动态治理校验（PolicyGuardedTool 四阶段校验 + 参数安检 + 沙箱隔离），**就算上层装配逻辑出现漏洞，嵌套调用也无法绕过执行层校验**

> **两层防护是"叠加关系，不是互斥替代"。** 不能认为只要装配期裁剪完成，运行时校验就可以关闭；同样，不能只靠运行时校验、完全放任大量无关技能进入 Agent 的 prompt 上下文，会造成 token 膨胀、模型幻觉概率上升。

### 9. 工具底座与技能底座的核心差异

#### 9.1 治理对象不同

- **技能底座**：治理**技能资产包**，管控能力的分发、筛选、版本、多租户隔离
- **工具底座**：治理**函数调用行为**，管控每一次调用的身份、参数、风险、执行环境

技能底座管理的是"一个能力包"（可以包含一组 scripts 脚本、多个函数入口）；工具底座管理的是"单次函数调用"（每个业务函数对应一个 FunctionTool 实例）。**一个技能包可以向下注册出多个工具对象**，这是二者粒度不完全对齐的现实情况。

#### 9.2 生命周期不同

- **技能底座**：全生命周期覆盖——从下载、入库、更新、分发到删除，属于**长期资产管理**
- **工具底座**：仅覆盖单次 Agent 会话生命周期——工具实例只在 Agent 运行期间驻留内存，会话结束随即销毁，属于**临时运行时管理**

当 Worker 容器重启，内存里全部 FunctionTool 实例销毁；磁盘上由技能底座维护的技能池 manifest 账本完整保留。**容器重启之后，AgentBuilder 重新读取磁盘元信息，向下再次实例化工具底座对象，业务可以恢复运行——这也是热刷新、长任务不丢失进度的底层支撑。**

#### 9.3 面向主体不同

- **技能底座**：面向**大模型 LLM**，提供能力描述文本，解决"模型知不知道该调用哪个能力"
- **工具底座**：面向**本地 Runtime 运行时**，提供函数执行能力，解决"系统能不能安全执行这个动作"

**如果缺少技能底座，只有工具底座**：依然可以跑工具调用，但所有 schema、描述都需要硬编码写死，无法做市场拉取、多语言变体、父子 Agent 权限裁剪；模型看到的能力集合无法动态变更，新增能力就要改代码重启。

**反过来，如果只有技能底座，没有工具底座**：就只有一堆 SKILL.md 文档，没有任何实际执行能力，**模型只能看文档，不能干活**。

#### 9.4 扩展形态不同

- **技能底座**：支持动态热加载，从 MinIO 对象存储拉取技能包，更新文件签名后直接刷新生效，**不需要重启容器、不中断长任务**
- **工具底座**：分为静态注册（启动时批量加载内置函数）与动态注册（技能包下发后实时注册工具实例）

集群场景下，**AgentTeams Manager 负责把技能包投影到 MinIO**，属于技能底座集群侧分发逻辑；Worker 节点收到通知后本地技能底座完成更新，再向下通知本地工具底座做动态注册。**集群分发属于技能底座的延伸，而不是工具底座的职责。**
