# 02. GSD Core 五步生命周期闭环：The Phase Loop 状态机深度拆解

> 「如果你不能用一句话把一个功能说清楚，那说明你还没想明白。」在软件开发中，任何模糊的需求最终都会变成线上 Crash。GSD Core 将所有开发工作收敛成一个单一、严苛、可重复运转的核心心智模型：**The Phase Loop（阶段循环）**。

<!-- more -->

## 阶段循环（The Phase Loop）全景

GSD Core 将项目开发切分成多个阶段（Phase）。每个阶段从诞生到归档，必须严格按顺序通过 5 个步骤（含 1 个可选步骤）：

```text
+----------+      +-------------+      +--------+      +-----------+      +----------+      +--------+
| Discuss  | ---> | (UI Design) | ---> |  Plan  | ---> |  Execute  | ---> |  Verify  | ---> |  Ship  |
| 澄清决策 |      | (可选UI契约) |      | 规划切片|      | 并发落盘   |      | 机器验收 |      | 归档发版|
+----------+      +-------------+      +--------+      +-----------+      +----------+      +--------+
```

这不仅是一套敏捷工作流程，它本质上是一个**严密的防御型状态机**。每一步的存在，都是为了拦截前一步无法解决的某一类致命缺陷。

---

## 逐步拆解：为什么每一步都不可或缺？

### 1. Discuss（讨论决策）：在写计划前锁定「How」
- **防范的风险**：模型靠「猜」做技术选型。
- **运行逻辑**：
  在 `ROADMAP.md` 中，一个阶段的目标通常只描述了「做成什么样子（What）」，并没有说明「怎么实现（How）」。如果直接让 AI 做 Plan，它会根据泛化知识挑选一个看似合理、实际上与你架构风格相悖的方案（例如你用轻量原生路由，它给你装了一堆沉重的第三方库）。
- **执行产物**：几分钟的人机快问快答后，生成 `{phase}-CONTEXT.md`，将锁定下来的硬性决策（依赖项、错误处理策略、作用域边界、数据流向）固化为只读契约。

### 2. UI Design（可选视觉契约）：UI-SPEC 消除歧义
- **防范的风险**：前后端与视觉呈现上的「各执一词」。
- **运行逻辑**：
  对于带有前端界面的任务，运行 `/gsd-ui-phase`。它不会直接写 React 或 Vue 代码，而是通过 `gsd-ui-researcher` 生成一份 `{phase}-UI-SPEC.md`。
- **核心约束**：详细规定排版规范、组件清单（Component Inventory）、交互边界、极端长文本溢出策略。在代码实现之前先把交互视觉的边界锁死。

### 3. Plan（规划切片）：解耦、防重叠与上下文防爆
- **防范的风险**：单任务过大引发模型遗忘；并行任务撞车修改同一文件。
- **运行逻辑**：
  由 `gsd-planner` 启动全新子代理，结合 `CONTEXT.md` 与调研结果，将任务细化拆解成 2~3 个原子级 `PLAN.md`。
- **核心机制**：
  - **Task 边界控制**：每个 Task 保证能够在一个干净的上下文窗口内完整交付。
  - **波次分组（Waves）**：根据文件修改重叠度分析，互不干扰的 Plan 被排在同一波次（Wave 1）并发执行；有文件依赖的 Plan 顺序推迟到后续波次（Wave 2）。
  - **Plan-Checker 双重拦截**：生成计划后，独立的只读审核代理 `gsd-plan-checker` 从 12 个维度（需求覆盖、依赖拓扑、测试命令有效性等）全面挑刺，未通过则自动打回重做。

### 4. Execute（并发落盘）：原子化提交与状态推进
- **防范的风险**：模型批量修改 20 个文件，中途出错直接死锁无法定位。
- **运行逻辑**：
  调度多个 `gsd-executor` 分头认领本波次的 Plan。每个 Executor 都在独立干净的窗口中读取指令，编写代码，并为每一个 Task 单独生成一次原子化的 Git Commit。
- **输出产物**：每个 Plan 完成后生成 `{phase}-{N}-SUMMARY.md`，详细记录实际变动的文件、完成的验收条件，以及与原计划偏差的地方。

### 5. Verify（机器验收）：反向目标推导（Goal-backward）
- **防范的风险**：虚假绿灯（False Green）——测试全都通过，但用户真正要的功能根本没做。
- **运行逻辑**：
  由专门的 `gsd-verifier` 读取阶段目标与 `CONTEXT.md` 决策，对代码库进行客观事实求证。
- **绝不相信模型的自评**：
  - 代码有没有实现？必须通过测试运行命令的真实退出码（Exit Code 0）来证明。
  - 需求是否满足？逐一检查 `REQ-ID` 覆盖情况。
  - 只有机器客观证据全部通过，状态才标记为 `passed` 并写入 `{phase}-VERIFICATION.md`；一旦发现缺口，自动生成修补计划（Fix Plan），闭环回滚。

### 6. Ship（发版归档）：状态收敛与阶段完结
- **防范的风险**：半吊子工程、分支残留、开发记录丢失。
- **运行逻辑**：
  运行 `/gsd-ship`，合并工作分支，创建 Git 标签或 PR，将本阶段产生的中间临时产物归档到 `.planning/milestones/`，并在 `STATE.md` 中将当前阶段正式打勾。
- **准备进入下一循环**：主控会话清空当前指针，平滑滑向下一个 Phase。

## 阶段生命周期的原子状态机

在底层的 `STATE.md` 中，状态不是随意书写的自然语言，而是受到严格生命周期约束的枚举值：

| 状态值 | 含义 | 触发时机 |
|--------|------|---------|
| `Ready to plan` | 阶段已创建，等待讨论与规划 | `/gsd-new-project` 或新增阶段完成 |
| `Executing Phase N` | 正在执行该阶段的某个 Plan | 第一波次 Executor 启动 |
| `Phase N complete` | 该阶段已通过机器验证并正式归档 | `/gsd-ship` 执行成功 |
| `All phases complete` | 里程碑下所有阶段均已完成，等待终审 | 最后一个阶段归档完成 |
| `<version> milestone complete` | 里程碑正式打标完结 | `/gsd-complete-milestone` 执行 |

如果在中途发生方向调整或者执行失误，系统提供安全的回滚命令 `/gsd-undo`，能够依靠 Git 历史与状态快照，在不破坏无辜文件的前提下安全回退整个阶段状态。

## 架构反思：纪律带来真正的速度

业余开发者觉得写这些 Spec、Summary、Verification 是「浪费时间」，恨不得一句话让 AI 直接改代码。但内核维护数十年的经验告诉我：**没有状态机和规范约束的 AI 开发，看似前 10 分钟飞快，接下来的 3 天你都在帮它修由于上下文丢失制造的诡异 Bug。**

GSD Core 的 Phase Loop 将不可靠的大模型执行，锁进了一个确定性的轨道里。每一步都有门禁，每一步都有证据，这才是成熟团队实现 7×24 小时自主工程交付的核心法宝。
