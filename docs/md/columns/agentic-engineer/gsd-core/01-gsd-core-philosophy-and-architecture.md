# 01. GSD Core 核心架构：反上下文腐化（Context Rot）与双层执行模型

> 「烂程序员关心代码，好程序员关心数据结构和它们在内存中的流动。」在 AI 编程时代，大模型的**上下文窗口（Context Window）就是它的易失性 RAM**。当你的会话被垃圾日志和琐碎历史塞满时，再聪明的模型也会变得痴呆。

<!-- more -->

## 什么是上下文腐化（Context Rot）？

很多初学者甚至部分资深工程师都有一个迷思：「既然现在模型支持 200k、甚至 1M 的上下文窗口，那我是不是可以把所有东西都一股脑塞进去，让它一直聊下去？」

答案是：**绝对不行。**

在神经网络的注意力机制中，窗口变大不等于注意力不变。随着交互轮数增加，一个被称为 **Context Rot（上下文腐化）** 的物理现象会不可避免地发生：

1. **注意力稀释（Attention Dilution）**：有效指令（System Prompt / 关键规则）在长达十几万 Token 的对话历史中被淹没，模型对约束条件的服从率急剧下降。
2. **错误级联放大（Error Cascade）**：前序轮次中模型哪怕出现了一次微小的幻觉或错误假设，只要留在历史记录里，后续轮次就会把这个错误当成既定事实不断自圆其说。
3. **推理成本与延迟陡增**：每一次交互都要为膨胀的历史 Token 全量计算 KV Cache，响应越来越慢，账单越来越贵。

**结论很残酷**：一个已经运行了 150k Token 琐碎会话的模型，其实际编码能力还不如一个拥有干净 10k Token 的精炼模型。

## GSD Core 的核心解法：主客双层架构

GSD Core（v1.7.0）没有选择写几千行微调补丁去教大模型「如何记住所有事情」，而是从系统架构层面彻底重构了执行流：**主控会话做减法，专业子代理干脏活。**

```text
+--------------------------------------------------------------------+
| 主控会话 (Lean Main Session)                                        |
| 职责：用户交互、生命周期流转、读取 .planning/ 状态、分派子任务            |
| 上下文负载：极低（保持在 < 20k Token，杜绝膨胀）                       |
+--------------------------------------------------------------------+
       |                                              ^
       | 派发专用 Prompt + 约束条件                      | 返回结构化摘要
       v                                              | (SUMMARY.md / PASS)
+--------------------------------------------------------------------+
| 干净子代理 (Fresh-Context Subagents)                                |
| 每次启动：全新的 200k 纯净窗口                                      |
| 职责：深入代码库调研、编写复杂代码、运行测试套件、执行严苛验证         |
| 任务结束：进程销毁，不向主会话回传中间过程日志，避免上下文污染         |
+--------------------------------------------------------------------+
```

### 1. 主控会话（Lean Main Session）：薄调度器
- 主会话扮演操作系统微内核（Microkernel）的角色。
- 它绝不直接读几万行源码，也绝不打印跑测试时的几百行终端输出。
- 它只负责维持当前的生命周期指针（例如：当前处于 Phase 3 的哪个 Plan），并通过文件向子代理下达简短指令。

### 2. 独立子代理（Fresh-Context Subagents）：跑完即焚
- 所有的代码搜索、方案调研、单元测试运行、文件编写，全部在独立的 Subagent 中执行。
- 每个 Subagent 启动时拥有 100% 崭新的上下文窗口，装载的仅仅是该子任务必需的上下文（`PROJECT.md`、当前 `PLAN.md` 和关联代码片段）。
- 一旦工作完成，Subagent 将产物写入磁盘，只向主会话返回一个精简的状态信号（例如：`status: complete`，修改了哪些文件，生成了哪个 Commit）。中间产生的海量 Token 随着子进程结束被彻底回收。

## 状态持久化：以文件系统替代易失性记忆

如果模型每次启动都是崭新的窗口，那么前一个阶段做出的架构决策、用户定下的业务规则，靠什么传递？

大多数平庸的设计会引入外置向量数据库、Redis 或专有的后台 Daemon。但 GSD Core 采用了经典的 UNIX 哲学：**文件系统就是最好的状态机。**

在项目根目录下的 `.planning/` 文件夹中，存放着所有人类与 AI 达成共识的契约文件：

```text
.planning/
├── PROJECT.md          # 项目愿景、核心约束、不可违背的底线
├── ROADMAP.md          # 里程碑与阶段划分（Phase 1..N）
├── STATE.md            # 当前精确运行位置、各阶段进度、历史决策记录
├── config.json         # 运行配置、模型路由规则、工作流开关
└── phases/
    ├── 01-auth/
    │   ├── 01-CONTEXT.md       # 人机讨论沉淀的确定性决策（非模糊想法）
    │   ├── 01-RESEARCH.md      # 生态与技术选型调研报告
    │   ├── 01-01-PLAN.md       # 第 1 阶段第 1 个执行切片
    │   ├── 01-01-SUMMARY.md    # 真实执行记录与 Commit 跟踪
    │   └── 01-VERIFICATION.md  # 目标反向推导的机器验证结果
    └── 02-payment/
```

### 文件系统的三项绝对优势：
1. **天然具备版本控制（Git-Tracked）**：任何阶段的计划变更都可以随时 `git diff` 查看，或者一键 `git revert`，零黑盒。
2. **跨 Session 零摩擦续接**：关掉终端、换一台电脑、甚至换一个模型（比如从 Claude Code 切到 Codex 或 OpenCode），新 Agent 只要读取 `STATE.md`，3 秒内就能在完全一致的状态下继续工作。
3. **人类即时干预门槛极低**：如果 AI 规划偏了，人类不需要通过聊天框费尽口舌纠错，直接打开编辑器改两行 Markdown 文件，下一次调度就能强制收敛。

## 总结：好品味的工程架构

GSD Core 的哲学可以用一句话概括：**大模型的概率是不确定的，但软件工程的流程必须是确定性的。**

它没有试图发明一个无所不能的「超级智能体」，而是把大模型放进了一个拥有清晰护栏的流水线车间里：通过文件做持久化状态、通过子代理保持注意力纯净、通过确定性脚本做机器验证。这才是工业级 AI 辅助工程应当具备的模样。
