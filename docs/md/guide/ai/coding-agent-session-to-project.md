# Coding Agent 为什么正在从 Session 走向 Project？

同事的 Agent 已经在改这个功能了，自己的 Agent 却不知道，还傻傻地又做了一遍。

彼此看不到进度，就可能出现这样的重复劳动。10 月 20 日，开发者 Elliot Hesp 在 Cursor 论坛反映过这种信息不通的问题。他用 GitHub Issues 跟踪工作，也在用 Cursor Projects。一个人用时很顺手，到了团队协作，大家却只能看到自己的 Agent 和任务板。同事的 Agent 正在做什么、刚发现了什么问题，要去问人才知道。

即便问到了“这个功能有人在做”，接手时还是有一串事情要确认：代码改到哪了，测试跑过没有，现在等审查，还是等另一个人继续？同事得翻一下会话，把 PR 和测试链接发过来，再补一句哪些地方还没做完。

这个场景在日常开发里也很熟悉。需求写在文档里，临时决定可能在群聊里，也可能是领导随口提了一句，联调进度则记在某位同事脑子里。接手的人看完文档、翻过代码，还是有些地方对不上，只好再去问原来的同事：这段为什么保留着，那个方案后来还做不做？

这么来回问几句，事情总算接上了。只是问的人要等，回答的人也得停下手头的活，回忆当时的情况。

换成 Agent，一位开发者还可能同时开着几个 Session。这个改后端，那个补测试，另一个准备接客户端。后端刚确认的约定，得告诉客户端；上一轮没做完的部分，下一轮也得交代清楚。会话多了，开发者就要在几边来回补背景、传结果。

**一件事还没做完，会话已经换了好几轮。** 如果每轮都要人重新交代目标、进度和约定，Agent 写代码省下来的时间，就有一部分花在了交接上。

Coding Agent 开始从 Session 走向 Project，就有这层原因。目标、进度和约定得在会话之外留下来，后面的 Agent 才有地方查，也有地方接着更新。

**Session 负责眼下这一步，Project 组织还没做完的整件事。**

最近，GitHub Copilot App 的 Projects 进入公开预览，Cursor 也在北京时间 11 月 11 日发布了多人 Projects 的测试版。它们都在尝试把跨会话的工作接起来。

拿一次字段迁移来说，后端改完了，客户端还要接着改，旧版 App 又不能不管。下面就跟着接手的 Agent，看它怎样找到前面的约定、确认进度，再把自己的这部分做完。迁移情节、PR 和测试记录均为讲解示例。

### 太长不看

- **会话结束了，事情还没做完。** Project 把目标、任务和结果留下来，让后面的 Session 能接着做，少让人重新交代一遍。
- **接手要知道前面做到哪。** 哪份约定有效、谁在做、测过什么，都要查得到。后端测试通过，并不代表客户端也改好了。
- **可以先拿一次交接试试。** 用已有的 Issue 串起设计文档、PR 和 CI，再开一个新会话，看看它能否找到该做的下一步。

### 先找对约定

这次迁移要把用户资料里的 `nickname` 换成 `display_name`。后端 Agent 已经提交了代码，客户端同事准备让自己的 Agent 接着做。

它先找到了最初那条需求：“替换字段名”。可评审时，大家已经改过主意了。线上旧版 App 还在读 `nickname`，后端得同时返回两个字段，等旧版退场再清理。

如果这个决定只留在上一轮聊天里，新 Agent 看到旧字段还在，很可能以为上一个 Agent 没改干净。

人接手时，可能会在群里问一句：“旧字段怎么还在？”熟悉情况的同事解释一下，就明白了。Agent 也需要知道这个原因。

可把整段聊天塞给它，它还得分辨哪些只是提议，哪些最后定了下来。只给一句“字段迁移已完成”，又容易让它以为客户端也改好了。

这时候，一段写清楚的约定就很管用。

> 用户资料逐步迁到 `display_name`。迁移期间，后端同时返回 `nickname` 和 `display_name`，两者值一致，以兼容旧版 App。客户端本轮改读新字段，旧字段清理另行跟踪。这条约定取代最初需求中的“直接替换”，依据是已评审的接口契约。

新 Agent 读到这里，才知道**旧字段是特意留下的**，自己这轮要改的是客户端。

用 Copilot App 安排这轮工作时，可以把后端和客户端仓库关联到同一个 Project，把迁移目标说清楚，再把评审过的接口契约放进 Library。给客户端 Agent 派任务，就让它按这份契约来改。

GitHub 文档也特意提醒，分配任务时要说明使用哪些资料。尤其是新旧两版方案都还在的时候，光把文件放进去不够，接手的 Agent 还得知道这次按哪份做。

放到 Cursor 的多人 Project 里，这份约定可以保存在共享 Context 中。它对应目录 `/cursor/stores/self`，项目成员的 Agent 都能读写，文件会同步到项目 Agent 使用的云端和本地环境。换个 Agent 接手，也有地方找到它。

至于**哪份是现行版本、哪条已经作废**，仍要在资料里写清楚。

### 接上未完的任务

约定找到了，接下来要弄清进度。后端说的“做完了”，到底做完了多少？

有时指代码写好、PR 提交了，有时指后端已经合入、测试也过了。至于客户端，可能还没开始，也可能已经有同事派了 Agent 在改，只是我们没看见。

在 Copilot 的 Overview 里，可以先按状态找这项工作：后端还有未关闭的 PR，就去 `Open` 看关联的会话和 PR；兼容方案还等人确认，就去 `Needs input` 看待处理事项。需要细看时，再点进会话，查计划、改动和当时的讨论。

这样，客户端同事不用只凭一句“做完了”判断。后端到底停在哪一步，可以顺着 PR 查；客户端改读、旧字段清理，也要继续作为未完工作留在项目里。

在 Cursor 里，接手的线索则放在项目任务上。按 10 月的官方更新说明，每项任务都有 ID、状态、执行 Agent 和关联 PR，由 Coordinator 更新，也能放到看板里查看。

到了这次多人版本，每位同事有自己的 Coordinator 和 Worker：前者安排工作，后者执行任务，大家共用一块任务板。客户端同事从自己的对话进去，也能查这次迁移做到哪了。

假如任务里只写了“后端测过了”，却没放测试链接，客户端的 Coordinator 还可以去问后端同事的 Coordinator。Cursor 会从对方聊天分出一条侧边会话来回答，并标明发送者身份。这条会话能读任务板，不能修改它。问一句背景，不会顺手把对方任务的进度也改了。

过去这一步常靠同事转发链接，再解释一句“看这个 PR，测试在这里”。现在 Agent 有机会沿着任务记录自己找过去，缺的那一段再问。**谁在做、做到哪、结果在哪，能从同一项任务里查下去。**

### 看清测过什么

假设后端留下的记录是这样的。

> 后端 PR #84，提交 `a1b2c3d`。CI #315 的接口测试通过。响应里同时包含 `nickname` 和 `display_name`，两个字段的值一致。

这条记录能说明，这个后端版本会按约定返回两个字段。至于客户端读的是哪一个，还得去看客户端代码。

接手的 Agent 顺着客户端代码往下找，界面果然还在用 `nickname`。这下该做什么就清楚了：改掉读取逻辑，再补一条测试，确认它读的确实是 `display_name`。

这里还有个容易漏掉的小地方。正常接口里两个字段的值相同，客户端即使还在读旧字段，页面看起来也完全正常。

**只检查“名字显示对不对”，可能根本测不出客户端有没有改。**

这里可以在客户端单元测试里故意设一道小关：让 `nickname` 是“旧昵称”，`display_name` 是“新显示名”，然后检查页面显示的是“新显示名”。如果代码还在读旧字段，这条测试就过不了。

这两个不同的值是特意构造的测试数据，用来检查客户端选了哪个字段。实际后端仍按契约返回相同的值。

客户端 Agent 做完后，把自己的 PR、提交和测试结果也挂到任务上。下一位再来看，就能分清：后端测的是两个字段都返回，客户端测的是读到新字段。

这些结果也要回到项目里。Copilot 的说明文档可以留在 Library，会话和 PR 从 Overview 查；Cursor 可以更新共享任务，把结果链接写回 Context。原始测试结果仍留在 CI，接手的人或 Agent 沿链接查看。

**“测过了”后面，最好能接上“哪个版本，测了什么”。** 相关代码后来又改了，原来的结果能否继续用，也就有依据可查。

### 会话结束，项目继续

再过几天，负责清理旧字段的 Agent 进来。前两轮会话早就结束了，后端和客户端的 PR 也都合入了，它却还不能直接删掉 `nickname`。

还差一件事：旧版 App 是否已经满足退出条件？这个条件没确认，旧字段就还得留着。迁移做到哪一步，要看整件事的约定，不能只数合了几个 PR。

从架构上看，关键就在这里：**这些信息要活得比一次 Session 更久。**

一次 Session 有自己的上下文，负责完成眼前这段工作。Project 则把迁移目标、当前约定、任务状态和结果入口保留下来。新 Agent 进来，先查自己这一步需要什么；做完后，把新的进展和结果写回去。

这样，后端会话可以结束，客户端可以换个 Agent，旧字段清理也可以过几天再做。几轮执行都围着同一个迁移目标，前面确认过的事、还在等的事，有地方继续跟踪。

我们平时也靠设计文档、任务系统和交接记录做这件事。文档漏写了、进度忘更新了，就喊原来的同事来补。Project 尝试把这些动作接进 Agent 的工作过程：开始前查当前记录，做完后补进展，缺信息时再问。能接好这几步，人才有机会少整理一次背景。

不过，记过的东西也可能被后来的更新弄丢。9 月的早期测试版中，开发者 Lutz Leonhardt 就报告过：自己确认过的一项决定，在项目笔记两次改写后消失了，第二天 Agent 又来问一遍。这是他当时的个人经历，不能当成当前版本的结论。

所以，这一层还得管好记录怎么更新。已经定下来的约定，不能在整理笔记时悄悄没了；方案改了，也得让后来的人知道哪条作废了。不然解释一遍的活，还是会回到人身上。

前面拆解 [DeepSeek Super-agent](https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650410862&idx=1&sn=0c38f8c34cd8194d84bf2be3f039e15a&scene=21#wechat_redirect)时，我们聊过 Router 怎么派活、Worker 怎么带回 PR。顺着往下看，这篇关心的是 PR 交回来以后：剩下的工作放在哪，下一位 Agent 怎么接着做。

### 从一次交接开始

这套思路用到自己的开发里，可以先拿一次交接试试。还是这次字段迁移，用已有的 Issue 当入口，把约定在哪、谁做到哪、结果去哪看写清楚。

比如后端提交 PR 后，在 Issue 里留这样一段：

> 当前约定见仓库中的 `docs/profile-api.md`。双字段并存，旧需求里的“直接替换”已由本次评审修正。后端 PR #84 待审查，由后端同事跟进。提交 `a1b2c3d` 的 CI #315 已验证双字段返回且值一致。客户端待开始，由客户端同事负责，尚未分配执行会话。清理旧字段仍在等待。旧版 App 的退出条件由客户端负责人确认，确认结果回填此任务。

接口契约还在设计文档里维护，测试详情还在 CI，**Issue 把入口串起来就好**。这样改方案时，不必到处复制一份再挨个改。契约更新了，在任务里补一句改了什么、为什么改，后来的人和 Agent 都能顺着查。

客户端同事准备启动 Agent 时，先在这条 Issue 上确认由谁接手，再让 Agent 看契约、后端 PR 和测试。开始做了，就把执行会话挂回任务，方便别人查到。交代任务也可以再具体一点：

> 在单元测试中让两个字段取不同的值，确认客户端读取 `display_name`。完成后，在同一 Issue 回填客户端 PR、对应提交和测试结果，保留旧字段清理的等待状态。

发现另一位同事已经在改，就先说清楚谁继续，免得两边各做一份。两份文档说法不一样，也得问清最后按哪份来。问完把负责人或决定补回对应记录，下一位就少问一遍。

然后换个新会话，只给它这个 Issue，看看它会怎么接。

它能否找到保留旧字段的原因，认出同事正在做的任务，分清后端和客户端分别测过什么？如果还需要我们从头讲一遍，就顺着它卡住的地方补记录。这样很快能看出，交接到底缺了哪一块。

回到开头，自己的 Agent 先查到这块已经有同事在做，接着找到对方的 PR 和测试，知道该接哪一步，就少一次从头再来，也少一次人工传话。

**会话可以结束，没做完的事还有地方接着做。** 这也是我觉得从 Session 走向 Project 最值得借鉴的地方。
