作者：小康，C/C++ 编程博主关键词：Linux、信号、SIGINT、SIGKILL、sigaction、signalfd、异步信号安全前言面试官问："按下 Ctrl+C，程序是怎么被终止的？"大多数人答："发了一个 SIGINT 信号。"面试官继续追问："信号是怎么从键盘走到你的进程的？为什么标准信号会丢？为什么 handler 里调用 printf 可能死锁？SIGKILL 为什么不能被捕获？"这些问题，光背"信号是软件中断"是答不出来的。这篇文章不背概念。我们从一次 Ctrl+C 的完整旅程讲起，用图把信号的产生、未决、递送、处理画清楚。看完你会明白：信号不是立刻打断你的程序，而是内核在"某个特定时刻"才顺手把它交给你。 理解了这个时刻，信号所有的"怪脾气"都能推出来。一、信号是什么？信号（Signal）是内核（或其他进程）发给进程的一个"异步通知"。 你可以把它理解成一张便利贴：有人贴在进程身上，写着"发生了某件事"，进程在合适的时候会看到并做出反应。常见的信号，值得记住这几个：信号编号触发场景默认动作SIGHUP1终端断开终止SIGINT2键盘 Ctrl+C终止SIGQUIT3键盘 Ctrl+\终止并 core dumpSIGKILL9kill -9终止，不可捕获SIGSEGV11非法内存访问终止并 core dumpSIGPIPE13写已关闭的管道/socket终止SIGTERM15kill 默认发送终止SIGCHLD17子进程状态变化忽略SIGSTOP19暂停进程暂停，不可捕获SIGTSTP20键盘 Ctrl+Z暂停进程收到信号后，可以有三种反应：执行默认动作、忽略、自定义 handler 处理。其中 SIGKILL 和 SIGSTOP 是特例，任何进程都不能捕获、阻塞或忽略它们。原因很朴素：必须给系统管理员留一条"一定能终止/暂停任何进程"的后路，否则一个写了死循环还屏蔽了所有信号的程序，就再也没人管得了它了。二、一次 Ctrl+C，完整走了哪些步骤？我们把这趟旅程拆开：1. 你按下 Ctrl+C，终端收到这个按键2. 终端驱动（tty）识别出这是"中断字符"，把它翻译成 SIGINT3. 内核把 SIGINT 发给前台进程组里的每个进程：在目标进程的 task_struct 里，把 pending 位图中 SIGINT 对应的位置 14. 此时进程可能正在跑、也可能在睡觉，信号并不会立刻执行5. 当进程从内核态返回用户态的那一刻（比如系统调用返回、中断返回），内核会检查一下：有没有待处理的信号？6. 有，就在用户栈上构造好现场，跳去执行 handler（或默认动作）；handler 执行完，通过 sigreturn 回到进程被打断的位置看图：看到第 ④ 步了吗？这就是信号所有"怪脾气"的源头：信号只在"内核态返回用户态"这个检查点被处理。 所以：• 进程正在用户态狂跑？定时器中断会让它陷入内核再返回，返回时就能检查到信号• 进程正在 sleep / read 阻塞？信号到来会唤醒它，系统调用提前返回 EINTR，然后处理信号• 进程是僵尸？没有任何"返回用户态"的机会，所以 kill -9 对它没用（上篇的结论，现在有了更深的解释）另外补一个相关的联动：上篇虚拟内存里讲过，访问非法地址会触发缺页中断，内核发现地址不合法，接下来做的事，就是给进程发 SIGSEGV。段错误的本质，就是内核用信号通知你"你越界了"。三、信号的三个阶段：产生、未决、递送一个信号的生命周期，分三个阶段：• 产生（Generate）：kill、键盘、硬件异常、alarm 定时器到期等都会产生信号• 未决（Pending）：信号已产生，但还没被处理。内核在 task_struct 里用一个位图记录：第几号信号处于未决• 递送（Delivery）：真正执行 handler 或默认动作阶段之间还有一道关卡：信号屏蔽字（signal mask）。进程可以"阻塞"某些信号，被阻塞的信号即使产生了，也会一直停在 pending 状态，不会被递送，直到解除阻塞。注意区分两个容易混淆的词：• 阻塞（Block）：信号先攒着，以后再处理• 忽略（Ignore）：信号来了直接丢掉，什么都不做看图：用 sigaction 注册 handler，是标准做法：#include &lt;signal.h&gt;void on_sigint(int sig) { /* 处理逻辑 */ }int main() {    struct sigaction sa = {0};    sa.sa_handler = on_sigint;    sigemptyset(&amp;sa.sa_mask);         // handler 执行期间额外要阻塞的信号    sa.sa_flags = SA_RESTART;         // 被打断的系统调用自动重启    sigaction(SIGINT, &amp;sa, NULL);    while (1) pause();                // 等信号}一个容易被忽略的细节：handler 执行期间，触发它的那个信号会被自动阻塞（除非设了 SA_NODEFER）。所以同一个信号的 handler 不会被"自己"重入，这是内核帮你做的保护。关键问题：信号会丢吗？会。上篇 SIGCHLD 的坑，现在可以给出完整的解释。未决信号在 task_struct 里是用位图记录的：第 N 号信号，对应第 N 位。一个位只能表示"有"或"没有"，没法表示"有 3 个"。所以标准信号（1~31 号）不排队：信号阻塞期间来了 3 次，位图里也只有一个 1，递送时只处理一次，另外两次凭空消失了。Linux 另外提供了实时信号（SIGRTMIN ~ SIGRTMAX，通常是 34~64 号），它们用队列记录，发几次就处理几次，还能通过 sigqueue 携带一个整数或指针数据。看图对比：所以工程上有个原则：信号只适合传递"发生了某件事"，不适合传递"发生了几次"。 需要精确计数的场景，用管道、消息队列或者 Socket。四、handler 里到底能做什么？为什么 printf 可能死锁？这是信号最容易踩坑的地方。先理解一个事实：handler 可能在你程序的任意一条指令之间被执行。因为信号是异步的，它可能恰好在主流程执行到 printf 内部、malloc 内部的某一步时到来。这时内核暂停主流程，跳去执行 handler，handler 跑完再回来。如果这个 handler 里也调用了 printf，会发生什么？看图：printf、malloc、free 这些函数内部都有锁或全局状态，不是"可重入"的。 它们被信号打断后，再在 handler 里调用一次，轻则数据错乱，重则像图里一样死锁。能安全地在 handler 里调用的，只有一小批**异步信号安全（async-signal-safe）**函数，比如 write、_exit、kill、signal、sigaction（完整列表见 man 7 signal-safety）。记住一句话：handler 里只做最简单的事：设置一个标志位，或者 write 一个字节，其他工作交给主流程。标志位的经典写法：volatile sig_atomic_t g_quit = 0;         // 必须是 sig_atomic_t，保证读写是原子的void on_sigint(int sig) {    g_quit = 1;                           // 只改标志，不做别的}int main() {    // ... sigaction 注册 on_sigint ...    while (!g_quit) {        do_work();    }    cleanup();                            // 在正常上下文里做善后，安全    return 0;}这就是"优雅退出"的标准姿势：收到 SIGINT/SIGTERM，handler 只置标志，主循环发现后自己去清理资源、保存数据、再退出。更好的方案：把信号变成"文件描述符事件"后端服务通常靠 epoll 做事件循环。如果信号还要用标志位轮询，很别扭：信号来了，epoll_wait 可能正阻塞着，要靠 EINTR 才能醒。更优雅的做法是 self-pipe（自管道）技巧：handler 里只做一件安全的事——往管道里 write 一个字节，让主循环通过 epoll 监听管道的读端，就把"异步的信号"变成了"同步的 fd 可读事件"。看图：这个思路在 Nginx、Redis、libevent 等高性能网络框架里都在用。Linux 上还有更省事的 signalfd：先把信号阻塞，再创建一个专门读信号的 fd，直接丢进 epoll：sigset_t mask;sigemptyset(&amp;mask);sigaddset(&amp;mask, SIGINT);sigaddset(&amp;mask, SIGTERM);sigprocmask(SIG_BLOCK, &amp;mask, NULL);      // 先阻塞，防止走默认动作int sfd = signalfd(-1, &amp;mask, SFD_NONBLOCK | SFD_CLOEXEC);// 把 sfd 加入 epoll，可读时 read 一个 signalfd_siginfo，就拿到了信号信息不再有 handler，也就没有"handler 里只能做安全操作"的限制，信号处理和其他 I/O 事件用同一套逻辑。这是现代 Linux 服务端处理信号的推荐方式。五、三个必须避开的陷阱陷阱一：用 signal() 而不是 sigaction()signal() 是历史遗留函数，在不同系统上语义不同：有的 handler 执行一次后就恢复默认动作，有的不会阻塞同一信号，有的不重启被打断的系统调用。新代码一律用 sigaction，行为明确、可移植。陷阱二：写关闭的管道/socket，进程被 SIGPIPE 直接干掉这个坑在 IPC 篇提过：往读端已关闭的管道，或对端已断开的 socket 写数据，内核会给进程发 SIGPIPE，默认动作是终止进程。网络服务里客户端随时可能断开，如果不处理，服务器会莫名其妙地退出。signal(SIGPIPE, SIG_IGN);                 // 全局忽略，之后 write 返回 -1 且 errno = EPIPE// 或者针对单次发送send(fd, buf, len, MSG_NOSIGNAL);         // 这次发送不产生 SIGPIPE陷阱三：多线程程序里，信号到底发给谁？发给进程的信号（如 kill 发送的），内核会任意挑一个没有阻塞该信号的线程来处理。这意味着，你根本无法预测是哪个线程执行了 handler，甚至可能打断一个正在持锁的工作线程。标准做法是：在主线程创建其他线程之前，先阻塞所有信号（子线程会继承信号屏蔽字），再专门开一个线程，用 sigwait 同步地等待信号：看图：这样做的好处： 信号处理彻底摆脱了"handler 里只能做安全操作"的限制。信号线程是普通线程，可以放心调用任何函数（加锁、写日志、通知其他线程退出），代码逻辑也更清晰。六、高频面试题精析Q1：信号是什么？内核是怎么实现的？信号是内核或其他进程发给进程的异步通知。内核在 task_struct 里用一个位图记录未决信号，用另一个位图记录被阻塞的信号。进程从内核态返回用户态时，内核检查有没有"未决且未阻塞"的信号，有就去执行对应的 handler 或默认动作。Q2：为什么 SIGKILL 和 SIGSTOP 不能被捕获、阻塞、忽略？为了保证系统管理员始终有办法终止或暂停任何进程。如果这两个信号也能被屏蔽，一个有 bug 或恶意的进程就可能让自己"刀枪不入"。Q3：信号会丢吗？标准信号（1-31）不排队，未决位图只能记"有没有"，不能记"有几个"，重复到来的同一信号会被合并。实时信号（34-64）使用队列，不会丢。Q4：信号处理函数里能调用哪些函数？只能调用异步信号安全函数，如 write、_exit、kill、sigaction 等（见 man 7 signal-safety）。printf、malloc、free 内部有全局状态或锁，在 handler 里调用可能死锁或破坏数据。Q5：signal 和 sigaction 有什么区别？signal 在不同系统上语义不一致（是否重置 handler、是否重启被打断的系统调用等），可移植性差。sigaction 行为明确，可以精细控制信号屏蔽字和各种标志，新代码应统一使用。Q6：多线程程序里，信号发给哪个线程？怎么设计？发给进程的信号由内核任选一个未阻塞该信号的线程处理，无法预测。推荐做法：主线程在创建线程前阻塞所有信号，再专门开一个线程 sigwait 接收；或者使用 signalfd，把信号变成 fd 事件，融入 epoll 事件循环。结语回到开头的问题：Ctrl+C 之后发生了什么？一句话概括：内核在你的 task_struct 里贴了一张便利贴，等你"从内核返回用户态"的那一刻，才顺手把它交给你。理解这个"检查点"，信号所有的怪脾气都有了解释：• 为什么信号会丢：便利贴用位图记录，只能记"有没有"，记不了"有几张"• 为什么 handler 里不能随便调函数：它可能在主流程任意一步被插入执行• 为什么 kill -9 杀不死僵尸：僵尸没有"返回用户态"的机会• 为什么推荐 signalfd / self-pipe：把异步的信号，变成同步的 fd 事件，融入事件循环下篇预告：《图解 Linux 系统调用：用户态怎么"陷入"内核？一次 read 到底经历了什么？》——本篇反复提到"从内核态返回用户态"，那么，进程是怎么"进入"内核的？syscall 指令做了什么？为什么系统调用比普通函数调用慢得多？几张图给你讲透。如果你想把这些底层原理真正用到项目里，我整理了 30 个 C++ 硬核实战课程：线程池、内存池、无锁队列、高性能网络库、协程库、Mini-Redis、Mini-Nginx 等，每个设计决策都讲"为什么这么做"。感兴趣可以加微信：jkfwdkf，备注「项目实战」。觉得有收获，点赞、在看、转发，让更多程序员看到 🙏

## 三、信号的三个阶段：产生、未决、递送



一个信号的生命周期，分三个阶段：



• 产生（Generate）：kill、键盘、硬件异常、alarm 定时器到期等都会产生信号

• 递送（Delivery）：真正执行 handler 或默认动作

• 阻塞（Block）：信号先攒着，以后再处理



• 忽略（Ignore）：信号来了直接丢掉，什么都不做

### 关键问题：信号会丢吗？



会。上篇 SIGCHLD 的坑，现在可以给出完整的解释。



未决信号在 task_struct 里是用位图记录的：第 N 号信号，对应第 N 位。一个位只能表示"有"或"没有"，没法表示"有 3 个"。所以标准信号（1~31 号）不排队：信号阻塞期间来了 3 次，位图里也只有一个 1，递送时只处理一次，另外两次凭空消失了。



Linux 另外提供了实时信号（SIGRTMIN ~ SIGRTMAX，通常是 34~64 号），它们用队列记录，发几次就处理几次，还能通过 sigqueue 携带一个整数或指针数据。看图对比：



所以工程上有个原则：信号只适合传递"发生了某件事"，不适合传递"发生了几次"。 需要精确计数的场景，用管道、消息队列或者 Socket。



## 四、handler 里到底能做什么？为什么 printf 可能死锁？



这是信号最容易踩坑的地方。先理解一个事实：



> handler 可能在你程序的任意一条指令之间被执行。

因为信号是异步的，它可能恰好在主流程执行到 printf 内部、malloc 内部的某一步时到来。这时内核暂停主流程，跳去执行 handler，handler 跑完再回来。

> handler 里只做最简单的事：设置一个标志位，或者 write 一个字节，其他工作交给主流程。

## 五、三个必须避开的陷阱



### 陷阱一：用 signal() 而不是 sigaction()



signal() 是历史遗留函数，在不同系统上语义不同：有的 handler 执行一次后就恢复默认动作，有的不会阻塞同一信号，有的不重启被打断的系统调用。新代码一律用 sigaction，行为明确、可移植。



### 陷阱二：写关闭的管道/socket，进程被 SIGPIPE 直接干掉



这个坑在 IPC 篇提过：往读端已关闭的管道，或对端已断开的 socket 写数据，内核会给进程发 SIGPIPE，默认动作是终止进程。网络服务里客户端随时可能断开，如果不处理，服务器会莫名其妙地退出。



### 陷阱三：多线程程序里，信号到底发给谁？



发给进程的信号（如 kill 发送的），内核会任意挑一个没有阻塞该信号的线程来处理。这意味着，你根本无法预测是哪个线程执行了 handler，甚至可能打断一个正在持锁的工作线程。



标准做法是：在主线程创建其他线程之前，先阻塞所有信号（子线程会继承信号屏蔽字），再专门开一个线程，用 sigwait 同步地等待信号：

## 六、高频面试题精析



Q1：信号是什么？内核是怎么实现的？



信号是内核或其他进程发给进程的异步通知。内核在 task_struct 里用一个位图记录未决信号，用另一个位图记录被阻塞的信号。进程从内核态返回用户态时，内核检查有没有"未决且未阻塞"的信号，有就去执行对应的 handler 或默认动作。



Q2：为什么 SIGKILL 和 SIGSTOP 不能被捕获、阻塞、忽略？



为了保证系统管理员始终有办法终止或暂停任何进程。如果这两个信号也能被屏蔽，一个有 bug 或恶意的进程就可能让自己"刀枪不入"。



Q3：信号会丢吗？



标准信号（1-31）不排队，未决位图只能记"有没有"，不能记"有几个"，重复到来的同一信号会被合并。实时信号（34-64）使用队列，不会丢。



Q4：信号处理函数里能调用哪些函数？



只能调用异步信号安全函数，如 write、_exit、kill、sigaction 等（见 man 7 signal-safety）。printf、malloc、free 内部有全局状态或锁，在 handler 里调用可能死锁或破坏数据。



Q5：signal 和 sigaction 有什么区别？



signal 在不同系统上语义不一致（是否重置 handler、是否重启被打断的系统调用等），可移植性差。sigaction 行为明确，可以精细控制信号屏蔽字和各种标志，新代码应统一使用。



Q6：多线程程序里，信号发给哪个线程？怎么设计？



发给进程的信号由内核任选一个未阻塞该信号的线程处理，无法预测。推荐做法：主线程在创建线程前阻塞所有信号，再专门开一个线程 sigwait 接收；或者使用 signalfd，把信号变成 fd 事件，融入 epoll 事件循环。
