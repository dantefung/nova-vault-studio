     // 申请 1GB    getchar();                         // ① 此时观察 top：VIRT 涨了 1GB，RES 几乎没变    memset(p, 1, 1UL &lt;&lt; 30);          // 真正写入    getchar();                         // ② 此时观察 top：RES 才涨到 1GB    return 0;}top 里有两列要分清：• VIRT：进程的虚拟地址空间大小• RES：真正占用的物理内存malloc 大块内存时，glibc 底层调用的是 mmap。而 mmap 只是在进程的虚拟地址空间里"划出一段地址"，并没有分配物理页，页表里甚至还没有对应的表项。 这叫惰性分配（Lazy Allocation）。看图：那么，程序第一次访问一个"未分配"的页，会发生什么？CPU 去查页表，发现这一项 present 位是 0（甚至根本没有这一项），于是触发一次缺页中断（Page Fault），把控制权交给内核。内核检查这个地址是否在合法的虚拟区间内：合法就分配物理页，不合法就给进程发 SIGSEGV（也就是我们熟悉的"段错误"）。完整流程如下：缺页分两种，面试常问：• Minor Page Fault（次缺页）：不需要读磁盘。比如首次访问新分配的匿名页，内核清零一个物理页就行；或者所需页已经在内存里（如 Page Cache），只是页表还没建立映射。开销是微秒级。• Major Page Fault（主缺页）：需要从磁盘读数据（比如第一次访问 mmap 的文件页、或被换出到 swap 的页），开销是毫秒级，慢几个数量级。想看自己程序缺页多少次，可以用：/usr/bin/time -v ./a.out        # 看 Minor / Major page faultsperf stat -e page-faults ./a.out所以回到开头那个问题的答案：malloc 成功 ≠ 拿到了物理内存，第一次写入时才通过缺页中断真正分配。 这就是 RES 比 VIRT 小得多的原因。四、mmap：把文件"直接搬进"虚拟地址空间理解了缺页，mmap 就简单了。它做的事是：在虚拟地址空间里划一块区域，把它和某个文件（或匿名内存）关联起来，等程序访问时，靠缺页中断按需把数据带进来。mmap 有两个维度：私有映射 MAP_PRIVATE共享映射 MAP_SHARED文件映射写入不回写文件（写时拷贝），加载可执行文件、动态库就是这样写入会同步到文件，多进程可共享，用于 IPC、数据库匿名映射大块 malloc 的实现父子进程共享内存上篇讲的共享内存，就是 shm_open + MAP_SHARED。现在我们来看文件映射为什么比 read 快：用起来就像访问数组：int fd = open("data.bin", O_RDONLY);struct stat st;fstat(fd, &amp;st);char* p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);printf("%c\n", p[0]);            // 访问时触发缺页，内核把对应文件页映射进来munmap(p, st.st_size);close(fd);                        // 映射建立后，fd 可以关，映射依然有效mmap 快在哪？ 省掉了页缓存到用户缓冲区的那次 CPU 拷贝，读文件变成"直接访问内存"，随机访问大文件时非常方便。Kafka、RocketMQ、LevelDB、SQLite 都用到了它。但它不是万能的：小文件频繁映射、解除映射，反而因为缺页和页表操作比 read 慢；对特别大的文件顺序读，read 配合预读也很快。工程上要根据访问模式选。五、写时拷贝（COW）：fork 为什么快得离谱？最后回到第三个问题：一个占 10GB 内存的进程 fork，只要几毫秒，怎么做到的？如果 fork 老老实实把 10GB 内存全拷贝一份，既慢又浪费。而且绝大多数情况下，子进程 fork 后马上就 exec 去执行别的程序了，这 10GB 拷贝完全白费。聪明的做法是写时拷贝（Copy-On-Write）：1. fork 时只复制页表，不复制物理内存。父子进程的页表指向同一批物理页。2. 内核把这些共享页在页表里都标成只读。3. 谁想写某一页，就触发一次缺页中断，内核这时才给它拷贝一份新的物理页，改写它自己的页表。看图：六、三个必须避开的陷阱陷阱一：malloc 成功，不代表内存真的够用Linux 默认允许"超额承诺"（overcommit）：malloc 时只检查虚拟空间，不检查物理内存够不够。等程序真正写入、缺页要分配物理页时，如果物理内存耗尽，内核会启动 OOM Killer 杀进程。也就是说，内存不足的报错，可能不出现在 malloc 返回 NULL 那一刻，而是在几小时后某次普通的写入，程序被直接杀死。 排查线上 OOM 时，要看 dmesg | grep -i oom，而不是只看代码里有没有判 NULL。陷阱二：首次访问缺页，造成延迟抖动低延迟系统（交易、游戏服务器、高频网络服务）里，刚分配的内存第一次被访问，会触发缺页，延迟从几十纳秒跳到微秒级，形成尾延迟毛刺。常见对策是启动时预热：memset(buf, 0, size);                        // 提前触发缺页，把物理页占住mlock(buf, size);                            // 锁定，防止被换出到磁盘mmap(NULL, size, ..., MAP_POPULATE, ...);    // 映射时就预先填充内存池、对象池在初始化阶段"先摸一遍内存"，很多时候就是出于这个目的。陷阱三：对大内存进程 fork，COW 可能让内存翻倍Redis 做 RDB 持久化时，会 fork 一个子进程去写盘，靠的就是 COW，父进程可以继续处理请求。但如果这期间写入很频繁，父进程会不断改写共享页，每改一页就触发一次拷贝。最坏情况下，内存占用接近翻倍。这也是为什么 Redis 官方建议，机器内存要留出足够余量，不能把 maxmemory 设到接近物理内存上限。另外，fork 本身要复制页表，进程越大页表越大，10GB 以上的进程 fork 也可能造成毫秒级到上百毫秒的阻塞。七、高频面试题精析Q1：虚拟内存有什么作用？三个：隔离（每个进程有独立地址空间）、连续（物理零散、虚拟连续，简化内存分配）、超量（虚拟空间可大于物理内存，配合惰性分配和换页）。Q2：什么是缺页中断？分几种？访问的虚拟页当前没有有效映射时，CPU 触发的异常，由内核处理。分次缺页（不需读磁盘，微秒级）和主缺页（要读磁盘或 swap，毫秒级）。地址本身非法时，内核会发 SIGSEGV。Q3：malloc 一定会分配物理内存吗？不会。malloc 只是分配虚拟地址空间（小块从堆里切，大块用 mmap），物理页在第一次访问时通过缺页中断才分配。Q4：fork 为什么快？COW 是怎么工作的？fork 只复制页表，父子共享物理页并标记只读，写入时触发缺页，内核再给写入者拷贝一份新的物理页。Q5：mmap 和 read 有什么区别？read 要把页缓存拷贝到用户缓冲区（一次 CPU 拷贝），mmap 把页缓存直接映射进虚拟地址空间，省掉这次拷贝，但依赖缺页触发加载。适合大文件随机访问，不适合大量小文件频繁映射。结语虚拟内存看起来复杂，其实核心只有一句话：进程看到的是虚拟地址，CPU 通过页表翻译成物理地址；翻译不到，就触发缺页中断，让内核"现场补课"。• malloc 的惰性分配：页表里先不建映射，用到才补• mmap 读文件：把页缓存直接映射进来，用到才加载• fork 的写时拷贝：先共享页，写的时候才复制这三个看似不相关的机制，用的是同一个思路：能拖到最后一刻再做的事，就不要提前做。下篇预告：《图解 Linux 进程与线程：fork、clone、exec 到底做了什么？线程为什么"轻"？》——线程和进程在内核里到底是什么关系？为什么说 Linux 线程本质是"共享资源的进程"？一张图给你讲透。如果你想把这些底层原理真正用到项目里，我整理了 30 个 C++ 硬核实战课程：线程池、内存池、无锁队列、高性能网络库、协程库、Mini-Redis、Mini-Nginx 等，每个设计决策都讲"为什么这么做"。感兴趣可以加微信：jkfwdkf，备注「项目实战」。觉得有收获，点赞、在看、转发，让更多程序员看到 🙏

但它不是万能的：小文件频繁映射、解除映射，反而因为缺页和页表操作比 read 慢；对特别大的文件顺序读，read 配合预读也很快。工程上要根据访问模式选。



## 五、写时拷贝（COW）：fork 为什么快得离谱？



最后回到第三个问题：一个占 10GB 内存的进程 fork，只要几毫秒，怎么做到的？



如果 fork 老老实实把 10GB 内存全拷贝一份，既慢又浪费。而且绝大多数情况下，子进程 fork 后马上就 exec 去执行别的程序了，这 10GB 拷贝完全白费。



聪明的做法是写时拷贝（Copy-On-Write）：



1. fork 时只复制页表，不复制物理内存。父子进程的页表指向同一批物理页。



2. 内核把这些共享页在页表里都标成只读。



3. 谁想写某一页，就触发一次缺页中断，内核这时才给它拷贝一份新的物理页，改写它自己的页表。

## 六、三个必须避开的陷阱



陷阱一：malloc 成功，不代表内存真的够用



Linux 默认允许"超额承诺"（overcommit）：malloc 时只检查虚拟空间，不检查物理内存够不够。等程序真正写入、缺页要分配物理页时，如果物理内存耗尽，内核会启动 OOM Killer 杀进程。



也就是说，内存不足的报错，可能不出现在 malloc 返回 NULL 那一刻，而是在几小时后某次普通的写入，程序被直接杀死。 排查线上 OOM 时，要看 dmesg | grep -i oom，而不是只看代码里有没有判 NULL。



陷阱二：首次访问缺页，造成延迟抖动



低延迟系统（交易、游戏服务器、高频网络服务）里，刚分配的内存第一次被访问，会触发缺页，延迟从几十纳秒跳到微秒级，形成尾延迟毛刺。常见对策是启动时预热：



内存池、对象池在初始化阶段"先摸一遍内存"，很多时候就是出于这个目的。



陷阱三：对大内存进程 fork，COW 可能让内存翻倍



Redis 做 RDB 持久化时，会 fork 一个子进程去写盘，靠的就是 COW，父进程可以继续处理请求。但如果这期间写入很频繁，父进程会不断改写共享页，每改一页就触发一次拷贝。最坏情况下，内存占用接近翻倍。



这也是为什么 Redis 官方建议，机器内存要留出足够余量，不能把 maxmemory 设到接近物理内存上限。另外，fork 本身要复制页表，进程越大页表越大，10GB 以上的进程 fork 也可能造成毫秒级到上百毫秒的阻塞。



## 七、高频面试题精析



Q1：虚拟内存有什么作用？



三个：隔离（每个进程有独立地址空间）、连续（物理零散、虚拟连续，简化内存分配）、超量（虚拟空间可大于物理内存，配合惰性分配和换页）。



Q2：什么是缺页中断？分几种？



访问的虚拟页当前没有有效映射时，CPU 触发的异常，由内核处理。分次缺页（不需读磁盘，微秒级）和主缺页（要读磁盘或 swap，毫秒级）。地址本身非法时，内核会发 SIGSEGV。



Q3：malloc 一定会分配物理内存吗？



不会。malloc 只是分配虚拟地址空间（小块从堆里切，大块用 mmap），物理页在第一次访问时通过缺页中断才分配。



Q4：fork 为什么快？COW 是怎么工作的？



fork 只复制页表，父子共享物理页并标记只读，写入时触发缺页，内核再给写入者拷贝一份新的物理页。



Q5：mmap 和 read 有什么区别？



read 要把页缓存拷贝到用户缓冲区（一次 CPU 拷贝），mmap 把页缓存直接映射进虚拟地址空间，省掉这次拷贝，但依赖缺页触发加载。适合大文件随机访问，不适合大量小文件频繁映射。



## 结语



虚拟内存看起来复杂，其实核心只有一句话：



> 进程看到的是虚拟地址，CPU 通过页表翻译成物理地址；翻译不到，就触发缺页中断，让内核"现场补课"。



进程看到的是虚拟地址，CPU 通过页表翻译成物理地址；翻译不到，就触发缺页中断，让内核"现场补课"。



• malloc 的惰性分配：页表里先不建映射，用到才补



• mmap 读文件：把页缓存直接映射进来，用到才加载



• fork 的写时拷贝：先共享页，写的时候才复制



这三个看似不相关的机制，用的是同一个思路：能拖到最后一刻再做的事，就不要提前做。
