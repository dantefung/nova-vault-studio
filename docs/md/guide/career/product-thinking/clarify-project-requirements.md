# 【精读】如何澄清一个项目需求？（曹宇/Heidixie呀）

> **核心结论**：项目需求澄清是一个**两次交接 + 三个环节**的协同流程。**业务 PM 讲清楚 WHY**，**产品经理 + 业务 PM 对焦项目目标/价值/衡量**，**产品经理细化方案设计**。重要的不是堆叠问题清单，而是**分清角色职责 + 分步对焦**。

> **关键洞察**：
> - **WHY vs HOW**：业务 PM 主理 WHY，产品经理主理 HOW
> - **三个核心问题**：项目目标 / 项目价值 / 成功衡量标准——任何项目必须先回答
> - **环节交接不能跳跃**：A 没讲清楚就别去关心 B
> - **大颗粒问题 vs 颗粒度**：必要时候把大问题**抽象成论文题目的形式**，便于检索前人经验

## 一、命题的澄清

**场景**：有业务方的产品，特别是企业内支撑类产品。

**三种角色**：
- **业务方**（多个团队时）→ **业务需求代表 / 业务 PM**
- **业务 PM** → 收集/诊断/统一业务策略 + 收口需求 + 与产品团队对接
- **产品经理** → 接收需求 + 转化为产品需求

**两种关键转换**：
- **原始需求 → 业务需求**：业务 PM 完成
- **业务需求 → 产品需求**：产品 PM 完成

中文都是「需求」二字，但内涵完全不同。

## 二、为什么要专门做这件事？

### 现实场景：粗颗粒问题模板

```
1. 我要什么
2. 何时要
```

**回答了，但几乎没用**。

### 为什么？

- **大部分人擅长回答 "我要什么" 和 "何时要"**
- **不擅长讲清楚：背景 / 问题 / 痛点 / 数据 / 案例**
- 类比：「我饿了，能吃这包泡面吗」没说清「我已经 N 小时没吃饭、对吃什么不挑剔、5 分钟能端上桌」

### 解决路径两条

| 路径 | 优劣 |
|------|------|
| **面对面聊**：从一个一个碎片信息问出全貌 | 慢，沟通成本高 |
| **优化问题清单**：一开始就收集高质量需求信息 | 高效，但不能**取代**当面沟通 |

## 三、问题清单 Beta 版设计

### 好的问题清单 3 个特征

1. **厘清职责**：分清业务需求代表、产品经理两个角色 → 问题清单**分类**
   - 业务 PM：讲清楚问题、问题重要性、对解决的期望
   - 产品经理：基于需求分析 + 其他输入 → 确认**项目目标 / 价值 / 衡量**
2. **提供回答指导**：直接给「术、法、器」
   - **术**：个体经验（怎么做的具体方法）
   - **法**：操作步骤（可复用的流程）
   - **器**：体系化方法论 + 适用条件
3. **问题能分能总**：不同场景用不同子集

### 问题清单的流程图（角色分配）

```
[原始业务需求]
     ↓
[业务 PM 收口与澄清] ← 重点讲 WHY + 业务期望
     ↓
[产品经理接手 + 综合输入] → 产品能力诊断 / 用户视角 / 行业分析
     ↓
[业务 PM + 产品 PM 对焦三大核心问题]:
   · 项目目标是什么？
   · 项目价值是什么？
   · 成功衡量标准是什么？
     ↓
[产品经理主导方案设计]:
   · 分期方案设计
   · 风险与挑战评估
   · 业务需求 → 产品功能列表 → 技术预研 + 成本评估
     ↓
[PRD 阶段 → 项目执行]
```

## 四、问题应该怎么被回答？

### 业务 PM 回答的 6 类问题

1. **项目对应的当前业务现状是什么**？
2. **当前业务问题 / 痛点是什么**？
3. **业务期望是什么**？
4. **业务上有成功的案例可以借鉴吗**？
5. **业务上对项目上线的时间窗是怎样的**？
6. **业务上对上线后的预期收益是怎样的**？

### 双方共同回答的 6 类问题（项目级共识）

1. **项目目标 / 想要达到的目的**
2. **项目价值 / 为什么重要 / 不做的后果**
3. **变化 / 前后对比**
4. **衡量指标 / 成功的衡量**
5. **项目范畴 / 范围内的标准**
6. **分阶段目标 / 优先级 / 路径**

### 产品经理回答的 6 类问题

1. **方案**是什么？
2. **方案的可选**项？
3. **方案如何变成可执行**的需求列表？
4. **风险**是什么？是否可被规避或转移？
5. **预估成本**是什么？
6. **新引入的依赖**是什么？是否可控？

## 五、双重萃取法（把工作归到流程）

任何场景都可以套用作者在工作中提炼的六步：

```
1. 接手问题或自己发现问题
   ↓
2. 分析问题
   ↓
3. 判断问题属于「解答型」还是「解决方案型」
   ↓
4. 解答问题 / 提供解决方案
   ↓
5. 跟进方案实施
   ↓
6. 校验问题是否已解决
   ↓ 回到 1（循环）
```

**适用一切场景**：汇报 / 规划 / 会议 / 项目立项 / 日常决策。

## 核心洞察

### 1. 问题颗粒度是关键

| 粗颗粒 | 细颗粒（推荐） |
|--------|---------------|
| 「怎么提需求」 | 「如何把『具体场景问题』抽象成『通用问题格式』以便检索？」 |
| 「产品怎么做」 | 「答案的输出要 30+ 人能听懂」 |

### 2. 三层交接不能跳

> 每个环节都应该致力于回答清楚**该环节的关键问题**，而不是跳跃式关心下一个环节。

当 A 环节问题都没讲清楚，**别去关心解决方案**。

### 3. 业务 PM 的核心价值不在于「懂产品」

业务 PM 真正价值 = 把**原始需求转化为业务需求**——这是产品经理视角整理需求的前置工序。

### 4. 问题清单的本质是「对话模版」

不是审计问题清单，不是官僚流程。**目的是把混乱沟通变成有结构的高效对话**。

## 跨领域应用

| 场景 | 应用 |
|------|------|
| 独立开发自己做需求 | 用三层框架：原始需求（用户反馈） → 产品需求（自己抽象） → 实施 |
| 副业团队协作 | 哪怕两个人也分「需求方」「执行方」 |
| AI Coding 项目 | 「业务 PM」= 你给 AI 的 prompt，「产品 PM」= AI 给你的方案 |
| 团队内沟通 | 三层框架用作内部分享大纲 |
