# 【万字】Agent 的本质：用 Token 换架构

> Agent 的本质：用更多成本（多轮推理 + 多次工具调用 + 更高延迟/Token），换开发与维护成本的下降（分支更少、扩展更快、长尾更适配）。

市场看到 Manus 这种 Agent 很兴奋。Agent 为什么会出现？它解决了哪部分问题？它在解决过程中有何困难和卡点？带着这些问题进入今天的学习。

<!-- more -->

## 为什么 Agent 会出现？

模型虽然很强大，但天生缺陷——它只包含训练后的内置数据。这产生第一个矛盾：

- 信息爆炸严重，模型跟不上节奏，也不愿意吃互联网上的垃圾数据
- 企业还有大量私有数据，在公司场景下必须与外部世界交流

所以 **Agent 出现的第一个原因是与外部世界进行信息交流**，尤其垂直领域数据不足时模型容易胡言乱语。

但问题是：如果仅仅这个原因，直接采用 Workflow（标准 RAG 逻辑）不就好了？

![RAG 逻辑](images/agent-token-architecture/001.png)

这就引出了 **Agent 最深的冲突：Agent 能做的事情 Workflow 都能做，那么 Agent 存在的意义是什么？** Workflow 可以做循环、重试、复杂策略，只不过这些必须由人显式编码。当环境复杂度上升，Workflow 的成本曲线会很难看：

![Workflow 成本曲线](images/agent-token-architecture/002.png)

企业真实场景里，复杂度增长来自三类"不可穷举"：

1. **工具/系统不可穷举**：今天查公网，明天查 A 公司知识库、后天查 B 的 CRM、再后天接入 CDE……
2. **意图组合不可穷举**：一个问题同时包含"解释概念 + 对比多家公司 + 要求给出原因 + 产出结构化表格"
3. **异常与边界不可穷举**：权限不足、字段缺失、数据冲突、召回为空、网页结构变化、接口限流……

这些都可以写进 Workflow，但会变成典型的分支爆炸 + 维护爆炸。**Agent 架构的优势就出来了**：判断用户意图、怎么调用工具、工具调用后的数据对不对，这些繁杂的事情全部丢给模型。

> Agent 解决的不是"怎么回答"的问题，而是给出一套将问题编译为可执行计划的框架。Agent 是一种工程架构层面的优化，核心不是"更聪明"，而是把工程师在开发期显式写死的控制流（if/else、编排、异常处理），**迁移到运行时由模型来决定**（路由、工具选择、多轮尝试、失败重试、补槽追问、结果校验）。

## Agent 的发展史

当前最经典的 Agent 架构是 ReAct，2022 年提出（论文《ReAct: Synergizing Reasoning and Acting in Language Models》）。那时不支持 Function Calling，需要自己实现——用提示词做识别输出，或做微调（成本高）。

**2023 年 6 月**，OpenAI 提出 Function Calling，作为 ChatGPT 正式能力，成为事实标准，Agent 出现变得顺滑。

**2025 年**，国内 Agent 概念从年初 Manus 开始火热。追溯早期出圈的 Agent 是 2023 年 3 月的开源项目 Auto-GPT。从"2025 AI 应用元年"转向"2025 AI Agent 元年"，模型推理能力和上下文长度大幅加强，下半年工具调用能力明显增强。

**MCP 概念火起来**：解决 Function Calling 留下的工程维护问题，让人少开发工具、直接用社区的，几乎成为事实标准。

**2025 年 10 月**，Claude 正式提出 Skills 技术，对整体 Function Calling 进行补足。

现阶段使用 **Skills + Function Calling + 上下文工程**，准确率已经可以做到 90%+。

> 结论：之前对 Agent 的很多质疑乃至产品体验差的问题，在 2026 年应该会得到很大缓解。你怎么优化都可能比不上模型一次能力升级。

## Function Calling

FC 就是用一套工程架构把之前模型判断（如何用工具）的工作流替代掉。流程：

1. 对话中，LLM 根据用户问题判断是否需要调用函数
2. 如果需要，输出结构化 JSON 请求（含函数名和参数）
3. 真正调用脚本的是后台程序，拿结果再二次调用模型

![Function Calling 流程](images/agent-token-architecture/003.png)

几个要点：
- **模型不会直接调用工具**，只返回结构化调用指令（这是模型专门训练的结果）
- 如果工具接口挂了、容错不好，模型就不会回答用户了
- Tools 过多会占用上下文长度
- FC 使用好坏很依赖模型对意图识别的能力（主要靠 description 参数）

## MCP

MCP 为什么出现？回归 Function Calling——它解决的是"单个模型怎么按你定义的 JSON 协议调你自己的 API"。但**工具变多后维护就爆炸了**。

案例：企业有 10 个 AI Agent（N）接 20 个数据源/工具（M）。如果每个应用为每个工具写专用适配代码，需要 200 个集成点。生产上的 Agent 可能同时调 ChatGPT、Gemini、DeepSeek，它们的 Tools 接口还不一样。

MCP 引入"客户端-服务器"架构标准化：**集成点从 N×M 骤降到 N+M**。都把 MCP 当成一个"工具总线"：

- **MCP Server（工具提供者）**：暴露工具列表 + 接受调用 + 返回结果
- **MCP Client / Host（AI 应用）**：连接 server、发现工具、转发调用、回传结果给模型

![MCP 架构](images/agent-token-architecture/004.png)

### 遗留问题

MCP 解决工具过多的维护问题，但**不能解决工具多了乱调用、错调用的问题**，还有工具爆炸、工具如何组织的问题。

## Skills

Anthropic 对 Skill 的定义：一个文件夹，装着说明文档、脚本和资源，模型执行任务时先扫一圈所有 Skills，觉得哪个有用就把完整内容拉进上下文。

> Skill = 一份可反复调用的专业 SOP + 说明书，由模型自己按需加载

Skills 诞生的原因：

### 一、提高工具调用稳定性
把"怎么用工具把事做对"的套路（选择条件、步骤、校验、兜底）沉淀为可复用模块，降低随机性。以前这在 ReAct 工程架构里，现在有 Skills 可降低工程难度。

### 二、长提示词与硬编码流程的维护问题
提示词正在往伪代码方向发展，为稳定输出不断加东西（业务规则、数据规则、工具规则、输出规则、合规规则、few-shot 示例），导致：
- 上下文常驻：成本高、干扰大
- 版本不可控：改 Prompt 影响全局，回滚困难
- 复制漂移：A 项目 copy 一份、B 项目 copy 一份，三个月后不一致
- 排障困难：不知道错在哪

Skills 的解题思路跟 MCP 类似：把所有配置信息写到统一地方，需要时再拿出来。

![Skills 案例](images/agent-token-architecture/005.png)

**案例**：老板 BI Agent 配置了一批 Tools/MCP 工具（get_sales_report、get_marketing_spend、get_cashflow_status）和两个 Skills（boss_bi_dashboard_cn 教模型如何按老板视角解释数字、excel_analysis_skill 教模型用 code execution 分析 Excel）。用户问"看看今年 Q3 的营收和投放，简单说说是不是该收一收预算？"流程：
1. **Skill 检索**：模型遍历 Skills 的 meta，激活 boss_bi_dashboard_cn，读取 instructions.md 拉进上下文
2. **Skill 里面决定工具调用**：instructions.md 写清楚了该先查什么、用什么工具
3. **数据处理 + SOP**：走 Function Calling 逻辑拿数据，按 instructions 使用

## ReAct 框架

编排层是智能体系统的核心控制单元，负责组织信息流和执行推理循环。常见推理框架：**ReAct** 与 **CoT**，可扩展到 **ToT**（思维树）。

- **ReAct**：强调模型在回答前进行连续的内省和行动选择，提高准确度和可追溯性
- **CoT（思维链）**：引导模型通过生成中间推理步骤分解问题，增强解决复杂问题的准确性（降低幻觉）
- **ToT（思维树）**：在 CoT 基础上允许模型在多个备选思路间比较，适用于探索多种方案的策略任务

### ReAct 和 CoT

ReAct 与 CoT 都是推理策略框架（编排层具象化实现），描述如何组织模型的推理过程、生成步骤、提示词结构。

> ReAct 规定了：先思考（Thought）→ 行动（Action）→ 等待结果（Observation）→ 再思考……而这个"Thought"怎么写？通常就是一个 Chain of Thought 推理块。

所以 **ReAct 是容器，CoT 是内容**。ReAct 是最"Agent"化的、CoT 是最基础的。Agent 架构中不可能每一步都调用工具，很多时候只是"组织思维/语言"，CoT 可以有效降低幻觉率。

## 结语

市场之所以为 Manus 这类 Agent 兴奋，不是因为它"更聪明"，而是因为它把原本需要工程师在 Workflow 里写死的路由、工具选择、重试等控制流，**迁移到运行时由模型来决定**，从而在"工具多、意图组合多、异常多"的企业场景里显著降低开发与维护成本。

过去三年的脉络：ReAct 提供推理+行动的循环框架，Function Calling 让工具调用标准化，MCP 缓解工具爆炸带来的集成维护成本，Skills 把"怎么把工具用对"的 SOP 沉淀下来提升稳定性。

> 25 年工具调用已取得长足进步，但**记忆模块依旧是老大难问题**。2026 年底层模型一定会在这块做出突破。
