# 不懂上下文切换，无法真正吃透 Linux 内核进程管理

> 从原理到源码到线上排查，把进程上下文切换讲透。

---

## 一、为什么要吃透进程上下文切换

### 1.1 上下文切换在 Linux 调度体系中的核心地位

`top` 或 `vmstat` 里的 `cs`（context switch）数字高不一定马上有病，数字不高也不能证明身体倍儿棒。真正重要的是：它为什么发生，谁在切换，切换之后 CPU 在干什么。

Linux 调度器决定哪一个可运行任务占用 CPU，这个交接动作就是上下文切换。没有它，CFS、EEVDF、实时调度、CPU 亲和性、负载均衡这些机制都只是纸上的排班表。

### 1.2 进程切换 vs 线程切换 vs 中断上下文切换

- **进程切换**：两个不同进程，通常需要切换地址空间
- **线程切换**：同一进程内线程共享 `mm_struct`，不需要重新切换用户页表，但寄存器、内核栈、TLS、FPU 状态等仍要处理
- **中断上下文切换**：硬中断到来时 CPU 暂停当前指令流，`current` 仍指向被中断任务。硬中断不能睡眠，但中断退出后可能触发调度

### 1.3 性能视角

直接成本：寄存器保存/恢复、栈指针切换、调度状态维护、CR3/PCID/ASID/TLB 处理。

间接成本更麻烦：任务 A 刚把热点数据塞进 L1/L2 缓存，任务 B 被调度上来挤掉缓存行，A 再运行时需重新加载。CPU 使用率只有 60% 但负载很高，往往就是 CPU 忙着唤醒、抢占、迁移、等待锁。

## 二、核心基础

### 2.1 进程上下文：用户上下文 vs 内核上下文

- **用户上下文**：用户态寄存器、指令指针、栈指针、FPU 状态、TLS 等
- **内核上下文**：内核栈、调用链、跨调用保存的寄存器、调度状态、地址空间信息

系统调用进入内核不等于进程上下文切换——可能只是特权级转换，没有换任务。

### 2.2 task_struct 核心字段

`__state`（运行/睡眠状态）、`stack`（内核栈）、`on_rq`/`on_cpu`（运行队列和 CPU 状态）、`prio` 系列（优先级）、`sched_class`（调度类）、`se`（公平调度实体，含 vruntime/lag/deadline）、`mm`（用户地址空间）、`nvcsw`/`nivcsw`（自愿/非自愿切换计数）、`thread`（架构相关线程状态）。

### 2.3 内核栈机制

每个线程有独立内核栈。`switch_to()` 切换任务时，关键动作是把旧任务内核栈指针保存到 `prev->thread.sp`，再加载 `next->thread.sp`。换完 `%rsp` 后，CPU 已经站在另一个任务的调用栈上。

### 2.4 寄存器上下文

x86_64 的 `__switch_to_asm` 重点保存 callee-saved 寄存器。用户态寄存器通常在进入内核时已保存到 `pt_regs`。

## 三、上下文切换核心原理

### 3.1 本质：CPU 执行权转移

上下文切换的本质不是"保存一堆数据"，而是 CPU 执行权发生了转移，保存和恢复状态是为了让这次转移可逆。

### 3.2 两类切换

- **主动切换（自愿）**：任务 sleep/wait/yield，主动放弃 CPU
- **被动切换（非自愿）**：时间片耗尽、高优先级任务抢占、负载均衡迁移

### 3.3 进程 vs 线程切换开销对比

| 成本项目 | 同进程线程切换 | 跨进程切换 |
|---------|--------------|-----------|
| 通用寄存器与内核栈 | 需要 | 需要 |
| 调度器状态更新 | 需要 | 需要 |
| 用户页表上下文 | 通常相同 | 通常不同 |
| TLB 复用 | 更有利 | 取决于 PCID/ASID |
| 缓存工作集影响 | 取决于线程工作集 | 取决于进程工作集 |
| NUMA 与迁核代价 | 可能很高 | 可能很高 |

线程切换不一定始终便宜很多——缓存和迁核代价取决于实际工作集。

## 四、完整切换流程

### 4.1 调度入口

`schedule()` → `__schedule()` → 选任务 → `context_switch()` → `switch_to()`。

### 4.2 进程选择

经典 CFS 用红黑树按 vruntime 排序，选取最左实体。Linux 6.6 开始转向 EEVDF：任务需满足 eligibility 条件，再选择虚拟截止时间更早的实体。

### 4.3 核心步骤

1. 保存 callee-saved 寄存器到旧内核栈
2. 保存旧 `%rsp` 到 `prev->thread.sp`
3. 加载 `next->thread.sp` 到 `%rsp`
4. 从新任务栈弹出寄存器
5. 进入 `__switch_to()` 处理 FPU、FS/GS、TLS、PKRU 等
6. 地址空间切换：`switch_mm_irqs_off()` 处理 CR3/PCID/ASID

### 4.4 切换收尾

`finish_task_switch()` 处理旧任务状态、性能事件、RCU、tick 等。新任务从自己上次暂停的 `switch_to()` 之后继续执行。

## 五、关键源码

### 5.1 x86_64 switch_to 汇编

核心汇编将 callee-saved 寄存器压栈 → 保存 `%rsp` → 加载新 `%rsp` → 弹出寄存器 → `jmp __switch_to()`。没有显式恢复指令指针，通过切换栈和恢复返回地址让控制流自然回到新任务原来的位置。

### 5.2 地址空间切换

`switch_mm_irqs_off()` 读取当前加载的 mm、ASID 和 TLB generation，决定是否需要刷新。现代 x86 利用 PCID 避免每次切换清空全部 TLB。

## 六、开销详解

### 6.1 直接开销
寄存器读写、栈数据保存恢复、页表切换、调度器函数调用、运行队列加锁等。

### 6.2 间接开销（通常更严重）
- TLB 失效导致页表遍历
- 缓存污染：新任务工作集挤掉旧任务缓存行
- 跨 NUMA 节点迁移增加内存访问延迟

### 6.3 软开销
调度队列遍历、vruntime/lag/deadline 维护、压力统计、perf 事件、RCU、负载均衡等。

## 七、线上排查实战

### 7.1 核心工具

| 工具 | 用途 |
|------|------|
| `vmstat` | 系统整体 cs、r、b、in |
| `pidstat -w` | 进程级自愿/非自愿切换 |
| `pidstat -w -t` | 线程级切换 |
| `/proc/<PID>/status` | 读取 nvcsw/nivcsw |
| `perf stat` | 总切换数量 |
| `perf sched latency` | 调度延迟 |
| `perf sched timehist` | 时间轴、等待时间、运行时间 |

### 7.2 自愿切换过高

业务频繁主动阻塞：futex、epoll_wait、poll、read、nanosleep 等。排查方向：锁竞争、连接池不足、线程数远超资源数。

### 7.3 非自愿切换过高

CPU 过载、可运行线程太多、实时任务抢占、容器 CPU 配额、任务频繁迁移。排查方向：运行队列长度、线程数、cgroup 限制、CPU 亲和性。

### 7.4 优化方案

1. 线程数匹配 CPU 核心数（CPU 密集型）或下游容量（I/O 密集型）
2. 减少共享状态，锁分片，缩短临界区
3. 避免惊群，唤醒要有针对性
4. 慎用 CPU 亲和性，防止负载失衡
5. 别乱改调度策略为 SCHED_FIFO
6. 持续测量：vmstat → pidstat → perf sched → 火焰图

## 八、高级特性

### 8.1 调度策略

- `SCHED_OTHER`：默认公平调度，nice 影响权重
- `SCHED_FIFO`：实时 FIFO，同优先级无时间片轮转
- `SCHED_RR`：实时轮转，同优先级有时间片轮转

### 8.2 内核抢占模型

非抢占 → 自愿抢占（cond_resched）→ 可抢占（广泛抢占点）→ PREEMPT_RT（最低调度延迟）。

### 8.3 优先级反转

高优先级线程等低优先级线程释放锁，低优先级被中优先级压制。内核通过优先级继承缓解。

### 8.4 Linux 6.6 EEVDF

EEVDF 利用任务 lag 判断 eligibility，再根据虚拟截止时间选择任务，更好兼顾延迟敏感任务和不同 slice 请求。

## 九、面试核心问题

- **进程切换为什么比线程切换开销大？**：核心差异来自地址空间，线程共享 mm 时通常可避免页表切换，但缓存和迁核代价取决于实际工作集
- **中断上下文为什么不能发生进程切换？**：硬中断不是可调度任务，没有睡眠与恢复语义，但中断退出后可能触发调度
- **switch_to 为什么需要汇编？**：C 编译器无法精确控制寄存器压栈时机和栈指针切换
- **高并发如何避免无效上下文切换？**：控制活跃线程数、减少锁竞争、避免惊群、合理设置线程池/连接池/队列长度、保持局部性

## 十、实践建议

- 少创建"以防万一"的线程
- 给线程池和任务队列设置边界
- 监控 cs、自愿/非自愿切换、CPU migration、运行队列长度与 P99 延迟
- 压测观察线程数增加后吞吐是否线性增长
- 升级内核时注意调度器变化（CFS → EEVDF）
