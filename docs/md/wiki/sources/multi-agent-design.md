# 多 Agent 系统的设计哲学

> 当多个 AI 智能体协同工作时，1+1 远大于 2。真正决定系统好不好的，不是 Agent 的数量，而是任务怎么拆、角色怎么分、信息怎么传、边界怎么控。

![文章封面](images/multi-agent-design/001.jpeg)

## 01 Multi-Agent 不是「群聊」，而是「协作操作系统」

单 Agent 像一个自由职业者，什么都自己来，灵活但上限低；多 Agent 系统像一家公司，有分工、有流程、有审批。

一个成熟的多 Agent 框架，通常包含**六层架构**：

| 分层 | 主要职责 | 关键设计问题 |
|------|---------|-------------|
| 任务层 | 接收用户目标，形成可执行任务 | 任务能不能拆？验收标准清不清楚？ |
| 编排层 | 决定谁做什么、何时做、如何合并 | 串行、并行、图编排还是动态调度？ |
| Agent 层 | 执行具体推理、工具调用和局部决策 | 角色边界在哪？上下文多大？用什么模型？ |
| 工具层 | 连接代码、搜索、数据库、API 等 | 权限怎么控？失败了怎么重试？ |
| 记忆层 | 保存任务状态、历史事实、长期偏好 | 记什么？什么时候召回？怎么过期？ |
| 评估层 | 检查结果质量、事实一致性 | 怎么自动验证？什么时候需要人介入？ |

![六层架构](images/multi-agent-design/002.jpeg)

**关键事实**：Agent 只是系统中的一个节点。真正决定系统稳定性的，是编排、状态和边界控制——就像一支军队的战斗力，不取决于单个士兵有多能打，而取决于指挥体系有多清晰。

## 02 为什么要拆分 Agent？

单 Agent 存在四个天然的天花板，模型再强也绕不过去：

### 天花板一：上下文容量有限

上下文窗口虽做到几十万 token，但「装得下」不等于「用得好」。同时塞入需求、搜索、实现、测试、审查，注意力被稀释——每个环节做到 60 分，没有 90 分。

### 天花板二：角色冲突

写代码的人给自己的代码打分，天然倾向于打高分。同一 Agent 既生成又审查，「自我审查」基本等于没审查——有研究显示自我审查发现缺陷的概率比独立审查低 60% 以上。

### 天花板三：缺乏对抗验证

单 Agent 推理路径是线性的，如果起点假设错了，错误会一直延续到执行结束才暴露。如果有另一个 Agent 从不同角度挑战假设，问题在早期就能被揪出来。

### 天花板四：无法并行

搜索代码库、分析架构、研究技术方案——这三件事明明可以同时做，单 Agent 却只能一件一件来。

![单 Agent 天花板](images/multi-agent-design/003.jpeg)

> 拆分 Agent 的本质不是「多找几个人干活」，而是通过角色分离，让每个 Agent 只聚焦一件事，再通过结构化协调，合力产出高质量结果。

## 03 角色设计：给 AI 团队分配「专业岗位」

最常见的五种角色：

| 角色 | 核心职责 | 关键要求 | 绝对不能做 |
|------|---------|---------|-----------|
| **Manager**（编排者） | 拆解任务→分配角色→汇总结果→质量把关 | 全局视野、判断力 | 不写代码、不搜文件 |
| **Explorer**（探索者） | 搜索代码、分析架构、收集信息 | 只读权限、广撒网 | 不改文件、不产出方案 |
| **Developer**（执行者） | 写代码、改配置、实现功能 | 在隔离环境中操作 | 不审查自己的代码 |
| **Reviewer**（审查者） | 审查质量、安全漏洞、规范遵守 | 独立性、批判性思维 | 不改代码、只提意见 |
| **Tester**（验证者） | 生成测试、运行回归、检查覆盖率 | 不信任实现代码 | 不修改被测代码 |

**黄金法则**：一个人的代码，另一个人审查，第三个人测试。执行者 ≠ 审查者 ≠ 验证者，三个角色必须是三个独立的 Agent 实例，不能是同一个 Agent 换个 Prompt 就上场。

### 同一个模型，不同的「人格」

角色的差异靠 System Prompt 约束出不同的行为模式：

- **Developer**：「你是专业的代码实现者，只负责写代码。不要审查自己的代码——那是 Reviewer 的工作。」
- **Reviewer**：「你是严格的代码审查者，默认态度是不信任。只提修改意见，不要动手改代码。」
- **Tester**：「你是测试工程师，目标是找出代码的缺陷。假设代码里一定有 Bug，你的任务就是证明它。」

## 04 三种经典协作模式

### 模式一：Manager-Worker（中心化调度）

```
      Manager
      /    |    \
   Worker Worker Worker
```

Manager 拆解任务、分配下去、汇总结果。适合软件功能开发、Bug 修复等复杂任务的一次性交付。

- 优点：责任清晰，质量可控
- 缺点：Manager 是瓶颈，其能力决定系统上限

### 模式二：Pipeline（流水线接力）

```
AgentA → AgentB → AgentC → AgentD
```

每个 Agent 负责一个环节，做完传给下一个。适合数据处理、CI/CD 检查链、内容生产流水线。

- 优点：高度专注，数据流清晰，容易定位问题
- 缺点：串行等待，上游错误被下游放大

### 模式三：Peer-to-Peer（对等协商）

```
AgentA ⇄ AgentB ⇄ AgentC
```

每个 Agent 地位平等，各自独立形成判断，然后对比、辩论、达成共识。适合架构设计评审、技术选型讨论。

- 优点：多视角覆盖盲区，对抗性验证
- 缺点：协调成本高，可能陷入「辩论死锁」

### 真实系统：三种模式混搭

一个代码重构任务：

1. **专业分工**：Manager 拆子任务，Explorer 搜分析、Developer 编码、Reviewer 审查
2. **并行处理**：32 个文件按模块拆 4 组，4 个 Developer 并行
3. **流水线接力**：Developer 写完→Reviewer 审查→Tester 测试

总时间 ≈ 4 个阶段耗时，而非 32 个文件逐个串行。

## 05 Agent 之间如何通信？

### 方式一：结构化输出传递

Agent 之间通过 **JSON Schema** 传递信息，而不是自由文本。自由文本容易遗漏和误解，结构化字段零歧义。

```json
{
  "files_found": ["src/auth/login.ts", "src/auth/token.ts"],
  "auth_method": "JWT",
  "token_storage": "localStorage",
  "concerns": ["token 未加密存储", "缺少 refresh 机制"]
}
```

### 方式二：Manager 中转

Worker 之间不直接通信，所有信息由 Manager 汇总后再分发。Manager 的核心职责是「翻译和精简」——从 5000 tokens 的报告中提取 500 tokens 关键上下文传给下游，减少噪音、节省 Token。

### 方式三：共享上下文文件

Agent 之间通过读写中间文件传递信息，类似微服务消息队列。

- Manager 创建 task.md（任务描述、分配、状态）
- Worker A 完成后写入 result_a.json
- Worker B 启动时读取 task.md + result_a.json
- 所有 Worker 完成后 Manager 读取汇总

好处：解耦、可追溯、可恢复——任务中断了从中间文件继续，不用从头重来。

### 方式四：环境变量注入

通过环境变量或 Metadata 注入小而固定的配置信息（项目路径、分支名、部署环境、约束条件等），直接注入上下文。

## 06 从 Demo 到生产：工程落地的七个真正难点

真正的难点不是模型能力，而是**可控性**——知道系统在做什么、为什么这么做、出了问题怎么定位、怎么恢复、怎么控制成本。

| 能力 | 为什么重要 | 设计建议 |
|------|-----------|---------|
| **可观测性** | 知道哪个 Agent 做了什么、为什么 | 记录任务、消息、工具调用、状态变化 |
| **可恢复性** | 长任务可能中断或失败 | 保存任务状态，支持从节点恢复 |
| **权限最小化** | 多 Agent 增加误操作面 | 按角色配置工具权限 |
| **成本控制** | 多 Agent 放大 Token 和工具成本 | 预算、轮次上限、停止条件 |
| **冲突处理** | 多个 Agent 可能给出不同结论 | 引入主 Agent 或 reducer 做最终决策 |
| **人工介入** | 高风险决策不能全自动 | 审批节点、暂停点、回滚方案 |
| **结果验证** | LLM 输出不能天然可信 | 测试、静态检查、事实引用、审查器 |

### 工具权限分级

| 工具类型 | 风险等级 | 推荐权限策略 |
|---------|---------|-------------|
| 只读代码搜索 | 低 | 多数 Agent 可用 |
| 文件编辑 | 中 | 只给 Executor 或主 Agent |
| Shell 命令 | 中到高 | 白名单或沙箱执行 |
| 外部 API 写入 | 高 | 需要审批或专用 Agent |
| 凭据访问 | 极高 | 默认禁止，必要时最小授权 |

> 工具越多，能力越强，风险也越高。权限边界比工具数量更重要。

## 07 五个关键实践 + 五个常见反模式

### ✅ 五个关键实践

1. **先 Scout 再 Split**：先一个 Agent 快速只读侦察，搞清楚任务实际规模和结构，再决定拆多少个 Agent
2. **设定 Agent 数量上限**：轻量 1-3 / 中量 3-5 / 重量 5-8。超过 8 个，先想想是不是应该拆成多个独立任务
3. **为每个 Agent 设定 Stop 条件**：不是「做完再停」，而是「满足条件就停」。Scanner 覆盖 90% 就停、Analyzer 找 Top 10 就停
4. **Manager 不做具体工作**：职责只有三个——拆解任务、分发和汇总、质量把关。一旦亲自上手，角色混淆，整体效率下降
5. **Parallel + Pipeline 混搭**：独立子任务用 parallel，有依赖的用 pipeline，需要多视角碰撞用 peer-to-peer

### ❌ 五个常见反模式

| 反模式 | 表现 | 后果 | 修正方法 |
|--------|------|------|---------|
| **过度拆分** | 5 个文件改动用了 5 个 Developer | 协调成本吃掉并行收益 | 同类任务少于 3 个不打散 |
| **角色交叉** | Developer 同时充当 Reviewer | 自我审查 = 没审查 | 强制分离不同 Agent 实例 |
| **全串行** | Pipeline 6 步，实际 3 步可并行 | 用户等太久 | 识别独立子任务，改 serial 为 parallel |
| **无结构输出** | Agent 之间传自由文本 | 下游可能误解上游结果 | 关键节点用 JSON Schema 约束 |
| **Manager 亲自动手** | Manager 看到 Developer 写得不好就自己改 | 职责混乱，Worker 闲置 | 让 Developer 重做，而非代替 |

## 写在最后：七个判断标准

判断一个多 Agent 框架好不好，看这七个问题：

1. 它如何拆任务和调度 Agent？
2. 它如何隔离和共享上下文？
3. 它如何管理工具权限和审批？
4. 它如何保存中间状态和长期记忆？
5. 它如何合并多个 Agent 的冲突结论？
6. 它如何验证结果是否真的完成？
7. 它如何控制成本、轮次和停止条件？

框架的 API 会不断变化，模型会不断出现，但这些设计问题是相对稳定的。

![结语](images/multi-agent-design/007.png)

> 多 Agent 协同不是「人多力量大」，而是 **角色清晰 × 信息通畅 × 边界明确**。三个要素缺一不可。

> 好的多 Agent 设计，每个 Agent 都像一颗棋子——单看很简单，组合起来却能解决极其复杂的问题。不好的设计呢？每个 Agent 都觉得自己很厉害，凑在一起却像一盘散沙。
