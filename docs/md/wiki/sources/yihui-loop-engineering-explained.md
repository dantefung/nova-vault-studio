# Loop Engineering 到底是什么？一篇文章彻底搞懂

> 很多开发者使用 AI 依然停留在「人肉循环」：人发指令 → AI 写代码 → 人手动复制报错 → AI 修改。yihui 深度拆解 Loop Engineering（循环工程）的本质：将单次交互升级为带有停止条件、自动化工具链与自愈机制的自主执行循环，介绍 Orchestrator、Loop Library、真实项目落地能力与局限。

<!-- more -->

Loop Engineering，最近你多半被这个词刷屏了。一个月前硅谷的大佬们还在讲 Harness，这个月开口闭口都是 Loop。

概念一个月换一茬，很多人开始慌：又要学新东西了？

先说结论：不用慌。这篇文章会把 Loop Engineering 讲明白，再给你推荐一个能直接上手的开源库。看完你会发现，它没那么玄，你甚至已经在用它的核心机制了。

读完这篇，你会知道：

1. Loop Engineering 到底是什么，和你现在用 AI 的方式差在哪

2. Orchestrator（编排者）是什么，为什么说你其实已经在用了

3. 想落地，你真正要做好的两件事，以及好循环的四个自查问题

4. 开源库 Loop Library 怎么用：现成的循环提示词，加一行命令安装的 Loopy 技能

5. 一个跑在生产环境的真实案例：用户提需求，Agent 自动开发、测试、上线

## 你现在用 AI 的姿势，是人肉循环

想想你平时用 AI 编程的样子：

1.写一段提示词发给 Agent

2.Agent 干完活，你回来测试

3.发现不对，再写一段提示词

4.再测试

提示词、测试、提示词、测试，如此无限循环下去。

哪里不对劲？这个循环里最累的环节是你。AI 负责写代码，你负责测试、找问题、汇报问题。说好的 AI 帮人干活，结果你成了 AI 的测试工程师。

那能不能让 AI 自主跑完所有流程？

能。这就是 Loop Engineering 的核心：把循环的执行者，从你换成 Agent。

## Orchestrator：循环的总控台，你其实已经在用了

具体怎么落地？先认识一个概念：Orchestrator，编排者。

它是整个循环的总控台。你把目标和交付标准设定给它，它自动派活给 Agent 执行，执行完自己验收，没达标就带着问题重新派发，一直干到达标为止。主打一个使命必达。

听着挺高级，其实你可能已经在用了。Claude Code 和 Codex 里的 /goal 命令，本质上就是一个 Orchestrator：你设定完目标，Agent 自己去想要做什么、然后执行、验收，不达标自己再来一轮。

所以编排机制这一层，现在的 Coding Agent 已经全给你做好了，轮不到你操心。

## 你真正要做好的只有两件事

想实现 Loop Engineering，剩下的功课就两件：

第一，把目标交代清楚。一个合格的目标一定是具体的、有边界的：做什么、做到什么程度、范围在哪，都要写明白。

第二，把验收标准说清楚。验收标准是让 Agent 知道「什么时候算做完了」，必须足够明确，最好能量化。

拿个例子对比一下。一次性提示词长这样：

> 把这个网站搞快一点。

循环提示词长这样：

> 找出加载最慢的页面，做一个针对性优化，然后重新测一次。变快了就保留改动，没变快就撤掉。重复这个过程，直到每个页面都达标，或者再怎么改也没有明显提升为止。

后者多了什么？测量方式、保留条件、停止条件。Agent 拿到前者只能干一轮，拿到后者就能自己转起来。

下一节要介绍的开源库 Loop Library，文档里有个说法我很认同：一个好的循环，要能回答四个问题。

1. Agent 到底要完成什么？

2. 它怎么知道这一轮的尝试有没有用？

3. 这一轮学到的东西，下一轮怎么用上？

4. 什么时候该收工，什么时候该停下来找人？

写循环提示词之前，拿这四个问题过一遍，基本不会跑偏。

## Loop Library

道理都懂，落笔还是不会写？给你推荐一个开源仓库 Loop Library：

它由 Forward Future 团队维护，目前 2000 多个 star。对你有用的是两部分：一个收集循环提示词的在线目录，和一个叫 Loopy 的 Skill。

逛目录：标准的循环提示词长什么样

打开它的在线目录（signals.forwardfuture.com/loop-library），里面收录了几十个经过审核的循环：SEO 审计、测试覆盖率、生产错误清理、文档同步，都是拿来就能用的。

每个循环的格式很统一：什么时候用（Use when）、提示词原文（Prompt）、怎么验收（Verify）、注意事项（Notes）。

拿目录里的「SEO/GEO 可见性循环」举例，它的目标写得非常明确：

> 对可抓取性、索引状态、页面意图、标题、内链、结构化数据、来源引用和答案优先内容做一次 SEO/GEO 审计。把发现的问题按预期影响排序，先修影响最大的那个，然后用同一套抓取和目标查询基准，在搜索引擎和 AI 答案引擎上重新测一遍。重复，直到没有严重技术问题、每个优先查询都有明确的可作答页面、基准测试里不再有高影响的缺口。

对照前面那四个问题看：做什么（SEO/GEO 审计并修复）、怎么验证（重跑同一套抓取和基准测试）、学到的怎么用（按影响排序，永远先修影响最大的）、什么时候停（三个条件全部满足）。全齐了，这就是标准答案的样子。先抄再仿，比闭门造车快得多。

目录里还有不少偏技术、适合 Vibe Coding 的循环，重构、测试、性能优化都有，大家可以自行去学习。

## 放进真实项目，Loop 能跑到什么程度

前面讲的都是原理和工具。但 Loop Engineering 真正有意思的地方在于：放进一个真实项目里，它能自动到什么程度？

我做了一个完整的综合实战，场景是这样的。

我们有一个部署上线的无限画布产品，用户可以在前端提交反馈，比如「我想要 Seedream 5 这个模型」。这条反馈会进入管理后台，变成一条待处理的记录。

你在后台给这条记录设定一个 Agent 处理目标：要做什么、做到什么程度。接下来的事情全自动：Agent 每隔半小时轮询一次数据库，发现有「需处理」的记录，就自动跑开发、测试的循环，直到跑通，把状态标成「AI 测试完成」。

你在开发环境验收，没问题就把状态切成「可上线」。之后 Agent 会接着把项目构建、部署的全流程也跑完。

定时轮询用的是 Codex 的 Tasks 功能：点左上角的 Tasks，手动创建一个任务，填入提示词，设置每 30 分钟执行一次。

## 最后，泼点冷水

Loop Engineering 对大部分新手来说，其实并不适用。它通常要到特定的开发阶段，或者你有一定工程背景才用得上，因为它对目标提示词的要求非常高。目标写歪一点，Agent 就朝着歪的方向勤奋地跑一晚上。

另外，从 Prompt Engineering 到 Harness 再到 Loop，概念一个月换一茬，你不需要有新概念焦虑。

现阶段，把和 Agent 对话的基本功练好才是最实在的。多沟通、多写提示词、多测试。和 AI 协作这件事没有捷径，用得越多越顺手。

到了某个阶段，你自然会开始琢磨：能不能让它自己跑完整个流程？到那时候，Loop Engineering 就不再是一个需要学习的概念，而是你自然而然会去做的下一件事。
