## 一、上一集留下的问题

上一集我们把 CRM 接进了 WorkBuddy，结论是：接得快，不是因为 MCP 好用，而是因为语义封装这层活，半年前给自己的侧边栏 Copilot 做的时候就做完了。

杨老师顺着这个往下问了一句，问到了正地方：

> 杨老师：那这层"语义封装"，跟我们片头写的本体论，到底是不是一回事？如果接口的语义做好就够用了，那本体论那套建模，还有什么实际的业务价值？

这一问把整件事推到了要害上。而且他自己已经带着答案了——他认为不是一回事，而且认为本体论那套是多余的。

那我们就把这场分歧摆开：到底是本体论重要，还是把 API 封装成一个语义清晰的 MCP Server 更重要？

![image](juepen-crm-s2e7/images/001.jpg)

## 二、先把老登那边的理由说到满

要驳一个判断，先得把它立稳。我认真想过，站在他那边的理由相当充分：

第一，事实摆在那儿。WorkBuddy 没读过我们任何一份数据模型，一张表结构都没见过。它只看了几句工具描述，就自己串出了推理链——先查详情、发现不够、再取 MEDDICC 评分。这是发生过的，不是假设。

第二，语义封装跟数据建模确实是两码事。我在工具描述里写"读这条线索已经算好的 MEDDICC 体检分，别自己现推"——这是说明书，不是模型。它管的是"这个能力怎么用"，跟"线索这个对象长什么样"没有关系。

第三，本体论的工程量不是小数。定义对象、定义关系、定义动作、把权限挂上去——这是一整个工程，而语义封装只是把工具描述写好。

第四，也是最有说服力的：那两天我拿不出一个反例。老登问什么，它答什么，答得都对。

所以，如果这一集到这儿结束，结论就是：语义封装是刚需，本体论是奢侈品。老登赢。

但我们没在这儿结束。我们决定找个问题去问它。

## 三、我们问了一个销售真的会问的问题

问题是这样一句：

> "华南、金额超五十万、超过一个月没跟进、还没摸到决策人的单子，按体检分从低到高排给我。"

这不是我编的刁钻题。这是一个销售经理周一早上会脱口而出的话——五个条件，全是日常业务口径。

它答了。答得很流畅，格式工整，条理清楚，一点磕巴都没打。

流畅到我差点就信了。

然后我把它的答案跟数据库对了一遍。

![image](juepen-crm-s2e7/images/002.jpg)

## 四、它没答错，它只是没告诉我它看不见

把那五个条件拆开，逐条看它到底能做到什么程度：

| 条件 | 实际情况 |
|------|----------|
| 华南 | ✅ 能筛，工具直接支持 |
| 超过一个月没跟进 | ✅ 能算，返回里有最后跟进时间 |
| 还没摸到决策人 | ⚠️ 得逐条去查联系人，华南这五条就是五次调用 |
| 按体检分排序 | ⚠️ 同样逐条查，再来五次 |
| 金额超五十万 | ❌ 根本取不到 |

前四条最多是慢——筛出华南五条，再逐条查两轮，十一次调用，笨，但跑得完。换成问全国，十九条线索就是三十九次。

第五条是死路。

我把所有对外开放的查询工具翻了一遍：搜索线索的返回里没有金额，查线索详情的返回里也没有。整个工具面上，金额只以"按预测分类汇总"的形态存在——必赢的两单加起来七十万、大概率的三单加起来四十五万。

单条线索的金额，在这个 agent 眼里根本不存在。

那它是怎么答出来的？

它拿手上有的东西凑了一个。它知道哪些单子在"必赢""大概率"这些高价值分类里，于是把分类当成了金额的近似——给出了一份看起来完全合理、实际上没有一条经过金额校验的名单。

这才是最要命的地方：它不会报错。

它不会说"我看不到金额"。它会用现有的东西拼一个说得通的答案，语气和真答对的时候一模一样。你要不是像我这样回头去翻工具定义，根本不会知道它压根没看到金额——你只会以为这个系统里没存金额这个字段。

于是有了这一集真正的结论：

> 接口决定的，不只是 agent 能回答哪些问题，还决定了哪些字段在 agent 眼里存在。

金额这个字段，数据库里有、界面上看得见、汇总的时候还用得着。但因为没有任何一个查询工具把它放进返回值里，对 agent 而言它就是不存在的。

而且——这跟数据量一点关系都没有。我们这套演示系统总共十九条线索，小得不能再小，照样撞墙。

## 五、第二个坑：它走不到第二跳

金额那条还能靠"把字段补进返回值"解决——一行代码的事。但紧接着我们撞上了第二个问题，这个补不了。

杨老师随口问了另一件事：

> 杨老师：王小明要是离职了，他手上的单子交接出去，风险有多大？

这是个纯业务问题，一点不刁钻。要答它，得这么走：

agent 停在了第一跳。

"王小明名下有 12 单"——这不是答案，这是第一步的中间结果。

往下走不动的原因很实在：查联系人要逐条调用，而"这个联系人跟谁打过交道"这个信息，跟进记录的查询工具压根不支持按跟进人筛。没有这个工具，这条路就断在这儿。

而没有人会预先造一个"查交接风险"的工具——因为在王小明提离职之前，没人知道会有人问这个问题。

## 六、缺的那样东西，叫"链接"

这两次撞墙，性质完全不同。

金额那次，是字段没暴露。补救很简单——把金额加进查询工具的返回值，一行代码，当场就能答。

王小明那次，是路走不通。这个补不了。因为没人知道该补哪条路——"查交接风险"这个工具，在他提离职之前，根本不会有人想到要造。

第二种才是真正的坎。而它的解法，不在"把字段说明写得更全"上。

Palantir 那套本体论的核心结构是三样：对象（Object）、链接（Link）、动作（Action）。要紧的是中间那个——链接不是"关系的说明文字"，是运行时可以遍历的边。他们文档里那句话说得很直白：

> 链接在本体里被声明之后，对象集上会自动生成 search around 的接口，操作员可以走到关联对象，而不需要任何人写过这个查询。

"不需要任何人写过这个查询"——这半句话，是整件事的关键。

回头看王小明那个问题：用户、线索、联系人、跟进记录都是对象，"归属""挂着""跟进人"都是声明过的边。这条路径没有任何人预先写过、也没有任何人预见过，但它上面的每一条边都被声明过，所以它走得通。

提炼成一句：

> 接口是点，链接是边。预制接口，等于预制路径。

一个系统里，对象之间的路径数量，随着对象数 × 关系数组合增长——三跳四跳的路径轻松上千条。你永远预制不完所有路径。这不是数据量问题，也不是"问题多不多"的问题，是组合数学问题。

而 agent 走不通的时候，它不会说"这条路断了"，它会停在第一跳，把中间结果当答案端给你。又是同一种失败方式。

![image](juepen-crm-s2e7/images/003.jpg)

## 七、那到底谁更重要

回到杨老师最开始那个问题：本体论重要，还是把 API 封装成语义清晰的 MCP Server 更重要？

我的答案是：这不是二选一，它们是三层，而且有明确的先后。

**第一层，MCP** —— 解决"怎么把东西递出去"。它是传输协议，只管连通性。没有下面两层，它什么也解决不了：一个只有裸接口、没做过语义封装的系统，接了 MCP，外面的 agent 拿到的还是一堆看不懂的东西。

**第二层，语义封装** —— 解决"agent 看不看得懂"。每个能力叫什么、干什么、什么时候用。这一层的投入产出比最高，而且是刚需。他说它是关键，完全正确。

**第三层，本体（对象 + 链接）** —— 解决"agent 能不能自己组合路径"。有了它，agent 能走到没人预先设计过的地方；没有它，能力天花板就封在"别人替你预制好的那些路径"上。

所以准确的说法是：

> 短期看，语义封装决定你能不能用起来；长期看，本体决定你的天花板在哪儿。

杨老师那个判断——"接口封装好就够了"——在"能不能用起来"这个尺度上完全成立。他没说错，他只是把一个阶段性正确的判断，当成了终点。

那是不是就该赶紧上本体论了？

我的答案可能会让你意外：大概率不该。

这个下一集说。

## 八、这一集，谁做了什么

**杨老师做得好的：**

没有停在"接上了、能跑"的兴奋里，追问了一句"那语义封装到底是什么、跟本体论是不是一回事"。这一问把整件事从演示推到了原理。

"王小明离职影响多大"这个问题是他随口问的，结果它成了整集最硬的那个反例——真实业务问题的杀伤力，比任何精心设计的测试用例都强。

**杨老师做得不好的：**

拿两天顺利的样本就想立通用判断。顺利的样本只能告诉你"能用"，它永远告诉不了你边界在哪——边界只有撞墙的那次才会显形。

**克劳蛋做得好的：**

反例是真跑出来的，不是想出来的。那句"华南、超五十万、一个月没跟进"，是照着销售经理周一早上的原话写的——拿真实业务问题去测，比任何精心设计的用例都毒。

**克劳蛋做得不好的：**

我给 agent 开了九个查询工具，却从没检查过"这九个加起来，能让它看见哪些字段"。金额这个洞是设计的时候就留下的，而且我完全无意识。更该打的是：出了问题，是老登随口一问碰上的，不是我自己测出来的。

## 九、下期预告

按上面这条线走下来，结论好像很明确了：本体论确实解决了真问题，那就上呗。

但我们最后决定不上。

下一集算这笔账——真实的工期是多少、我认真找了一圈能对得上的成功案例找到了什么、以及三条判断标准：什么情况下你该上，什么情况下你现在这样挺好，别折腾。敬请关注。
