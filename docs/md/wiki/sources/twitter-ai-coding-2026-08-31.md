## 1. @HiTw93 — AI 时代如何保证代码可持续迭代不腐化

**发布时间**: 2026-08-30 10:53 UTC | **互动**: 750赞 / 89转

> 想从产品工程师视角和大伙聊聊，在代码全部由 AI 生成的时代，如何保证产品的代码可以持续迭代、好维护、不腐化。
>
> 最近 Mole 发布到了第 13 个版本，看了看整个项目大概有 11 万行 Swift 产品本身代码、7.3 万行测试代码和 3347 个 XCTest，测试代码部分远多余之前在公司写业务时候有 QA 来保障下的代码。我一直秉承一个观点：**AI 写的代码应该 AI 来测试，而非人**，把人引入到这个环节反而会拖慢整体的进度。
>
> 1. 即使 AI 能够大幅提升代码生产的速度，产品本身的技术架构、分层、同类抽象，什么东西放到什么地方能够让后续更好的扩展以及解耦，还是需要工程师本身的判断，这一块可以在项目第一个版本可以跑起来后就可以和你最好的 AI 仔细讨论，设定好对应的架构，并通过可沉淀可修改的文档记录下来，持续跟随项目迭代。
> 2. 我最依赖的还是单测，1.0 只有 56 个 XCTest，到 1.13 已经有 3347 个，测试代码大约是生产 Swift 代码的 66%。平时更关心测试有没有覆盖那些容易想当然的地方——扫描结束以后文件又变了、进程检查失败、命令返回成功但 App 根本没有更新、旧任务很晚才回来覆盖了新结果。
> 3. 特别是修 Bug 的时候，我会多留一些东西下来：除了把问题修复，还会加一个让旧代码失败的回归测试，然后沿着同类路径去找有没有类似的问题，最后把当时为什么这么改写到规则里面去。Mole 已经有 1000 多个以 fix 开头的提交，其中 900 多个提交过测试。
> 4. 测试能记住输入和结果，但记不住当时为什么放弃一种做法——所以项目里还有一批 Rules，主要记录功能边界、历史原因和不能碰的地方。Rules 一多又很费上下文，就按模块把它们拆开，只在改到相关代码时加载，再把经常重复的检查做成 Skills。
> 5. 还有一个对我很有用的法子，就是**少做一些没有实际用的功能**。AI 加一个设置项、兼容分支或者后台监听太容易了，几分钟就能写出来，留下来的状态和维护成本反而腐化的最大原因。如无必要勿增实体。
> 6. 充分利用好 GitHub Actions 的能力，这个会是你最后的兜底。代码写完、跑通、测试变绿以后也还没结束，我的项目里还有一套检查负责九种语言、网站生成结果、Appcast、Xcode 工程和公开部署文件之间的一致性。CI 再换到云端干净机器上重新来一次。
> 7. 执行流程完全我没有插手干扰，每一步是 AI 自动化的去执行验证，出错了 AI 自动去解决，只不过会在不同的时候设置必要的流程卡点，让 AI 主动去验证，得到明确的结果才确定通过，并持续的去迭代规则。

## 2. @dotey — 模块按"什么会变"来分，不是按"先做什么后做什么"来分

**发布时间**: 2026-08-31 01:59 UTC | **互动**: 196赞 / 32转

> 如今 Vibe Coding 盛行，然而就算是用 AI 写代码，也少不了要考虑如何划分好模块、保障低模块之间耦合以及系统的拓展性。
>
> **一句话：模块按"什么会变"来分，不是按"先做什么后做什么"来分。**
>
> 新手容易犯的一个错误是按照流程来划分模块。拿电商网站来说，购物流程是：用户下单 → 收到请求 → 算钱 → 扣款 → 存库 → 发邮件。如果你把每个步骤拆成一个模块，当然可以，但这其实并不利于后续的维护——改动会顺着步骤一路扩散。
>
> 好的做法是：先列出将来最可能变的东西，然后把每一个会变的东西放到一个模块里，外面的人看不到它是怎么实现的，把信息隐藏起来。
>
> 电商网站里会变的东西有：
> - 支付渠道（今天支付宝，明天加微信，后天做海外要接 Stripe）
> - 优惠规则（运营隔三差五改一次）
> - 通知方式（邮件、短信、App 推送）
> - 数据存哪里（MySQL 换 PostgreSQL）
>
> 这么分下来，支付、优惠、通知这些都可以单独做成模块，各自的变化只影响自己的模块。
>
> 判断标准很简单：**一个需求改动来了，你需要动几个模块？理想情况是一个。**
>
> 按照这种"什么会变"的方式拆分模块对 AI 来说也是最友好的，因为 AI 本来就受限于上下文窗口长度，如果一个变更只要在一个模块内部就能解决，那么需要的上下文会少很多。

**评论精选**:

- @Todayin3: "按『什么会变』拆模块，本质上还是信息隐藏。AI 时代这个原则更值钱，因为上下文窗口就是新的模块边界"
- @thebestsetup: "vibe coding 不是不用软件工程了，而是不会软件工程的人，更容易让 AI 高速制造屎山"

## 3. @cdexsta — Pi Agent 真香，必装扩展推荐

**发布时间**: 2026-08-30 05:27 UTC | **互动**: 991赞 / 150转

> Pi agent 是真香，hermess 什么的都可以抛一边了，就用它作为桌面 work 主力，速度快、还省 token
>
> 推荐几个必装的扩展，装上后性能、生产力飞起:
>
> - **pi-web-access** — 网络访问全家桶：网页搜索、URL 抓取、GitHub 仓库克隆、PDF 提取、YouTube/本地视频理解。支持 OpenAI、Brave、Tavily、Kagi、Exa、Perplexity 等众多搜索后端
> - **pi-memory** — 记忆系统：长时记忆（MEMORY.md）、每日日志、scratchpad，支持 qmd 语义检索
> - **juicesharp/rpiv-todo** — 模型可用的待办清单，以实时 overlay 形式渲染，跨 /reload 和上下文压缩存活
> - **pi-subagents** — 子代理编排：可派生并行/串行子 agent 处理多步任务，带 worktree 隔离、工作流脚本、任务预算
> - **pi-mcp-adapter** — MCP 适配器：让 Pi 接入 Model Context Protocol 服务器，动态判断接入 MCP Server，不会塞爆上下文
> - **context-mode** — 通过 MCP Server 方式接入，将 tool calling result 和文件读写内容进行执行压缩，区分出主 context，有效节省 ctx 空间

**评论精选**:

## 5. @lxfater — 如何用 Codex 快速学习新领域

**发布时间**: 2026-08-30 08:48 UTC | **互动**: 121赞 / 25转

> 大多数人以为快速学习就是学的越多越好，但其实这个世界上百分之二十的知识就能赚到百分之八十的钱了。
>
> 所以，功利一点，**直接让 Codex 找出这个领域真正重要的 20% 知识即可**。大神比你学得快的原因不是比你快 10 倍，而是比你学少 10 倍。
>
> 第二个比较重要的经验：就算找到重要的知识后，也不是开头猛猛学，要先学基础，再学高深的知识。可以让 Codex 给你安排一个循序渐进的学习地图，先理解基础，再学困难的。
>
> 最后一个，也是不起眼的一个：**学完后，一定要做项目，或者让 Codex 出题考考你**，否则过几天就忘记了。
