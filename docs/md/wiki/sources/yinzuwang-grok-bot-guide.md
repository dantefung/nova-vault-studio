# Grok Bot 完全使用指南：从会用到用好，附可直接复制的提示词

你让 Bot 查资料，它交来一份摘要。 你让它「负责情报」，它却可能一直空转、持续扣额度。 差别在于：岗位怎么定，做到哪一步必须停下来问你。

Grok Bot 带来的核心变化，是把"提问"变成了"委派"。[@sairahul1](https://x.com/sairahul1) 在《How To Build a One-Person Company Using Grok Bot》里有一句最好用的区分："A prompt is a request. A bot is a role."——提示词是一次请求，Bot 是一个岗位。请求结束就结束；岗位有职责、有标准、有边界，可以反复接活。

这正是 Grok Bot 不一样的地方：每个 Bot 有自己的云电脑、文件、工具和运行时间，任务在后台执行，不依赖你一直开着电脑。36氪报道提到，它能免 API 费用直通 X 数据，还能创建 Routines 全天候运行。于是工作方式从"接一句话答一句"，变成"接任务—执行—交付"。

但委派不是许愿。先讲清交付标准与停下等批准的边界，再根据实际用量和结果调整任务；模型路由、共享环境和额度的具体限制，下文分别说明。

所以本篇的思路是：先把岗位写清楚，再把请求写规范，然后把稳定流程存成技能，最后才谈定时自动化。文中提示词都可以直接复制，把方括号替换成自己的内容即可。记住一条判断标准：每个环节都能回答"它做完了，我怎么验证"。

🎯 30 秒看懂

![](https://pbs.twimg.com/media/HUUDiGNbgAAezxj.jpg)

Grok Bot 是带云电脑的云端 Agent：给它任务，它在云端环境里浏览、整理、起草、定时执行；平台覆盖桌面与移动设备，后台任务不依赖你一直开着笔记本，具体功能以账户界面和官方说明为准。

它的工作方式更像"接任务—执行—交付"，不是只在聊天框里回答问题。Team Bots 还能配置共享文件、技能、插件和记忆，发布给团队使用；[@0xwhrrari](https://x.com/0xwhrrari) 的拆解指出，一次共享纠正可以改善下一位同事的对话，原则是"可复用的判断放进记忆，变化的数据留在源头"。在群聊里派活时，给目标而不是给任务清单（[@sairahul1](https://x.com/sairahul1)）——Bot 拿到目标才能自己规划步骤，拿到清单只会机械执行。

先用可检查的小任务验证工作方式，再逐步扩大范围。岗位、请求、权限和自动化的安排见下文，具体功能与价格以账户界面和官网说明为准。

📌 小结：Grok Bot 能接任务；先把岗位和交付标准讲清楚。

🛠️ 上手 5 步

![](https://pbs.twimg.com/media/HUUDjgla8AAcL_1.jpg)

总的原则是把协作模型压到最简单：总控负责拆解、分派和验收，执行者负责单项任务，并把产物和证据放进约定位置。整条路径是：一次性任务做顺、做可靠，再存成技能，明确动作边界，最后才自动化（[@unicodef1wn](https://x.com/unicodef1wn) 的 AI Company-in-a-Box 路线图同样坚持 "one-time task→reliable→skill→automate"）。

## 第 1 步：🎯 写好岗位说明（4 句）

[@sairahul1](https://x.com/sairahul1) 的岗位说明只要四句：管什么、好结果长什么样、哪些必须先问、哪些绝不能碰。他警告："Bots that have to ask about everything are useless. Bots that never ask are dangerous."——全问等于没用，全不问等于危险。新建 Bot 时先给它清晰的名称和固定目录，让它读项目说明、复述目标与限制，别把私人记忆或无关历史直接带进新岗位。另加一条交付纪律：完成时说明产物位置、验证方式和缺口；[@unicodef1wn](https://x.com/unicodef1wn) 把它写成 "No proof, no done."

```
角色：你是 [岗位名称]。
目标：只负责 [职责范围]；不负责 [范围外事项]。
好结果：[可检查的质量标准]；缺少证据的结论标为待核实。
必须先问：涉及 [付费/发布/删除/敏感资料] 前先等我确认。
绝不做：[明确禁止事项]；完成时报告产物位置、验证方式和缺口。
```

📌 小结：岗位说明是 Bot 的长期上下文入口，写一次，省千次解释。

## 第 2 步：💡 搭好请求结构

[@Bober\_smart](https://x.com/Bober_smart) 教程里的好请求包含五个要素：结果、来源、约束、交付格式、何时停下等批准。请求越完整，Bot 越少瞎猜，来回越少。尤其要把"何时停下等我批准"写明：沉默不等于批准，涉及对外动作和花钱的事，Bot 必须停下来问你。

```
我要的结果：[可验收的结果]
资料来源：[文件/链接/数据]
约束条件：[范围/风格/禁区]
交付格式：[格式与保存位置]
停下时机：遇到 [情况] 时停下，等我批准后再继续。
```

📌 小结：好请求把"想要什么"翻译成"能验收什么"。

## 第 3 步：🧠 Teach a task 存成技能

[@sairahul1](https://x.com/sairahul1) 建议用 Teach a task 演示不超过 10 分钟的流程，演示后存成技能；最适合的特征是 "Recurring. Multi-tool. Stable."（重复、多工具、稳定）。[@cgnot996](https://x.com/cgnot996) 也主张：做熟的流程存成技能，长期规矩写进 Bot 描述，别让一条对话越滚越长。演示得到的内容仍要检查，剔除只适用于本次的临时处理。保存前让 Bot 复述步骤、输入、输出和失败时的处理方式，确认无误再决定是否启用。

```
角色：你是流程记录助手。
目标：把我接下来演示的 [流程名称] 整理为可复用技能草稿。
产出格式：按「前置条件、步骤、输出、异常处理」整理，保存到 [路径]。
完成标准：逐项复述，标出仅对本次有效的变通和需要人工判断的节点。
```

📌 小结：技能是"怎么做"，记忆是"知道什么"，别混为一谈。

## 第 4 步：🔐 分级授权，从可逆任务开始

[@Bober\_smart](https://x.com/Bober_smart) 建议从 1–3 个 Bot 起步，先只做可逆任务。[@sairahul1](https://x.com/sairahul1) 列出六个起步 Bot——Chief of Staff、Scout、Quill、Forge、Guide、Ledger——可供参考，不必一次装满；先复用职责合适的 Bot，再考虑新建。动作按风险分级：0 只读、1 起草、2 可逆写入，可在约定范围内执行并报告；3 对外发布、4 花钱或不可逆操作，必须先获明确批准。无法判断等级时，先停下问人。[@Bober\_smart](https://x.com/Bober_smart) 提醒多个 Bot 共用云电脑，分工不能代替权限隔离。

📌 小结：先从可逆任务起步；对外动作和高风险操作，明确批准后再做。

## 第 5 步：✅ 定时触发

流程稳定、权限边界明确后，才把它设为定时任务。[@sairahul1](https://x.com/sairahul1) 提到定时与事件触发两种方式：定时适合节奏固定的检查，事件触发适合"有变化才处理"的场景。[@cgnot996](https://x.com/cgnot996) 用 cron 脚本盯数据，有实质变动再通过 Webhook 叫醒 Bot；据他实测，每周少 8–10 次空转。先选低风险、容易检查的场景，明确频率、无变化时如何处理、失败时向谁报告。测试运行若实际触发执行，也可能消耗额度；先到用量页面核对，再调整频率。

```
角色：你是 [例行任务岗位]。
目标：按计划检查 [对象/来源]，识别 [需要关注的变化]。
产出格式：有变化时按 [摘要格式] 写入 [路径]；无实质变化时记录「无更新」。
需要先问人的边界：沿用已约定的权限分级；超出范围时只汇报并等待批准。
运行频率：[频率]；失败时向 [人/渠道] 报告。
```

📌 小结：自动化放大一切，包括错误，所以先小跑再加速。

🚀 4 个最值得抄的实战用法

## 🎯 1. 每日 X 信息简报

把公开信息收集变成可验收的日常产出，是 Grok Bot 最常见也最容易做砸的用法。[@sairahul1](https://x.com/sairahul1) 在《How To Build a One-Person Company Using Grok Bot》里把这类岗位叫 Scout：「A prompt is a request. A bot is a role.」先定义岗位再派任务；他在群聊场景主张「给目标不给任务清单」。36氪报道 Grok Bot 可免 API 费直通 X 数据、搜索阅读与监控推文，但未给出额度与期限，实际能力以当前界面为准。

做法是先限定主题、时间窗与来源标准，原始材料与摘要分开保存。[@cgnot996](https://x.com/cgnot996) 建议 X 搜索走自带免费额度，原始推文存进文件，对话里只回要点和链接。坑在于把监控当授权：不登录未授权账号、不抓私人内容、不顺手转发。

```
角色：你是 [主题] 信息研究员（Scout）。
目标：整理 [主题] 在 [时间范围] 内值得关注的公开 X 内容。
输入：搜索词 [关键词]；优先 [账号/领域]；排除 [无关内容]。
产出格式：最多 [条数] 项，每项含两句内摘要、原文链接、账号与发布时间；原始链接清单存 [路径]。
完成标准：每条可打开核对；区分事实、观点与归纳；无可靠结果就说明。
需要先问人的边界：不登录未授权账号、不抓私人内容、不点赞转发或联系作者；主题不清先问我。
```

📌 小结：简报的价值在可追溯，不在条数。

## ✅ 2. 用证据验收交付

AI Company-in-a-Box 把完成门控写成「No proof, no done.」：完成前跑六项检查，证据不足就退回，claim 必须过 gate。[@Bober\_smart](https://x.com/Bober_smart) 的好请求公式是结果＋来源＋约束＋交付格式＋何时停下等批准——验收标准要在请求里写死，而不是事后追认。

坑在汇总、研究、自动化任务最容易「说完成」却不给复查路径。做法是要求每个任务交代产物位置、验证方法和缺口；没有实际检查的内容标为未验证，不声称已完成。

```
角色：你是交付验收助手。
目标：核对 [任务名称] 是否达到约定标准。
输入：任务要求 [路径/文本]；待验收产物 [路径/链接]。
产出格式：按「产物位置、验证方法、已满足项、缺口与风险」报告。
完成标准：结论逐项对应任务要求；没有实际检查的内容标为未验证。
需要先问人的边界：无法访问产物、标准冲突或需修改原件时暂停询问；验收不等于发布批准。
```

📌 小结：完成是证据，不是状态词。

## 🔐 3. 定期复核岗位说明与记忆

[@0xwhrrari](https://x.com/0xwhrrari) 的记忆工程原则是「可复用的判断放进记忆，变化的数据留在源头」。凡可能晋升为共享规则的内容，写一张审核卡回答五个问题：谁说的、在哪核实、归谁负责、批准了吗、何时过期。

坑是过期事实、私人偏好和团队规则放错桶——一旦写进共享记忆，会被下一位同事直接复用。定期检查岗位说明中的越界、返工和格式漂移，把共性问题改进说明，而不是在对话里临时提醒。

```
角色：你是岗位说明与记忆审阅助手。
目标：检查 [岗位说明路径] 是否仍适合当前工作。
输入：岗位说明、我指定的近期交付样例 [路径/范围]。
产出格式：列出职责不清、反复返工、格式偏差和证据不足的例子，并给出最小修改建议。
完成标准：每项建议指向具体样例；区分事实观察与推断；找不到来源的规则不保留。
需要先问人的边界：不得自行改写或启用新规则；遇到私人资料或样本不足先询问；修改须经我确认。
```

📌 小结：记忆需要台账，不是越存越多。

## 🤖 4. 从手动流程走向定时自动化

顺序是「一次性任务→可靠→技能→自动化」。[@sairahul1](https://x.com/sairahul1) 支持定时与事件触发；[@cgnot996](https://x.com/cgnot996) 建议定时任务放慢、无变化不汇报，还可用 cron 脚本盯数据、有实质变动再经 Webhook 叫醒 Bot（他自测每周少 8-10 次空转，属个人样本）。

坑是定时运行消耗额度，且一次成功不等于流程稳定。先选低风险、易检查的场景，明确频率、无变化处理、失败报告，运行一段时间后依据实际结果调整。

```
角色：你是自动化流程设计助手。
目标：评估 [任务] 是否适合转为 Routine，并准备配置草案。
输入：手动流程说明 [路径]、样例输入 [路径]、验收标准 [内容]。
产出格式：给出触发频率 [频率]、输入输出、无变化处理、失败处理和人工检查点；保存草案到 [路径]。
完成标准：每一步可复查；失败时不会重复执行高风险动作；说明仍需人工确认的环节。
需要先问人的边界：未经我批准不得创建或启用 Routine；不自动对外发送、发布、付款或删除。
```

📌 小结：自动化是奖励稳定，不是奖励勤奋。

## 🔐 共用电脑不是安全边界

多个 Bot 共用同一台云电脑、文件和浏览器登录态。[@Bober\_smart](https://x.com/Bober_smart) 的教程说得直白："Do not use separate Bots as a security boundary." Bot 的名字和岗位不能代替权限隔离——换一个 Bot，并不换底层电脑。

坑在于把"分工"误当"隔离"，随手把敏感资料放进共享目录，以为换个 Bot 就换了门。云端只放当前任务所需资料，连接越少越容易管理；浏览器登录态可能被沿用，敏感调查尽量放在私聊里做。[@sairahul1](https://x.com/sairahul1) 的提醒同样适用："The bot gets a session, not a secret." 不要在提示词里放密码或密钥。

📌 小结：把不同 Bot 当安全边界是幻觉，最小化资料和连接才是真边界。

## ⚠️ 删除 Bot 不等于撤销登录

删掉一个 Bot，并不会清理它在第三方网站上的登录授权。这是 [@Bober\_smart](https://x.com/Bober_smart) 特别指出的坑：很多人以为删 Bot 就万事大吉，其实会话还留在原服务里，随时可能被沿用。

把删 Bot 当收尾的第一步：不再使用某项连接时，先到对应服务检查会话并撤销访问，再回来断开连接器。OAuth 和共享凭据代表不同授权方式，按实际权限逐项审阅。

📌 小结：删 Bot 是收尾的开始，撤销登录才是结束。

## 🤖 看不到模型，Opus 路由不改单价

官方说明：用户不能在 Grok Bot 中选择、指定或屏蔽底层模型，也没有模型选择器；任务可能被动态路由，但你无法确认或指定具体模型。所谓"免费用 Opus 5.5"是系统内部调度，不是可控的模型配置。

官方还说明，"routing a task to Opus 5.5 doesn't change what it costs you per token"。坑在于把路由当省钱开关或功能承诺；实际做法是按可见功能和实际结果验收，预算按当前计费说明规划。

📌 小结：路由是路由，账单是账单，都别当成可选项。

## 💰 额度省在刀刃上

[@cgnot996](https://x.com/cgnot996) 整理了 12 招续航办法，提醒读者关注模型与工具的实际用量，而非只看消息条数。长对话可能增加上下文处理量和消耗，具体扣费与重置规则以账户用量页面和官网说明为准。

所以长期规矩写进 Bot 描述，做熟的流程存成技能，长资料存进文件并只引用相关部分；看图、拉片等多模态任务可先整理成摘要，再交给 Bot 处理。[@cgnot996](https://x.com/cgnot996) 建议把原始推文存进文件、对话里只回要点和链接，并让定时任务在无变化时少做无效汇报。

📌 小结：省额度不是少用，是不让 Bot 重复读、重复跑、空转轮。

## 💰 价格与资格以官网为准

试用额度可能受到时间和用量限制，大任务可能提前耗尽；启用按量付费前先设月度上限，并在账户页面检查当前用量。不同档位的订阅与按量计费规则可能不同，别按别人的截图或旧帖规划预算。额度快用完时，把文件和断点存进归档目录，写一份接管说明。套餐资格与价格以官网为准。

📌 小结：一切以官网当前说明为准，截图不保值。

✅ 收藏清单

- ☐ 每个 Bot 有明确岗位、输入范围和禁止事项
- ☐ 长期规则写进说明，重复流程整理成待审技能
- ☐ 只连接当前任务必需的服务，并检查授权范围
- ☐ 只读、起草、可逆写入与对外动作分级处理
- ☐ 发布、付款、删除和权限变更先获得明确批准
- ☐ 每次交付包含产物位置、验证方法和未解决问题
- ☐ 原始来源与摘要分开保存，结论能追溯
- ☐ 长任务拆解并保存进度，避免上下文堆积和重复执行
- ☐ 定时任务说明频率、无变化处理和失败处理
- ☐ 使用共享云端环境时避免放入无关敏感资料
