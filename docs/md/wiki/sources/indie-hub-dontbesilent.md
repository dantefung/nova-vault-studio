# dontbesilent 平时怎么用 Codex？我分析了他的 534 个会话

过去 9 个月，dontbesilent 在本地留下了 534 个 Codex 会话文件，总体积约 781 MB。

我分析了这些记录。其中，289 个会话可以明确识别为他本人发起的任务，包含 1668 条用户消息。对应的执行记录里，还有 6797 次终端操作、703 次文件修改和 88 次图片检查。

这些数字展示了一种少见的使用结构：Codex 已经进入他的真实工作环境，持续参与任务执行、流程维护、方法沉淀和系统治理。

## 他的 Prompt 很薄，工作环境很厚

dontbesilent 的很多指令非常短：「你看看什么情况」「根据这个做一下」「存一下最新数据」「和老数据整合去重」。

这些短指令能够驱动复杂任务，因为我已经位于真实项目中，可以读取本地文件、历史版本、数据索引、项目规则和已有脚本。Prompt 只负责分派任务，完整背景由工作环境提供。

## 他在生产可复用的组织能力

这 534 个会话中，与 Skill 和 Agent 有关的用户消息有 569 条，是出现频率最高的一类主题。

dontbesilent 对 Skill 的使用已经超过了调用层。他会使用 Skill，也会拆解 Skill、修改 Skill、测试 Skill、删除没有实际价值或风险过高的 Skill，还会追问同一个 Skill 在不同 Agent 中读取的到底是不是同一份真源。

这看起来像一个技术细节，实际上是一种组织设计。

## 更关键的是，他会用 Codex 改造 Codex

多数任务都可以概括为「用工具完成工作」。dontbesilent 还有另一类任务：用 Codex 修改 Skill，用 Codex 检查 Agent 的安装方式，用 Codex 建立知识库规则，用 Codex 同步多个 Agent，再让更新后的 Codex 去完成下一批工作。

递归结构：用 Codex 完成工作，再用 Codex 改进完成这些工作的 Codex。

一次标题任务做得好，可以沉淀成标题 Skill；一次知识库整理暴露了版本冲突，可以沉淀成新的权威规则；一次跨 Agent 调用出现偏差，可以回到真源和同步机制中修复。

## 他给 Codex 建立了事实秩序

dontbesilent 的做法是建立 SOURCE_OF_TRUTH.md。通过导航规定：不同类型的资料应该去哪里找，哪个文件是当前入口，什么属于原始记录，什么属于派生结果，多个版本冲突时按什么规则处理，证据不足时哪些结论必须保留为「待确认」。

普通知识库解决的是「AI 能不能找到文件」。这套系统进一步解决的是「AI 找到 3 个互相冲突的文件后，知不知道该怎么办」。

## 他把 Codex 设计成组织的执行层

在这个结构里：
- 文件夹相当于部门边界
- SOURCE_OF_TRUTH.md 相当于事实与版本制度
- Skill 相当于岗位 SOP
- 脚本和工具相当于基础设施
- 多个 Agent 相当于可以临时组建的专业角色
- 对话中的「继续」「不对」「确认」，相当于管理反馈和授权节点

## 这种用法并不轻松

这套用法有明显成本：
- 建设 Skill、知识库和同步机制需要投入
- Agent 获得的行动能力越多，错误的影响范围也越大
- 系统会不断膨胀，需要持续治理

## 为什么他确实比大多数人用得深

dontbesilent 同时在 4 个层级工作：
1. 让 Codex 直接完成文件、数据、代码、视觉和内容任务
2. 让结果进入固定目录、历史主库和下一步流程，脱离聊天窗口继续发挥作用
3. 把重复判断沉淀成 Skill、脚本、模板和规则
4. 继续用 Codex 维护知识真源、同步机制、Agent 边界和整个工作环境

别人使用的是一个更聪明的工具。他正在建设的是一个可以积累、可以治理、也可以不断改造自己的个人 AI 组织。
