# 用问题空间定位法认识 单身汉 DSH（DeepSeek Harness）

DeepSeek Harness（DSH）终于来了，它是个新东西。介绍它的文章有两类：一类教你怎么装、怎么用，一类评测它多强、比谁强。但看完你还是不知道它到底是个什么。

这篇换一个视角，用一套判断框架把它拆开——这套框架叫**问题空间定位法**，五步：

> 它解决什么 → 它本质是什么、怎么解决 → 它在生态位里站哪 → 什么前提成立 → 值不值得投入

## 第一步，它解决什么问题

判断一个东西，先问它撞的是哪类问题。

DSH 解决的，不是「AI 会不会写代码」——那早就解决了。它解决的是这类问题：

1. 一个长任务，聊到后面，模型记不住前面了，只能手动重开。
2. 想把活拆给几个 AI 并行干，再收回来，只能自己开一堆窗口、写胶水代码。
3. 想本地跑，代码和数据不出这台机器。

这三件，模型再强也解决不了——它们不是「聪明不聪明」的问题，是「怎么调度」的问题。

## 第二步，它本质是什么、怎么解决

把 DSH 的词换成你认识的老概念，顺便看每个概念怎么解决第一步那三个问题。

- **子代理 = fork 一个子进程。** 记不住前面，就拆：把任务拆成子任务派给子代理，子代理带着你聊过的全部内容去干，交回一个结果——不用重新喂一遍上下文。
- **工作流脚本 = 流水线。** 想并行又不想手动开窗口，就写一段脚本，把上百个子代理按阶段编排，结果自动校验，不合格的丢弃。
- **沙箱 = 进程权限。** 想本地跑、数据不出机器，就把文件操作限制在指定目录，越界时一次性申请授权。

翻译完就清楚了：**DSH 是「调度 AI 的运行时」，它之于 AI，像操作系统之于进程**——操作系统不管单条指令多聪明，管的是调度、通信、权限。DSH 干的是同一件事。

## 第三步，它在生态位里站哪

DSH 不是孤立出现的。看它，得先看同一块地方还有谁、各自着重解决什么问题。

- **Codex、Claude Code**：单个模型，解决「把代码写好」。调度不归它们管——并行、拆任务，得你自己手动。
- **Pi**：也是个 harness，思路和 DSH 相反。同样面对「上下文太长、太贵」，它用压缩和删减，DSH 用继承。
- **WorkBuddy**：平台化，解决「开箱即用」，面向企业分发，不走深度编排。

各自占的位置：**Codex/Claude 占「把代码写好」，Pi 占「省上下文」，WorkBuddy 占「分发」，DSH 占「调度 + 本地」。**

再补一个反直觉的事实：**在 DSH 里，模型本身只是插件，它能把 Codex、Claude Code 当成后端挂进来。** 你以为它是竞品，其实它能反过来调度它们。

## 第四步，什么前提下成立

前提是：

- 本地优先
- 长周期可拆分的重活
- 会写脚本

前提不成立时，编排变成负担，本地模式要自己补权限治理——最先崩。

## 第五步，值不值得投入

做长期重活、要本地可控的人，值得学它的编排；轻用户不必，普通聊天够用。
