# 【精读】我用 WorkBuddy 搭了一套 AI 招聘流水线：HR 简历处理从 8 小时压到 0 分钟

> **核心结论**：HR 招聘流程中**简历筛选**是最大瓶颈——一个岗位一天上百份简历，现实中很多简历根本没被打开过，靠抽签决定生死。作者用 **WorkBuddy**（国内桌面端 Agent 产品）搭建了一套全自动流水线：邮箱采集 → 结构化提取 → 飞书多维表存储 → 简历评分 → 推送业务负责人 → 预约面试。**HR 只做一件事：挑人**。

> **关键洞察**：
> - **瓶颈环节**：筛选流程两道关、评价标准不一致 → AI 把"主观判断"转化为"客观规则"才能精准执行
> - **三层架构**：**技能（Skill）+ 连接器（Connector）+ 自动化（Automation）**，三者缺一不可
> - **渐进式落地**：不要一次覆盖全流程，先把高频环节跑通，再逐步扩展
> - **WorkBuddy vs Coze/Dify**：Coze/Dify 偏向工程师严密逻辑（数据传输格式步步错），WorkBuddy 容错性更高、对非技术同学友好
> - **8 小时 → 0 分钟**：简历处理从 8 小时压到 0 分钟，HR 只看评分结果

## 一、招聘流程现状

完整招聘流程拆解：

1. 从邮箱或招聘平台下载简历
2. HR 初筛
3. 初筛通过 → 业务负责人筛选
4. HR 反馈结果 → 预约面试时间
5. 安排面试官面试
6. 填写面试结果

**两个核心痛点**：
- 两道筛选关评价标准不一致 → HR 推过去的简历业务部门不想要
- 简历入人才库录入工作量巨大

**解决方案原则**：把主观判断转化为客观规则，规则客观了，AI 才能精准执行。

## 二、SOP 拆解：哪些环节适合 AI？

**适合 AI（规则可循）**：
- 信息提取：字段固定
- 结构化存储：填表
- 简历打分：标准事先定义
- 面试问题准备：基于简历内容生成

**必须人工（专业判断/沟通）**：
- 最终面试决策
- 跟候选人深度沟通
- 谈 offer

## 三、WorkBuddy 三大能力

| 能力 | 作用 | 在本场景的应用 |
|------|------|----------------|
| **技能（Skill）** | 把完整步骤写成 Skill 文件，下次遇到同样事情 AI 照做 | 把整个 HR 流程写成 `hr-resume` Skill |
| **连接器（Connector）** | 与外部系统交互（飞书多维表、邮箱等） | 邮箱采集简历附件 + 写入飞书多维表 |
| **自动化（Automation）** | 定时任务触发整个流程 | 每天早上 9 点自动检查邮箱 + 走完整流程 |

**三者叠加 = 完整自动化**：
```
技能定义怎么做 → 连接器完成外部交互 → 自动化决定何时做
```

## 四、流程搭建 6 步实现

### 步骤 1：项目初始化

本地新建项目目录 `HR-Workflow`，WorkBuddy 打开。

### 步骤 2：简历自动采集（自动化任务）

**三个核心问题**：

1. **如何让 WorkBuddy 拿到邮箱邮件？** → 邮箱连接器（按邮箱类型选择）
2. **如何判断是简历投递？** → 主题格式约束（如 `应聘xxx岗位-姓名`）
3. **如何保证不重复下载？** → 本地项目存"下载清单"，以邮箱地址为唯一 ID

### 步骤 3：简历信息提取

读取 PDF/Word，提取候选人关键信息：

```json
{
  "姓名": "",
  "性别": "",
  "年龄": "",
  "手机号": "",
  "邮箱": "",
  "求职意向岗位": "",
  "毕业院校": "",
  "学历层次": "",
  "专业名称": "",
  "是否985/211": "",
  "工作年限": "",
  "是否大厂背景": "",
  "工作经历摘要": "",
  "技能清单": ""
}
```

**关键技巧**：让 AI 主动推断（院校→985/211、工作年限计算、公司→大厂背景），**不确定就写"未知"，不要硬填**。

### 步骤 4：简历评分（核心环节）

**6 维评分框架**：

| 维度 | 解释 | 权重 |
|------|------|------|
| 学历匹配度 | 院校层次 + 专业对口性 | 10% |
| 经验相关性 | 工作年限 + 行业/岗位对口 | **30%** |
| 技能契合度 | 技能匹配程度 | 10% |
| 项目深度 | 项目规模/复杂度/量化成果 | **30%** |
| 稳定性指标 | 跳槽频率 + 职业连贯性 | 10% |
| 综合潜力 | 成长性 + 学习能力 + 管理潜力 | 10% |

每个维度满分 10 分，按权重加权后总分满分 10 分。

**标准管理**：
- 评分标准放在飞书文档，HR + 业务负责人协同维护
- 每个岗位单独文档，含**岗位描述 + 评分标准**
- 维护一份"岗位评分标准地址导航"，WorkBuddy 自动读取

**评分 Prompt 模板**：
```
根据候选人简历内容和岗位评分JD、岗位评分标准，对候选人进行简历打分，
并输出总结评价、以及建议面试问题。

## 简历内容
{...}

## 简历标准获取地址导航
{...}

## 输出要求
1. 简历得分为 1-10 分
2. 总结评价 150-200 字
3. 结合简历内容生成最值得问的 5 个问题
```

### 步骤 5：候选人信息存储（飞书多维表）

表结构（**字段名必须与步骤 3 的 JSON 字段名完全一致**，否则数据写入会出错）：

```
姓名 / 性别 / 年龄 / 手机号 / 邮箱 / 求职意向岗位 /
毕业院校 / 学历层次 / 专业名称 / 是否985/211 /
工作年限 / 是否大厂背景 / 工作经历摘要 / 技能清单 /
当前状态
```

**WorkBuddy 直接创建表结构**：授权飞书连接器后，用自然语言让 WorkBuddy 自动建表。

### 步骤 6：流程整合（自定义 Skill）

把所有步骤串成一个 Skill 文件 `hr-resume`：

```
1. 读取邮箱附件
2. 结构化提取（按 JSON 模板）
3. 根据岗位名从飞书多维表拿评分标准 + 岗位描述
4. 简历评分 + 总结 + 面试问题生成
5. 写入飞书多维表
6. 得分 ≥ 8 分 → 自动推送到业务负责人
```

## 五、最终架构

```
自动化任务（每日 9 点）
    ↓
hr-resume Skill（自定义）
    ↓
├─ 邮箱连接器（采集附件）
├─ 飞书连接器（多维表读写）
└─ 评分 + 推送（自动）
```

**整套流程跑完后**：HR 只需要在飞书多维表里看一眼评分结果，挑出高分候选人进入下一轮。

## 六、实际运行的校准原则

工作流搭建完成 ≠ 一劳永逸。**实际运行中需要不断校准**：

- 岗位要求会变 → 评分标准跟着调
- 业务负责人判断会变 → 评分标准同步调整
- **典型问题**：某岗位推 10 份高分简历给业务负责人，只有 2 份符合要求 → **说明这个岗位的评分标准不合理**，要重新校准

## 七、WorkBuddy vs Coze/Dify

| 维度 | WorkBuddy | Coze/Dify |
|------|-----------|-----------|
| 设计对象 | 面向大众的任务助手 | 面向开发者的低代码工具 |
| 容错性 | 高（关注最终意图） | 低（步步对，每步格式错则后续全错） |
| 交互 | 自然语言描述规则 | 拖拉拽（业务复杂时像蜘蛛网） |
| 门槛 | 非技术友好 | 工程师严密逻辑 |

**作者结论**：Coze/Dify 是 AI 发展过程中的阶段性产物，WorkBuddy 逐渐在吃掉 Coze 的很多场景，但**不是完全替代**，是迁移。

## 八、给企业的渐进式落地建议

> **不要一开始就追求覆盖整个流程，先把几个高频环节跑通，效果稳定后，再逐步接入后续的流程，渐进式推进反而更稳妥。**

## 核心方法论提炼

### 1. 业务问题比技术更重要

作者先拆解招聘流程，找到痛点（两道关评价标准不一致、录入工作量大），再设计技术方案。**技术是业务的脚手架，不是目的本身**。

### 2. 渐进式自动化

不要追求"全自动 + 全覆盖"。从**高频 + 痛点**切入：
- 高频：每天上百份简历筛选
- 痛点：HR 录入工作量大

跑通核心环节（评分 + 存储）再扩展。

### 3. 客观规则优先

AI 擅长执行**规则明确**的任务，不擅长**主观判断**。把"业务负责人觉得 OK 不 OK"这种主观判断，转化为"分数 ≥ 8 分推送"的客观规则。

### 4. 持续校准是常态

自动化流程上线后，**真正的难点不是搭建而是校准**。每周/月根据实际推送效果，调整评分标准、字段定义、阈值。
