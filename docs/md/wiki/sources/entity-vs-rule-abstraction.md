# 实体抽象 vs 规则抽象

今天下午我读了一篇 88 页的论文。满屏公式，搁平时我翻两页就关掉了。这次不一样——我拉着 AI 陪我一段段读，它把公式翻成人话，我负责提问、抬杠。一个钟头读下来，还真读明白了。

论文叫《A Programming Paradigm for Spatiotemporal Composability》，北大和 DeepSeek 出的，是那个开源框架 dsh 的理论底子。名字吓人，内容其实就一句话：

> **程序运行的时候，组件能不能说装就装、说拆就拆，拆完还不留痕迹。**

就这个事，论文写了 88 页。

## "拆干净"有多难

你手机上的插件、电脑上的扩展，装的时候往系统里添了一堆东西，卸的时候理论上得全收走。现实是大多数软件卸完还留一堆配置、一堆文件、一堆后台进程。

论文说，要做到拆得干净，得同时满足两条。

**第一条，时间上的。** 组件装的时候动过哪些地方，拆的时候全得复原。像搬家的书架：装的时候先底板、再侧板、最后隔板；拆就得倒过来——先拿隔板，再倒侧板，最后撤底板。顺序错了，拆不动。

**第二条，空间上的。** 组件之间要能声明「我需要什么」，系统自动配好。像插座和插头：插头说「我要电」，插座就给电。组件不用自己满世界找依赖，喊一声就行。

读到逆序恢复那一段，我愣了一下。论文说，复原得按相反的顺序一步步反着做——就是倒着拆书架那个道理。

我研究 dsh 源码（deepseek-harness）的时候见过这写法：它卸载组件就是严格倒着清理。当时只觉得「这么写是对的」，没想过为什么。论文给了答案：**这不是习惯，是数学必然。** 你想复原一件事，就得把每一步反着做回去。

## 一个反直觉的发现

我原来以为，「拆干净」等于「回到装之前的样子」。论文说不对，没必要。

它说，恢复只要做到**「没有观察者能区分」**就行。你换了张同款沙发，颜色、坐感都和原来一样，家里没人看得出来——这就够了。你不需要把旧沙发变回来，你需要的是看起来和旧沙发一样。

> **所谓「干净」，不是物理还原，是观感等价。**

这句话后来我想了很久。它解释了不少事：备份为什么能压缩？因为恢复出来「看着一样」就行。文章为什么能写摘要？因为对读者来说，关键信息在就够了。

## 实体抽象 vs 规则抽象

理论读完，我开始往自己熟悉的领域套。我拿两个东西对比：pi 和 dsh。

**pi** 是一个最小可运行的智能体（earendil-works/pi）。你可以把它想成一台组装好的电脑，主板、CPU、内存都焊在机箱里。能换零件、能加内存、能升显卡，但整台电脑本身是固定的。**它抽象的是「实体」。**

**dsh** 是另一种思路。它抽象的是一套运行规则：任何符合规则的零件都能插上去，包括「把整台电脑换掉」。它不是一台电脑，它是「怎么组电脑」的规则。**它抽象的是「规则」本身。**

这两个抽象差了一个维度。实体是具体的，规则是通用的；有了规则能长出任意实体，有了实体推不出规则。所以 dsh 能长出 pi 那样的东西，pi 却长不成 dsh——不是功能上的差距，是维度上的差距，像「下棋的规则」和「一枚棋子」。

## 维度高，就一定更好吗？

不一定。这是我这篇论文最大的收获。

因为所有抽象，最后都得有实体来承载。dsh 的规则再高级，也得跑在一堆代码上；而那套「万能」设计，一开始在效率和适配性上，可能反而不如 pi 这种贴着场景做的实体。**万能工具箱什么都能修，但你拆电脑，还是专用的螺丝刀顺手。**

所以我对「维度」的理解，最后落成一句：

> **维度高，是可能性大，不是能力大。能力 = 可能性 × 落地质量。**

天花板再高，得看实际跑起来的那个实体兑现了多少。

## 落到我自己身上

我的工具一直用「粗粒度」方案——每个任务放独立的隔离空间跑，像一个个集装箱。以前我总觉得这不够高级，看到别人搞精细的组件化，会心虚。

读完这篇，我释然了，也给自己立了条规矩：**在场景没触到维度天花板之前，粗粒度、贴场景的方案，往往比高维度抽象更实际。要不要升级，答案只有一个：痛了才改。** 等我真的需要「运行的时候换零件」那天，再为那套高级抽象付「万能工具箱的笨重」。

## 一个判断框架

这篇论文没给我答案，但给了我一个判断框架。现在我看任何工具、任何方案，先问两句话：

1. 它的维度在哪——是实体，还是规则？
2. 它的落地质量怎么样——跑起来利落，还是笨重？

然后记住：**别为了「看起来高级」去升级。够用、顺手、拆得开，比参数好看更重要。**

就像我组装电脑那年学会的：**好看的主机箱，不如一颗够用的 CPU。**
