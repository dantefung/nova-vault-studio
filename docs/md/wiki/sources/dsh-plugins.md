# 从架构到 Agent 工作流，聊聊 DSH 插件该怎么选

架构师（JiaGouX）我们都是架构师！架构未来，你来不来？前两天的两篇文章，先梳理了 DSH 的运行架构，又拆开 Cordis 看了插件的依赖和生命周期。继续往下研究，总会碰到一个很实际的问题：社区已经有了侧边栏、TUI、视觉、记忆、定时任务和多 Agent 工作流，自己的环境里到底先装什么？

这几天，DSH 插件像雨后春笋一样冒出来一大批。热闹当然是好事，真要动手安装，光看功能分类还不太够。

![插件生态](images/dsh-plugins/001.png)

有的插件只是帮人少敲几次路径，有的会给 Agent 增加工具，有的把信息留到下一次会话，还有的能在没人盯着时启动一个新任务。它们都叫插件，解决的问题却不一样。

如果只是想尽快把 DSH 用起来，一个比较省事的顺序是：先装 `dsh-at-file`；Web 和终端入口，从 `dsh-better-sidebar`、`dsh-TUI` 里挑一个；工作里经常要看截图，再加上 DSH Vision Toolkit。Mnemon、Automation 和 Workflow，可以等项目真的遇到跨会话记忆、定时运行或固定多 Agent 流程的问题时再装。

这个顺序谈不上标准答案，思路也很简单：先解决眼前最常见的麻烦。至于要保存长期数据、调用外部服务，甚至让 Agent 自己定时开工的插件，等确实用得上时再加。

## 选插件，先看它改了哪一层

DSH 在仓库首页写着一句 **Everything is a Plugin**。前面拆源码时已经能看到，这里的插件不只是给界面多加一个按钮。

DSH 启动时，Profile 决定当前环境装进哪些插件，Cordis 再按依赖关系决定谁先启动、谁在依赖变化时退出或重载。插件也能注册工具、监听事件和保存状态。界面、模型 Provider 和会话存储，都是这样接进 DSH 的。

表面上都叫"装个插件"，实际改动的地方差得很远。`dsh-at-file` 只在输入框里补一段路径；Vision Toolkit 会把新工具交给 Agent，处理图片时还可能访问外部服务；Mnemon 会把信息留到当前会话之外；Automation 则会在会话之外，按时间启动一个新 Agent。

把它们放回系统里，大致可以看成四层：

| 改动位置 | 装之前多看什么 | 代表插件 |
|---------|-------------|---------|
| 交互入口 | 依赖、操作习惯、能否快速退回 | at-file、TUI、better-sidebar |
| Agent 工具 | 参数、外部服务、数据去向 | ModLens、Vision Toolkit |
| 跨会话状态 | 存储、迁移、卸载残留 | Mnemon |
| 调度与工作流 | 权限、审批、失败恢复 | Automation、Workflow |

交互入口不顺手，关掉通常就结束了。工具可能把数据送到外部，记忆插件会留下长期数据，定时任务还会产生新的会话、结果和失败现场。所以选插件时，除了看它能做什么，也可以顺手问一句：**停用以后，还会留下什么？**

## dsh-at-file：小功能，反而最适合先装

让 Agent 读代码、改文档，路径是个很小、又绕不过去的麻烦。仓库一大，文件名敲错、相对路径漏一截，刚展开的对话就得停下来重来。

`dsh-at-file` 做的事情很简单：在输入框里键入 `@`，搜索当前工作区的文件或目录，选中以后把相对路径放进对话。

![dsh-at-file 文件搜索界面](images/dsh-plugins/002.png)

https://plugin.dshx.dev/item/omdsh-dev/dsh-at-file/

它适合排在前面，主要是因为改得少。插件只负责填路径，不会顺手把整份文件塞进上下文。文件要不要读、什么时候读，仍然由 Agent 根据任务决定。

它对路径也做了几道限制：常见的依赖、缓存和构建目录会被跳过；搜索不会顺着符号链接跑出工作区；绝对路径和工作区外的路径会被拒绝。大型仓库仍要留意索引数量和忽略规则，手工输入带空格的文件名也有一些限制。

目前可以把版本锁在 v0.6.2：

```bash
dsh plugin --profile web add https://github.com/omdsh-dev/dsh-at-file/archive/refs/tags/v0.6.2.tar.gz
```

它不会让 Agent 突然变聪明，只是把一个每天都可能重复的动作做顺了。插件不保存跨会话数据，也不会把文件内容直接塞进上下文，出了问题通常容易排查。

## Web 和终端，选一个顺手的入口

路径的问题解决以后，接下来就看平时从哪里打开 DSH。

如果工作时浏览器一直开着，`dsh-better-sidebar` 会比较顺手。它在侧边栏里放进了文件管理、编辑预览、内嵌浏览器、真实终端、Git 面板和后台任务。查文件、看 Diff、观察子 Agent 的进度，来回切窗口的次数会少一些。

https://plugin.dshx.dev/item/omdsh-dev/DSH-better-sidebar

功能多了，依赖也会跟着多。它的真实终端用到了 `node-pty`，Git 面板可以暂存、提交和还原文件；项目要求 Node.js 20 以上、pnpm 10 以上。如果 pnpm 拦下依赖的构建脚本，最好先确认脚本做了什么，再决定是否放行。

平时主要待在终端，`dsh-TUI` 更直接。流式 Markdown、工具调用卡片、命令和文件补全、会话恢复、上下文信息，都可以在终端里处理；模型调用和会话保存依然由 DSH 服务完成。它目前还是 public beta，需要 TTY、官方 `dsh` CLI 和 pnpm 10 以上版本；Node.js 版本要求是 `^22.19` 或 `>=24`。

这两个插件没有必要逐项比功能。better-sidebar 适合把 Web 变成日常工作台，dsh-TUI 适合不想离开终端的人。两个都装也行，只是 Agent 不会因此多会一项本事，反而多了一套要维护的界面。

## 视觉很好用，图片去了哪里也得看

`dsh-at-file`、better-sidebar 和 dsh-TUI 改的主要是人的操作方式。DSH Vision Toolkit 再往里走了一步，它会给 Agent 加上一组处理图片的工具。

DeepSeek 目前常用的文本模型不能直接看图，可前端开发、UI 还原和报错排查，偏偏经常从一张截图开始。Vision Toolkit 能做图片问答、长截图 OCR 和元素定位，也能裁图、取色、比较像素差异、截取 HTML 页面。

有了文字、坐标和处理后的图片，Agent 才能继续改页面、查问题，而不是停在"请描述一下截图"这一步。

安装包名是 `@anionex/dsh-vision-toolkit`：

```bash
dsh plugin --profile web add @anionex/dsh-vision-toolkit
```

它要求 Node.js `^22.19.0` 或 `>=24.0.0`，还需要 Python 3.11 以上。第一次启动时会准备独立的 Python 环境，本地没有依赖缓存还会联网下载。

**免配置只是少填几项参数，并不代表图片没有离开电脑。** 它的默认视觉服务不用 API Key，图片理解请求却会发到外部共享服务。裁剪、像素对比、颜色分析、前景提取、SVG tracing 和 HTML 截图这些操作，则可以留在本地完成。

公开截图和普通 UI 稿，用默认服务比较省事。碰到内网页面、客户数据或未公开设计稿，可以换成可信的视觉端点，或者只使用本地工具。

工作中经常拿截图和 Agent 沟通，这个插件很容易派上用场。如果平时处理的都是代码和文本，暂时不装也没有损失。

## 记忆插件，可以晚一点再装

一次任务结束以后，总有些信息希望下次还能接着用。Mnemon 做的就是这件事。

`dsh-mnemon` 把记忆分成了几类：眼前这个任务要用的上下文，原样保留的项目文档，以及以后需要时再查的长期记忆。默认后端是 Mnemon Native，也可以换成其他 Provider。

https://plugin.dshx.dev/item/omdsh-dev/dsh-mnemon/

多个 Agent 长期围绕同一个项目工作时，共享项目事实和决策记录很有价值。不过，如果眼前的问题只是每次都要重复说明仓库约定，先把约定写进项目文档往往更直接。文档能审查，能跟着代码一起做版本管理，也更容易确认 Agent 到底读到了什么。

**Mnemon 还有一个容易忽略的地方：卸载插件不会自动删除本地或远程记忆。** 插件停了，数据还在。存在哪里、怎么备份、换环境时怎样迁移、不再使用时如何清理，都需要项目自己安排。

这也是记忆插件适合晚一点再装的原因。等项目确实反复遇到跨会话召回的问题，它会很有帮助；在那之前，先多维护一份长期数据，未必真的省事。

## 自动运行之前，先让任务跑稳

再往后是 Automation 和 Workflow。它们会直接碰到 Agent 的启动、失败恢复和多 Agent 协作，事情比当前会话顺不顺手复杂得多。

`dsh-automation` 用来定时执行任务。每次运行都会新建根 Agent 和 Session，不会继承创建任务时的聊天记录与审批。它只提供 `read-only`、`workspace-write` 两档权限；任务中途如果需要人工批准，本次执行会直接失败。

![dsh-automation 定时任务界面](images/dsh-plugins/003.png)

https://plugin.dshx.dev/item/titanwings/dsh-automation/

这种方式适合边界清楚、结果容易核对的任务，比如定期跑回归、生成仓库报告、刷新固定产物。任务本身还经常需要追问，或者完成标准每天都在变，加上定时器也只是定时碰壁。

目前项目提供的固定安装标签是 v0.1.6，使用时可以继续锁住这个版本。

DSH Workflow（https://plugin.dshx.dev/item/icetomoyo/dsh_workflow/）更适合那些已经跑顺、以后还会反复跑的多 Agent 任务。任务怎么拆、每一步跑到哪里、留下了哪些产物、从哪里恢复，它都会记下来。像代码审查、并行调研这类流程，用它可以少做一些重复编排。

偶尔让两个子 Agent 分头查资料，DSH 自带的调度已经够用。Workflow 目前要求 Node.js 22.19 以上，安装前还得核对仓库里的 `compatibility.json`。它是跟着一份确定的 DSH 版本开发的，而 DSH 仍处于开发者预览阶段。这个时候，兼容记录比功能列表更值得先看。

这两类插件适合先在有人看着的时候把任务跑稳，再考虑定时执行或固定工作流。这样出了问题，至少能分清是任务没说清，还是权限、调度和恢复出了岔子。

## 装上之前，再看一眼权限边界

插件装得上，只是第一步。README、源码仓库和最近更新时间还得接着看；出现在目录里，也不等于代码、依赖和权限已经有人检查过。

刚开始接触 DSH 插件，手工装一两个反而更容易摸清流程。把 Profile、锁文件、重启、禁用和卸载都走一遍，碰到安装失败或版本冲突时，心里大致知道该从哪里查。

**Profile 很适合分开管理依赖和配置，试验、切换、回退都方便，但它不是安全沙箱。** 插件和 DSH 宿主仍在同一个 Node.js 进程里。Cordis 的 `inject` 管的是插件依赖哪些 Service，以及这些插件何时启动、何时退出。插件如果直接调用 Node.js 的文件、网络或进程能力，`inject` 并不会拦住它。

安装前多看几眼仓库是谁在维护、版本能不能锁住、`package.json` 里有没有安装脚本，Node.js 和 pnpm 版本能不能对上，能避开不少麻烦。Profile 的配置和锁文件也值得留一份，真碰到问题，至少还有路可退。

DSH 现在仍是开发者预览版，后面出现不兼容改动并不意外。这次对照的 DSH 源码提交是 `47f943859bef60e4160492346772ded9b24f765a`。现阶段锁住插件版本，留好配置和锁文件，通常比追着每天出现的新项目全部装一遍更踏实。

## 写在最后

最近把这些插件逐个看下来，慢慢形成了一个习惯：除了看它能加什么，也看关掉以后还会留下什么。输入补全几乎不留痕，视觉工具会带来新的数据边界，记忆插件会留下长期状态，自动任务则会留下运行结果和失败现场。

这个角度不一定适合所有人，但比单看功能多少，更容易估出后面的维护成本。

DSH 把 Agent 运行时的很多位置都开放了出来，社区才能这么快补界面、加工具、做记忆和工作流。这套插件系统的想象空间确实很大。只是走得越靠近 Agent Loop，越会碰到权限、数据、失败恢复这些熟悉的软件工程问题。

插件不必一次装齐。先挑一两个眼前真用得上的，跑顺以后再往里走，更适合现在这个还在快速变化的 DSH。
