# 前端 Skill 驱动的团队 AI Coding 实践：从个人到整体提效

> 当团队里的后端、PD、设计师都在用 AI 写前端代码，怎么保证产出是「一个团队的产物」而不是 AI 的随机产物？答案：把前端规范做成 Skill，前置到 AI 写第一行代码之前。

![文章封面](images/frontend-skill-team/001.jpeg)

---

## 01 背景：AI 能写代码了，但可维护性、规范一致性成了新问题

过去半年，团队几乎全员进入 AI Coding 状态：后端用 AI 写前端模块、PD 用 AI 搭可交互原型。问题逐渐暴露：

- **风格漂移，AI 味浓**：A 同学搭的项目像后台管理模板、B 同学的像官网落地页，布局、配色、交互各走各的
- **技术栈生态不匹配**：AI 偏好 Vite + Next.js + Tailwind + lucide-react，而线上是 ice + Fusion / umi + Ant Design（XOps），不加约束就引入未经审计的外部依赖
- **自创轮子遍地**：`<input>` 配 40 行 CSS 的搜索框、原生 `<button>` 加全套手写样式
- **信息不对齐**：跨端开发时不知道规范长什么样
- **原型活不过评审**：PD 搭的原型技术栈上和正式开发完全脱节

**典型现象**：后端用 AI 全栈跑通一个工具，业务方说「太丑」、设计说「不符合规范」、后端说「前端帮忙调一下」。前端打开代码——Tailwind 散落几十个文件、各种手写 SVG、原生 `<input>` 加一堆 CSS——功能跑通了，但全都是技术债。

![后端 AI 全栈跑通的技术债](images/frontend-skill-team/002.jpeg)

## 02 尝试过的路径

### 前端基础课：做了，但不够

即使认真学习了，也没法大胆尝试——真实工程环境里的踩坑经验才是决定代码能不能上线的关键，这些隐形知识不是一门课能覆盖的。

### 团队知识库：想做，但有门槛

- 技术债没理清就开始攒规则，知识库本身会变成新的技术债
- 多人贡献，冲突没人仲裁。没有强 owner 和明确 review 机制，规则之间容易打架

### 自建 R2C 平台：尝试后发现不适合

重点关注了 Aone Super（集团内部一站式需求研发平台），接入 SDK 并开发了内部 Anchor 平台，但几轮测试验证下来并不适合：

- 对项目本身需要配置改造 + 安装浏览器代理插件，有成本
- 长链路稳定性在打磨，长任务偶尔中断
- 自维护 API Key 模式，人力维护 + token 消耗成本不可控

**关键洞察**：「独立平台 + 自维护 API Key」模式很难走通。需要的是「长在日常工具里、零额外门槛」的能力。

## 03 认知转变：从「做平台」到「做 Skill」

![认知转变](images/frontend-skill-team/003.jpeg)

为什么是 Skill 而不是其他？因为上面所有路径，都没解决同一个问题：**「AI 写代码那一刻」的规范对齐**。

- 基础课：指望人先学会再动手，但没人看，隐性知识传递困难
- 知识库：想把规范、坑点攒齐再给 AI 用，攒不齐不说，攒着攒着还可能变成了债
- 独立平台：在 AI 和代码之间多加了一层，跟日常工作流脱节

**三条路的共同问题**：都在 AI 写代码之前加了一个前置动作，而实际工作中大概率不会发生。Skill 则相反：不用人先上课、不用人先查文档、不用人切到另一个平台，**规范直接预加载在 AI 最熟悉的工作流的上下文里，AI 一动手就已经带着约束**。

## 04 an-frontend-skill 的五维结构

### 盘点现状：三种技术栈

| 分类 | 技术栈 | 特征 |
|------|--------|------|
| 经典稳态系 | Ice + Fusion + React16 + Formily | 沉淀久、依赖深，升级成本巨大，核心诉求「求稳不翻车」 |
| 稳定性标准系 | x-ops + ProComponent | 已升级技术栈与组件库的团队主力业务项目，规范统一 |
| 通用新建系 | React 18 + Ant Design | 尚未收口的存量项目和新起项目，最容易「放飞」 |

三种技术栈的技术栈、UI 库、请求库、表单方案几乎都不同，一份「放之四海皆准」的规范根本不存在。

![五维结构图](images/frontend-skill-team/004.jpeg)

**反着问自己**：一个前端老师傅接手一个陌生仓库时，脑子里在跑哪些判断？把这些判断一条条挖出来，写成 AI 能照做的指令，就是 Skill 的由来。

### 五维结构

| 维度 | 含义 | 对应文件 |
|------|------|----------|
| **When** | AI 什么时候该加载规范 | SKILL.md 顶部触发场景 |
| **What** | 在这个语境下该选什么 | tech-selection.md（技术选型矩阵） |
| **Don't / Why** | 绝对不能碰什么 + 理由 | aicoding-rules.md |
| **How** | 标准答案长什么样 | component-templates.md |
| **Map** | 周边能力怎么挂载 | 设计 Token / i18n / 项目子 Skill |

目录结构：

```
an-frontend-skill/
├── SKILL.md              # 主入口：触发场景 + 项目识别路由 + 硬约束概要 + 选型总则
└── reference/
    ├── aicoding-rules.md     # Don't/Why：完整硬性约束
    ├── tech-selection.md     # What：技术选型矩阵
    ├── component-templates.md # How：标准样板
    ├── coding-standards.md   # 代码规范详解
    ├── yunan-xops-design.md  # Map：稳定性设计规范
    ├── domain-repository-map.json  # 路由事实源
    ├── glossary.md           # 术语表
    ├── contacts.md           # 问题对接路由
    └── skills/               # 嵌入的项目专属子 Skill
        ├── goc-frontend/     # 经典稳态系
        └── x-ops/            # 稳定性标准系
```

### 维度 1：触发场景（When）

> **只要对话涉及 React/TSX 代码的生成、修改、重构、评审，即使用户未显式提及本 Skill，AI 也会主动加载。**

包括：新建项目脚手架、新增组件/Hook/页面、重构既有模块、接入团队内部组件库/设计系统、选型决策、后端做端到端交付时的前端部分。

### 维度 2：技术选型矩阵（What）

**第一层：项目类型路由**（解决既有项目的识别问题）

| 项目 | 锁定技术栈 | 理由 |
|------|-----------|------|
| 历史项目 A | Ice.js 2.x + Fusion + Formily | 历史决策，不动 |
| 历史项目 B | 团队私有 Pro 组件库 | 强绑定中后台体系 |
| 新项目 | React 18 + TS + Vite + XOps + ahooks | 本节真正的「选型」 |

**第二层：新项目场景表**

| 场景 | 首选 | 不推荐 |
|------|------|--------|
| UI 组件库 | Ant Design | Tailwind（绕过 Token） |
| 表单 | Ant Design Form | Formily（社区萎缩） |
| 状态管理 | ahooks / Zustand | Ice Store（停止维护） |
| 数据请求 | 内部请求库（magic-request） | SWR（与团队栈重复） |
| 图表 | AntV (G2/G6) | ECharts（包比较大） |

### 维度 3：硬性约束（Don't / Why）

8 条硬约束，每条都附 Why：

1. **禁用 any**：用 unknown + 类型守卫。Why：any 是 TS 的逃生舱，逃生舱只能由 reviewer 主动开
2. **禁用 Tailwind**：统一 CSS Modules + Design Token。Why：原子类与 Token 体系冲突
3. **禁用第三方 iconfont / 散落 SVG**：统一使用团队私有 icon 包。Why：图标是品牌资产
4. **Hook 必须在顶层调用**：禁条件/循环内调用。Why：React 规则
5. **组件单一职责，单文件 `<200 行`**：超出必须拆
6. **API 调用必须走统一封装**，禁裸 fetch。Why：错误处理、loading、鉴权、埋点都在拦截器里
7. **禁手写 useState + useEffect 模拟数据请求**：用 useRequest。Why：遗漏 race condition / 取消 / 缓存
8. **禁硬编码颜色 / 间距 / 圆角**：必须用 Token

### 维度 4：标准样板（How）

![组件三段式样板](images/frontend-skill-team/005.png)

4 套样板，每套都是「最小可运行 + 团队约定写法」：

- **公共组件三段式**：`index.tsx` + `index.module.css` + `types.ts` + 桶导出
- **API 调用层**：双轨——通用项目用 axios + 拦截器；锁定栈项目用团队私有配置式请求库
- **列表页**：useRequest + Table + columns prop 的完整骨架
- **表单页**：Form + Form.Item + name + rules + onFinish 的标准写法

### 维度 5：跨能力集成（Map）

挂载两类已有的团队产物：

**① 设计语言映射**（稳定性设计规范）：Design Token（颜色/间距/圆角/字号/阴影）+ 设计稿元素到 Ant Design/团队私有组件的映射 + 图标库用法。前端 Skill 不再独立维护 Token，而是引用设计同学的产物。

**② 国际化方案**（an-i18n-setup）：基于集团国际化框架，覆盖文案抽取、key 生成、多语言文件组织、运行时切换降级。

**调用顺序**：
1. 主 Skill → 解析项目类型 + 注入硬约束
2. 命中设计场景 → 加载 yunan-design-system
3. 命中 i18n 场景 → 加载 an-i18n-setup
4. AI 生成代码 → 三方规范同时在场

## 05 实践落地案例

![案例总览](images/frontend-skill-team/006.jpeg)

### 案例 1：Status 云产品健康看板

- **场景**：借助 Aone Super 的 D2C/R2C 能力，全新平台，1 页面/10 组件/9 核心接口
- **研发周期**：3 周
- **AI 代码采纳率**：80%
- **问题**：D2C 还原效果一般，出码后需人工反复微调；长上下文导致链路中断
- **价值**：首次验证 D2C/R2C 可行性

### 案例 2：CFD 演练平台（老旧项目升级）

- **规模**：23 页面 / 80+ 组件 / 30 API 接口
- **旧栈**：Umi 3 + Ant Design Pro → **目标栈**：Umi 4 + xops-design + ProComponents
- **传统手工升级**：1-2 周（60% 时间花在样式/组件替换）
- **AI + Skill 升级**：**3 天**（手动对齐规范接近 0）
- **价值**：Skill 约束下 AI 自动遵守目标技术栈，省掉逐文件手工对齐

### 案例 3：AIOps 项目（设计直接 AI Coding）

- **场景**：设计同学绕过「出设计稿→交付前端→还原→走查」链路，直接 AI Coding → 可交互原型
- **规模**：3 页面 / 24+ 组件 / 8 核心接口
- **代码可复用率**：从 `<30%` 提到 **70-80%**
- **前端接入耗时**：从 2-3 天压到 **半天**
- **价值**：「原型即代码」从理念变成现实

### 案例 4：一国一云国际化（批量改造）

- **场景**：多平台支持中英文多语言。去年故障平台、变更平台用内部方案做国际化，两个平台约 2 个月。这次用 Skill 流水线，三个平台 **2 周全部完成**。
- **Skill 做了什么**：6 步自动化流水线 + 5 个配套脚本
- 3 个平台工作量：故障管理（GOC）、变更管控（CM）、风险巡检（CIS）

## 06 场景延伸：R2C 需求转代码

![R2C 流程图](images/frontend-skill-team/010.jpeg)

在 Skill 基座之上，进一步探索了 R2C（Requirement-to-Code），已沉淀为 **an-r2c Skill**：

| 阶段 | 内容 | 状态 |
|------|------|------|
| PM 阶段 | PRD 解析 → 用户确认 → requirement.md | 已实现 |
| UI 规格阶段 | 设计稿/D2C DSL 解析 → 用户确认 → ui-spec.md | 已实现 |
| 技术方案阶段 | 仓库分析 + 范围确认 + 方案生成 → tech-solution.md | 已实现 |
| 代码生成阶段 | 路由/接口/UI/逻辑，全自动串行 | 已实现 |
| 验证阶段 | 启动 dev server + 视觉校验 | 已实现 |
| AI Code Review | AI 自动 Review 是否符合 Skill 约束 | 规划中 |
| 部署触发 | 自动触发构建和部署流程 | 规划中 |
| 线上验证 | 部署后自动化验证 | 规划中 |

**三个关键设计**：

1. **流程拆成 10 个阶段文件**：每个阶段只管一件事，规避了「规则堆在一个大文件里、超过 4000 字后 AI 遵循度下降」的坑
2. **依赖一键集成**：6 个子 Skill 随主 Skill 打包分发，安装成本从「装 6 个 + 配 MCP」降到「装一个 + 首次授权一次」
3. **写码前先出结构化 Spec**：约 30% 的场景会在这一步就暴露需求与设计稿的不一致

**落地效果**：一个标准 CRUD 需求，从需求文档到浏览器跑起来约 **20 分钟**，对比过去「后端试写前端→前端帮忙 review 改完」的 **2-3 天** 大幅压缩。

角色重构：后端开始端到端交付、产品自己开发需求、前端从「写每个页面」转向「review AI 产出 + 攻坚复杂场景」。

## 08 尚未解决的难题：AI Coding 提效量化

效率提升是直观可感的，但量化目前没有统一标准。考虑用 3 个粗粒度口径自我观测：

- **改造前后人天对比**：同类规模下无 Skill vs 有 Skill 的人天差
- **首次产出 review 通过率**：AI 第一次产出代码需要打回返工的比例（目标从 60%+ 降到 `<20%`）
- **Skill 使用侧信号**：下载量、收藏量、主动反馈数

## 09 思考：能力沉淀 > 个人提效

![个人到组织](images/frontend-skill-team/011.jpeg)

**核心论点**：个人写得快不是竞争力，把「怎么写得对」沉淀成可复用的能力资产，让所有人都写得对，才是。

团队的产出从来不取决于最强的那个人，而取决于最弱的那一环。部分同学用的工具弱、token 额度有限；新人对项目历史背景一无所知——没有 Skill 约束，AI 会按默认偏好写代码，reviewer 返工量比不用 AI 还大。

**真正的杠杆**不是让能力出众的人更快，而是把所有人的底线一起抬上来。哪怕用着普通的工具、有限的额度，也能稳定产出符合规范、可被接手的代码。

Skill 就是这个杠杆：它把「资深前端脑子里的判断」固化成一段 AI 每次都会自动加载的上下文，**边际成本几乎为零：写一次，团队里每个人、每次对话都在复用**。

**建议其他团队**：从自己的研发或业务流程出发，锁定一个反复出现的痛点，用 AI 解决它，然后把方案抽象成 Skill。

## 10 回顾与展望

![结语动画 1](images/frontend-skill-team/013.png)
![结语动画 2](images/frontend-skill-team/014.png)

**核心认知转变**：规范落地的切入点是 AI 的上下文。课程、文档、平台解决的都是「人知不知道」的问题，但 AI Coding 场景下真正决定产出质量的是「AI 生成那一刻的上下文里有没有规范」。**Skill 本质上是把规范从被动参考变成主动注入。**

**演进方向两条线**：

- **横向扩角色**：后端接口契约（OpenAPI spec → Skill）、测试用例生成约束、PD 原型工程化规范
- **纵向延链路**：接入 code review 自动化、CI 前置校验、部署后巡检，形成「生成→审查→验证」的完整 Skill 链

最终目标：团队研发流程的每个质量关口都有 Skill 约束在场，AI 在整条链路上都带着团队经验运行。
