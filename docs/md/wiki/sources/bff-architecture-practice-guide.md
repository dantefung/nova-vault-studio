# BFF 架构实践指南

> BFF（Backend-for-Frontend，面向前端的后端）是一种架构模式：为不同的前端客户端（Web、App、小程序）提供专属的后端适配层，解决前后端分离架构中普遍存在的数据聚合和多端接口适配问题。它主要做三件事：**数据剪裁、接口聚合、响应格式适配**。

## 与 API 网关的区别

| 维度 | API 网关 | BFF |
|------|---------|-----|
| 定位 | 流量基础设施层 | 业务数据编排层 |
| 核心职责 | 路由、统一鉴权、限流、SSL、协议转换、黑白名单 | 数据聚合、字段裁剪、多端差异化返回 |
| 业务感知 | 不感知具体业务 | 感知前端页面和客户端差异 |
| 部署粒度 | 通常全局一个 | 可按端或按业务域拆多个 |

网关管"流量能不能进来、怎么分发"，BFF 管"进来之后的数据怎么组装成前端想要的样子"。两者职责不能上下乱迁移。

## 主要功能

- **数据聚合**：并行调用多个下游微服务，将分散数据整合为前端所需结构
- **多端定制 API**：根据 Web/App/小程序不同的展示需求裁剪字段
- **统一异常处理**：标准化 HTTP 状态码和错误结构，屏蔽内部异常细节
- **短时缓存**：对聚合结果做短时间缓存，仅适用于弱一致性、读多写少的数据
- **调用编排与容错**：统一管理下游调用的超时、重试、降级策略

## 代码实践

BFF 一般独立部署为 Spring Boot 应用，典型场景有两类。

### 接口适配与数据裁剪

同一个订单接口，App 端只需要精简字段省流量，Web 端需要完整字段支撑复杂页面——各自 BFF 接口返回不同结构。

### 数据聚合的两种方式

**方式一：CompletableFuture**（同步 Spring Boot 项目常用）

```java
CompletableFuture<List<Product>> productsFuture = 
    CompletableFuture.supplyAsync(() -> productClient.getProducts(orderIds), executor);
CompletableFuture<PaymentInfo> paymentFuture = 
    CompletableFuture.supplyAsync(() -> paymentClient.getPaymentInfo(orderId), executor);
CompletableFuture.allOf(productsFuture, paymentFuture).join();
```

两个注意点：必须指定线程池（默认 ForkJoinPool.commonPool() 在高并发下极易被打满）；单服务降级——某个下游超时时返回默认值，而不是让整个接口失败。

**方式二：Project Reactor**（高并发非阻塞场景）

Reactor 基于非阻塞 I/O 和事件驱动模型，但要求全链路（包括下游 Client）都是响应式的，否则混合使用反而会阻塞事件循环。

## 避坑指南

1. **避免代码复制**：不同 BFF 之间的公共逻辑应下沉到公共 SDK，禁止每个 BFF 复制粘贴
2. **避免过度聚合**：单个 BFF 接口不建议聚合过多下游服务，遵循单一职责
3. **先评估必要性**：业务简单、客户端类型单一的场景，额外维护一层 BFF 得不偿失
4. **职责清晰有边界**：Web BFF 专注复杂嵌套对象，App BFF 注重数据裁剪，互不干涉

## 落地约束

**严格边界**——BFF 不做的事：
- 不实现核心业务规则和复杂领域计算
- 不写数据库事务，不直接操作数据库
- 不承载领域核心逻辑
- 不做网关该做的限流、全局路由

**拆分方案**：

| 方式 | 优势 | 劣势 |
|------|------|------|
| 按端拆分（Web/App/小程序） | 天然支持多端差异，各端独立迭代 | 相同业务聚合逻辑容易重复 |
| 按业务域拆分（商品/订单） | 逻辑复用性好，业务内聚 | 多端差异化处理不够直观 |

**反模式**：BFF 中编写核心业务计算、直接操作数据库、BFF 之间互相远程调用、将网关逻辑下沉至 BFF、一个接口聚合十几个下游服务且无降级预案。

## Trade-off 讨论

**导入导出走 BFF 吗？** 超大文件场景下，BFF 仅负责接收请求下发异步任务，核心后端异步处理写入 OSS，前端直接下载。海量数据流量不经过 BFF。

**多一层有必要吗？** 多一层意味着多一层数据转换（大量 DTO/VO 转换）、部署和运维成本增加。判定参考（满足多条再考虑）：
- 存在多端客户端，且各端数据需求差异明显
- 前端请求零散，一个页面需要调用多个后端接口
- 频繁需要字段裁剪
- 页面需要跨多个服务组装数据

## 总结

> 能满足当前业务场景、团队能维护得住的架构，就是好架构。BFF 不是银弹，大厂的方案也不一定适合我们的阶段。拆分之前先想清楚：痛点到底是多端适配，还是接口聚合？如果只是其中一个，也许一个轻量的适配层就够了。
