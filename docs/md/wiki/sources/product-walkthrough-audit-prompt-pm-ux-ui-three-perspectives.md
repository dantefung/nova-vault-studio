# 产品体验走查提示词：同时以产品经理、UX 研究员与 UI 设计师视角验收并分级修复

> 一份可直接投喂给高能力 Agent 的产品体验走查提示词：以「用户能否快速理解产品、独立完成任务、出错后能否恢复」为验收标准，从首次打开走到核心任务完成并确认结果，覆盖空状态、加载、输入错误、权限不足与失败恢复，检查多尺寸、键盘导航与焦点可见性；用信息架构、流程、效率、反馈、视觉层级、设计系统一致性六个维度逐路径检查；按 P0-P3 分级（核心任务无法完成/关键任务高频失败/可完成但有冗余/视觉文案细节）并处理根因合并；可选在授权环境直接修复已复现的 P0/P1（可分派子 Agent），修复后用相同设备尺寸数据与步骤复走并给出改前改后对照；交付物为「最多 3 个最优先问题 + 问题表（优先级｜页面与场景｜复现步骤｜实际表现与用户影响｜证据｜具体改法｜可验证的验收条件）+ 已查未查范围」。

<!-- more -->

**采集说明**：本文整理自社区评论区共创的最终提示词（原帖以「综合了一下评论区的建议，最终提示词」引出）。它把「产品体验走查」从一件依赖人工经验、周期漫长的事，变成一条**可交给 Agent 执行的标准化流水线**：明确验收标准、明确路径、明确分级、明确交付格式。

**核心设计思路**：走查不再是「挑毛病」，而是**以验收标准驱动的、可验证的工程任务**——每条结论都必须能落到「页面与场景 + 复现步骤 + 证据 + 具体改法 + 可验证的验收条件」上。

## 完整提示词（可直接复制使用）

```text
你负责这次产品体验走查，请同时从产品经理、UX 研究员和 UI 设计师的视角判断。以用户能否快速理解产品、独立完成任务、出错后能否恢复为验收标准。自行规划顺序并开始走查。

输入（按需填写）
产品入口或材料（网址、项目目录、原型、截图）｜目标用户和核心任务｜执行模式（仅走查 / 走查并修复，默认仅走查）。已有信息从上下文获取，缺项先列出假设并继续。确实缺少可用入口或材料时，指出需要补充的最少信息。

1. 从第一次打开产品开始

用新用户的视角，实际走完「首次打开 → 找到入口 → 完成核心任务 → 确认结果」。按产品实际情况，再覆盖回访用户的高频任务。按任务重要性和使用频率安排顺序，随后检查可达的主要页面与交互。

对关键步骤截图，记录卡住的位置、用户可能的误解和额外操作。覆盖适用的空状态、加载、输入错误、权限不足和失败恢复。按产品支持范围检查不同屏幕尺寸、键盘导航和焦点可见性。会改变数据的操作用测试环境和测试数据验证。

有可运行环境就实际操作。无法运行时，基于截图、原型或代码做静态评审。逐项标明「实测」「静态发现」或「待验证」。

2. 用六个维度检查每条路径

检查信息架构中的入口、命名和分组是否符合用户预期。

沿着用户流程检查下一步是否清楚，走错后能否返回并继续。

评估操作效率，找出重复输入、多余点击和可省掉的等待。

验证反馈机制是否说明当前状态、操作结果和出错后的下一步。

检查视觉层级是否突出主操作，文字、间距和对比度是否便于阅读。

对照现有设计系统检查组件一致性，涵盖外观、文案和行为。

3. 分级，必要时修复并复验

P0 核心任务无法完成且无可行替代，或已发现严重数据丢失风险。P1 关键任务高频失败或明显受阻，用户需要绕行。P2 可完成任务，但存在多余步骤、误解或局部不一致。P3 视觉和文案细节。

同级按影响范围和发生频率排序，影响相近时优先做成本低的改动。同一根因合并记录，证据不足的项单列待验证。

选择「走查并修复」时，优先在授权的开发或测试环境中修复已复现的 P0/P1。可将互不冲突的问题分派给子 Agent，由主 Agent 集成和验收。缺少子 Agent 时按优先级逐项处理。其余问题写成可执行建议。需要产品或设计取舍的改动，列出取舍供评审。

修复后用相同设备、尺寸、数据和操作步骤复走，能截图时提供改前改后的同状态对照。记录可测的变化，例如操作步数或错误恢复结果，并检查相邻流程。缺少对照证据时说明原因。

4. 交付走查结果

先给出最多 3 个最值得优先处理的问题，再按优先级列问题表。每项写明「优先级｜页面与场景｜复现步骤｜实际表现与用户影响｜证据｜具体改法｜可验证的验收条件」。最后列出已查和未查范围。若执行了修复，附改动位置、对照截图和复验结果。
```

## 设计要点拆解

### 一、验收标准前置，而不是「感觉不对」

「以用户能否**快速理解产品、独立完成任务、出错后能否恢复**为验收标准」

这一句把主观走查转成了三个可判定的问题：**理解成本**、**任务完成度**、**失败可恢复性**。后续每条结论都必须能对应到其中至少一条，否则不予记录。

### 二、三视角并行，而不是单一角色

| 视角 | 关注什么 | 对应维度 |
|:---|:---|:---|
| **产品经理** | 用户能不能理解这是什么、该做什么 | 信息架构、流程清晰度 |
| **UX 研究员** | 任务能不能独立完成、卡在哪 | 操作效率、反馈机制 |
| **UI 设计师** | 看不看得懂、点不点得准 | 视觉层级、设计系统一致性 |

「同时」三个视角，是这份提示词与常规「帮我看看这个页面」的根本差别——它要求在同一遍走查里覆盖产品逻辑、体验流程与视觉实现三个层。

### 三、六维度 = 一张固定的检查表

```text
信息架构 → 用户流程 → 操作效率 → 反馈机制 → 视觉层级 → 设计系统一致性
```

固定维度带来两个好处：**不漏**（每条路径都过一遍）与**可比**（不同页面、不同轮次的结果能横向对照）。

### 四、P0–P3 分级 + 同级排序规则

| 级别 | 判定标准 |
|:---|:---|
| **P0** | 核心任务无法完成且无可行替代，或已发现严重数据丢失风险 |
| **P1** | 关键任务高频失败或明显受阻，用户需要绕行 |
| **P2** | 可完成任务，但存在多余步骤、误解或局部不一致 |
| **P3** | 视觉和文案细节 |

**同级排序有明确规则**：先看影响范围与发生频率，影响相近时**优先做成本低的改动**。这避免了「先改最容易的」这种常见偏差。

**同一根因合并记录**——避免一个布局问题被拆成五条重复工单；**证据不足的项单列待验证**——避免猜测被当成结论写进报告。

### 五、执行模式二分：仅走查 / 走查并修复

| 模式 | 行为 |
|:---|:---|
| **仅走查**（默认） | 只输出问题表与可执行建议，不动代码 |
| **走查并修复** | 优先在**授权的开发或测试环境**修复已复现的 P0/P1 |

「优先在授权环境修复**已复现**的」三个限定都很关键：授权环境（不改生产）、已复现（有证据）、P0/P1（不越权做取舍）。需要产品或设计取舍的改动**列出取舍供评审**，而不是 Agent 自行拍板。

**可把互不冲突的问题分派给子 Agent，由主 Agent 集成和验收**——这是把走查做成可并行工程任务的关键设计。

### 六、修复后必须复走，且要给对照

「修复后用**相同设备、尺寸、数据和操作步骤**复走，能截图时提供**改前改后的同状态对照**」

固定变量复走是唯一能让「我改好了」变成可验证结论的方式。同时要求记录**可测的变化**（操作步数、错误恢复结果），并**检查相邻流程**——防止修 A 弄坏 B。

### 七、交付格式固定，便于直接进工单系统

```text
优先级｜页面与场景｜复现步骤｜实际表现与用户影响｜证据｜具体改法｜可验证的验收条件
```

七要素缺一不可：**验收条件**是其中最容易被漏掉、也最有价值的一项——它把「建议」变成了可被下一个人直接执行的判定标准。

交付顺序也有讲究：**先给最多 3 个最值得优先处理的问题**，再给完整表——让读者先拿到结论再决定要不要细看。

### 八、诚实标注证据等级

「逐项标明『**实测**』『**静态发现**』或『**待验证**』」

这是整份提示词里最容易被忽略、却最能防止误导的一条。跑不通的环境、只有截图的静态评审、以及存疑的推断，三者必须分开标注，否则「静态发现」会在传递中被误当成「实测结论」，最终变成错误修复。

## 使用建议

1. **先选一条核心路径**：首次使用的完整闭环（首次打开 → 找到入口 → 完成核心任务 → 确认结果），不要一上来就全站扫。
2. **能跑就跑**：有可运行环境就实测，静态评审只是退路。两者证据等级不同，不要混着汇报。
3. **截图要带状态**：关键步骤截图时同时记录卡住的位置、用户可能的误解和额外操作，否则复现步骤会缺一环。
4. **修复前先确认授权边界**：涉及删除数据、修改生产配置的操作一律不自动执行。
5. **验收条件先写再改**：让 Agent 在动手前就把「怎么算修好了」写清楚，避免改完再争论。
