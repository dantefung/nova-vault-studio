# Pi 在做减法，DeepSeek Harness (DSH) 却想让 Agent 自己进化

## DSH 和 Pi Agent，走的是两条几乎相反的路线

![Pi vs DSH 路线对比](images/pi-vs-dsh/001.jpeg)

DSH（DeepSeek Harness）和 Pi Agent，走的是两条几乎相反的路线。

**Pi 的哲学是做减法。**

Mario Zechner 做 Pi，就是嫌 Claude Code 这类工具越来越重，于是把核心砍到极简：

```
read / write / edit / bash
```

四个工具，系统提示词很短，没有 Plan Mode、Subagent、MCP，默认也不做复杂权限控制。

![Pi 的极简工具集](images/pi-vs-dsh/002.jpeg)

**Pi 相信的是开发者。**

核心越薄，越容易看懂、修改；复杂能力需要时，再由人通过扩展加回来。

**DSH 则是另一条路：做加法，然后再把它拆碎。**

它不是保留一个不可动的极简核心，而是把整个 Agent 系统的各个部分——

模型、工具、文件系统、Shell、沙箱、会话存储、Subagent，甚至 Agent Loop 本身——

都做成可替换的插件。

官方提供的 Coding Agent，也只是这些插件的一种默认组合，并不是唯一答案。

如果简单概括：

> **Pi：核心固定，外围可扩展。DSH：更接近「几乎没有不可替换的核心」。**

两者对「复杂度」的态度也很不一样。

**Pi 认为：**

> 复杂度是一种负担，能删就删。

**DSH 更像认为：**

> 复杂度无法避免，与其消灭，不如把它结构化、模块化，让系统可以重新组合。

一个是在主动限制复杂度。

一个是在试图驯服复杂度。

真正有意思的，其实是另一个问题：

## 谁来扩展 Agent？

![谁来扩展 Agent](images/pi-vs-dsh/003.jpeg)

Pi 目前主要还是：

```
人写 TypeScript 扩展 → 显式安装 → Agent 获得新能力
```

扩展权本质上掌握在人手里。

而 DSH 已经开始尝试另一种东西：

**让 Agent 在运行过程中发现自己的能力缺口，现场生成并挂载新的工具，然后继续完成原来的任务。**

也就是：

```
发现自己不会 → 检查当前能力 → 现场造一个工具 → 挂载 → 接着用
```

![Agent 自我扩展流程](images/pi-vs-dsh/004.jpeg)

当然，现在这个能力还非常实验性。

动态插件目前主要存在于内存里，重启之后不会保留，也没有做到自动验证、沉淀成永久插件。

但方向已经很明确：**把「扩展系统」这件事情，也逐渐交给 Agent 自己。**

## 结论

所以从前景上来说，我会更看多 DSH 一些。

Pi 已经证明了：

> 极简 + 可扩展的 Harness 是一条能跑通的路。

而且这种克制本身就是它最大的优点。

但 Pi 的哲学决定了，它的核心会一直保持克制：核心尽量什么都不管，把扩展权交给开发者和社区。

DSH 则激进得多。

它赌的不只是：

> "给开发者一套更好的积木。"

而是：

> **让这些积木可以被重新组合，甚至未来让 Agent 自己长出新的积木。**

如果这条路线真的跑通，DSH 的想象空间，可能会比传统的极简 Harness 更大。
