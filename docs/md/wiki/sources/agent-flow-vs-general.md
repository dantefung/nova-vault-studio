# 从 Agent Flow 到 AI Native：为什么通用 Agent 是「饮鸩止渴」

> 通用 Agent 不是恰当目标。直接从用户问题出发，哪怕是 hardcode、哪怕是 if else、哪怕是几个固定的 LLM Call，只要能帮助用户更简单、更可靠地解决问题，它就是好的方案。

## 01 Agent Flow

作者在做「小玩具」：Agent Flow（[symphlo](https://github.com/huisezhiyin/symphlo)），想在某些特定场景和受众群里取代现有的 Agent Skill。

![Agent Flow 架构](images/agent-flow-vs-general/002.jpeg)

Flow 本质上是传统 Flow 的强化，核心不是让用户理解节点、连线和 JSON，而是让用户用自然语言描述目标，然后让 LLM 去理解目标、生成 Flow、修改 Flow、运行 Flow。

Flow 本身降级为编排层，不对 Node 和细节负责，只负责链路控制、任务下发和结果回收。Node 可以是 QwenWork、Codex CLI、影刀 RPA、千牛接口、阿里内部运维 Agent——核心理念是把任务切分下发，让节点负责执行。

**具体 case**：电商用户要汇总报表，通过 QwenWork 拿一些数据、通过影刀 RPA 拿一些数据、通过千牛接口拿一些数据，最后汇总三份数据，通过 DWS 写到钉钉文档，再把文档发到钉钉群。

以前写 Skill 几乎不可能在一个任务 loop 里完成这个长链路，Agent Flow 确实可以实打实地、无介入地直接跑通。

**核心理念**：把 Agent 作为能力之一，而不是当成一切。不幻想 world agent，而是把一整条任务链路拆成合适的 Node，上升到编排层和控制层。

## 02 最小任务单元和确定执行

Agent Flow 的逻辑与「最小任务单元（最小混沌单元）」理念契合。大模型输出是概率性的，每次派发的任务最好有具体上下文、工作量适中、可以闭环确认结果。

Flow 的每一个 Node 就是一个最小任务单元——让 QwenWork 执行某动作，或呼叫外部工具处理某段逻辑，做完再进下一节点。

**关键判断**：YAML、Flow、hardcode 是可靠的，纯自然语言是不可靠的。基于 YAML 的 Flow 自生成和自维护，远比松散的 Skill 简单高效。

同一个任务开两个不同对话，通用 Agent 很可能用两种完全不同的思路去做，一个成功一个失败。业界靠堆 Memory 解决，但哪个通用 Agent 敢说自己的记忆系统能彻底解决问题？

> 用户要的不是大模型像程序员解 bug 一样去「探索」路径，用户要的是：用最低的认知负担，确定地、可靠地完成复杂任务。

## 03 用户为什么选择你的 Agent？

原因只有两个：

### 第一，只有你能解决某些问题

不要迷信框架先进性。真正关键的是，你拥有别的 Agent 拿不到的东西——**数据和接口**。

最经典的例子是「AI 前女友」——看似简单，但真正能做好的人寥寥无几，因为很难拿到完整的聊天记录。淘宝商品数据、钉钉聊天记录，这些才是 Agent 最宝贵的财富。通用模型再聪明也做不到突破安全限制进入你的数据库。

> 谁有真实的高质量数据，谁能够背靠核心的产品和功能，谁就能做出独一无二的 Agent。

### 第二，你真的能解决问题

这句话听起来像「废话」，却是很多 LLM 产品最容易本末倒置的地方。

RAG、MCP、Tool Calling、Multi-Agent、Agent Loop……这些对用户来说毫无意义。用户只关心一件事：我的问题解决了吗？

大部分客户的真实需求，其实只要三个有顺序的 LLM Call 加上两个 API 就能解决；但很多产品非要上一堆通用能力，搞各种复杂的 Loop——要不烧掉大量 token 换来客诉，要不任务无法复现成功。

> **Agent 的核心不是架构，不是 loop，不是 harness，而是用户是否愿意为它解决的问题付费。** 只要可以解决问题，客户根本无需在意是不是用了 hardcode，甚至无需在意用的是不是 LLM。

## 04 Hardcode 是美丽的

通用 Agent 远不如 hardcode 「美丽」——因为美丽的定义就是「客户愿意掏钱」。

我们排斥 Hardcode 是一种惯性：过去人工写代码成本高、维护有成本、扩展有成本，所以追求抽象、通用、平台化。但 LLM 时代这个前提变了——**代码是「廉价」的**。

- 写一个 Flow 是廉价的
- 写几个固定的 LLM Call 是廉价的
- 给一个付费客户手搓一条 Agent Flow，也是廉价的

对 LLM 来说，10 个 if else 比一大堆抽象工厂要更容易理解。**代码维护者变成了 LLM，而 LLM 更喜欢简单明确的逻辑。**

## 05 AI Native / LLM Native

「AI Native」的本质非常简单：**基于 LLM，让 AI 解决用户的问题。**

不是让产品看起来有 AI，不是让架构看起来先进，也不是让用户学习 Agent、Loop、RAG、MCP。用户真的有一个问题，AI 真的帮他解决了，解决得更轻松、更可靠、更便宜，用户愿意继续用、愿意付费——这才是 AI Native。

现在很多东西是旧系统往自己身上贴了一层 AI 的皮——旧框架还是旧框架，只是某个环节多调了一次 LLM、某个页面多塞了一个聊天框。

> 秉持一种强硬的态度去「砍掉」所有挡路的东西，脑子里只保留一个念头：用户的一句自然语言，到底能不能把这个任务完整跑通？

## 06 程序员的自我修养

技术引入 LLM 的目的就是：提效。把所有「挡路」的流程、审批、权限统统干掉。

作者写内部运维 Agent（WarRoom）项目时深有感触：想让它查日志，但日志系统需要人工授权；想让它看代码，代码库需要手动开权限；想接入更强的模型，审批批不下来。每一步都在受阻，Agent 说要查日志，人就得去点；Agent 说要看权限，人就得去申请——**又变成「人肉胶水」**。

原因很简单：过去 20 年所有的基建都是为「人类」设计的，不是 LLM friendly 的。

Aone 团队把这个内部运维 Agent 做出来了，证明了：只要基础设施对 LLM 足够友好，模型和 Agent 就可以进入研发现场，修 bug、写需求，成为超级助手。

## 07 一千张 A4 纸叠起来依然是厚的

作者发现自己越来越像一个 Master Agent，持续接收任务、拆解分发给 Sub-agent。当前组织架构对 LLM 是极度不友好的——层级再怎么包装成扁平，只要任务、权限、上下文和反馈的链路很长，它就还是厚的。

真正的扁平不是物理空间上离得近，而是**组织的链路足够短**：

- 一个想法从顶设到一线，经过多少层转述？
- 一个需求从 PM 到开发，经过多少次解释？
- 一个权限从需要到拿到，需要多少张工单、多少次私聊、多少个审批？

**理想状态**：每个人都可以成为「超级自由人」，不被部门和权限限制，只要看到问题可以直接写代码、推送、部署、全权负责。

> 把「人」做成「Agent」，把任务和交流变成 TCP/IP 协议——点对点，可靠，稳定，充分。

## 08 回到 Agent Flow

为什么要做 Agent Flow？不是为了做更复杂的架构，不是为了证明 Flow 比 Skill 先进，更不是为了生造技术黑话。

> 在 LLM 时代，Agent 的方向绝对不是花里胡哨的技术名词和复杂通用的架构设计，甚至通用 Agent 都不是一个恰当的目标。

直接从用户问题出发，哪怕是 hardcode、哪怕是 if else、哪怕是几个固定的 LLM Call——只要它能帮助用户在 LLM 的汹涌洪流里更简单、更可靠地解决问题，它就是好的方案。

> **放弃高大上的名词，放弃那些让人痴迷的技术架构，认真地和用户聊一聊。从现在开始，去设计和开发一个可以解决他们问题的 Agent，无论多么「丑陋」和 hardcode，而不是在无尽的技术名词里潜泳，那样只会被溺毙。**
