# Harness 重构 90 万行遗留系统：实践摘要

## 核心结论

这篇案例证明 Harness Engineering 的价值不在于让 AI 多写代码，而在于把需求、设计、实现、验证和验收变成有状态、可阻断、可审计的生产流程。遗留系统重构的关键策略是将旧代码当作行为需求来源，而不是必须保留的实现资产。

## 案例结果

- 团队规模：2 到 3 名全栈开发者加 AI。
- 旧系统：约 90 万行代码，文档和测试接近空白。
- 新系统：约 12 万行代码、15 万行文档、6,000 多个测试、86% 覆盖率。
- 交付节奏：从半年不到 3 个需求或紧急 Bug，提高到两个月 30 多个新功能。

这些数字由原作者报告，未公开提供工程证据供独立核验。

## 关键实践

1. **旧代码是需求证据，不一定是迁移资产**：当旧架构已经失控时，逐段搬迁可能继续携带技术债。可以保留产品行为和边界，用新架构重新实现。
2. **质量左移到需求和设计**：需求、验收标准和架构设计都必须经过 AI 与人工交叉审查；验收标准要写清通过、失败和量化阈值。
3. **实现者与裁判分离**：专职 SubAgent 分别审查架构、安全、契约、性能、运行时、规范和测试，并用确定性命令验证结论。
4. **门禁判定标准不能由 Agent 静默修改**：覆盖率等红线放在独立配置中，修改即暂停工作流等待人工确认。
5. **覆盖率不等于测试质量**：对增量代码运行变异测试，检查测试是否能杀死故意注入的错误。
6. **人工审查上移**：人重点审需求、设计、关键路径代码和验收证据，不再机械逐行阅读全部 AI 产出。
7. **状态外置且防篡改**：Python CLI 管理工作流状态，Hook 限制写操作，支持恢复上下文和审计每一步。
8. **上下文按 L1/L2/L3 分层**：常驻最小路由和红线，阶段性加载角色与 Skill，专项资料按需查询。

## 可执行检查清单

- [ ] 是否明确旧代码中要保留的是行为、数据、协议还是实现？
- [ ] 需求文档是否消除了含糊词、隐含假设和边界缺失？
- [ ] 验收标准是否包含失败路径和量化阈值？
- [ ] 架构设计是否检查了已有实现、复用机会和跨端协议？
- [ ] 实现 Agent 与审查 Agent 是否独立？
- [ ] 质量阈值是否存放在受保护配置中？
- [ ] 是否对新增或修改测试运行变异测试？
- [ ] 工作流状态是否只能通过受控命令推进？
- [ ] 人工审查是否覆盖需求、设计、关键代码和验收报告？
- [ ] 上下文与模型是否按任务风险分层分配？

## 风险与边界

- 完全重写仍有遗漏隐性行为和边缘业务规则的风险，需要双轨运行、回归样本和业务验收兜底。
- 多 Agent 审查会增加 Token、时间和维护成本，应按风险裁剪，不应把所有需求都跑成最高规格。
- 变异测试计算成本高，优先用于增量和关键模块。
- 人工审查上移要求工程师具备系统设计判断力，对经验不足的团队仍需培养路径和明确责任边界。
