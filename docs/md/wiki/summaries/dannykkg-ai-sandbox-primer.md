# Kg：AI 的工作间——Sandbox 入门

## 核心结论

**Sandbox 不是某种具体软件，也不等于 Container 或虚拟机——它是一套「控制程序能力 + 缩小事故爆炸半径」的方法论。** 真正的安全靠三道防线叠加：① 创建环境时少给能力、② 操作前按规则自动放行或拦截、③ 运行时对每一次真实访问都强制检查。任何一层都可能出错，所以不能把希望全押在一次判断上。

## 关键洞察

1. **Sandbox ≠ Docker Container ≠ VM**：三者不是同一层概念。Sandbox 是「目标」（限制能力与影响范围），Container / 操作系统权限 / VM 是「实现目标的工具」。Docker 跑起来不代表安全，VM 隔离再强也不等于权限控制做完了。
2. **六类被控制的资源**：文件系统、进程、网络、身份与凭据、计算资源、生命周期。漏掉任意一项都可能被绕过——尤其是「进程」必须跟随整棵进程树，否则外层禁网但能 fork 子进程替自己联网。
3. **凭据的最佳做法是「代办窗口」**：不把真正的 Token 放进 Sandbox，程序只能说「请帮我读这个仓库」，外面的代办服务验证请求后替它完成。这样程序始终看不到真 Token，杜绝被打印或外传。
4. **预分配 + 使用时拦截，两层都要做**：门禁卡先决定能开哪些门（创建时减少能力），刷门时门锁再校验一次（运行时强制执行）。只做预分配不够（卡可能被盗），只做拦截也不够（规则可能漏写）。
5. **不能只检查命令文字**：要落实到「实际打开了哪个文件 / 创建了哪个进程 / 连接了哪个地址 / 用了多少资源」。上层规则负责「理解它想做什么」，底层 Sandbox 负责「限制它实际能做什么」。
6. **限制过少不安全，过多则无法工作**：最小权限原则的难度在于「刚好够用」。弹窗让人审批是不可靠的——人会疲劳，习惯性点「允许」。明显危险的能力应该直接移除，而不是交给人判断。
7. **面向 AI Agent 的新要求**：系统不仅要拦住危险操作，还要用**机器能理解的方式**说明「为什么被拒绝、允许范围是什么、下一步可以怎样安全地继续」。这是 AI Native Sandbox 区别于传统 Sandbox 的关键。

## Sandbox 与 Container / VM / gVisor / MicroVM 对照

| 形态 | 类比 | 隔离强度 | 开销 | 适用场景 |
|------|------|----------|------|----------|
| OS 级 Sandbox | 同一栋房子里上锁的房间 | 中 | 极小 | 桌面应用、本地开发工具 |
| Container (Docker) | 大楼里的独立公寓，共享内核 | 中 | 小 | 通用部署，但**默认配置不等于安全** |
| gVisor（用户态内核） | 公寓 + 翻译层拦截系统调用 | 中高 | 中 | 需要更强隔离但能容忍兼容性 / 性能代价 |
| VM / MicroVM | 独立小房子，独立内核 | 高 | 大 | 互不信任、来源复杂的程序 |

> VM 提供更强的墙，但「程序能访问哪个网站 / 用哪个 Token」这些细粒度规则仍需额外的权限、网络和身份系统。

## 可靠的 Sandbox 三道防线

| 层级 | 触发时机 | 做什么 |
|------|----------|--------|
| 第一层：减少能力 | 创建 Sandbox 时 | 只挂载必要目录、不放长期密钥、用独立用户、设置 CPU/内存/时间上限 |
| 第二层：规则检查 | 程序准备执行某动作前 | 按规则自动放行 / 询问用户 / 直接拒绝 |
| 第三层：运行时强制 | 主进程或子进程真实访问资源时 | 底层重新校验读权限、写权限、网络目标、内存配额 |

三层必须并存，因为任何一层都可能出错。

## 判断 Sandbox 是否真可靠的 7 个问题

不管遇到什么产品或技术，都可以先问：

1. 它保护的对象是什么——个人电脑、服务器，还是其他租户？
2. Sandbox 里能看到哪些文件，哪些目录可以写？
3. 主程序启动的子进程是否受到同样限制？（即：限制是否跟随进程树）
4. 网络是全开、全关，还是按目标和操作控制？
5. 密码和 Token 是否真的进入了 Sandbox？（真正的 Token 进了环境变量 = 不安全）
6. CPU、内存、磁盘、运行时间有没有硬上限？
7. 出现问题后，能否查到它执行了什么、修改了什么、访问了哪里？

> 答不清这 7 题的「有沙箱」，通常只是一句模糊的宣传。
