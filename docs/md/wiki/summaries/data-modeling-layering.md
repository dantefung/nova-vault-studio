# 数据建模分层摘要

## 核心概念：两条线，不是上下级

| 线 | 内容 | 解决的问题 |
|----|------|------------|
| **建模抽象层次** | 主题域 → 概念模型 → 逻辑模型 → 物理模型 | 业务怎样逐步翻译成数据结构 |
| **数据加工层次** | ODS → DWD → DWS → ADS | 数据进入数仓以后怎样逐层加工 |

两者**不是上下级关系**。逻辑模型 ≠ DWD，物理模型 ≠ ODS。一个模型可能贯穿多个数仓层。

## 六步落地顺序

1. **梳理业务过程**：获客→下单→支付→采购→生产→发货→回款
2. **划分主题域**：围绕稳定的业务对象和业务过程，而非组织架构
3. **建立概念模型**：统一业务认知——实体是什么、事件是什么、关系是什么
4. **建立逻辑模型**：先定粒度（一行代表什么），再区分事实和维度
5. **形成物理模型**：字段类型、分区、索引、排序、更新方式、存储引擎
6. **落到数仓分层**：ODS/DWD/DWS/ADS 逐层加工

## 关键原则

- **主题域**：不照搬组织架构，围绕稳定业务对象建立。"订单"不属于销售，而属于交易主题
- **概念模型**：不纠结字段命名和数据库选型，先解决"客户到底是什么""取消 vs 退款"等业务认知统一
- **逻辑模型**：粒度是核心。粒度混乱会导致指标重复计算（如订单级金额被明细级数量重复 5 次）。还需处理缓慢变化维问题
- **物理模型**：同一个逻辑模型在不同数据库中形成完全不同的物理结构。完成标志是表能持续稳定产出数据，而非 CREATE TABLE 成功
- **反向验证**：随便拿一个指标（如销售收入）往上追：ADS → DWS → DWD → ODS → ERP 源字段。能解释清楚才算体系

## 三个评价问题

1. 业务能不能解释清楚？
2. 指标能不能稳定算准？
3. 数据或模型变化后，能不能快速知道影响在哪里？
