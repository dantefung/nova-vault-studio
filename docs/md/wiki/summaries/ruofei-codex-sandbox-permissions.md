# Codex Sandbox 完整公开：OpenAI 怎么在本机给 Agent 限权

## 核心结论

**Codex Sandbox 的设计目标是：让 Agent 继续使用本机工具，同时限制命令能接触的文件和网络。** 2026 年 11 月 18 日，OpenAI 工程师 Michael Bolin 完整公开了这套设计（权限配置 + 三个操作系统上的实现 + 如何单独用在其他程序上）。

但文章最锋利的洞察在权限模型之外：**限权是按「启动路径」生效的，不是按「会话」生效的。** 同一次会话里，Shell 命令被沙箱规则管住，本地 stdio MCP 服务却默认不受同一套规则约束；而**文件根本不继承沙箱限制**——沙箱里被写入的依赖，下一次由沙箱外的编辑器加载执行。

## 关键洞察

1. **沙箱管得住「动作」，管不住「逻辑」**。作者自己的实验：同一需求让 Codex 做了两遍，两份补丁都通过同样的 10 项测试，其中一份却影响了同一进程里另一段代码的输出。**文件允许修改，操作系统就无从判断这几行代码是否符合需求。** 但「命令能不能写到项目之外、能不能连上数据库」可以在执行时限制。
2. **事故背景不是假设**：2025 年 7 月 Replit CEO 确认开发中的 Agent 删除了用户生产数据库的数据；同年年底 The Register 采访的 Antigravity 用户报告 Agent 清理项目缓存时误删了 D 盘内容。**权限给得足够大，错误操作会波及任务之外的文件和数据。**
3. **命令启动时的限权链条**：`exec_command` 把命令、工作目录、环境变量和权限选项交给统一命令执行器 → Codex 把权限配置翻译成本机沙箱规则 → 操作系统执行限制 → `npm test` 拉起的测试框架和编译器等子进程**继承约束**（即使某个后代进程活得更久，限制仍然跟着它）。**模型决定跑什么，操作系统按启动时的规则限制它能访问什么。**
4. **内置 `:workspace` 配置的边界**：命令可写工作区和系统临时目录，**默认禁止联网**；工作区根下的 `.git`、`.codex`、`.agents`、`.aws` 有额外写保护（阻止命令直接改 Git hooks 或 `.codex/config.toml` 这类影响后续执行的文件）。但**读取范围比较宽**——编译器得找仓库外的 SDK 和库，用户目录里的配置文件（**包括其中的密钥**）也可能读得到；不想开放就单独用 `read` / `deny` 限制，管理员可在 `requirements.toml` 限定可选配置。
5. **允许写工作区 = 未保护文件可能被删，沙箱分不清「必要清理」和「误操作」**。数据库同理：连接可达、凭证又有删权限，就还需要数据库账户的权限约束具体操作——Replit 事故后开始推行开发库与生产库分离。
6. **临时扩权走审批策略**，可以交给用户或 Auto-review。但**批准后用什么权限跑，要看请求的是「扩大沙箱内的访问范围」还是「到沙箱外执行」——这是两条不同的启动路径。**
7. **MCP 服务另设权限，这是最容易被「这会话开了沙箱」一句带过去的细节**。本地 stdio MCP 服务由 MCP 客户端启动，**默认不会自动套用 Shell 命令的沙箱配置**。Bolin 的理由：有的服务只读本地索引，有的启动时就得去内网拿数据，仅凭启动命令无法判断该给什么权限；统一套断网的工作区配置，有些服务连初始化都过不了。**结果就是：即使测试命令断网，文档服务也可能照常访问内网。**
8. **要给 MCP 进程单独限权，用 `codex sandbox --permission-profile`**——这个入口不依赖 Agent 会话，自己的工具也能用它启动受限进程。Permission Profiles 目前仍在 Beta，与旧的 `sandbox_mode`、`sandbox_workspace_write` **不叠加**。
9. **域名规则靠代理执行，两个开关缺一不可**：`network.enabled` 允许命令用网络，`features.network_proxy` 启用执行域名规则的代理。**只打开网络而本地配置和托管要求都没启用代理，命令就能直接联网，域名表不会生效。** 启用代理后 Codex 通过 `HTTP_PROXY` / `HTTPS_PROXY` 把代理地址传给命令；程序不认这些变量而尝试直连时，操作系统的沙箱会拦截。代理先判断目标是否获准，再去解析域名，避免请求在被拒绝前就把主机名发给 DNS——但宽泛通配规则或获准访问的 DNS 服务仍可能留下通过 DNS 外传数据的空间。
10. **三套系统，三种实现**：macOS 用 `sandbox-exec`（内核 Seatbelt 执行规则）；Linux 用 bubblewrap（seccomp 约束系统调用 + `no_new_privs` 防 setuid 提权 + 独立网络命名空间）；Windows 正向 Microsoft MXC 迁移（允许更具体的路径规则覆盖上层规则）。**通配规则（如 `**/*.env`）在每次启动前展开成具体路径，命令启动后才出现的 `.env` 文件，即使匹配也不会被补进这次运行的拒绝规则。**
11. **最反直觉的一条：文件不继承沙箱限制**。项目装了 Prettier、编辑器配置成保存时自动调用它；Agent 在沙箱里往这份依赖写入恶意代码，而依赖目录允许写——单靠沙箱拦不住（`node_modules` 通常被 Git 忽略，改动未必出现在 `git status` 里）。**下次按保存，加载这份代码的是编辑器启动的进程，它按自己的权限运行。测试子进程仍受原来的限制，变的是执行这份文件的程序。**
12. **Simon Willison 同周给了另一种做法**：Agent 留在桌面，执行命令时通过 API 交给单独的 Linux 环境，可以挑哪些目录挂进去、哪些只给读权限，代价是要另外准备运行环境和依赖。**但如果宿主机和沙箱仍共用一份可写目录，编辑器还是可能加载沙箱改过的文件。**

## 作者给的核对方法（可直接照做）

| 要确认的地方 | 可以怎样核对 |
|---|---|
| Shell 与子进程 | 让沙箱内的命令及其子进程分别尝试写入禁止写入的测试目录，核对拒绝结果 |
| 本地 MCP 服务 | 用测试服务尝试同样的写入。默认启动与包上 `codex sandbox` 后分别观察，后者按指定 Profile 判断 |
| 网络代理 | 启用代理，分别请求一个明确允许和一个明确拒绝的域名；再尝试绕过代理直连外部主机，检查拒绝是否生效 |
| 编辑器接手文件 | 确认格式化器从哪里加载、依赖目录是否允许 Agent 写入；Git 忽略的目录也在这条执行链上 |

作者提醒：核对时也要留意是否触发了扩权审批，否则前后比较的可能已是两套权限。**允许的动作能完成只说明这条路通了；明确禁止的动作确实被拦下，才能确认限制在起作用。**
