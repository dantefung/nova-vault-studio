# Agent 迭代环境闭环

> 人是环境的产物，Agent 也是。**让 Agent 变好的最快路径，是先把它放进一个能持续产出有效反馈的环境，再把迭代成本压到可以忽略。**

## Pattern

```text
① 环境自建（Dogfood）
   每天全量使用自己的产品 → 发现卡点 → 立刻用 AI 修
   ↓
② 痛点定位：区分「产品问题」与「基建问题」
   基建问题优先（它会卡住整个迭代循环）
   ↓
③ 基建清障
   把环境依赖、热更新、发布链路一个个打通
   ↓
④ 迭代成本骤降 → 验收变快 → 进入无限迭代
   ↓
⑤ 反馈自动回流（挖掘问题日志 + 用户反馈 → 自动修复）
   ↓
   回到 ①
```

关键不在于步骤多，而在于**顺序**：基建不通，后面全是空转。

## ① 环境自建：你是自己的第一个用户

> 如果你每天刷抖音，都是那些毫无营养的奶头乐，那投入时间获得的上下文就是这样，所以这个人大概率也很难成长。

人是环境的产物，Agent 也是。**为 Agent 构建一个良性循环的环境，让它获得更好的上下文，也让人类获得更好的上下文**——这件事至关重要。

做法就是 **Dogfood（狗食自己的产品）**：你做一个产品，就要每天都用它、观察用户怎么用。

原文的实践样本（产品 NewMax）：

- 每天都在用它，觉得哪里卡住就立刻用 AI 优化，直到它能真正解决问题才给到用户
- 用它构建应用，搭建自己的 Agent 与定时任务
- 让它构建一个 Loop，每天自己挖掘问题日志与用户反馈并自动修复
- 让它自己提交外链、找达人、写 SEO

**一个副产品是产品边界的暴露**：当群体逐渐下沉时，产品会在某个用户群体出现断层，很多人用不明白了——这一刻你就知道了产品的边界，或者需要更多其他策略去拓展人群（比如依靠教学、依靠达人这类传播节点）。

## ② 痛点定位：产品问题 vs 基建问题

优化过程中最难熬的阶段是：

> 你想让它变好，它却有百般问题，导致你让它完成一次有效迭代的成本极高。这时候人就很痛苦，因为你可能花上 1–2 天，它才好了那么 1%。成本高、好的有限，投产比很低，人就逐渐地不愿意再次投入。

这是**投入意愿的杀手**，不是技术问题。判断两类痛点：

| 类型 | 特征 | 优先级 |
|---|---|---|
| **产品问题** | 功能缺失、体验不好、效果不佳 | 常规迭代节奏处理 |
| **基建问题** | 环境依赖、热更新、发布链路等卡住整个循环 | **优先**——它让每一次迭代的边际收益趋近于零 |

### 基建问题的识别信号

原文案例：优化移动端时发现热更新存在问题，导致在外面用着用着卡壳，没法修复，必须回家用电脑先更新桌面端才能同步移动端。

这种问题的共同特征是：**它不产生新功能，但把后续所有迭代的可行性都锁死了。**

## ③ 基建清障

识别出基建问题后，目标要立刻改：**首要任务不是加功能，而是先打通环境和依赖，让迭代能更顺畅。**

原文的处理方式：

- 依赖桌面端开发环境更新 → **先做工具让它能自动更新**
- 依赖 TestFlight 发新包 → **让它自己去发新包**

清障完成后，你就有了优化的环境。这时候再遇到问题，只需要跟它说一句话，它自己就自行修复了，**验收过程就会变得非常迅速**。

## ④ 口喷式无限迭代

> 每个产品，只要你在自己使用，你都会主动优化它。因为你创造了使用环境，你就会发现许许多多细节的场景，产品的细节都是在这些场景里不断探究优化出来的。

但想优化它，还需要一个**迭代环境**。如果每次迭代成本极高，你就会懒得处理。

> **为了让自己更松弛，就去解决这些基建卡点。先把他们优化好，AI 产品自然就会进入一种口喷无限迭代的正向循环里。**

注意这个循环的因果方向：**不是靠意志力坚持高频迭代，而是先把迭代变便宜**。

## ⑤ 反馈自动回流

基建通了之后，反馈回路可以自动化：

```text
用户反馈 + 问题日志
      ↓
  Loop 每天自动挖掘
      ↓
   自动修复 + 自动验证
```

此时人在环里的角色从「执行修复」变成「判断该沉淀什么、该丢弃什么」——这正是[[concepts/ai-escape-speed]] 里说的「人类先验」层。

## 延展：GTM 同样适用

做产品是这样，GTM 也是这样。

- 想要外链提得快 → 用自动化浏览器脚本功能，不断提、不断沉淀脚本；沉淀多了，提的自然就快了
- 写宣传材料 → 让它自己录屏、自己写公众号、同步发推特、自己转成视频发布出去

> 痛苦，是改变的重要原动力。**你越不想自己做的事情，就越该想办法自动化它。**

## Failure Modes

- **把基建问题当产品问题修**：功能越加越多，迭代成本不降，每个版本都在还债。
- **跳过环境自建直接要反馈**：没有真实使用场景，上下文是空的，Agent 学不到东西。
- **用「养号」代替迭代**：无流量无违规的老号没有养号价值，核心是内容与产品本身。
- **在高成本环境里硬扛**：花 1–2 天换 1% 改善，投产比过低，人就会停止投入——这时候该修的是基建不是产品。
- **只做模型层反馈优化**：模型层（RSI）是模型厂商的事，应用侧能优化的是套壳层与人类先验层。

## Quality Gate

1. 是否每天都在真实使用自己的产品？
2. 卡点是否按「产品问题 / 基建问题」分类过？
3. 基建问题是否优先于功能需求处理？
4. 环境依赖（热更新、发布链路、工具链）是否都能自动打通？
5. 上一次有效迭代的耗时是多少？趋势是升还是降？
6. 反馈是否已自动回流（问题日志 + 用户反馈）？
7. 人类是否在做「该沉淀什么、该丢弃什么」的先验判断，而不是只做执行？
