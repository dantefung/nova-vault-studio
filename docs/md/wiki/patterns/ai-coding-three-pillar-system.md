# AI 编码三支柱：流程、知识库、工具

> 让 AI 听话，靠的不是更多规则，而是让它在每一步只看到该看的东西。**流程**让 AI 可控，**知识库**让 AI 能积累，**工具**让 AI 能接触真实环境。

## Pattern

```text
问题诊断
  上下文丢失 / 需求语义漂移  → 流程
  经验不沉淀 / 规则膨胀      → 知识库
  看不到真实环境             → 工具
        ↓
三支柱闭环
  流程：定阶段、定产出、定停下点   → 可控
  知识库：可检索、可晋升、可淘汰   → 可积累
  工具：接环境、做确定性检查       → 可验证
        ↓
共同约束：AI 注意力有限
  规则按阶段加载 · 阶段只读上游产物 · 知识按需检索
  一个通用工具替代上百接口 · 确定性检查交给脚本
```

## 起点：规则膨胀的反面教材

最初的解法很直接：写一个流程 Skill，把开发步骤列成清单，让 AI 照着走。结果 AI 总是漏步，只能不断往里加限制和规则。

不到一个月，这份 Skill 从 500 多行涨到 800 多行，开头还多了五条「铁律」，标题写着「违反任何一条即为失败」，第一条就是「逐步执行，禁止跳步」。

**规则越多，AI 反而越不听话。** 原因不在模型能力，而在注意力分配：上下文里塞进的东西越多，每条规则分到的注意力就越少，最要紧的那几条反而被埋掉。

这条经验是整套体系的设计起点：**注意力预算是稀缺资源，必须显式分配。**

## 支柱一：流程让 AI 可控

### 阶段化的流水线骨架

编排器本身不分析需求、不写代码，只做调度。每个阶段的产出都写成**编号固定的文档**，下游阶段只读上游的文档；整个需求的进度记录在一个状态文件里。

关键设计是**规则按阶段拆分**：N 个阶段各有一份规则片段，进入哪个阶段才加载哪一份。AI 每一步只看到当前阶段要守的那几条，而不是背着全部规则。

### HALT：让人在关键节点接手

流水线上设有多处需要人确认的节点（HALT）：

- 每组阶段结束时停下，等人确认后才进入下一组
- 多仓库需求在协议锁定前额外再停一次
- 按条件触发的确认点：覆盖矩阵自检不通过、上下文即将用满

### 多仓库协同：人是消息总线

团队按端分工，客户端和服务端由不同的人负责、各自驱动 AI，于是一个需求会同时跑着两条流水线。方案刻意回避了多 Agent 通信那套复杂机制：

- 每个仓库有自己的流水线与状态文件，两边的 AI 互不感知、互不调用
- 需要共享的内容（澄清问答、协议定义、测试用例）以文件形式提交到公共仓库
- **人是消息总线**：人决定何时唤醒哪一端，HALT 节点就是同步点
- 流程恢复时，AI 重新核对公共仓库里的事实
- 每一次协同都留在 git 记录里，可追溯、可审计

### 防漂移三道闸

覆盖矩阵能拦住「AI 自己加戏」，却拦不住另一种走样：PRD 规定「上限 20」，设计写对了，任务拆分时被概括成「一键全部收回」，实现照着概括做——每一步单看都合理，结果与需求不一致。

对策是每道关口都回到原文核对，而不是相信上一手的概括：

| 关口 | 约束 |
|------|------|
| 设计出口 | 对数字上限、多选与互斥、禁止项逐条核对设计与 PRD 原文语义，冲突即停下等人 |
| 拆分出口 | 任务描述必须引用技术设计的对应章节，不允许凭印象概括 |
| 实现入口 | 写代码前必须回读技术设计原文，任务描述只作索引；不一致以设计为准并上报 |

### 覆盖矩阵：PRD 与设计的双向自检

技术设计必须包含一张必填的 PRD 覆盖矩阵：把 PRD 拆成功能点，每个标注它出自 PRD 的哪一节，再写明它在设计中的落点（接口、类、字段）。矩阵生成后做双向自检：

- PRD 的每一节都要有功能点覆盖（漏了 = 需求没做全）
- 设计中的每个接口、字段、事件都要能在矩阵中找到对应功能点（多了 = AI 加戏，退回澄清）

### 流程的四个价值

1. **问题前移**：歧义在澄清阶段暴露，协议变更在动代码前被拦下
2. **全程可追溯**：产出是落盘文档而非会话对话，从 PRD 一条出发可顺藤摸瓜找到设计落点、任务与代码
3. **可中断可恢复**：进度只记在状态文件，下游只读上游文档，不靠会话记忆；换台电脑也能续上
4. **人的精力花在判断上**：AI 把每步做完、把结论摆出来，人只在确认节点做方向性决策

## 支柱二：知识库让 AI 能积累

### 三层知识，各管各的

![三层知识对照](../images/x-flow-ai-coding-engineering/004.png)

| 层 | 存什么 | 什么时候用 | 谁来维护 |
|----|--------|------------|----------|
| 代码图谱 | 代码事实：定义在哪、谁调用谁、模块怎么依赖 | 定位代码、评估改动影响面 | 工具自动生成，代码变更后重建索引 |
| 模块文档 | 业务模块抽象：流程、边界、设计决策、已知坑 | 出技术设计前、修陌生模块 bug 前 | AI 与人协作，需求归档时更新 |
| 记忆 | 协作经验：踩过的坑、被纠正过的做法、与人的约定 | 每个阶段开始前按关键词检索 | AI 自动捕获，会话中随时写入 |

**关键区分**：规则约束 AI 行为，每次会话强制加载；知识供 AI 按需检索，用到才读。分清「要守的规则」和「要查的知识」，规则清单才不会越写越长。

### 第一层：代码图谱——事实交给工具

代码本身就是真相。难点在怎么高效找到它：AI 默认全文搜索，搜到一堆匹配行再逐个打开文件自己拼调用关系，既费上下文也容易漏。

接入了开源工具 `codebase-memory-mcp`：本地用语法解析器把整个仓库解析成图谱，函数/类/模块是节点，调用/引用/依赖是边，以 MCP 服务形式提供，查询毫秒级完成，不依赖外部数据库或云服务。

由此确立一条原则：**代码事实绝不手写进文档。** 文档里一旦写了「某个函数在某个文件里」，代码一重构它就过期了——AI 读到过时信息，比没读到更糟。代码事实只由图谱回答，不抄进文档，也不写进记忆。

### 第二层：模块文档——只写「为什么」

图谱能回答代码是什么，却回答不了为什么。为什么这里用推送而不是轮询、一次登录按什么时序调用哪些模块、状态在什么条件下切换——这些要么藏在代码背后，要么散落在十几个文件里。

每个代码模块对应一篇文档，固定分几部分：职责范围（含「不负责什么」）、设计决策和背后的原因、模块之间的交互约定、关键调用时序与状态流转（用 UML 图画，只画容易理解错的那几条）、已知的坑。

两条写作原则：**写语义保证，不写函数签名；写约定，不写文件清单。**

更新纪律交给流程：出技术设计前、修模块 bug 前，AI 先读相关文档避免与已有决策冲突；真正写代码时反而不读，直接看代码。需求归档时把关键决策写回受影响的文档。文档不再依赖某个人记得更新，而是每个需求都会经过一次。

### 第三层：记忆——AI 自己记

给 AI 设一条始终生效的规则，让它在会话中留意三类信号：用户的纠正（「不对」「应该是」）、反复尝试才解决的问题、用户主动告知的关键信息。捕捉到后整理成结构化记忆：**原来怎么做、正确做法是什么、为什么。**

记下来只是一半，还要在需要时被想起来。记忆不每次全量加载，而是按关键词检索。编排器在设计、实现、测试阶段开始前注入相关记忆，阶段自己再检索一次，两者取并集——即使跨了会话、编排器漏了注入，经验也不会丢。

过时与推翻的处理借鉴时序知识图谱 Graphiti 的思路：新事实推翻旧事实时旧事实必须退出当前视图。但**没有保留失效标记，而是直接删除**，需要追溯时交给 git 历史。AI 写入一条纠正之前，先检索同主题的旧记忆，命中就一并删掉，保证同一件事只有一个当前答案。

### 层与层之间：晋升、升级与淘汰

![知识库晋升升级淘汰机制](../images/x-flow-ai-coding-engineering/005.png)

**写入前先归类。** 专属于某模块的知识写进模块文档；跨模块通用约定写进全局约定；协作相关的内容写进记忆；行为约束是规则（不属于知识库）；代码定义与调用关系哪里都不写，交给图谱。

**记忆晋升为文档。** 一条记忆被反复验证、成为稳定约定后，晋升进模块文档或全局约定，原条目随即删除。一次全量审计中记忆从 **148 条精简到 24 条**——大部分不是被丢弃，而是找到了更合适的位置：几十条业务口径蒸馏进各模块文档，通用引擎经验晋升为全局约定，真正删掉的只是错位和重复。

**少升级为规则。** 沉淀的经验并不都会变成规则：问题第一次出现先写进记忆；同类问题反复出现、说明记忆没能防住，才考虑升级为规则。规则每次会话都加载，每多一条其他规则就被稀释一点；记忆按关键词检索，命中时效果与规则相同，没命中时不占任何注意力。

**AI 只能提建议。** 进化记录先进入待审阅区，由负责人逐条决定升级为规则、沉淀为记忆还是拒绝。已落地的 13 条进化记录里，10 条沉淀为记忆，只有 3 条升级成了规则。

**用数据淘汰。** 借助 AI 编程工具自带的钩子机制，在配置里注册「工具调用后」触发的钩子，AI 每次读文件或做文本搜索都会自动跑一个统计脚本：判断访问的是不是记忆或模块文档目录，从返回内容提取条目锚点，汇总命中次数、最近命中时间与检索关键词。一条目一分钟内只计一次；脚本异常静默退出，绝不影响 AI 正常读文件。

一个反直觉的技巧：**图谱工具的调用不触发钩子**，所以特意把图谱层排除在钩子之外，迫使 AI 只能通过读文件和文本搜索访问它们，埋点才能生效。

有了这份数据，淘汰就有依据：内容过时或无价值的直接删除；有用但检索不到的补上关键词；常被命中的说明确实有用，值得完善甚至晋升。**知识值不值得留，不再全凭感觉。**

## 支柱三：工具让 AI 能接触真实环境

工具层必须贴着技术栈做，但思路通用。做两件事：把 AI 看不到却影响交付的信息接进来；把 AI 做不稳又必须一次做对的工作交给脚本。

### 通用工具 + 手册，而不是上百个工具

游戏开发里关键事实往往不在代码里：运行时报错打在编辑器控制台、资源要由编辑器导入后才有身份标识、界面结构记录在 prefab 文件里。

自研的 Cocos MCP 一端以 MCP 协议连接 AI，另一端通过 WebSocket 连接装在 Cocos Creator 里的插件，开放读取编辑器主进程与场景进程日志（可按级别过滤）、调用编辑器内部接口、以及一个探活工具。

但编辑器内部有上百个消息接口。若每个接口都包装成一个 MCP 工具，工具列表会非常庞大——**每个工具的名字、说明和参数都会进入上下文**，工具越多占用越大，AI 选错工具的概率也越高。

做法是反过来：MCP 端只暴露**一个通用工具**，参数只有三个（消息属于哪个模块、调用哪个接口、传什么参数）；「该调哪个、怎么调、哪些不能调」全部写进一份配套 Skill——接口速查表、按风险分级的调用规则、常用操作的标准步骤。AI 先加载 Skill，再通过通用工具间接调用具体接口。

好处是工具列表只多了一个工具，AI 却能用上编辑器的全部能力；约束放在手册里，需要新增或收紧时改一份 markdown 就够了，不必改代码、重新发布 MCP 服务。

### 索引新鲜度：绝不返回过期结果

代码图谱靠刷新保持最新，刷新 Skill 由事件触发：合并大分支、批量重构之后，或人主动要求时。AI 在图谱里查不到一个明知是最近才加的函数时，会先提示「索引可能滞后了」并建议刷新，而不是把「查不到」当成「不存在」。

一次刷新先增量重建代码图谱，再顺带重建 prefab 引用索引；刷完从最近一周的提交里挑一个新增的符号查一遍，查得到才算成功。

prefab 引用索引单独做，因为代码图谱只解析代码、不认识 prefab，而 prefab 引用脚本用的不是类名，是一串压缩过的资源 ID，藏在几百 KB 的 JSON 里。图谱工具不支持自定义节点和边，所以在 MCP 里单独做了一组查询工具：不依赖编辑器在线，直接读资源文件建索引，支持双向查询（某脚本被哪些 prefab 和场景引用、挂在哪个节点；某 prefab 上挂了哪些脚本）。

索引自带新鲜度保障：每次查询前先比对文件修改时间，发现变化就当场重建，**绝不返回过期的结果**。因此日常查询不需要等刷新，刷新 Skill 对它只做例行对齐。

### 结构复杂的产物交给脚本

设计稿转界面是迭代次数最多的链路。最初让 AI 直接生成 prefab，但 prefab 是由编辑器维护的结构复杂 JSON，节点层级、组件挂载和属性互相关联，AI 很难保证结构正确。于是把生成工作全部交给脚本，AI 只留在需要理解的环节：

审查脚本检查设计稿图层树（重复图层、状态分组、不规范命名）→ AI 结合审查结果和需求文档提出语义重组方案（节点怎么命名、哪些状态归并、哪些节点抽成公共部分）→ 方案经人确认后由重组脚本生成新设计稿，人在 Photoshop 里再确认一次结构 → 导出脚本导出切图与界面清单 → 生成脚本根据清单生成 prefab → AI 编写界面 TypeScript 业务代码 → 借编辑器接口导入，再由挂载脚本挂到 prefab 根节点、自动绑定所有界面元素。

分工原则：**结构复杂、必须精确的产物，不要让 AI 直接生成；AI 只做判断，生成交给脚本。**

### 审查 Skill：从「懂代码」到「懂项目」

通用审查工具只看代码本身。在其基础上做了四处改造：

- **对照需求审查**：读取本次需求在流水线里的产物（精化 PRD、技术设计、测试报告、缺陷记录），直接拿 PRD 覆盖矩阵当基线——有设计没实现的报缺失，有实现没设计的报超纲；归档摘要里记录砍掉的功能，还要反查有没有被偷偷实现
- **带着项目知识审查**：从需求标题、变更文件名、新增类名和提交信息提取关键词，检索相关约定、踩坑记录和历史缺陷，结论尽量指明违反了哪条约定、重现了哪个历史问题。**Skill 本身不内置任何项目经验，全部来自知识库，知识库一更新下次审查立刻生效**
- **AI 协作产物也要审**：规则、Skill、记忆一旦合入主分支会被所有人的 AI 自动加载，和业务代码一样要审——新增规则有没有和代码现状矛盾，Skill 改动有没有破坏流水线调用约定，记忆里有没有把一次性经验写成通用约定
- **审查范围要诚实**：用分支相对主干的变更确定范围，避免把主干合并进来的他人改动混进审查；问题修复后复审只看增量，逐条核对上一轮待办清单并检查修复本身有没有引入新问题

## 统一哲学

回头看这几个工具，背后是同一个设计哲学：

> 能用工具确定性检查的，交给工具；需要理解和判断的，交给 AI；只有反复出现、又无法工具化的行为约束，才写成规则。

## Failure Modes

- **规则膨胀**：靠不断加规则来约束 AI，看似严谨实则稀释注意力，反而更不听话
- **事实写进文档**：文档里的代码位置一重构就过期，AI 读到过时信息比没读到更糟
- **上下文全量加载**：所有知识、规则一次性塞进上下文，与规则膨胀同源
- **信任上一手的概括**：需求在多轮转述中走样，每一步单看合理，累积后与需求不一致
- **工具列表膨胀**：每个接口一个 MCP 工具，工具说明本身就吃掉大量上下文并提高选错概率
- **图谱当作永不失效的事实源**：不刷新就查到旧结构，把「查不到」误判为「不存在」
- **产出无过期判断**：索引或缓存返回过期结果，AI 据此做出错误修改
- **让 AI 直接生成复杂结构产物**：prefab 这类编辑器维护的 JSON 难以保证结构与属性正确
- **经验只进不出**：知识库只增不减，最终变成没人能检索到的大杂烩
- **绕过确认节点**：把该由人判断的方向性决策交给 AI，出错成本最高

## Quality Gate

1. 每个阶段是否有明确的产出物与固定的编号？
2. 下游是否只读上游文档，而不是依赖会话记忆？
3. 规则是否按阶段拆分，进入哪一阶段才加载哪一份？
4. 是否存在明确的人工确认节点，且触发条件可判定？
5. 是否有覆盖矩阵做 PRD 与设计的双向自检？
6. 每一道关口是否回到原文核对，而不是信任上一手的概括？
7. 进度是否只记在状态文件里，可跨会话、跨设备恢复？
8. 代码事实是否只由图谱回答，不写进文档或记忆？
9. 知识是否分层、是否按需检索、是否有晋升与淘汰机制？
10. 工具是否已经收敛为通用工具 + 手册，而非无限膨胀的列表？
11. 确定性的检查是否都交给了脚本？
12. 每一步 AI 看到的东西，是否都只包含该步需要的内容？
