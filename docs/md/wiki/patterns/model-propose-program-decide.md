# 模型提议程序裁决模式（Model Propose, Program Decide）

> 模型负责灵活理解与决策提议，确定性工程程序负责权限校验、规则裁决与状态写锁。

## 核心定义

**模型提议，程序裁决（Model Propose, Program Decide）** 是构建企业级可靠 Agent 系统的基石工程原则：模型永远不是状态的直接写入者，也不是系统副作用的直接触发者。模型的所有“动作”在架构底层均降级为一份**结构化申请（Proposal）**，由确定性的工程运行时对其执行鉴权、前置条件校验、配额约束与状态写锁，合格才予落地，不合格则直接拒绝。

## 核心设计法则

### 1. 唯一写者原则（Single Writer Principle）

- 系统中存在一个纯代码实现的确定性状态内核（Core），它是任务状态（Ticket / Quest）的**唯一合法写入者**。
- 模型在 ReAct 循环中发出的“接单”、“结单”、“派工”，仅被视为主观意向；内核在代码层核对发件人权限、当前状态机流转规则、配额上限，校验通过后才更新数据库。
- **收益**：模型发生幻觉、受到 Prompt 注入攻击或出现逻辑跳跃时，最坏结果仅是提交了一笔被内核拒绝的无效请求，系统的状态机永远不会被破坏。

### 2. 先记账再动手（Outbox Pattern）

长期运行的 Agent 最怕执行到中途进程崩溃或网络闪断：

- 将模型计划执行的全部外部动作（启动 Worker、发送群通知、调用外部 API）与核心状态变更**在同一笔本地数据库事务中入账**；
- 事务提交后，由独立的后台巡检进程（Dispatcher / Relayer）按日志逐条调度执行；
- 崩溃重启后，未完成的动作沿着 Outbox 账本断点重放；而针对无法幂等重放的编码工作，则注入系统提示引导 Agent 重新检查代码库与环境实际状态后再行决策。

### 3. 外部文本永远只是数据（Untrusted External Input）

Agent 长期监听外部环境（群聊、Issue、PR 评论、邮件），所有外部输入都可能潜藏对抗性恶意指令：

- 明确系统指令与外部数据的优先级顺序，外部文本永远位于权限最低层；
- **防传话失真与注入隔离**：上游路由 Agent 向下游执行 Worker 派活时，严格限制派单备注字数（如限制最多 30 个词），**严禁上游 Agent 替执行者撰写实现计划与验收标准**；Worker 必须直接调取并阅读原始消息数据，避免层层转述导致语义走样或安全沙箱逃逸。

### 4. 主动行为灰度化（Dry-run Policy Testing）

主动性是最容易引发线上风险的特性：

- 新接入的业务规则（Policy）或权限默认处于**试运行（Dry-run）**模式；
- 模型照常针对环境事件进行分析决策，但在入账时仅标记“若放开策略我将认领此工作”，不实际创建工作流或提代码；
- 管理人员定期审计试运行记录，确认命中率与误判率符合预期后，方在配置端开启自动执行权限。

### 5. 人的优先级物理硬置顶

在资源分配和会话抢占上，人类介入永远具备最高优先级：

- **等待人类的任务排在队列最前**：系统仪表盘首屏直观展示卡在人类环节的工单；
- **保留人类专属并发通道**：当 Worker 线程池全满时，保留专门配额供人类指令唤醒已有任务，新生成的自动化任务绝对不能把人类消息挤出队列；
- **送达与阅读语义分离**：消息进入 Worker 上下文不算数，唯有在模型推理步中被真正作为输入消费才算已读。若工单关闭时仍有未读的人类消息，系统自动触发回退重评机制。
