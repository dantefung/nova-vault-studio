# 0 代码 Vibe Coding 游戏工作流

> 零游戏开发经验、零代码基础，3 个月独立完成 Steam 抢先体验游戏，累计 20 万玩家入库、2100+ 条评测 97% 好评。结论只有一句：**AI 干 90% 的活，但那 10% 的判断决定游戏好不好玩。**

## 硬数据

| 指标 | 数值 |
|---|---|
| 项目 | 《群侠传：幸存者》，单机独立游戏，Steam 抢先体验（EA）免费开放 |
| 上线时间 | 2026 年 8 月 |
| 开发周期 | 约 3 个月（4 月提交第一个 Commit） |
| 起点 | 无游戏开发经验、没打开过游戏引擎、一行代码没写过 |
| 成绩 | 累计超 20 万玩家入库；2100+ 条评测，97% 好评，「好评如潮」 |
| 上线前预期 | 愿望单才堪堪过 1000 个 |
| 上线后 | 第二天激活数一晚涨到五六千；5 天左右玩家累计砍敌超 10 亿只；三天收到 200+ 条反馈；上过 Steam 首页「人气蹿升的免费游戏」第二位 |

## 全流程分工

作者自述的完整链路（本文为 4/4 篇，覆盖第 8、9 章）：

```text
需求澄清与对标调研
   ↓
AI Coding：引擎、模型与协作方式
   ↓
AI 美术：风格统一与资产制作
   ↓
AI 动画、特效与 CG
   ↓
AI 音频：音乐、音效与配音
   ↓
AI 辅助发布与运营   ← 本文重点
   ↓
玩家反馈 → 人的判断 → 下一版迭代
```

每一环的共同形态：**人定义「什么算对」，AI 执行「怎么做到」**。

## 第 8 章：AI 辅助发布与运营

### 出包、上传与更新公告

上架 Steam 本身很辛苦（平面物料、商店详情页、宣传片、成就系统），但**与开发有关的部分交给 AI**。

AI 的做法：遍历 Steam 文档库，判断出需要装 Steamworks SDK 与 SteamCMD，在命令行弹出辅助登录通知，并指导完成上传后在 Steamworks 后台设置 Depot 与分支。

作者最终把整套发布固化成了**一句话指令**：

```
清理工作树，分批提交，然后出包，版本号为0.1.2，上传Steam以后写提交日记，
然后向我汇报自0.1.1.5以来所有的更新内容，这份汇报是我撰写更新公告的参考。
```

关键设计是**让 AI 读 Commit 记录自动汇总**成「新增 / 修复 / 变动」清单——更新公告里的大段清单多数由 AI 写，亮点段落人起草、AI 只负责搜集素材与润色。

### 成就配置：用 Browser-use 填 Steam 后台

游戏有 61 个成就。Steam 后台表单要填名称、描述和 API Name，手填太累，于是直接让 GPT 用 Browser-use 代填，「吃了个饭回来就全搞好了」。SteamStats 收集的 1700 多个数据项目同样这样填完。

### 数据闭环：性能 + 玩法双轨

Steam 支持匿名数据聚合收集，作者收集两类：

| 数据类型 | 内容 | 用途 |
|---|---|---|
| **性能数据** | 每一波的帧率摘要。本地记一份，玩家提交反馈时随诊断包附上；再通过 Steam 匿名聚合看全体玩家的低帧波次占比 | 定位掉帧，排优化优先级 |
| **玩法数据** | 武学、道具的选取率和胜率 | 观察平衡和内容方向 |

AI 负责数据拉取、分析、归档，并输出阶段性报告。

### 玩家反馈：飞书多维表格 + lark-cli

- 游戏主菜单的「制作人的一封信」里预埋反馈入口，直达**飞书表单**，分 Bug、崩溃报告、玩法建议三类，降低提交成本。
- 该表单是飞书**多维表格**，飞书命令行工具 `lark-cli` 登录后可自行拉取数据甚至回填标记，于是表格与本地数据存档被连起来。
- **反馈不由人逐条审核**：每天 AI 拉数据、去重、聚类，告诉作者这个版本可能有什么问题、哪些已修、哪些还要动，**最后由人拍板**。
- 日常化的还有：玩家群里的一句话被复制给 AI，问「你评估一下，能做吗？」能做就落进下一版更新。

## 第 9 章：人的判断在哪里

上线前评论区主要是「又多了一个垃圾 AI 游戏」「浓浓的页游风味」，作者原话是「一个制作人的前十个作品都是垃圾，所以尽快做完它们吧」。上线后的结果完全相反。

作者的结论拆成两半：

> **AI 固然会影响玩家对一个游戏的第一印象；但最终一款用 AI 做的游戏可以走多远，玩家愿不愿意留下、愿不愿意给予好的评价，最后还是看游戏好不好玩。**

具体到「10% 的人的部分」：

| AI 能做的 | AI 回答不了的 |
|---|---|
| 5 分钟内给几十个技能的草案 | 「这些技能，玩家用起来真的爽吗？」 |
| 几百个道具的效果 | 「这个道具让构筑更有意思了，还是只让数字变得更大？」 |
| 几千字的对话文案 | 「这些对话，真的能让玩家感受到我想在剧情里表达的东西吗？」 |

所以：**最终还是得由人作为一个人，去测试、去感受、去拍板。**

## 方法论沉淀

| 原则 | 做法 | 避免的坑 |
|---|---|---|
| **一句话发布** | 把出包、上传、提交日记、汇总变更固化成一条指令 | 每次手动执行漏步骤 |
| **Commit 即数据源** | AI 读 Commit 记录生成变更清单 | 更新公告靠人回忆，漏写 |
| **表单交给 Browser-use** | Steam 后台表单让 Agent 填 | 手填 61 个成就 + 1700 个数据项 |
| **反馈入口前置** | 游戏内直连飞书表单，多维表格 + lark-cli | 反馈散落在评论区，无法结构化 |
| **反馈交给 AI 聚类** | AI 去重聚类，人只拍板 | 人肉审核反馈，耗尽热情 |
| **人的时间投在判断上** | 人只做取舍，拍板 | 人被当成执行机器，产出更糟 |

## 边界与风险

- **AI 影响第一印象，但不决定留存与口碑**。用 AI 做完不保证有人玩，只保证「做得出来」。
- **「一个人撬动大团队」有前提**：愿意付出时间、努力与耐心。技术门槛被抹平了，**判断门槛和迭代密度没有被抹平**。
- **本文是 4/4 系列的第 4 篇**，作者原文只覆盖第 8、9 章；第 1–7 章（需求、编码、美术、动画、音频）在同系列前 3 篇。
