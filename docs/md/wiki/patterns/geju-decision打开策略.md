# Geju（格局）— AI决策打开策略

> 专治 Codex "苟帝"综合征：过度兼容、局部细节陷阱、重构恐惧、温和答案偏差。内置8种打开格局打法，让 AI 秒变暴论输出机。

## Key Points

- **核心问题**：AI 经常因为害怕破坏东西，保留旧行为、旧命名、旧路径、别名、shim 和双轨流程；在看清整个系统前就钻进一个字段/函数；给出礼貌、平衡、低风险但不解决问题的答案
- **核心理念**：大胆假设，小心求证。产出有启发性、有杠杆、能打开设计空间的**强假设**
- **触发词**：格局打开 / think bigger / 挑战保守方案 / 避免过度兼容 / 跳出局部细节

## 要对抗的4 个问题

| 问题 | 表现 | 反制 |
|------|------|------|
| **兼容性崇拜** | 保留旧行为、旧命名、旧路径、别名、shim、双轨流程 | 问清真实契约是什么；如果没有明确承诺，优先选择更干净目标 |
| **局部细节陷阱** | 看清整个系统前就钻进一个字段/函数/段落/迁移路径 | 回到产品/架构目标；先定方向，再优化实现细节 |
| **重构恐惧** | 因为 diff 看起来大、迁移看起来麻烦，就避开更好的方向 | 把"正确目标"和"如何抵达"分开 |
| **温和答案偏差** | 给出礼貌、平衡、低风险但不解决问题的答案 | 先给尖锐 thesis；点名什么应该删除、合并、拆分、重塑 |

## 打开格局的8 种打法

| 打法 | 核心问题 |
|------|----------|
| **从终局倒推** | 如果六个月后系统变得很好，那时应该是什么样？从目标往回推。 |
| **零历史包袱假设** | 如果从零开始，没有老调用方，会怎么设计？ |
| **杀掉错误概念** | 同一个生命周期有两个名字？没有真实契约的过渡 wrapper？直接说删。 |
| **十倍问题** | 如果使用量、复杂度、团队数量扩大十倍，哪里会崩？ |
| **反向约束** | 如果这个约束不存在，会怎么做？再判断是否值得保留。 |
| **不可妥协原则** | 先列 2-4 条设计不能违反的原则。 |
| **有品位地删除** | 删除也是设计动作，不要把删除藏在"以后再简化"。 |
| **先假设，再求证** | 先给大胆 thesis，再给验证路径和可推翻条件。 |

## 工作流

1. 从最高但仍有用的层级重构问题
2. 点名继承来的约束（兼容性？迁移困难？既有命名？局部实现形状？）
3. 判断约束是否真实（公开 API/持久化数据/已文档化集成/用户承诺 → 真实；内部调用方/过时命名/旧包结构 → 惯性）
4. 给出高格局 thesis（含 kill list）
5. 至少使用一个打开格局的打法
6. 只有选项有实质差异时才给 2-3 个方案，并明确推荐一个
7. 回到执行（第一个不可逆决策、第一个证明点、什么证据会推翻 thesis）

## 相关概念

- **`goudi`（苟帝）**：主要给 Claude Code 用，把宏大方向压实到可验证的第一步
