# TeamAI 黄金三件套

> 面向 Agent 的开发有三个很重要的工具：**Spec（做什么）、Skill（如何做）、Test Asset（是否正确）**。它们的核心媒介都是 Markdown——这是 LLM 时代人机高效协作的核心媒介。

## 从 Vibe Coding 的怪现象说起

Vibe Coding 刚流行时很火，但很快出现负面真实案例：

- 调用 LLM 次数非常多，解决不复杂的问题也要调很多次，token 消耗直线上升
- 出现删库和越权等生产事故

**根因**：不给 Agent 做约束，Vibe Coding 的交付物只能停留在浅应用层面。

更根本的问题是业务开发本身的性质：**业务开发大量建立在对历史、对业务的理解之上，而这种理解往往具有二义性**。

> 客户/PM 说「我要一个审批流」，Dev 或 AI 做了个简单的 Yes/No 按钮，但客户实际要的是多级会签、退回、转办等复杂逻辑。

**核心洞察**：聊天记录不是需求文档，它是信息的漏斗。**二义性是业务开发最大的杀手。**

## 三件套的分工

| 工具 | 回答什么 | 性质 | 核心内容 |
|---|---|---|---|
| **Spec** | 做什么 | 智能体开发的蓝图 | 意图、决策、计划、执行，对应不同 Markdown 文件 |
| **Skill** | 如何做 | 可复用的代码与能力模块 | 目录结构：Markdown + scripts + references + assets |
| **Test Asset** | 是否正确 | 持续自动验证技能是否符合规格 | 结构化测试用例（步骤/动作/目标/前置条件/期待结果） |

**关键变化**：Markdown 从记录性文档，地位越来越重要，已经基本和代码一样重要。人已经不写代码，人通过 Markdown、通过 Spec 让 AI 去写代码。

> **Vibe（发散）→ Spec（结晶）→ Build（执行）：Spec 才是代码，代码只是编译产物。**

**Spec 需要更严格的测试来兜底**：长程任务开发中，给一个简单要求，模型知道你单测的目标就是变绿，于是各种动作让单测变绿——这违背了 TDD 初衷。所以要用更严格的 TDD 守住底线。

## 让 Markdown 具备 Code 的能力

团队为 Code Review 做了工具，也让 Markdown 可以被 Review——但重点不是 PR 阶段的 review，而是**更前面的阶段：人和 Agent 沟通时的 Markdown**。在 IDE 上做插件完成 review，review 历史也被记录下来。同时还在做更强的 Markdown 校验器，让 Markdown 具备更强的语义特征。

## 把 Skill 做到开发级别

**先澄清一点**：Skill 不只是一个 SKILL.md 单体文件，它是一个目录结构：

```text
skill-name/
├── SKILL.md        # 入口
├── scripts/        # 执行脚本
├── references/     # 更复杂场景的 Markdown
└── assets/         # 模板资源
```

### 开发级 Skill 的五大原则

| 原则 | 含义 | 反模式 |
|---|---|---|
| **模式驱动** | 先选模式再写内容，模式决定目录、门条件、约束集 | 所有 skill 写成同一个模板 |
| **约束前置** | 把弱模型最常犯的错误写成显式禁令 | 期望模型自己悟 |
| **描述即索引** | description 是搜索入口，要包含用户实际输入的关键词 | 总结内部工作流 |
| **配置外部化** | 业务数据放 references/assets | 在 SKILL.md 内联 |
| **可量化验证** | 每个 skill 有 evals.json，改进必须通过 holdout 验证 | 凭感觉说变好了 |

### 五种 Skill 模式

| 模式 | 做什么 | 例子 |
|---|---|---|
| **工具包装器** | 把某个东西简单包装一下，相当于随到随用的专家 | 多维表格查询 |
| **生成器** | 产生最终交付物 | 生成 PPT、文档 |
| **审查器** | 评判完整性、执行度、有没有违反规约 | 代码/文档审查 |
| **反演器** | 针对复杂问题不断追问、越问越细，发挥大模型的通识能力 | 需求澄清 |
| **Pipeline** | 把上面这些包装起来的严格多步骤工作流 | 复杂 Skill 的最终形态 |

**选模式的套路**：是不是固定输入结构、要不要打分、要不要收集用户上下文、要不要做严格验证。

**Frontmatter 是硬约束**：必须以能被大模型加载、激活触发为目的去写——要以「触发」为目的，而不是以「更好地表达这个 Skill 能干什么」为目的。功能上只能在五种模式里挑一种。不按规格写，被触发的概率就不如按规格写。

### G1-G6 六条通用禁令

通过收集实际工作情况做强化学习迭代，找出十几种「门禁」。G1-G6 是六条相对清晰的通用禁令：

1. 只输出 SKILL.md 原始内容——不加对话前后缀、不加代码围栏
2. 不输出自我评价
3. Frontmatter 只放元数据——不塞业务 schema
4. 禁止根目录文件
5. 不自创 metadata.pattern——必须是五种之一
6. 不可执行代码

针对每个特有模式另有定义，加起来十几条。**这不是标准答案，得根据每个团队的实际情况定义。**

**门禁的实测效果**（由强化学习工具发现的约束）：

| 模式 | 效果提升 |
|---|---|
| pipeline | +169.1% |
| tool-wrapper | +162.9% |
| reviewer | +153.9% |
| inversion | +45.5% |
| generator | +37.9% |
| **平均** | **+113%** |

> 这些约束在顶级模型下通常不需要如此显式，但保留它们不会有害。

**门禁的落地方式**：早期是把 Skill 开发规范写成 Markdown 文档发给团队让大家照做，效果不太好。后来做了一个**线上评估工具**——把写好的 Skill 打包提交，自动检查是否通过门禁与用例，可以放进 Pipeline 构建时用，也可以手工用。

难点在于**本地造不出那么多 test case** 来检查是否违规，放到一起做就容易多了，一试就能试出来。

## 快速需求的半自动化开发

### 需求分类

| 类型 | 特征 | 走法 |
|---|---|---|
| **项目需求** | 复杂、周期长 | 标准 Pipeline 一步步走 |
| **快速需求** | 从拿到需求到上线三天内能做完 | 半自动化流水线（团队占比约 60%） |

### 三段流水线：两头有人，中间没人

| 段 | 负责人 | 做什么 |
|---|---|---|
| **前级** | 人（A） | 需求拆解：项目管理工具、产品管理工具的信息处理成 Markdown，加开发知识库 |
| **中级** | AI 无人值守 | N 个 Agent 自主开发，五阶段状态机 + TDD 内循环 + 质量门禁 + 异常处理 + 执行轨迹全记录 |
| **后级** | 人（B） | 集成测试：审查 MR、合并、真机集成测试，AI 做各端单测验证 |

**前级产出三样东西**往下游传递：

- **Task** —— 有标准格式
- **Open Spec** —— 只产生需求相关的部分，不产生所有 Spec 文档
- **auto-dev.yaml** —— 传递开发规约，包括隔离方式

**前级的卡点：数据库知识处理**。PRD 和技术文档存在数据库里，这块处理最难。

**中级的质量门禁**：从十几种门禁里筛出 **8 个跟快速需求场景密切相关的红线**，AI Coding 绝对不能逾越。比如单个文件代码改动一定有上限。

### 测试资产化：不打破测试同学的心流

**现实约束**：测试同学和开发同学的动手能力差异非常大，很多测试同学还是用脑图写测试方案，让他换成写 Markdown 会遇到很大挑战。

**解法**：本着不改变同学习惯的方式——他用 Markdown 就用 Markdown，用脑图就用脑图。把脑图传到测试平台，平台自动转成 Markdown，再定时刷成测试目标与用例，一键部署。

### 自愈能力：成为底线

以前自动化测试效果不好的重要原因：除接口测试外，大部分集成测试的自愈能力非常弱，UI 稍微调整就不能自适应。

关键做法：**脚本不持有 locator，失败时由 HealListener 做层级化自愈**。

## 个体团队：TeamAI 的第一步

TeamAI（AI for the whole Team）分两个独立阶段：

```text
第一阶段：个体团队
  每个程序员像团队一样工作
  = 围绕自己个人能力和风格，打造专属 Agent
        ↓
第二阶段：人机团队协同
  人类团队 + Agent 团队
  = 快速需求自动化开发（两头有人、中间没人）
```

**没有第一步的个体团队——让每个程序员都能围绕自己的个人能力和风格打造自己专属的 Agent——很难跨越到第二步。**

技术角色边界也发生融合：每个程序员都成为「全栈 + 专家」的复合角色。
