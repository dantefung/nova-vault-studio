# 上下文工程五环节

> 用好一个 AI Coding Agent，就是围绕五个环节做工具建设：**知识库、工具调用、对话历史、项目记忆、现场清理**。没有唯一标准，但围绕这五点投入，通常能收到显著效果。

## 与「写选压隔」四操作的关系

[[patterns/context-engineering]] 从**上下文内容管理**角度总结了四操作（写、选、压、隔），本篇从**工具建设**角度给出五个环节。两者不是替代关系：

| 视角 | 关注什么 | 产物 |
|---|---|---|
| 四操作 | 每一轮往上下文里放什么、留什么 | 一套上下文组织策略 |
| 五环节 | 用什么工具、什么资产去支撑这些策略 | 一套工具链与项目目录 |

四操作回答「这一轮该带什么」，五环节回答「靠什么把这件事做对」。

## 环节一：知识库

代码知识库的三种形态：

1. **本地项目内代码管理** —— 团队目前主要用这种
2. **跨项目全域集中管理** —— 团队目前主要用这种
3. **语义表达的知识库** —— 从符号级到语义级（如 fast context），更激进

Code Graph 属于**符号加连接**的方式，介于前两者之间。

## 环节二：工具调用

AI Coding Agent 调用最多的是围绕代码检索的命令行工具，核心是 Git 和 Grep。但 Agent 用 Grep 效率并不高——Grep 是语义驱动的，而人有很强的符号表达。Claude Code 至今没支持 LSP 协议，没有语法树概念，全靠「阅读」理解代码。这就是长程任务里提示词规模越来越大、效果却不佳的原因。

**改写工具的两类手段**：

| 手段 | 做法 | 代表 | 取舍 |
|---|---|---|---|
| **调用后改写** | 先调本地工具，再对结果压缩改写 | rtk | 更成熟稳定 |
| **替换工具** | 用更 AI 化的新工具替换 Grep（符号语法树 + 语义嵌入模型混合检索） | — | 改善空间更灵活更大 |

结论：**改变工具，往往立竿见影**。

## 环节三：对话历史

分长期记忆与短期记忆。长程任务里对话信息量大且非常稀疏，怎么从短期记忆里找出重点是核心问题。

| 方案 | 做法 | 风险 |
|---|---|---|
| **内置 compact** | 截断式瘦身 | 窗口省了，但早期用户意图和下一步动作可能一起被截掉 |
| **pi-vcc（语义折叠）** | 把「怎么查到的」（curl→失败→重拉→读七次）压成「已经知道了什么」，锚定核心指令 | 省下的上下文留给真正要产出的内容 |

压缩规则可按团队习惯定制，保留什么、不保留什么都可控。

## 环节四：项目记忆

把项目里真正的决策信息从对话历史、碎片文档里统一抽取、表达、保存好。

**通用记忆层的问题**：太重，且没法让每个同学都有参与感。

**本文团队的方案**——一组人类可读、本地手工可编辑的 Markdown 文件：

```text
项目记忆/
├── 项目简介      # 这个项目是什么
├── 项目规约      # 团队约定的硬性规则
├── 决策日志      # 已经做出的决策及其理由
├── 墓碑          # 已确认错误的做法，不再重试
├── 候选记忆      # 上了日程还没动手的
└── 主体表        # 团队特有术语，类似领域模型里的概念模型
```

关键性质：**既给 Agent 用，也给人用**，人可以手工编辑。

## 环节五：现场清理

长程开发的典型症状：当任务存在方案调整或缺陷修复，Agent 改好了主线代码和文档，却在项目里留下一地废弃垃圾。

| 清理对象 | 手段 |
|---|---|
| **文档清理** | 涉及语义，只能靠模板机制调用大模型 |
| **代码清理** | 借助 LSP 做标准动作，识别废代码、死代码 |

AI 容易产生哪类垃圾代码已有不少定论（比如 Claude Code 最容易产生哪类），把这些配上去让它自动收尾——**钩子方式自动处理**或**斜杠命令手工处理**。

## 心法四动作：卸载、精简、检索、隔离

前面五个环节，最终都归结为四个核心动作：

| 动作 | 做法 | 效果 |
|---|---|---|
| **卸载** | 渐进式加载，把东西保留到文件里，真正需要时再 load 进来 | 有了无限空间 |
| **精简** | 让上下文里只出现当前问题真正需要的信息 | 减少噪声 |
| **检索** | 快速准确地找到本地文件里的片段加载进来 | 按需取用 |
| **隔离** | 把复杂问题拆成简单问题 | 上下文更清晰 |

## 硬约束：上下文用量上限 45%~55%

任务越来越长，上下文长度对大模型的智能水平影响很大。实测散点图显示：

- **上下文用量上限基本在 45%~55% 之间**，超过就进入「滞胀」往下跌
- 关键不是**你写的那段话**，而是**整个 Agent 到底给大模型发了哪些内容**
- AI 能完成的任务长度大约**每 7 个月翻一倍**（METR 数据）——任务越来越长，上下文管理越来越关键

## 上下文的三种调整方式

1. **改变输入方式** —— 通过改变跟 Agent 的对话调整最终上下文
2. **对 Agent 的工具做比较重的二次开发**
3. **（推荐）用现成插件调它的内容** —— 用正则规则、或嵌入轻量级向量做语义比对，做本地的过滤、改写、增强

每个工具（Claude Code、Pi 等）对上下文的内部定义不同，但大逻辑一致：**分 Block（一上来就固定摁死的部分，只能在对话开始时替换）和 Stack（动态上去的部分，可以用插件替换成你需要的表达）**，最后再提交给大模型。

## 验证闭环：没有 Trace 就没有 Loop

Loop 的本意是：与其把规则给大模型定死，不如让它多试几次。落到用好工具这件事上：

```text
日常大量实践
   ↓
一定要有 Trace 工具 ← 没有它就定位不了问题
   ↓
定位五个板块里哪块出了问题
   ↓
通过工具的外围配置或使用方式做调整
   ↓
把工具箱打造得更好 → 回到实践
```

**Trace 工具的具体做法**：把 Agent 的对话集中收集到本地，展开能看到 request/response 里到底发了什么、跟你预期一样不一样；还能统计它来回做了几次交互、跑一个任务花多长时间。写点简单 SQL 就能知道自己智能体执行任务的情况，动手能力强的还能挂报警。
