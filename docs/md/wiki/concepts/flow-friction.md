# 流动摩擦（Flow Friction）

> 当 AI 让开发环节变成价值流中最快的一环，真正限制团队吞吐的不再是代码生产速度，而是需求、设计、Review、测试和发布之间等待、切换与返工产生的阻力——即"流动摩擦"。

<!-- more -->

## 核心定义

**流动摩擦**（Flow Friction）：AI 加速代码生产后，需求、设计、Review、测试和发布之间因节奏不匹配而产生的等待、切换与返工阻力。

AI 对团队各环节的加速并不均匀：

| 环节 | 加速幅度 | 新瓶颈 |
|------|----------|--------|
| 需求 | ~1.2× | 决策速度（客户会议、利益相关者对齐、优先级冲突） |
| 设计 | ~1.5× | 体验判断（用户路径、异常状态、跨端一致性） |
| 开发 | ~5.0× | 代码生成能力爆发 |
| Review | ~1.3× | 上下文恢复、一致性检查 |
| 测试 | ~1.3× | 验证能力（不是测试数量） |

## 三种摩擦表现

### 1. 上游饥饿 + 下游拥堵同时发生

开发者认为没有足够需求/设计可推进（饥饿），但已生成的代码在 Review/测试环节大量排队（拥堵）。开发环节像一条入口缺车、出口拥堵的高速公路。

### 2. 歧义固化成代码

过去需求歧义在开发中逐步暴露。现在 Agent 迅速选择合理解释并完整实现，歧义被更快地固化成代码，最终变成一组需要修改的代码、测试、文档和接口。

### 3. 并行开发增加共有成本

Git 冲突只是表层问题。不同 Agent 在相邻模块中引入不同的抽象、命名和错误处理方式。每个 PR 单独看正确，放在一起失去一致性。

> **AI 降低了写代码的成本，却提高了团队共同拥有代码的成本。**

## 返工放大机制

当开发比上下游快得多，团队让 Agent 提前探索、重构、补测试，试图填满产能。这增加了尚未完成的变化，把局部提速转化为系统返工。

- 不成熟需求更快变代码 → 歧义暴露于 Review → 成组修改
- 并行开发增加 → 抽象/命名不一致 → Code Review 变成上下文恢复
- 测试规模增长 ≠ 验证能力增长 → 问题发现越晚 → 返工成本越高

## 设计流动摩擦

当开发从瓶颈变成最快环节，团队不能继续只优化开发。需要重新设计的六个流动节点：

1. 产品能否持续形成有效决策
2. 设计能否及时提供可消费的体验边界
3. 代码能否以小批次安全并行
4. Review 能否获得足够上下文
5. 测试能否验证真正的业务行为
6. 生产反馈能否回到下一轮决策

## 作者金句

> AI 原生团队的竞争力，不在于能够同时启动多少 Agent，也不在于一天能够生成多少需求、原型、代码和测试。真正重要的是，团队能够让多少变化以较少的等待、冲突和返工，从一个尚未确认的想法，持续流动为用户可以感知的价值。

> 代码可能已经足够快了。接下来需要重新设计的，是变化穿过整个团队时的流动摩擦。
