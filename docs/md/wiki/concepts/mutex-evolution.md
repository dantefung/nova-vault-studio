# 互斥锁的演化：从关中断到读写锁

> 并发编程中锁的演化史——每一步都是被前一步的缺陷逼出来的。

## 核心定义

互斥锁（Mutex）是并发编程中用于保护临界区的同步原语，确保同一时刻只有一个线程能访问共享资源。其演化路径反映了工程实践中"发现问题→解决问题→引入新问题"的迭代本质。

## 关键洞察

1. **竞态条件的根源是"读-改-写"三步不可分割**——`count++` 在 CPU 层面是读→改→写三步，线程交叉执行导致结果不确定。这是所有并发 bug 的根源。

2. **软件方案被硬件优化破坏**——Peterson 算法逻辑正确，但现代 CPU 和编译器的乱序执行导致其失效。最终只能靠硬件提供的原子指令（TAS/CAS）解决。

3. **自旋锁 vs 互斥锁的核心取舍是"空转 vs 睡眠"**——自旋锁适合纳秒级临界区（内核），互斥锁适合微秒/毫秒级（用户程序）。选择取决于"等待时间 vs 睡眠唤醒开销"的权衡。

4. **死锁的四个必要条件缺一不可**——互斥、持有并等待、不可剥夺、循环等待。打破任意一个即可防止死锁，实践中常用"固定加锁顺序"策略。

5. **读写锁是"读多写少"场景的优化**——多线程读安全，不需要互斥，只有写需要排他。这是对互斥锁"一刀切"保护的改进。

## 演化全貌

```
关中断（粗暴，不适合用户程序）
  → Peterson 算法（被 CPU 乱序破坏）
    → 硬件原子指令 TAS/CAS
      → 自旋锁（空转，适合临界区极短场景）
        → 互斥锁（睡眠等待，用户程序标准选择）
          → 读写锁（读多写少场景优化）
```
