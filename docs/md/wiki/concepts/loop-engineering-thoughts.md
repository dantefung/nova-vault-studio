# Loop Engineering 深度思考：从控制论到 AI 无人值守

## 一句话洞察

Loop Engineering 本质上是**控制论在 AI 领域的一次落地应用**——通过负反馈机制去收敛目标函数。核心思路是从"写 Prompt"转向"设计 Loop"，把人从流程中拔出来。五代工程演进（Prompt→Context→Harness→Loop→Graph）层层依赖，Harness 是地基，Loop 是上层调度。

## 核心概念

### 五代 AI 工程演进

| 时代 | 解决什么问题 | 核心局限 |
|------|------------|---------|
| Prompt Engineering (2023) | 怎么问才答得好 | 答错无自动纠偏，人工重来 |
| Context Engineering (2025) | 模型缺背景答不准 | 只有信息没手脚，缺验证闭环 |
| Harness Engineering (2026.2) | 单次执行不可控不可信 | 仍要人触发让人盯，人成瓶颈 |
| **Loop Engineering (2026.6)** | **靠人盯，无人值守** | **成本失控** |
| Graph Engineering (2026.7) | Loop 间编排协同调度 | — |

**Harness vs Loop**：Harness 是 AI 代理的受控运行环境；Loop 是在这个环境之上叠加了自驱动能力的持续执行流程。Harness 是地基，Loop 是上层调度，没有 Harness，Loop 则是无源之水。

### 吴恩达三个环

技术 Loop → 产品 Loop → 用户 Loop，三层嵌套、不同速度、层层驱动。跳出单纯的技术视角，把 Loop 的涉众范围扩大到产品和用户。

### 控制论四大公理与 Loop 映射

| 控制论公理 | Loop 对应 |
|-----------|-----------|
| 构建负反馈闭环 | Maker-Checker 双校验、TDD Red-Green-Refactor |
| 可观测性 | 测试用例、证据链、日志 |
| 可控性约束 | 预算熔断、最大步骤限制、退出机制 |
| 离散迭代纠偏 | 单步修正、Red-Green 循环 |

### Loop 五大组件

1. **Automations（唤醒机制）**——人不用再去"盯着去喊"，自动化系统运行的前提
2. **Worktrees（沙箱环境）**——多 Agent 协同，每任务独立工作区，杜绝文件覆盖和环境污染
3. **Maker-Checker（双校验）**——对抗性思维，"一方做、一方质疑"，结合 Skills 经验库
4. **Connectors（通信模式）**——MCP、Function call 等，打通上下游系统
5. **Memory（长任务记忆）**——记录任务进度、过往尝试，防止多轮迭代后丢失目标

## 关键机制

### 如何让模型说"不"？三种方法

**方法一：TDD（测试驱动开发）**——TDD 的价值不是多写测试用例，而是**把需求翻译成反馈信号**。核心：Red-Green-Refactor 最小闭环。注重 TDD 左移：先定标准、后做开发、以结果反向驱动过程。

三个测试维度：单元测试环（定义桩函数→写用例→写实现）、接口测试环（AI 自发包收日志）、流程测试环（功能级回归验证）。

**方法二：证据链**——Maker-Checker 双校验不是靠猜，而是靠证据链。Maker 通过产品规则推演输出代码，Checker 使用证据链追溯 Review。本质上是对抗性思维。

**方法三：预算思维**——资源倾斜：高价值任务用聪明模型，低价值重复任务用便宜模型（Opus 成本是 GLM4-Flash 的 180 倍）。设置退出机制（最大步骤限制、预算熔断）。上下文压缩策略：高密度核心规则不压缩 + 增量信息克制压缩。

### 关键实践路径：从小闭环做起

**不要一上来就做全自动万能的循环**，先跑通最小可收敛闭环，再逐步放大自治边界，建立闭环间联系。核心四问：如何定义问题？如何定义开始？如何设计反馈？如何定义结束？
