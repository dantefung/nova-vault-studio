# AI Friendly 后端架构：让系统可被智能体维护

## 一句话洞察

真正的 AI Friendly 不是"给项目加一份 README"，而是让 AI Agent 在有限上下文、有限权限、有限试错成本下，正确理解系统、定位边界、拆解任务、修改代码、验证结果、评估风险，并在自动化规则约束下安全推进系统演进。本质是从建设"可维护系统"转向建设"可被智能体维护的系统"——把隐藏在人脑、群聊、口头约定、历史事故里的系统知识，显式化、结构化、可检索化、可执行化、可验证化。

## 核心概念

### 后端系统 AI Friendly 的三大动机

1. AI Coding / Agentic Coding / Vibe Coding 进入工程现场，未来大量开发、排障、重构、测试、发布由 AI Agent 7×24 持续执行。
2. 大型后端有几十甚至上百个微服务，背后是 RDB、Redis、Kafka、RocketMQ、对象存储、搜索引擎、网关、风控等一整套复杂基础设施。
3. 人类老员工凭经验知道"哪个服务负责什么""这个字段不能乱动"，但 AI 不知道，只能通过代码、文档、工具、日志、测试、历史变更、运行环境去推断。

### 六类机器可读的系统事实层

| 事实类型 | 内容 | 提供什么 |
|---------|------|---------|
| 架构事实 | 业务域划分、服务分层、核心链路、服务拓扑 | 全局地图 |
| 服务事实 | 服务名、业务域、上下游、依赖、告警、发布方式 | 节点身份 |
| 领域事实 | 实体、状态机、生命周期、不变量 | 业务语义 |
| 接口事实 | 调用方、幂等、超时、限流、错误码、兼容性 | 协作契约 |
| 数据事实 | 表结构、字段含义、分库分表、枚举、脱敏 | 状态基础 |
| 运行事实 | QPS、TP99、错误率、强弱依赖、热点 key | 真实反馈 |

### 四大核心产物

1. **Architecture Map（全局架构地图）**：不是 PPT 大图，而是可被人阅读、可被 AI 检索、可被 CI 校验、可被 Harness 执行的系统级地图。回答：业务域、分层、核心链路、调用拓扑、消息拓扑、数据所有权、强弱依赖、发布/故障隔离边界、历史遗留与演进方向。
2. **System Card / Service Card（服务身份证）**：每个微服务的标准化卡片，含服务定位、核心职责（3-7 条，越多越说明边界腐化）、核心实体、数据所有权、接口/消息/依赖清单、运行特征、变更约束、测试入口、发布与回滚。放仓库根目录，由 CI 检查。部分自动生成：接口从 OpenAPI 生成，依赖从调用链生成，表结构从 schema 生成。
3. **领域模型 + 跨域链路模型（Domain Clarity）**：后端最核心资产是业务不变量。四类内容——不变量（写成可测试可断言）、状态机（机器可读定义）、幂等与一致性（requestId / businessKey / 最终一致 vs 强一致 / 事务消息 / outbox）、风险等级（低风险自动 PR，高风险人工 review）。
4. **SKILL（工程能力包）**：把团队高频工程任务沉淀为可复用任务包，含适用场景、输入信息、相关文件、操作步骤、风险检查、验证命令、输出要求。把高级工程师经验复制出来："加字段要先兼容写、再兼容读、再回填、再切流量、最后清理旧字段"。

## 关键机制

### Harness：安全执行轨道（七层）

SKILL 是能力包，Harness 是执行框架。七层：上下文装载层（精准分层可追溯，不一股脑塞全库）、工具层（权限边界，生产库默认只读）、计划层（修改前输出计划，高风险审批）、执行层（独立分支/worktree/sandbox）、验证层（跑测试，无验证不进 PR）、审计层（全程留痕）、回滚层（变更必须附回滚方案）。

更进一步，Harness 应成为架构规则的执行器：把分层、依赖方向、数据所有权、消息规范写成 Architecture Policy，AI 提交时自动检查是否违规。

### Test-Gated AI Development

测试从"防人出错"升级为"约束和指导 AI 行为"，成为 AI 的交通信号灯 / checkpoint。七类：单元测试（不变量、状态机、金额）、契约测试（防跨服务破坏）、集成测试（端到端业务流）、回归用例库（沉淀事故）、数据迁移测试（schema migration 最危险）、性能测试（N+1、缓存击穿）、架构验证（验证系统结构是否被破坏）。

### 可观测性即 AI 的眼睛

日志统一格式（traceId/spanId/bizId/errorCode）→ 错误码有语义（不能都叫 SYSTEM_ERROR）→ Trace 关联业务实体 → 指标有业务含义（支付成功率、库存扣减失败率）→ 告警关联 Runbook（可能原因、排查步骤、止血方式）。

### 分级权限模型（Tiered Access Control）

L0 只读代码文档 → L1 沙箱改码测试 → L2 查脱敏日志/测试库 → L3 创建 PR/触发 CI → L4 低风险服务自动合并发布 → L5 生产修复动作（强审计 + 人类预授权）。原则：不是把权限全给 AI，而是让 AI 在不同风险场景获得刚好足够的权限。

### 代码可导航 + 文档/架构即代码

- Code Navigation：稳定目录/命名/分层约定，DTO/DO/Entity/VO 不混用，减少"隐式魔法"（反射、动态代理、运行时拼接），提供导航锚点（接口入口、实体文件、状态机定义、外部依赖 client 封装）。
- Docs as Code：文档进仓库、和代码一起 review / 版本管理 / 参与 CI。
- Architecture as Code：architecture.yaml / ownership.yaml / critical-path.yaml / risk-policy.yaml，让全局架构变成可被 AI 读取、被 CI 校验、被 Harness 执行的工程资产。

## 演进三阶段

| 阶段 | 定位 | AI 能力 | 系统要求 |
|------|------|---------|---------|
| **Copilot** | 辅助人类 | 写代码、补测试、解释、生成文档 | 基本文档、代码规范、测试入口 |
| **Coworker** | 独立完成中低风险任务 | 新增接口、修 bug、补单测、写 migration、生成 PR | Service Card、SKILL、领域模型、契约测试、CI 约束 |
| **Operator** | Vibe Coding 的"黑灯工厂" | 线上值守、接收告警、分析日志、定位问题、执行回滚、沉淀 Runbook | 完整可观测性、权限分级、审计、自动化发布、灰度、回滚、安全策略 |

7×24 无人值守不是一步到位让 AI 接管生产，而是逐步扩大 AI 的可信半径：先低风险、强验证区域自动化，再进入复杂系统和生产运维。

## 改造 Roadmap（11 步）

1. 选中等复杂度、风险可控的业务域试点（不选玩具服务，也不选支付/资金最高风险服务）
2. 建立最小可用的全局 Architecture Map（可粗但必须真实，可不完整但不能误导）
3. 为试点服务补齐 Service Card
4. 梳理核心领域模型（实体、状态机、不变量、幂等规则）
5. 沉淀 5-10 个高频 SKILL
6. 补测试和契约（先覆盖核心链路和高频变更点）
7. 建立 AI PR 模板（变更说明、影响面、测试结果、风险点、回滚方案）
8. CI 变硬门槛
9. 接入只读可观测工具（脱敏、限权、审计）
10. 允许 AI 低风险自动 PR（先人工 review）
11. 逐渐扩大范围

**关键**：不要先追求"无人化"，要先追求"可验证"。无人化不是目标本身，可验证的自动化才是目标。

## 一句话点评

本文把"AI Friendly"从口号落地为 14 个可执行的工程维度，核心洞见是：**系统知识的显式化是 AI 参与系统级开发的地基**。最值得借鉴的是三阶段演进（Copilot→Coworker→Operator）和"可验证优先于无人化"的务实路线——它避免了大而全平台化的陷阱，强调从一张最小可用的 Architecture Map 起步逐步深化。
