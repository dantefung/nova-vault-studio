# 上下文窗口的公摊面积：为什么 128k 不等于 128k 可用空间

> 模型厂商宣称的"支持 128k 上下文窗口"是单次请求所有内容的绝对上限，不是全给你放正文业务数据。系统设定、历史记录、RAG、工具定义、输出预算等都要"公摊"。

## Problem Context

当下大模型动辄宣称 128k、200k 甚至 1M Token 的上下文窗口，开发者误以为可以把整个项目代码库或长篇文档一次塞进去。然而实际上：

- 输入到 API 的内容比"业务正文"多得多
- 长上下文带来成本浪费、首字延迟、注意力分散三大副作用
- 业界出现了一种新型 bug：模型在长上下文中"看不到"用户的关键指令

如果不理解窗口的"公摊结构"，开发者会在 prompt 设计和工程优化中反复踩坑。

## Solution

将"上下文窗口"想象为买房：宣称 128 平的房子，公摊可能占 30 平——剩下 98 平才是你的正文业务数据可用空间。

### 五大公摊来源

| 公摊项 | 占用 | 来源 |
|--------|------|------|
| 系统设定（system message） | 几百到几千 Token | 模型角色 + 输出格式 + 安全策略，每次必带 |
| 历史记录（conversation history） | 与对话长度成正比 | 多轮对话中每一轮的 prompt + response 都累计 |
| 外挂知识库 RAG | 几百到几万 Token | 检索出的相关片段被拼接到 prompt 前部 |
| 工具与插件定义 | 几百到几千 Token | Function Calling、Tool Schema 等结构化描述 |
| 模型输出预算 | 由 max_tokens 决定 | 预留的生成空间（虽然不计入输入，但占总量） |

### 实际可用空间估算公式

```
可用正文 Token ≈ 128k
                - 系统设定（~2k）
                - RAG 拼接（~4k-8k）
                - 工具定义（~1k-3k）
                - 历史记录（取决于轮数）
                - 输出预算预留（~2k-4k）
                ≈ 100k（单轮无历史）
                ≈ 60-80k（5 轮对话 + RAG + 3 工具）
```

## 公摊结构的工程含义

### 1. 系统设定是固定成本

无论任务大小，模型每次请求都要读 system message。这意味着：
- 系统消息应当精简到极致——只保留必要约束
- 重复约束（"请简洁回答" + "用 Markdown 格式" + "中文回复"）应在单条系统消息中合并
- 多余的角色设定会被 Token 计价，但不增加模型表现

### 2. 历史记录是隐性放大器

多轮对话里，每一轮的 prompt 和 response 都会进上下文。10 轮对话后，历史可能吃掉 50k+ Token。这意味着：
- 长任务需要"上下文压缩"或"对话摘要"机制
- 子代理（subagent）模式能隔离长上下文——子代理的完整历史不会污染主代理

### 3. RAG 拼接是大头

如果用 RAG 检索 10 个相关片段，每个片段 500 Token，光 RAG 就占 5k。这是公摊中最大的一块。优化方向：
- 检索精度优于检索数量——少而准 > 多而杂
- 关键片段放最前面（注意力机制对前部更敏感）
- 设定最大 RAG 预算（如 ≤ 8k），超出后切换到压缩或分层检索

### 4. 工具定义是功能 vs 成本的 Trade-off

每加一个工具（约 200-500 Token）就吃掉对应 Token 预算。但少加工具又限制了模型能力。优化方向：
- 工具按需启用（按场景 profile 切换可用工具集）
- 工具描述精简到一句话能说清
- 同类工具合并为一个多功能工具

### 5. 输出预算是隐性天花板

max_tokens 决定生成多少空间。如果设置 max_tokens=8000 而实际只生成 1000 Token，多余的 7000 Token 仍占窗口总量。这意味着：
- max_tokens 不宜过大——以实际需求的 1.5-2 倍为佳
- 流式输出（streaming）能减少用户感知的延迟

## 长上下文的副作用

### 副作用 1：成本浪费

上下文越长，每次请求的成本越高。但同一信息在多轮中重复出现时，缓存命中率会下降。优化方向：
- 静态信息（系统消息 + 工具定义）→ 利用 prompt cache
- 动态信息（历史 + RAG）→ 避免重复，使用 session id 复用

### 副作用 2：首字延迟（TTFT）

塞给模型的信息越多，它吐出第一个字的时间越长。128k vs 8k 的 TTFT 可能差 5-10 倍。优化方向：
- 流式输出（streaming）降低用户感知延迟
- 预填关键信息在前部（注意力机制对前部更敏感）

### 副作用 3：注意力分散

长上下文里塞的内容越多越杂，模型越容易"抓不住重点"，甚至忽略核心指令。Lost in the Middle 现象——模型对中段信息的注意力明显弱于前段和后段。优化方向：
- 关键指令放最前或最后（不要放中间）
- 大文档分段处理而不是一次性塞入
- 用 RAG 按需检索而不是全文加载

## Trade-offs

- **窗口大 ≠ 任务好**：当业务需要长上下文（如代码库分析、长文档总结），增大窗口确实能提升表现；但当业务需要高频短交互（如客服问答），128k 反而成为"为了用满而塞东西"的负担。
- **RAG vs 全文本**：1M 窗口看似能装下整个项目，但 RAG 的检索精度通常高于一次性全文本——尤其当任务聚焦于"找相关信息"而非"理解全貌"时。
- **Token 经济 vs 表现精度**：精简系统消息能省钱，但太精简可能让模型行为不稳；最优解是"刚好让模型理解 + 关键约束都给到"。
