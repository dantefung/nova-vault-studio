# Durable Execution：把 Agent 任务进度从调用栈搬进可存储的状态机

## 一句话定义

**Durable（持久可恢复执行）**指把 Agent 的任务进度、调用意图和执行结果可靠地保存在进程之外，并在模型调用、工具执行等关键环节建立明确的恢复边界——使原进程退出或执行实例被替换后，任务仍能复用已确认的结果、核实未完成操作、继续推进。

一句话区分：**会话恢复让对话保持连续，Durable 让任务执行保持连续。**

## 核心问题：恢复对话 ≠ 恢复执行

普通 Agent 循环把进度留在**调用栈**里：

```text
收到输入 → 请求模型 → 得到 tool call → 执行工具 → 得到 tool result → 再请求模型 → 输出答案
```

进程崩溃后，函数调用栈、局部变量、Promise 全部消失。剩下的会话文件可能只记录：

```text
user: 向五位客户发送这份通知
assistant: send_batch_emails(recipients, body)
tool result: 尚未写入
```

**这份记录能证明模型提出了什么，却不能证明工具内部完成了什么。** `send_batch_emails` 是一个调用，内部发送了三封、四封还是五封，对外层循环不可见。

### 恢复对话与恢复执行的契约差异

| | 会话恢复 | Durable 恢复 |
|---|---|---|
| 目标 | 让模型重新获得上下文 | 让任务从正确位置继续 |
| 工具抽象 | 接收参数、返回结果的函数 | 必须公开「如何从中断中恢复」 |
| 契约强度 | 弱——不要求工具配合 | 强——同时影响调度、存储、工具接口 |
| 能否靠开关实现 | 能（加一个「保存 messages」开关） | 不能 |

**Durable 需要回答的五个问题**：任务由谁持有执行权？状态在哪个时刻生效？工具是否允许重放？等待怎样跨越重启？代码升级后如何解释旧状态？

### 最大的缺口：外部事实与本地记录之间的空隙

这是全文最关键的判断。即使把每封邮件拆成独立工具调用，仍存在一个聊天记录无法消除的窗口：

> **有调用意图、没有结果**，只能说明「可能执行过」。请求可能根本没发出，也可能已被接受但响应丢失，还可能已经收到回执、只差最后一次保存。

因此一套可靠机制必须同时处理两件事：

1. **内部状态如何提交** → 事务 + 持久任务可以解决
2. **外部动作如何确认** → 需要业务系统提供**幂等标识、原操作查询**，或明确的补偿与人工处理路径

**纯框架层无法凭空创造外部系统没有保存的事实。**

## 常见补丁为什么不够

| 常见做法 | 能解决什么 | 仍然缺少什么 |
|---|---|---|
| 保存聊天记录 | 重建模型上下文 | 工具内部进度、可靠等待与恢复策略 |
| 用数据库保存 messages | 提高历史数据保存能力 | 写入顺序、原子提交、执行状态机 |
| 进程崩溃后自动重启 | 恢复一个运行实例 | 从哪里继续、哪些动作不能重做 |
| 失败后重试整个 Agent | 再给任务一次机会 | 对已完成步骤和外部副作用的识别 |
| 给模型补一句「上次中断了」 | 帮助模型重新规划 | 缺失的业务事实与确定性的接续规则 |
| 给工具加 async/await | 让等待不阻塞线程 | 跨进程存在的等待关系和结果接回 |

**关键澄清**：问题不在于 JSONL 天生不可靠、SQLite 天生可靠。文件和数据库都能承载持久协议，差别在于**保存了什么、何时确认生效、崩溃后如何解释它**。

## Durable 的四项保证

1. **输入不因进程退出而消失**——已受理任务有稳定身份，客户端重试可关联原任务
2. **已确认工作可以复用**——保存完整的模型结果、工具结果和必要状态，恢复时不必重做
3. **未完成工作有明确去向**——正在执行 / 等待子任务 / 等待时间 / 结果不确定，各有对应的恢复方式
4. **执行过程可以被重新观察**——用户断线后可重新查看进度，观察连接不必陪着任务运行

**边界声明**（原文明确给出）：Durable 不等于「永不失败」，也不自动意味着外部动作恰好执行一次。服务持续不可用、凭据失效、工具结果无法确认时，任务仍可能进入失败或需要处理的状态。**它的目标是让失败留下可解释、可恢复的事实。**

## AgentScope 的落地实现

### 六种状态对象

| 对象 | 负责表达什么 | 邮件任务中的例子 |
|---|---|---|
| Conversation | 对话记录及其上下文范围 | 用户与邮件助手的持续对话 |
| Entry | 不可变的会话记录 | 用户要求、模型响应、工具结果 |
| Document | 可在事务中更新的结构化状态 | 收件人计划、发送回执、当前运行进度 |
| Task | 带阶段、检查点和终态的持久状态机 | 模型生成、工具调用、逐封发送 |
| Submission | 应用提交及其处理结果 | 发送请求是否排队、是否被处理、是否获得回答 |
| Commit | 一组关联变化的原子提交 | 保存回执，同时完成子任务并更新发送进度 |

**分层逻辑**：Entry 保留已发生的记录，Document 保存后续阶段需读取的数据，Task 决定下一步可以做什么。

### 原子提交：让记录、文档与任务一起生效

如果先写「工具完成」再保存工具结果，中间崩溃会留下一个没有结果的完成记录；反过来先保存结果再推进任务，接管者会误以为还需要执行。

一次 Commit 同时支持追加 Entry、修改 Document、创建或推进 Task、更新 Submission。提交顺序：

```text
取得 Session 的提交顺序
  → 在事务草稿中准备关联变化
  → 校验并冻结写集合
  → Storage 原子保存
  → 采纳已持久化的新状态
  → 更新视图、通知等待者、调度后续任务
```

**两个设计细节值得注意**：

- **串行化提交 + 事务外执行**：模型请求和工具执行在提交事务之外推进，一次外部调用持续十分钟不会占据十分钟的状态提交事务
- **受限的延迟提交**：仅用于正在生成的文本、运行中的工具输出等**可丢失进度**；一旦提交包含新消息、任务阶段、输入受理等关键变化，立即按普通提交持久化

### Task：把调用栈中的进度变成显式阶段

| 状态 | 含义 | 调度方式 |
|---|---|---|
| pending | 已持久创建，等待运行 | 调度器启动对应阶段 |
| running | 正在执行某个阶段 | 提交下一检查点、等待或结果 |
| waiting | 等待指定任务结束 | 保存依赖任务及汇合策略，当前不运行代码 |
| sleeping | 等待一个时间点 | 保存唤醒时间与下一阶段 |
| completing | 结果已决定，所属子任务尚未全部收尾 | 等待子任务收敛，不再运行自身阶段 |
| terminal | 已结束 | 保留最终结果，供其他任务读取 |

第四封邮件等待查询确认时的状态记录：

```json
{"kind":"send-notice","version":1,"input":{"operationId":"notice-2026-10-customer-4","recipient":"customer-4","bodyRef":"approved-notice-body"},"state":{"status":"sleeping","until":1793289600000,"checkpoint":{"phase":"confirm"}}}
```

**一条记录同时保存了原操作身份、下一阶段和唤醒时间。** 等待期间没有需要保留的函数调用或 Promise。

> **恢复从已保存阶段的入口重新执行，不会跳回崩溃前的某一行。** 一个阶段如果包含多个不可重复的外部动作，就应继续拆分阶段，或为这些动作保存可确认的操作身份。**单纯在函数内部增加更多 await，不会增加持久恢复边界。**

### 工具的两阶段设计：call 与 execute

| 阶段 | 行为 |
|---|---|
| **call** | 解析工具、校验参数、执行调用前检查，然后保存最终参数、**重放策略**和执行意图；提交成功后执行工具，最后提交结果 |
| **execute** | 作为「意图已保存、结果未确认」的恢复入口，判断能否使用保存的参数重新执行 |

**只有调用时保存的策略和恢复时的工具策略均为 safe，才使用已确认的参数重新执行**；否则保存 interrupted 结果和已提交的部分输出，让后续流程处理不确定性。

> **工具声明「可安全重放」是工具作者对业务行为的承诺，框架不会自动让发送邮件变得幂等。**

**如果只是把一个黑盒 `send_batch_emails()` 注册成普通工具，执行内核能知道这次调用中断，却不知道内部完成了哪几封邮件。** 更细的恢复需要把工具自身改造成多阶段任务。

### 自定义任务：把黑盒工具改造成业务任务

邮件助手注册发送任务类型，用 Document 保存已确认的收件人计划，为每封邮件建立子任务，并在同一次 Commit 中保存子任务身份和父任务的等待状态。

**父任务的等待不是内存中的 `Promise.all`，而是一条持久关系**：等哪些 Task、什么汇合策略、结束后进入哪个阶段。提供 `allSettled`（全等汇总）和 `failFast`（失败则请求其他子任务停止并等待收尾）两种策略。

故障恢复的最终效果：

| 邮件 | 恢复时的事实 | 继续方式 |
|---|---|---|
| 第 1～3 封 | 已提交终态与回执 | 直接读取，不再发送 |
| 第 4 封 | 已保存操作身份，没有确认结果 | 进入查询阶段；确认已完成后补记回执 |
| 第 5 封 | 任务已存在，尚未开始外部动作 | 从其初始阶段执行 |

**两层机制配合才能恢复到某一封邮件**：子任务创建与父任务等待一起提交，解决「进程退出后还记不记得这五项工作」；每封邮件的业务操作标识和查询阶段，解决「外部动作发生后如何核实」。

## 平台层：AgentCore 的延伸

### 状态层次：五类状态分别存储

| 状态层次 | 保存什么 | 谁解释并使用 |
|---|---|---|
| Harness 原生状态 | 上下文、消息、原生检查点及继续位置 | 对应框架及其适配层 |
| 平台执行事实 | 输入受理、执行权、工具授权、等待条件、结果应用和终态 | AgentCore 的执行协调与恢复机制 |
| 工具执行事实 | 原执行身份、物理进度、完整结果及交付状态 | 工具提供方；在分离架构中由 Hands 衔接 |
| 工作区与产物 | 文件、资源绑定、产物及必要版本 | Environment 与工具环境 |
| 用户可见视图 | 消息、进度、工具状态和最终结果 | 业务应用与观察接口 |

**平台不要求所有内容进入同一份聊天日志。** 较大的原生状态和结果可保存为不可变对象，由提交记录引用。

### 三个必须分别表达的进度

> 调用已被受理 / 工具已经完成 / 结果已经进入 Harness 上下文——它们之间可能间隔很久，也可能在任何一次交接时发生故障。

**将进度分别保存，恢复才能定位缺失的一步，而不是重新执行整段流程。**

### Brain–Hands 分离

| 逻辑职责 | 需要保留的事实 | 恢复目标 |
|---|---|---|
| Brain 推进 | 上下文、检查点、待应用结果及应用位置 | 从原阶段继续推理，不重复应用结果 |
| Hands 执行 | 原操作身份、执行进度、完整结果 | 查询或接回原操作，明确其完成范围 |
| 结果交接与调度 | 结果归属、交付进度、等待条件与恢复安排 | 已有结果能够再次交付，满足条件的任务能够再次获得执行机会 |

**核心是让「等待工具」成为可持久表达的状态。** Brain 提交调用和等待条件后理论上就可以释放执行资源；工具由独立机制推进；结果具备继续条件时，再由兼容的 Brain 实例读取原状态、应用原结果。

**但分离架构不能自动消除「动作已经发生、结果尚未确认」的窗口**——除非工具本身支持查询原操作或识别重复请求，这类不确定性仍需成为任务状态的一部分。

### Environment：让已保存状态拥有继续执行的条件

重新读取状态只是恢复的一部分。新的执行实例还需要兼容的内核、依赖、模型与工具配置，以及访问工作区和业务资源的权限。

> **状态说明任务走到了哪里，环境定义说明继续运行需要什么，调度机制决定由谁承接。** 对于本地 Agent 向云上迁移，这三部分共同构成**可迁移的执行单元**。

## 三层分工总结

```text
框架（AgentScope）  →  从哪里继续、怎样继续
平台（AgentCore）    →  状态长期保存在哪里、由哪个实例继续
业务系统            →  外部动作是否发生、如何核实
```

三者通过**存储契约与唤醒契约**连接，缺一不可。
