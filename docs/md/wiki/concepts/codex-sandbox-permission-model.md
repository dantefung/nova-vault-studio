# Codex 沙箱权限模型

> **同一个会话里，不同的启动路径拿到的权限不一样。** 「这会话开了沙箱」这句话掩盖了三个独立生效点：Shell 命令、本地 stdio MCP 服务、域名访问。**更反直觉的是：文件根本不继承沙箱限制。**

## 一句话定义

沙箱权限不是「给会话发一张通行证」，而是**在每次进程启动的那一刻，把权限配置翻译成本机沙箱规则**。于是：

| 启动路径 | 谁启动 | 默认是否受 Shell 沙箱约束 | 单独限权的方式 |
|---|---|---|---|
| **Shell 命令** | 统一命令执行器（`exec_command`） | **是** | 权限配置（`:workspace` / Permission Profile） |
| **本地 stdio MCP 服务** | MCP 客户端的 stdio 启动器 | **否** | `codex sandbox --permission-profile` 单独包裹 |
| **域名访问** | 操作系统网络层 | 取决于两个开关 | `network.enabled` + `features.network_proxy` |

**三个生效点互不覆盖：测试命令断网，文档服务仍可能访问内网。**

## 机制拆解

### 一、命令启动时的链条

`exec_command`（命令、工作目录、环境变量、权限选项）→ 统一命令执行器 → 权限配置翻译成本机沙箱规则 → 操作系统执行限制 → 子进程继承约束。

**模型决定要运行什么，操作系统按启动时的规则限制它能访问什么。** 即使某个后代进程比原始命令活得更久，限制仍然跟着它。

### 二、`:workspace` 这类内置配置的三档语义

| 档 | 默认行为 | 风险 |
|---|---|---|
| 写 | 工作区 + 系统临时目录可写 | **未额外保护的文件可能被覆盖或删除**，沙箱分不清「必要清理」和「误操作」 |
| 读 | 读取范围较宽（编译器要找仓库外的 SDK/库） | **用户目录里的配置文件（含密钥）也可能读得到**，需要 `read` / `deny` 精确收紧 |
| 网 | 默认禁止联网 | 读范围 + 可读 = 仍可能泄出 |

额外写保护名单：`.git`、`.codex`、`.agents`、`.aws` —— 防止命令直接改 Git hooks 或 `.codex/config.toml` 这类**会影响后续执行**的文件。

### 三、扩权请求分两条路径

批准之后「用什么权限跑」有区别：**扩大沙箱内的访问范围**与**到沙箱外执行**走的是不同的启动路径。审批策略可以交给用户或 Auto-review。

### 四、域名规则需要代理层

`network.enabled` 只是允许联网；**`features.network_proxy` 才让域名表生效**。代理按域名放行，程序不认 `HTTP_PROXY`/`HTTPS_PROXY` 而试图直连时，由操作系统沙箱兜底。**两处限制配在一起，「只访问这个包仓库」才真正成立。**

### 五、通配符规则的时间差

`**/*.env` 这类通配规则会在**每次启动前展开成具体路径**。**命令启动后才出现的 `.env` 文件，即使匹配，也不会被补进这次运行的拒绝规则。**

## 最反直觉的一条：文件不继承沙箱限制

沙箱内写入的依赖（如 `node_modules` 里的 Prettier），**下次由沙箱外的编辑器加载并执行**——编辑器按自己的权限运行，测试子进程仍受原限制，**变的是执行这份文件的程序**。而 `node_modules` 通常被 Git 忽略，改动未必出现在 `git status` 里。

**推论**：沙箱保证的是「这一次进程调用」，不是「这份代码永远安全」。

## 失效模式与对策

| 失效 | 表现 | 对策 |
|---|---|---|
| 以为会话开了沙箱就万事大吉 | MCP 服务仍能连内网 | 单独用 `codex sandbox --permission-profile` 包裹服务 |
| 只开网络不启用代理 | 域名表形同虚设 | 两个开关一起开，并确认托管要求也启用了代理 |
| 允许写整个工作区 | 误删无法区分 | 对关键路径加 `read` / `deny`；数据库侧用账户权限再收一道 |
| 以为沙箱能拦逻辑错误 | 两份补丁都过测试却互相影响 | 沙箱管不了「是否符合需求」，这要靠测试与 review |
| 用通配符规则保护密钥文件 | 启动后生成的文件漏网 | 关键路径用显式具体路径而非通配符 |
