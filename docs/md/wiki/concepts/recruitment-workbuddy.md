# recruitment-workbuddy

> WorkBuddy 在企业 HR 招聘场景的落地方案——把半手工 + 主观判断的招聘流程，重构为规则驱动 + Agent 执行的工业化流水线。

## 一句话定义

用 WorkBuddy（国内桌面端 Agent 产品）+ 自定义 Skill + 飞书多维表 + 邮箱连接器，搭建一套全自动 HR 简历筛选流水线，**HR 只做一件事：挑人**。

## 核心数据

- **效率提升**：简历处理从 8 小时压到 **0 分钟**
- **流程压缩**：HR + 业务负责人两道关 → AI 评分 + 自动推送
- **价值主张**：每份简历都按相同标准被评价，不再靠抽签

## 三层技术架构

```
┌─────────────────────────────────┐
│  自动化任务（每日 9 点）         │
└──────────────┬──────────────────┘
               ↓
┌─────────────────────────────────┐
│  hr-resume Skill（自定义）        │
└──────────────┬──────────────────┘
               ↓
       ┌───────┴───────┐
       ↓               ↓
┌─────────────┐  ┌────────────────┐
│ 邮箱连接器  │  │ 飞书连接器      │
│ (采集简历)  │  │ (多维表读写)    │
└─────────────┘  └────────────────┘
```

## 6 步实现路径

| 步骤 | 动作 | 关键技术 |
|------|------|----------|
| 1 | 项目初始化 | WorkBuddy 创建 `HR-Workflow` 目录 |
| 2 | 简历自动采集 | 邮箱连接器 + 主题格式约束 + 去重清单 |
| 3 | 信息提取 | PDF/Word 解析 + JSON 模板 |
| 4 | 简历评分 | 6 维评分框架 + 飞书文档维护标准 |
| 5 | 候选人存储 | 飞书多维表（字段名与 JSON 完全一致） |
| 6 | 流程整合 | 自定义 Skill 串起所有步骤 |

## 6 维评分框架

| 维度 | 权重 | 评估内容 |
|------|------|----------|
| 学历匹配度 | 10% | 院校层次 + 专业对口性 |
| 经验相关性 | **30%** | 工作年限 + 行业/岗位对口 |
| 技能契合度 | 10% | 技能匹配程度 |
| 项目深度 | **30%** | 项目规模/复杂度/量化成果 |
| 稳定性指标 | 10% | 跳槽频率 + 职业连贯性 |
| 综合潜力 | 10% | 成长性 + 学习能力 + 管理潜力 |

## WorkBuddy vs Coze/Dify

| 维度 | WorkBuddy | Coze/Dify |
|------|-----------|-----------|
| 设计对象 | 面向大众的任务助手 | 面向开发者的低代码工具 |
| 容错性 | **高**（关注最终意图） | 低（步步对，每步格式错则后续全错） |
| 交互 | 自然语言描述规则 | 拖拉拽（业务复杂时像蜘蛛网） |
| 门槛 | 非技术友好 | 工程师严密逻辑 |
| 生态融合 | 桌面端 Agent 生态 | 浏览器 SaaS 平台 |

**作者判断**：Coze/Dify 是 AI 发展过程中的阶段性产物，WorkBuddy 在逐渐迁移这些场景。

## 渐进式落地

> **不要一开始就追求覆盖整个流程，先把几个高频环节跑通，效果稳定后，再逐步接入后续的流程。**

落地步骤建议：
1. 先用 Skill 跑通**简历信息提取** + **结构化存储**（最容易出效果）
2. 跑通**简历评分**（与业务部门对齐标准）
3. 接入**自动化任务**（每日定时）
4. 最后接入**业务推送**（飞书消息 / 邮件）

## 持续校准

| 频率 | 校准内容 |
|------|----------|
| 每周 | 评分标准合理性（推 10 份只 2 份符合 → 调阈值） |
| 每月 | 字段定义（业务变化导致字段调整） |
| 季度 | 评分维度权重（业务重心变化） |
