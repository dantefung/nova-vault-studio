# 数据治理五大概念辨析

> 元数据、数据元、元模型、数据字典、数据模型——五个概念在不同层次回答不同的问题，搞清楚它们各自治理什么，是数据治理项目的认知前提。

<!-- more -->

## 一句话核心定义

| 概念 | 核心定义 | 治理对象 |
|------|----------|----------|
| **元数据** | 描述数据的数据——给数据补上身份、来源、加工过程和使用关系 | 数据本身的上下文信息 |
| **数据元** | 跨系统统一的业务语义标准——让同一个业务概念在不同系统中有统一表达 | 业务概念的标准定义 |
| **元模型** | 规定治理对象及其关系的框架——"管理什么对象、记录哪些属性、怎样关联" | 元数据平台的管理结构 |
| **数据字典** | 面向使用者的数据说明书——把元数据中使用者需要的信息整理出来 | 面向查询/使用的呈现方式 |
| **数据模型** | 业务数据本身的结构设计——真实业务怎样组织成数据结构 | 业务实体及关系 |

## 关键洞察

### 1. 元数据 ≠ 字段说明

元数据不仅是字段名称、类型、长度，还包括来源系统、业务定义、更新周期、责任部门、血缘关系、权限、质量结果等。它分为三类：
- **技术元数据**：数据库、表、字段、ETL 任务、血缘
- **业务元数据**：指标定义、统计口径、业务术语
- **管理与运行元数据**：权限、质量、责任人、生命周期

### 2. 数据元 ≠ 字段

字段是某个系统里的具体实现，数据元是跨系统的统一标准。
- CRM 的 `cust_type`、ERP 的 `customer_category`、数仓的 `customer_type` → 三个字段
- 但都表达"客户类型" → 一个数据元

数据元治理的核心问题不是"有多少字段"，而是"哪些字段表达同一件事"。

### 3. 元模型 ≠ 数据模型

虽然只差一个"元"字，但：
- **元模型**面对的对象是：系统、表、字段、任务、指标——治理信息的管理结构
- **数据模型**面对的对象是：客户、商品、订单——业务数据本身的结构

元模型定义框架，元数据往框架里填具体内容。

### 4. 数据字典 ≠ 全部元数据

数据字典是元数据的子集，是面向查询和使用的呈现方式。一条好的数据字典条目不仅要翻译字段名，还要带上定义、来源、统计口径和加工背景。

### 5. 五者是一条完整链路

成熟的数据治理不是一份 Excel 对应一个概念，而是让五个概念形成闭环：

> 数据模型里的字段对应数据元标准 → 数据开发持续产生元数据 → 元数据按统一元模型组织 → 数据字典提供使用者入口

## 常见混淆与对比

| 混淆点 | 正确理解 |
|--------|----------|
| "做了数据字典 = 完成元数据管理" | 数据字典只是元数据的一部分呈现方式 |
| "元模型 = 数据模型" | 元模型管治理信息的结构，数据模型管业务数据的结构 |
| "字段 = 数据元" | 字段是单系统实现，数据元是跨系统标准 |
| "批量导出字段+补中文名 = 数据元标准化" | 那是字段盘点，不是数据元治理 |
| "元数据就是字段描述" | 元数据还包含血缘、权限、质量、生命周期等 |

## 实际治理中的落地要点

1. **元数据先行**：不先理清元数据，后续所有治理对象都是模糊的
2. **数据元要标准化**：统一名称、类型、长度、值域、单位、编码
3. **元模型要统一**：不同团队对"对象"的定义必须一致，否则治理信息无法串联
4. **数据字典要有上下文**：不能只是字段翻译，要带上来源、口径、加工逻辑
5. **数据模型要落地**：模型画完不等于数据可用，要对应到真实的数据开发链路
