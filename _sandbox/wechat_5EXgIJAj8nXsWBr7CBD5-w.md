这部分就是大家常说的摘要压缩。上下文达到阈值时自动触发，手动 /compact 也可以进入相关摘要流程。

假设窗口是 200K，输出预留取 20K，阈值就是 167K。20K 是计算阈值时的预留上限，并不表示每次都生成 20K 摘要。



常规流程会在已有对话上下文上追加压缩要求，让模型生成摘要。提示词大致这样组织：



九项清单分别要求保留：



1. 用户请求与意图。



2. 关键技术概念。



3. 看过、修改过的文件和重要代码。



4. 错误与修复方法。



5. 已解决的问题和仍在排查的问题。



6. 所有非工具结果的用户消息。



7. 用户明确要求但尚未完成的任务。



8. 压缩前正在做什么。



9. 下一步；需要时直接引用最近的任务指令。



这份 prompt 很像一次工作交接，尤其强调用户的纠正、当前进度和未完成事项，尽量避免压缩后任务跑偏。



首尾重复禁止工具是因为，摘要agent为了复用缓存，仍保留原有工具定义，但是又不允许调用，所以提示词需要强调“这一轮只负责总结，不要调用工具”。



原会话也有 transcript 存档，对话历史存入./transcripts/，后续上下文按需访问。与上述提到的 Codex 的 ContextManagement 有些类似的意思。



### #SessionMemory 与 SessionMemoryCompact



这两个机制配合出现，可以分别理解成：**平时维护会话摘要，到压缩点复用这份摘要。**定期总结对话历史，这样就不需要在上下文窗口不够时专门压缩一次了。



这是个试验功能，受开关控制，不确定最新版是否还存在这个功能，但是我觉得很有借鉴意义，也非常的像 Codex 的 ContextManagement 功能。



SessionMemory 会在主对话过程中时刻检查条件（有几轮没压缩过了）。上下文增长、工具调用次数和是否来到合适的回合边界都会参与判断，满足条件后，后台 fork 一个 Agent 更新 summary.md。



这个 Agent 拿到的是当前父会话上下文、已有 summary，以及更新笔记的任务要求。

### #ReactiveCompact



ReactiveCompact 是上述压缩请求失败后的恢复机制。



正常模型压缩请求可能因为上下文超限等问题被服务端拒绝。此时程序尝试恢复出一份可用上下文，再继续原任务。ReactiveCompact 有重试上限，避免反复压缩失败。



核心实现同样缺失，不确定该机制是否依旧存在。
